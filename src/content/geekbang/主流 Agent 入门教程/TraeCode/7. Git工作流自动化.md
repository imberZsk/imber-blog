# 7. Git工作流自动化

> 来源：[TraeCode](https://time.geekbang.org/space/wiki/TraeCode_Tutorial)

## 7.1 小步提交

在功能分支运行测试，git status --short 查看所有文件，git diff 看未暂存改动，git add 明确选择文件后用 git diff --cached 再看本次提交。请助手基于暂存差异拟提交信息，人工核对后提交；不要把未暂存功能写进本次说明。

## 7.2 查询历史

让助手用 git log 和 git show 找到某个功能引入的提交，返回提交号及文件证据。提交信息只能提供线索，是否真正实现仍要读 diff。

## 7.3 合并前审查

在功能分支且工作区干净时，先确认基准分支，再 `git diff main...HEAD`，要求助手对照需求和测试查找回归。修复并独立验收后，保存 main 和功能分支的提交号。若第 5 章已经合并，使用保存的两个提交比较，不要期待 main...HEAD 仍有差异。

## 7.4 单独练习合并冲突

在新的临时 Git 仓库创建文本文件并提交。从同一基线分别建 branch-a 和 branch-b，各自修改同一行并提交。在 branch-a 合并 branch-b 应产生冲突。请助手解释两侧意图，人工决定结果，再 git add 和 git commit；检查合并提交包含预期文本。这个实验独立于账本，避免为了造冲突破坏主线函数接口。

回到实际账本，冲突解决后重新跑完整测试再提交。不能为消除冲突而盲选一整侧，也不能删除失败测试。合并后用明确提交号核对结果，已合并分支用 git branch -d 清理。

## 7.5 结束条件

需求、差异与验收对应；main 保持可用；无误提交数据文件。分支或会话名字不会隔离未提交文件，激进实验优先使用独立 worktree。
