# 14. 进阶学习

> 来源：[CodeBuddy](https://time.geekbang.org/space/wiki/CodeBuddy_Tutorial)

这套 CodeBuddy 教程，从第 0 章就先把产品形态说清楚，再选择 CLI 作为主线。随后处理 macOS、 Linux、Windows PowerShell 和 WSL2 四种环境，带着读者跑通第一次对话，建立项目记忆，认识权限模式、上下文和会话。

真正有价值的部分，是后面的七个案例。

接手陌生仓库时，先准备独立副本，先复现，再只修启动问题。给没有测试的项目补测试时，先确定测试契约，还用独立 Worktree 做对比练习。从报错到修复时，先读现场但不修改，用真实数据复现， 挖出根因，先写失败测试，再改代码。

到了重构，教程要求先给外部行为留证据，只抽取一个有价值的边界，失败就回退。做短链服务时， 又把第一版契约、本地验收、容器持久卷和云端部署串起来。自动化章节也没有把 AI 审查当万能答案，而是先建立可重复检查，再区分暂存审查与分支审查，最后连自动化本身也要验收。

第 10 和第 11 章继续把规则文件、子代理、MCP、Plan、Skill 和 Hook 接进来。

所以如果真的走完这 14 章，你学到的已经不只是 CodeBuddy 怎么用。

你学到的是一套小型但完整的 AI 编程纪律。

先复现，再修复。先写失败测试，再改代码。先让外部行为留下证据，再重构。共享配置提交，个人配置忽略。Hook 脚本先独立测试，再接入工作流。

刚好在对抗 AI 编程最常见的诱惑。

看见代码出来，就以为任务完成了。

教程本身已经把这个坑堵得很严。可到了团队和企业项目里，难度会继续上升。

陌生仓库不再是一个练习项目，而可能有几百个模块、多个服务和多年历史。测试契约不再只覆盖账单或短链，而要处理跨系统接口、权限、数据迁移和兼容性。一个子代理做审查也不够，调研、实现、测试、安全与性能可能需要并行推进，还要避免不同 Agent 互相覆盖修改。

这时，项目记忆需要升级成仓库级工程知识。

项目怎样启动，常用命令是什么，目录如何分工，架构边界在哪里，哪些操作必须人工确认，哪些结果能机器验收。这些都需要被持续维护，而不是在每次新会话里临时解释。

Plan 也要升级成规格。

教程里让 CodeBuddy 先想清楚再修改。复杂项目里，还要把业务目标、非目标、接口、约束、风险和验收标准整理成 spec，再拆成 plan 和 tasks。否则计划写得再漂亮，也可能是在错误需求上认真执

行。

Skill 和 Hook 也要升级成团队资产。

个人 Skill 解决自己重复做的验收，团队 Skill 则要可读、可测、可版本管理。Hook 不只执行一个本地脚本，还可能承担格式、测试、安全和提交门禁。它们一旦进入多人协作，稳定性与可维护性就变得重要。

所以在这里，我们想向你推荐一门课程，「企业级 AI 编程实战营」。它承接的正是这层放大后的问题。

课程用 SDD 把需求转成 spec、plan 和 tasks，用 Harness Engineering 把项目规则、权限、环境、测试和验收变成 Agent 可以遵守的工程护栏。Subagents、Worktrees、Skills、Slash Commands、 Permission 和 Hooks，会在真实复杂项目里组合使用。

三个项目也刚好对应 CodeBuddy 教程已经触碰过、但规模更大的场景。

从零构建 AI 智能体操作系统，练系统底座和 Agent Runtime。开发分布式延时投递服务，练复杂系统设计、高可用和增量演进。对 Dify 做企业级二次开发，练大型陌生代码库理解与最小侵入改造。最后进入 mq9 开源项目协作，接受维护者的真实 PR review，实际是否合并以 review 结果为准。
