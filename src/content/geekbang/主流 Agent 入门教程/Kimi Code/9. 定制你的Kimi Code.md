# 9. 定制你的Kimi Code

> 来源：[Kimi Code](https://time.geekbang.org/space/wiki/Kimi_Code_Tutorial)

前面八章，我们用的是"出厂设置"的 Kimi Code——它已经很好用，但还不是"你的"。这一章做三件事：认识配置文件的存放方式、用 `AGENTS.md` 给项目立下规矩、把你重复使用的流程固化成自己的 Skill。做完这些，Kimi 会越来越像一个了解你习惯的老搭档。

## 9.1 配置文件与数据都在哪儿

先建立一个全局认知：Kimi Code 的所有本地数据，默认都放在一个目录里——`~/.kimi-code/`（Windows 原生路线是 `C:\Users\你的用户名\.kimi-code\`）。里面值得你认识的有三样：

- `config.toml`：主配置文件，模型的选择、API 来源、各种开关都在这里；
- `sessions/`：你所有的会话记录（第 5 章讲过，按工作目录分组存放）；
- `logs/`：运行日志，排查问题时用得上。

日常使用中，最常用的调整是切换模型——在会话里输入 `/model`，从列表里选择即可，不用手动改配置文件。想改更细的设置（比如默认模型、自定义数据目录），去翻官方文档的 [Configuration](https://www.kimi.com/code/docs/en/kimi-code-cli/configuration/config-files.html) 章节，这里不展开——本章的重点是下面两个更有"创造感"的定制方式。

## 9.2 AGENTS.md：给项目立一份"家规"

到目前为止，你每次想让 Kimi 遵守某个约定，都得在对话里说一遍："提交信息用「类型: 简述」格式""代码注释用中文""改完记得跑测试"……说一遍它记一遍，新会话、新同事来了还得再说。

**AGENTS.md** 就是为解决这个问题而生的：在项目根目录放一个名叫 `AGENTS.md` 的 Markdown 文件，写下这个项目的约定，Kimi 每次在这个项目里工作时都会自动读到它——相当于给项目立了一份"家规"。

实战：在 `weight-tracker` 根目录创建 `AGENTS.md`，把这几条写进去：

```
# 项目约定

## 技术栈
纯前端三件套（HTML/CSS/JS），不引入框架和第三方库；数据存 localStorage。

## 代码风格
- 变量名用 camelCase，常量用 UPPER_SNAKE_CASE
- 注释用中文
- 每个函数开头用一行注释说明作用

## 工作习惯
- 改动计算逻辑（calc.js）后，必须打开 tests.html 跑一遍测试
- 提交信息遵循「类型: 简述」格式，类型从 feat / fix / refactor / docs / chore 中选
```

写好后，**新开会话**让它生效（已有的会话不会自动重新读取）。然后验证一下：随便让它改个小功能，观察它是否主动遵守了这些约定——比如改完 calc.js 后会不会主动提醒"该跑一遍 tests.html 了"。

AGENTS.md 的价值会随着项目变大而凸显：约定写一次，永远生效；团队里每个人、每个 AI 会话都遵循同一套标准。它是"把最佳实践沉淀进项目"的最省事方式。

## 9.3 自定义 Skill：把重复流程变成一句话

AGENTS.md 管的是"默认规则"，Skill 管的是"可复用的流程"。

想一想这几章里你重复做过的事：生成周报、按固定格式写提交信息、给应用做一遍功能体检……这些事每次都要打一大段提示词。Skill 让你把这段提示词**存成一个文件**，以后用 `/skill:名字` 一句话就能调用，甚至 Kimi 会在合适的场景自动想起来用它。

**Skill 放在哪儿？** 按作用范围分四级，优先级从高到低：

| 作用域 | 位置 | 什么时候用 |
| --- | --- | --- |
| 项目级 | 项目里的 `.kimi-code/skills/` 或 `.agents/skills/` | 只对当前项目生效 |
| 用户级 | `~/.kimi-code/skills/` 或 `~/.agents/skills/` | 对所有项目生效 |
| 额外目录 | 在 `config.toml` 里用 `extra_skill_dirs` 声明 | 团队共享的技能库 |
| 内置 | 随 CLI 自带 | 官方提供的常用技能 |

**文件长什么样？** 推荐"目录形式"：建一个以技能名命名的文件夹，里面放主文件 `SKILL.md`（还可以放脚本、清单等辅助文件）。`SKILL.md` 由两部分组成——YAML 头部（写元信息）和 Markdown 正文（写给 Kimi 的指令）。

来个实战。我们给体重管理项目做一个"周回顾"技能。在**项目根目录**创建 `.kimi-code/skills/weekly-review/SKILL.md`，内容如下：

```
---
name: weekly-review
description: 根据本周的饮食、运动、体重记录生成一段中文周回顾
whenToUse: 当用户要求生成本周回顾、周报、周总结时
---

请为用户生成一份本周体重管理回顾：

1. 读取应用的数据（localStorage 导出的 JSON，或用户粘贴的数据）
2. 统计：本周体重变化（对比上周末）、日均摄入热量、日均运动消耗
3. 找出：哪几天摄入超标、哪几天坚持得最好
4. 写一段 100~200 字的中文回顾，语气像朋友聊天，先肯定坚持、再温和地指出可以改进的一天
5. 保存为 weekly-review-本周日期.md
```

保存后**新开会话**让它生效。以后只要在会话里输入 `/skill:weekly-review`（或者直接说"帮我做个本周回顾"，它也可能根据 `whenToUse` 自动调用），它就会按这份流程执行。

再看头部那几个字段的作用：

- `name`：技能的名字，调用时用 `/skill:weekly-review`；
- `description`：一句话说明，Kimi 靠它判断"什么时候该自动想起这个技能"；
- `whenToUse`：更明确的触发时机描述。

技能还支持**参数**和**占位符**（比如 `$ARGUMENTS`、`${KIMI_SKILL_DIR}`），可以做更复杂的流程，这些属于进阶用法，用到时查[官方文档](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/skills.html)即可。

体会一下 AGENTS.md 和 Skill 的分工：**AGENTS.md 是"永远生效的规矩"，Skill 是"随叫随到的流程"**。一个让 Kimi 变得更懂项目，一个让 Kimi 变得更懂你。

## 本章小结

这一章我们把 Kimi 从"出厂设置"调成了"私人订制"：

- 本地数据集中在 `~/.kimi-code/`，日常最常用的调整是 `/model` 换模型；
- **AGENTS.md**：项目根目录的一份 Markdown，写下技术栈、代码风格、工作习惯，每次会话自动生效——永远生效的规矩；
- **自定义 Skill**：把重复流程写成 `SKILL.md`，用 `/skill:名字` 一句话调用，还能被 Kimi 自动触发——随叫随到的流程；我们给项目做了一个"周回顾"技能。

到这里，CLI 的个性化定制你已经掌握了。但 Skill 只是最轻的扩展方式——下一章我们认识四种更"重"的扩展机制：子代理、MCP、Hooks 与插件，把 Kimi 的能力边界再往外推一大圈。
