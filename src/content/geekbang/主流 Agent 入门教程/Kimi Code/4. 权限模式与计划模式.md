# 4. 权限模式与计划模式

> 来源：[Kimi Code](https://time.geekbang.org/space/wiki/Kimi_Code_Tutorial)

上一章里，Kimi 每创建文件、每跑一条命令都要弹窗问你，一路点头下来，安全是安全，但你大概也感觉有点黏人了。反过来，完全不管也不行——它毕竟能改文件、能跑命令，真放飞了你也睡不着。

这一章解决的就是"控制"问题：什么任务该管严、什么任务可以放手（三种权限模式）；复杂任务怎么先审方案再动手（Plan 模式）；以及它干活的中途，你还能做哪些操作（过程控制）。

## 4.1 三种权限模式：什么任务，配什么信任级别

先打个比方。Kimi Code 像你带的一位能力很强的同事，而权限模式就是你给他的信任级别：新人入职时事事汇报，合作久了可以例行放权，只有在完全输得起的环境里才敢彻底不管。

Kimi Code 提供三档，随时切换：

| 模式 | 开启方式 | 行为 | 适合什么时候 |
| --- | --- | --- | --- |
| **Always Ask（默认）** | 开箱即是 | 只读操作自动执行；改文件、跑命令等逐项问你 | 新手期、不熟悉的项目、高风险操作 |
| **Ask When Needed** | `/yolo` | 常规操作自动批准，但敏感操作仍然会停下来问你 | 知根知底、确认安全的批量任务 |
| **Never Ask** | `/auto` | 全部自动，它也不会再反问你 | 仅限"输得起"的环境 |

**Always Ask** 是你已经在用的模式，不再多说。重点看后两档。

**Ask When Needed（`/yolo`）** 是最实用的放权档位：常规的文件修改、命令执行不再逐项打扰你，效率明显提升。但它不是无条件放行，以下几类情况仍然会征求你的同意：

- 访问敏感文件，比如 `.env`、SSH 私钥；
- 执行危险命令，比如 `rm -rf`、`shutdown`；
- 退出 Plan 模式（下一节细讲）。

而且它只是"少问"，不是"不问"——它拿不准需求时，仍然会主动向你提问。所以像"把所有页面里的重复样式合并到 style.css，改完打开页面确认没变形"这种边界清楚、结果可验证的批量任务，用 `/yolo` 非常合适。

**Never Ask（`/auto`）** 是完全托管：所有审批自动通过，包括敏感文件和 Plan 退出，它也不会再向你确认任何事，连 `rm -rf` 这类危险命令的保护网都会撤掉。请把这句话刻在心里：**只在你完全输得起的环境里用它**——比如一次性容器、虚拟机、或者刚刚提交过、随时能还原的仓库。日常开发不要开。

切换方法：在输入框输入 `/yolo` 或 `/auto` 回车（它会打开权限模式列表并预选对应档位，确认即生效）。

我们的实战建议：**平时待在默认模式，遇到明确安全的大批量任务切 `/yolo`，`/auto` 暂时忘掉它。** 等第 8 章讲脚本化和自动化时，你会更理解什么时候才轮到它出场。

## 4.2 Plan 模式：复杂任务，先审方案再动手

权限模式管的是"执行时的松紧"，Plan 模式管的是"动手前的章法"。

有些任务你直接让它干，它也能干完，但过程可能跑偏：改了你不想改的文件、用了你不喜欢的方案。Plan 模式就是为此准备的——**它先输出一份行动计划，等你审阅批准后才动手**。适合改动较大、方向没把握、或者你想看看它思路的任务。

切换方式：按 `Shift-Tab`，或者输入 `/plan`。

现在实战。我们来给体重管理小助手加第二个功能：**每日热量预算**。先切到 Plan 模式（按 `Shift-Tab`，界面上会有模式标识），然后发送：

```
我想给应用加一个新功能：每日热量预算。
1. 页面上可以设置每天的热量目标（千卡），目标要持久保存
2. 每餐可以录入热量，比如"午饭 650 千卡"，按天汇总
3. 页面上能直观看到今天已摄入多少、距离目标还剩多少
先别动手，给我一个实现计划。
```

这次它不会直接写代码，而是输出一份计划：打算改哪些文件、分几步做、每步做什么。仔细看这份计划——**审核计划比审核代码省力气，方向不对在这里拦下成本最低。** 看完你有三种选择：

- **批准**：它就按计划开工；
- **拒绝**：它收手，你可以换个提法重来；
- **要求修改**：直接说出你的意见，比如"热量目标和体重记录放在同一个数据对象里，不要搞两套存储"，它会修订计划再给你看。

批准后它开始实现。完成后验证一下：刷新页面，把每日目标设为 1800 千卡，录入"早餐 400 千卡""午餐 650 千卡"，看看剩余额度算得对不对、刷新后数据还在不在。一切正常后，提交：

```
功能完成了，帮我提交这次改动，提交信息还是用「类型: 简述」格式
```

回顾刚才的过程：**先出计划 → 审计划 → 实现 → 验证 → 提交**。这就是一个规范的开发闭环，哪怕是一个人加一位 AI 的小项目，也值得这样走。以后每加一个功能，我们都走这个流程。

两个补充说明：`/plan clear` 可以在空闲时清除当前计划，重新开始规划；另外，退出 Plan 模式永远需要你确认——即使开了 `/yolo` 也不例外，这是防止"计划没审完就开干"的最后一道闸。

## 4.3 过程控制：它干活时，你还能做什么

Kimi 一旦开始输出，并不是"只能干等"。这几个按键让你随时介入：

**`Esc` / `Ctrl-C`：打断当前回合。** 发现它方向不对、或者你想换个说法，立即打断。注意区分：打断的是"当前这一轮输出"，**不会退出程序**；只有空闲时连按两次 `Ctrl-C` 才是退出。

**`Ctrl-S`：中途插话。** 它输出到一半，你突然想到要补充——不用等它说完，在输入框里把话打好，按 `Ctrl-S`，这句话会立刻注入当前回合，它马上就能看到并作出调整。比如它正在写页面，你插一句"配色清淡一点，不要用大面积深色"。

**`Ctrl+B`：转后台。** Shell 模式里跑的命令太久，按 `Ctrl+B` 把它转为后台任务，你可以继续聊别的，它跑完会通知你。

**`Ctrl-O`：折叠/展开输出。** 工具输出太长刷屏时，用它把输出卡片折叠起来，界面立刻清爽；想看细节再展开。

**`/undo`：收回最近的输入。** 话说出口发现不对，用它撤销最近的 prompt 重来。

这些按键不用刻意背，记住"它干活时我也能说能停"这个感觉，用两次就形成肌肉记忆了。忘了就 `/help` 翻一翻。

## 本章小结

这一章我们学会了和 Kimi 相处的"分寸感"：

- **三种权限模式**：默认的 Always Ask 逐项确认；`/yolo` 放权常规操作但守住敏感文件和危险命令；`/auto` 完全托管，只在输得起的环境用；
- **Plan 模式**（`Shift-Tab` / `/plan`）：复杂任务先审计划再动手，并用它实战了"每日热量预算"功能，走了一遍"计划 → 实现 → 验证 → 提交"的开发闭环；
- **过程控制**：`Esc`/`Ctrl-C` 打断、`Ctrl-S` 插话、`Ctrl+B` 转后台、`Ctrl-O` 折叠、`/undo` 收回输入。

到这里，单次对话内的操作你已经很熟练了。但一个项目是要做好多天的——关掉终端、明天再开，怎么接着干？聊到一半想开个新方向试试怎么办？下一章我们学会话与上下文管理，让项目可以"跨天续命"。
