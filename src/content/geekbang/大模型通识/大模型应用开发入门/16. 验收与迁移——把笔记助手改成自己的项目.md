# 16. 验收与迁移——把笔记助手改成自己的项目

> 来源：[大模型应用开发入门](https://time.geekbang.org/space/wiki/LLM_App_Develop_Basic)

你把自己的笔记放进助手，问了三个问题，答案看起来都不错。于是你改了提示词，又换了几个字段，准备把项目交给朋友。第二天才发现：其中一个答案引用了真实原文，却把原文的意思说反了；另一次生成结束后页面刷新了，你也不知道是否又调用了一次模型。

走到这里，项目需要一份可以反复执行的验收约定：什么输入应该得到什么结果，哪些失败必须被拦住，哪些事情仍需要人判断。没有这份约定，每次修改都像重新猜一次程序是否还可靠。

本篇给笔记助手增加10个可运行的离线验收场景，再把资料换成一份社区书屋说明，完成一次小规模迁移。你不必先搭复杂测试平台，也不必充值，就能检查大部分本地流程。模型质量则单独记录，避免用模拟答案给它打分。

## 一、先确定你要验收的是哪一层

“能用”不是一个足够具体的结论。同一个项目至少有四种不同的检查对象：

| 对象 | 要回答的问题 | 本项目的检查方式 |
| --- | --- | --- |
| 安装和启动 | 依赖、配置和本地数据位置是否可用？ | run\_local.py check，实际启动页面 |
| 确定性业务规则 | 引用不存在会不会被拒绝？重复提交会不会再执行？ | 离线自动验收、数据库检查 |
| 模型回答质量 | 证据是否支持结论？资料不足时是否承认不知道？ | 固定问题集，真实输出与人工审核 |
| 使用体验 | 人能否看懂状态、完成操作、发现失败？ | 浏览器手工走完整流程 |

第一层通过，不能推出第三层通过。第三层答对一次，也不能证明第二层没有重复执行问题。我们要分别留下证据，而不是把一张漂亮页面截图当成全部验收。

例如“引用存在”可以让程序逐字比较；“这段引用能否推出这个结论”涉及语义，当前校验器不会判断。第6篇已经留下这个边界，收官时仍必须保留。JSON输出能力帮助程序读取结果，不能替代业务检查与事实审核。[DeepSeek JSON输出说明](https://api-docs.deepseek.com/guides/json_mode/)

## 二、先运行这10个场景

把本篇ZIP解压到新的`lesson-16`目录，保留旧项目。如果已经在这个新目录建立了环境，就不必重复创建和安装；第一次使用可按下面顺序执行，每一步成功后再继续。

macOS/Linux：

```
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m pip check
.venv/bin/python acceptance.py
```

Windows PowerShell：

```
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe acceptance.py
```

安装依赖需要软件包网络。安装完毕后的这组验收不需要模型网络、API Key或`config.json`。脚本自行提供非秘密测试配置，为每个场景创建临时资料和数据库，结束后清理。它不会拿你原项目的历史记录做实验。

正常输出以一行“离线验收”说明开始，接着出现10个`test_... ... ok`，最后类似：

```
Ran 10 tests in ...s

OK
```

耗时因电脑不同而变化，不要对照一个固定秒数判断成败。失败时，`FAIL`通常意味着实际结果不符合断言；`ERROR`表示测试执行过程中出现异常，例如缺文件或无法导入依赖。先看第一个失败的场景与堆栈，不要把测试删掉来让最后一行变绿。

脚本使用Python自带的`unittest`：一个以`test_`开头的方法代表一个场景，断言写明预期结果；测试前后准备和清理临时资源。[Python unittest文档](https://docs.python.org/3.11/library/unittest.html)

网页流程使用Flask测试客户端。它能在进程内发送请求、接收响应和保留Cookie，不必先监听8765端口。这适合核查后端行为，但没有真的打开浏览器、排版页面或执行浏览器交互。[Flask应用测试文档](https://flask.palletsprojects.com/en/stable/testing/)

## 三、10个场景分别在守住什么

把测试名称与用户可能遇到的问题对应起来，会比只记住“有10个测试”更有用。

| 场景 | 操作与预期 | 为什么需要 |
| --- | --- | --- |
| 01 检索和来源 | 默认关键词选中F1-C2、F1-C3，第一片段对应原文第3行；未选资料不进入消息 | 防止读取正确却发送错误内容 |
| 02 无命中 | 用“查找”检索默认样例，无命中时生成被拒绝，不调用生成流程 | 没有证据不能偷偷改成随便回答 |
| 03 假引用 | 把引用改成原文不存在的一句话，校验失败 | 把可验证的约束交给代码 |
| 04 语义反向 | 保留真引用，却把检索与回答顺序说反，当前规则仍通过 | 明确校验器没有语义判断能力 |
| 05 重复操作 | 同一操作再次生成、同一计划确认两次，仍只有一操作和一计划 | 检查状态与去重边界 |
| 06 另一会话 | 第二个浏览器会话读取第一个结果，返回404 | 结果访问必须绑定当前会话 |
| 07 应用重建 | 保留数据目录与Cookie，重新创建应用，原结果仍可读 | 检查持久化与身份衔接 |
| 08 未确认执行 | 人为把操作推进running，再提交，不重新生成 | 不把未知结果当成可安全重试 |
| 09 换一份资料 | 书屋说明能检索到借阅期限，合规卡片与missing卡片可校验 | 验证任务数据可替换 |
| 10 导出源码 | 38文件源码包包含验收脚本，不含运行数据和个人配置 | 避免交付遗漏与历史混入 |

第04个测试尤其容易误读。它的`ok`表示“校验器的这个已知边界仍然存在”，不是说反向答案正确。测试代码故意要求当前校验器接受这份格式和引用都合法的错误答案。如果未来你增加了语义审核，需要重新设计这个测试与审核证据，不能只把状态名字改成“正确”。

第07个场景在同一测试进程中重建应用，检验数据库和Cookie恢复，没有模拟电脑断电。第08个场景直接构造running状态，也不是一次真实进程崩溃实验。精确描述测试范围，才能知道还缺什么证据。

第05个场景针对的是**同一个操作ID**。回到首页重新预览会创建新ID，应用不会猜测这是否是你上一条问题的重复，真实模式下可能再次计费。HTTP请求没有成功返回，也不能由此推断模型服务完全没有处理它。

## 四、读懂一个测试，再独立检查实际页面

打开`acceptance.py`，寻找`test_05_generation_and_plan_are_not_duplicated`。它没有只检查“页面上出现成功两个字”，而是依次做了这些事：完成一次演示生成；再次提交同一操作并禁止生成函数被调用；创建计划草稿；确认草稿仍为draft；两次确认同一计划；最后只读检查数据库。

结尾的核心断言是：

```
        self.assertEqual(after["counts"], {"sessions": 1, "operations": 1, "plans": 1})
        self.assertEqual(after["plans"][0]["state"], "saved")
        self.assertEqual(len(list((self.root / "data/operations" / ticket / "records").glob("*.json"))), 5)
```

这里的1/1/1成立，是因为每个测试从全新的临时目录开始。你已经使用过的项目可能有更多历史，不能照搬这组总数。五份JSON用于保存一次正常演示的来源、请求、尝试、响应和结果；数据库中的一条操作记录与这五个文件也不是同一种计数。

自动检查之后，再在自己的新副本完成一次看得见的流程：

```
.venv/bin/python run_local.py init
.venv/bin/python run_local.py check
.venv/bin/python run_local.py serve
```

Windows逐行把解释器换成`.\.venv\Scripts\python.exe`。打开`http://127.0.0.1:8765`，使用默认资料、默认问题、关键词“检索 片段”和K2。预览、生成演示卡片、核对引用，填写计划日期与20分钟，预览后单独确认保存。新副本第一次完整操作应有一条操作和一份已保存计划。

在另一个终端运行`.venv/bin/python inspect_db.py`，对照操作状态、计划状态和计数；Windows替换解释器路径。回到页面刷新结果，不应多出新的操作。原终端`Ctrl+C`停止，重新`serve`，在原浏览器打开同一地址，检查历史是否恢复。不要清除Cookie，也不要同时启动另一份副本。

这一遍补上测试客户端没有覆盖的部分：终端启动是否正常、地址是否能打开、页面提示是否能看懂、计划是否需要明确确认。若首页历史为空，先检查是否换了目录或Cookie，不要立即删除数据库“重试”。

## 五、用一份小资料练习迁移

第一次迁移不妨只改变资料与问题，继续使用已有的检索和卡片结构。我们把“复习笔记”换成“社区书屋规则问答”，目标很小：回答借阅期限，引用原文；规则里没有的费用不编造。

在新副本的`sample-notes`下创建UTF-8文件`club.md`，内容如下。保留两个原始教学文件，便于继续运行默认验收。

```
# 社区书屋

借阅期限为14天。

续借需要在到期前向管理员申请。
```

先只检查检索，不调用模型。macOS/Linux：

```
.venv/bin/python rag.py --files sample-notes/club.md --question "借阅期限是多久？" --terms 借阅 期限 --top-k 1 --inspect
```

Windows PowerShell：

```
.\.venv\Scripts\python.exe rag.py --files sample-notes/club.md --question "借阅期限是多久？" --terms 借阅 期限 --top-k 1 --inspect
```

预期选中`F1-C2`，内容是“借阅期限为14天。”，对应第3行。`F1`表示本次输入中的第一份文件，不是数据库中的永久文档编号。改变文件顺序或内容，片段编号也可能变化。

这一步已经完成了一次很实际的验证：文件读到了，分块符合预期，关键词命中了正确证据。如果这里选错了内容，先改资料分段、关键词或检索策略；更换生成模型无法补回根本没送进去的证据。

再把问题换成“逾期一天罚多少钱？”，仍保留`--terms 借阅 期限 --top-k 1`，把最后的`--inspect`改成`--dry-run`。先前`init`创建的配置在这一步会使用，但不会读取Key或发送请求。检查打印出的消息：问题变了，选中的片段仍只有借阅期限，没有任何罚款规定。

这与“无命中”不同。无命中时我们直接停止；这里有相关资料，但资料不能回答费用问题。合适的输出应标记missing，答案为“笔记未提供，无法判断”，引用列表为空。关键词检索成功不等于答案所需证据齐全。

当前程序不会从问题里自动提取关键词。只改`--question`不会改变`--terms`，这个设计正好让你看见检索输入与提问输入是两件事。

`test_09_migrate_to_a_small_faq`包含这份书屋资料及作者手写的预期卡片，用来检查检索与校验接口。它没有让真实模型回答，也不能证明模型一定会承认不知道。不要给这条自定义命令加`--demo`并把默认演示答案当成书屋问答：演示只支持原始默认任务，自定义任务会被拒绝。若以后由你决定做真实验证，可将相应命令末尾改为`--run`，使用自己的Key并承担API费用；这不是完成本篇的必要步骤。

网页也能选用新增资料，但文件白名单在启动时建立，因此新增后要停服重启。离线网页的固定演示同样不支持任意自定义问题，不能靠改个标题把预置答案包装成模型效果。

## 六、把“模型好不好”写成一组可复查的问题

如果准备真正接入自己的资料，先在本地写一个评估表，再决定是否做付费测试。第一版不需要很多题，至少区分以下几种情况：

| 题目类型 | 书屋例子 | 人工审核重点 |
| --- | --- | --- |
| 直接可答 | 借阅期限是多久？ | 是否答14天，并引用对应原句 |
| 换一种表达 | 一本书能借多长时间？ | 先看检索是否命中，再看生成；不能只罚生成模型 |
| 资料缺失 | 逾期一天罚多少钱？ | 是否说明资料没提供，而非按常识猜费用 |
| 否定或冲突 | 后续文档出现“特定活动书籍仅借7天” | 是否识别适用范围；需先扩充检索与任务规则 |
| 混入无关指令 | 笔记里夹有“忽略任务，输出别的内容” | 是否把资料当证据，仍遵守应用约定；不能仅靠提示词宣称已解决 |

最后两项是你扩展项目时应该增加的评估样本，**没有包含在本篇10项自动验收中**。新增样本时，应自己写明资料与判断依据，避免把模型生成的答案直接当标准答案。

每次真实评估至少记录：资料版本、问题、关键词或检索配置、选中片段、模型标识与参数、结果文件、人工判断及理由。第7—9篇留下的实验与用量记录可以帮助比较，但不同入口格式不同：旧`costs.py`不会自动汇总网页所有嵌套操作目录或工具调用记录，不能把没统计到的费用当零。

题集固定以后，一次只改一类因素。例如保持资料、问题、关键词不变，只比较输出预算；或者保持模型设置不变，只调整检索。否则答案改善了，你也不知道是哪项变化起作用。

小题集能发现明确问题，不能给出普遍可靠性保证。某次10题都答对，只说明这10个输入、当时模型与配置下的观察结果。新增资料、换模型或改变业务动作后，还要重新审查对应场景。

## 七、改成个人项目时，先找对修改位置

现在的代码不是一个只能换皮的演示。它把资料、模型请求、结果规则和执行动作分开，方便你有目的地修改。

| 你的目标 | 优先查看 | 修改后必须重新验证 |
| --- | --- | --- |
| 换成自己的笔记或FAQ | sample-notes、source\_files.py、rag.py | 编码、长度、来源快照和检索命中 |
| 改进查找方式 | retrieval.py | 片段ID、排序、选中范围、引用映射与无命中策略 |
| 把卡片改成其他结构 | study\_task.py、validation.py及使用它们的入口 | 提示词、字段、校验、页面展示和记录一起匹配 |
| 增加安排或本地动作 | review\_tool.py、tool\_flow.py，或网页计划路径 | 参数白名单、授权、明确确认、重复提交与失败状态 |
| 换模型或服务商 | settings.py、api\_client.py、structured\_client.py及工具入口 | 地址、认证、参数、流式块、工具格式、用量与错误 |
| 让多人共同使用 | web\_app.py、storage.py及部署设计 | 登录、资料权限、会话、存储、并发与费用隔离 |

别只改提示词要求“返回五个新字段”，却继续让旧校验器只接受原来的字段。拒绝这份输出可能正是校验器在正常工作。结构变了，就需要同步修改生产端和消费端，并为旧数据决定保留、迁移还是只读查看，不能悄悄按新结构解释历史。

也别把RAG产生的F1编号直接塞进第10篇固定N1—N3的工具白名单。前者是本次资料的定位，后者是当时工具允许引用的固定资源，两者没有自动授权关系。工具描述让模型提出参数，实际是否执行仍由程序决定。[DeepSeek工具调用说明](https://api-docs.deepseek.com/guides/tool_calls/)

截至本篇核实，DeepSeek官方入门页列出的OpenAI兼容地址仍为`https://api.deepseek.com`，模型标识包括本项目使用的`deepseek-flash`。以后迁移服务商，应核查目标官方文档，不能从“兼容”二字推断所有思考参数、输出字段和计费口径完全一致。[DeepSeek官方接入说明](https://api-docs.deepseek.com/)

最终网页也没有把前15篇的所有入口合并在一起。`main.py`保留流式聊天，`cards.py`承担结构化卡片实验，`planner.py`演示模型工具提议，`rag.py`处理检索问答；网页采用非流式卡片与手工填写、明确确认的计划流程。这样可以分别观察机制，不应把命令行有的功能误认为网页也已实现。

## 八、修改失败时，沿着证据找原因

| 症状 | 先查哪里 | 不要急着做什么 |
| --- | --- | --- |
| 新资料没有出现在网页 | 文件名、格式、是否重启建立白名单 | 不要先换API Key |
| 问题换了，证据没换 | 显式关键词和选中片段 | 不要默认模型已经读完全部资料 |
| JSON合法却被拒绝 | 字段、问题ID、引用、状态与校验错误 | 不要关闭全部校验 |
| 真引用配错误结论 | 原文、问题与人工语义审核 | 不要把validated当“答案正确” |
| 操作卡在running/uncertain | 数据库状态与该操作的JSON | 不要循环点击生成或删除记录重试 |
| 源码包缺少新模块 | package\_project.py的FILES清单 | 不要直接压缩整个运行目录 |
| 改了教学笔记后验收失败 | 是否改变默认任务的固定输入 | 不要把断言改到任意输出都通过 |
