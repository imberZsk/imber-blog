# 可观测性（04） - 监控、告警与质量回归闭环

> 把服务 SLI、模型成本和内容质量放进同一告警上下文，告警必须能指向负责人和处置手册。

## 学习目标

读完本章后，你应能复述本主题的关键数据流，选择至少一种替代方案，运行或审查最小实现，并根据日志、指标或测试结果解释失败原因。

## 为什么需要它

真实系统的问题通常不在 API 能否调用，而在输入边界、错误恢复和验收证据是否明确。本章给出可以进入设计评审和生产检查的最小框架。

## 核心决策

- 服务指标覆盖可用率、P95/P99、错误率和队列；AI 指标覆盖 token、拒答、引用和任务成功。
- 告警按用户影响和错误预算设置阈值，避免对每个单点错误通知。
- 坏例经过去敏、归因和人工确认后进入 Dataset。

## 落地步骤

1. 定义 SLO 与错误预算。
2. 为每个关键 Span 建仪表盘和 burn-rate 告警。
3. 告警关联版本、模型、Prompt、租户、trace_id 和 Runbook。

## 决策记录怎么写

上线前不要只留下“采用 监控、告警与质量回归闭环”这一句结论。把每个决策和验收证据放在同一张表里，后续模型、数据或流量变化时才能重跑对比。

| 需要回答的问题 | 当前决策 | 必须保留的证据 |
| --- | --- | --- |
| 决策 1 | 服务指标覆盖可用率、P95/P99、错误率和队列；AI 指标覆盖 token、拒答、引用和任务成功。 | 对应步骤 1 的数据集、日志或压测结果 |
| 决策 2 | 告警按用户影响和错误预算设置阈值，避免对每个单点错误通知。 | 对应步骤 2 的数据集、日志或压测结果 |
| 决策 3 | 坏例经过去敏、归因和人工确认后进入 Dataset。 | 对应步骤 3 的数据集、日志或压测结果 |

下面的记录可以直接放进项目设计文档。阈值由真实评测集和 SLO 决定，不使用脱离业务的固定“最佳值”。

```yaml
topic: 监控、告警与质量回归闭环
baseline:
  version: required
  dataset: required
candidate:
  version: required
  change: required
acceptance:
  quality: business_threshold
  p95_latency_ms: service_slo
  cost_per_success: budget_limit
rollback:
  trigger: any_acceptance_regression
  owner: named_on_call
```

## 生产避坑

- 只监控 HTTP 200 会漏掉空答案和错误引用。
- 高基数原文标签会拖垮指标系统。
- 没有版本维度无法确认回归来自哪次发布。

## 故障演练

1. 注入与“只监控 HTTP 200 会漏掉空答案和错误引用。”对应的失败条件，记录用户侧现象、Trace 中的首个异常 Span 和恢复动作。
2. 注入与“高基数原文标签会拖垮指标系统。”对应的失败条件，记录用户侧现象、Trace 中的首个异常 Span 和恢复动作。
3. 注入与“没有版本维度无法确认回归来自哪次发布。”对应的失败条件，记录用户侧现象、Trace 中的首个异常 Span 和恢复动作。

演练必须能回答三个问题：故障是否在预算内快速失败，是否会越权或产生重复副作用，恢复后是否能用同一数据集证明质量没有退化。只有错误日志、没有用户影响和恢复证据，不能算完成排障。

## 验收清单

- 关键输入、输出、预算和停止条件都有结构化记录。
- 正常、边界、失败和攻击样本都进入可重复运行的测试集。
- 质量、延迟、成本与安全指标能定位到版本和 trace_id。
