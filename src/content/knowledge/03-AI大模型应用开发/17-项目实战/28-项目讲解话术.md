# 二、为什么话术要单独练

同样一个知识库 Agent 项目，
有人讲成流水账（"我用了 RAG，
然后用了向量库，
然后……"），
有人讲成一个有问题、有取舍、有结果的故事。
后者拿 offer。

讲项目的黄金顺序是：**先讲业务问题 → 再讲架构链路 → 再讲核心功能 → 然后讲难点和取舍 → 最后讲结果**。
每个技术点都要绑一个业务价值，别孤立报菜名。

# 三、分钟版（电梯陈述）

适合开场自我介绍后的"简单说说你的项目"：

> 我做的是一个面向企业内部资料的 Agent 助手。用户可以提问制度、查询订单、计算报销，也可以在需要时创建工单。技术上，前端负责聊天、流式输出、引用来源和工具 trace；后端负责 RAG 检索、工具调用、安全校验、日志和统一响应。我重点解决了三个问题：**资料可信、工具可控、失败可排查**。

最后那三个"可"是钩子，面试官大概率会顺着追问其中一个。

# 四、分钟版（展开讲解）

被要求详细讲时，按这个顺序，每段 1 分钟左右：

1. **业务背景**：为什么普通聊天机器人不够（不懂企业私有知识、会编造、不能执行操作）
2. **整体架构**：前端、后端、RAG、工具、日志五块怎么协作
3. **RAG**：文档怎么切分、检索、返回引用，资料不足怎么拒答
4. **Agent**：怎么选工具、校验参数、回填结果
5. **安全**：prompt 注入、权限、写操作确认
6. **工程化**：测试、日志、成本、部署
7. **现场演示**：问制度、查订单、触发安全拦截
8. **复盘**：哪些还能继续优化

讲的时候始终回到你项目里的真实取舍，不要背定义。

# 五、三个高频追问，提前备好

**追问"你的 RAG 怎么做的？"**

> 我分离线入库和在线问答。离线解析文档，按标题和段落切 chunk，保留 source、section、permission 等 metadata，再生成索引。在线用户提问后先检索 topK chunk，把片段和问题一起拼进 prompt，要求模型只基于资料回答并返回 citation。调优时看坏 case：没命中就调切分、关键词、topK；命中了但答错就调 prompt 和引用约束。

**追问"Agent 工具调用怎么保证安全？"**

> 我不让模型直接执行业务动作。模型只提出工具名和参数，后端做白名单、参数 schema 校验、权限校验和风险等级判断。只读工具直接执行，写操作必须进人工确认。每次调用写入 tool trace，前端展示过程，后端保留日志，方便复盘误调用。

**追问"这个 demo 怎么变成生产系统？"**

> 补四块。安全：API Key 后端保存，权限后端校验，防注入。稳定：模型调用加超时、重试、降级、限流。可观测：记录 requestId、检索命中、工具调用、耗时、token 成本、用户反馈。质量：维护评测集，坏 case 进回归测试。这样不是跑通一次 demo，而是能持续排查和优化。

# 六、三个进阶项目的讲法

**企业级 RAG 怎么讲**

> 我不是只做了上传文档问答，而是补了企业场景最关键的三件事：权限、溯源和评测。入库时保留文件、页码、章节、表格和图片元数据；检索时先按用户权限过滤，再走 BM25+向量+rerank；回答时引用能回到原文。上线后用评测集看命中率、拒答准确率和坏 case。

**合同审查 Agent 怎么讲**

> 合同审查不是让模型自由点评，而是“解析合同 -> 抽字段 -> 检索法条/模板 -> 风险规则判断 -> 模型生成报告”。确定性规则负责金额、期限、违约金这类硬条件，模型负责条款解释和修改建议。报告里的每个风险点都要带合同片段和依据来源。

**多 Agent / MCP 平台怎么讲**

> 我拆 Agent 不是为了分角色，而是为了隔离上下文和权限。公共能力如 RAG、记忆、Prompt 模板、外部工具抽成 MCP 服务，不同业务 Agent 通过统一协议调用。每次请求用 trace_id 串起来，能看到模型、检索、工具每一步耗时和 token 成本。

## 10.2 边界实验必须证明能够停止和恢复

# 十一、项目讲解话术 的结果解释

解释“项目讲解话术”实验时先看首个偏差，而不是最后一条错误。最后的异常通常只是上游状态错误的结果；从末端反推容易误把症状当根因。

| 观察结果 | 可以支持的判断 | 下一步 |
| --- | --- | --- |
| 主链路没有达到预期 | 条件缺失、结果不可复现或失败后责任不清 | 先执行：保留基线，缩小变量；根因确认前不扩大范围 |
| 异常链路无法恢复 | 条件缺失、结果不可复现或失败后责任不清 | 先执行：保留基线，缩小变量；根因确认前不扩大范围 |
| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

“项目讲解话术”只有同时满足“结果符合结论条件，异常输入可解释、可恢复”，并且没有出现“条件缺失、结果不可复现或失败后责任不清”，才可以认为主链路通过。这里的“通过”只对当前固定版本、样本和环境有效，不能外推到尚未测试的容量、权限或数据分布。

如果“项目讲解话术”候选方案与基线差异很小，先检查证据分辨率是否足够；如果差异很大，先排除数据泄漏、环境漂移和版本不一致。两种情况都不能只看一个汇总均值，需要回到逐样本输出和中间状态。

“项目讲解话术”故障定位完成后，记录“现象、首个偏差、根因、改动、原样本复测”五项。缺少原样本复测时，只能标记为待观察，不能标记为已解决。

发布判断需要把“项目讲解话术”的质量、失败边界和恢复能力放在同一份记录中。以下任一条件缺失，都应停止扩量，而不是用“基本正常”替代证据。

- [ ] “项目讲解话术”的基线与候选只存在一个计划内变量。
- [ ] “项目讲解话术”的输入、代码、依赖、配置和数据版本可以追溯。

# 十三、总结

- **为什么话术要单独练**：讲项目的黄金顺序是：先讲业务问题 → 再讲架构链路 → 再讲核心功能 → 然后讲难点和取舍 → 最后讲结果。
- **分钟版（电梯陈述）**：适合开场自我介绍后的"简单说说你的项目"：
- **分钟版（展开讲解）**：业务背景：为什么普通聊天机器人不够（不懂企业私有知识、会编造、不能执行操作） -> 整体架构：前端、后端、RAG、工具、日志五块怎么协作 -> RAG：文档怎么切分、检索、返回引用，资料不足怎么拒答 -> Agent：怎么选工具、校验参数、回填结果
- **三个高频追问，提前备好**：模型只提出工具名和参数，后端做白名单、参数 schema 校验、权限校验和风险等级判断。
- **三个进阶项目的讲法**：我不是只做了上传文档问答，而是补了企业场景最关键的三件事：权限、溯源和评测。
- **演示脚本（别自由发挥）**：打开 demo，说明这是离线可运行的 Agent 工作台 -> 问"报销流程是什么" → 展示 RAG 和引用来源 -> 问"查客户 C1001 最近订单" → 展示工具调用 trace -> 问"创建高优先级工单" → 展示人工确认边界
