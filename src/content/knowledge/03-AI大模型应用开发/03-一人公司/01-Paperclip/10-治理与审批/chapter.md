# Paperclip（9）- 治理与审批：你是董事会

> 本章目标：搞懂治理（Governance）。会配置雇人审批、CEO 策略审批；知道董事会能强制干预哪些操作；看懂活动审计。理解人类在自治系统里扮演的「方向盘」角色。

前面几章 Agent 越来越能干、越来越自动。这一章回答一个关键问题：**那人去哪了？凭什么不失控？** 答案是——你坐在董事会（Board）的位置上，握着方向盘。

---

# 一、为什么需要治理？

「自治 AI 公司」听起来很爽，但完全放手是危险的：Agent 可能乱雇人、定错方向、烧光预算。Paperclip 的解法是**审批闸门（approval gates）**——在关键决策点插入「人类必须点头」的关卡。

> 核心理念：**放权 ≠ 失控**。日常执行交给 AI，关键决策留给人。这正是第 01 章说的「治理（governance）」落地。

---

# 二、两种审批类型

## 2.1 1）雇佣 Agent（Hire Agent）

当一个 Agent（通常是经理或 CEO）想雇新下属，它提交一个雇人请求，生成一个 `hire_agent` 审批，出现在你的审批队列里。

审批内容包含：拟雇 Agent 的**名字、角色、能力、适配器配置、预算**。

底层 API（了解即可，平时在 UI 点）：
```
POST /api/companies/{companyId}/agent-hires
{
  "name": "Marketing Analyst",
  "role": "researcher",
  "reportsTo": "{经理AgentId}",
  "capabilities": "市场调研",
  "budgetMonthlyCents": 5000
}
```

## 2.2 2）CEO 策略（CEO Strategy）

CEO 最初的战略计划，**必须经董事会批准**，CEO 才能开始把任务推进到 `in_progress`。这保证了「公司方向」有人类签字背书。

```
POST /api/companies/{companyId}/approvals
{
  "type": "approve_ceo_strategy",
  "requestedByAgentId": "{agentId}",
  "payload": { "plan": "战略拆解..." }
}
```

> 💡 这解释了第 05 章那个现象：新公司建好后 CEO「不动」——它在等你批准策略。这是设计如此，不是 bug。

# 三、审批工作流

```
pending ──▶ approved（批准，动作执行）
        ──▶ rejected（拒绝，动作被否）
        ──▶ revision_requested ──▶ resubmitted ──▶ pending（要求修改后重提）
```

完整流程：

1. 某 Agent 创建一个审批请求。
2. 它出现在你的审批队列（UI 的 Approvals 页）。
3. 你 review 请求详情和关联任务。
4. 你做三选一：
   - **Approve（批准）**：动作继续执行。
   - **Reject（拒绝）**：动作被否决。
   - **Request revision（要求修改）**：让 Agent 改了重提。

## 3.1 审批被处理后会发生什么？

回顾第 07 章心跳协议 Step 2：当你批准/拒绝一个审批，相关 Agent 会被**审批结果触发心跳**（`PAPERCLIP_APPROVAL_ID` 和 `PAPERCLIP_APPROVAL_STATUS` 被注入），它醒来后处理跟进——批了就执行，拒了就调整。**治理动作直接驱动 Agent 行为，闭环是自动的。**

---

# 四、审批界面看什么

在 Approvals 页，每个待审批显示：

- **谁请求的、为什么**
- **关联的任务**（请求的上下文）
- **完整 payload**（比如雇人请求里拟创建的 Agent 配置）

> 审批前务必看 payload。雇人审批里能看到「这个新 Agent 用什么适配器、多少预算、什么能力」——这些都是你该把关的。

---

# 五、董事会的「强制干预权」（Board Override）

除了被动审批，作为董事会你还有主动干预的权力，随时可用：

| 权力 | 说明 |
|------|------|
| **暂停 / 恢复** | 随时暂停或恢复任何 Agent |
| **终止（Terminate）** | 终止任何 Agent（⚠️ **不可逆**，相当于「解雇」） |
| **重新分配任务** | 把任何任务改派给别的 Agent |
| **覆盖预算限制** | 临时突破预算上限 |
| **直接创建 Agent** | 绕过审批流，自己直接建 Agent |

> ⚠️ **Terminate 不可逆**，慎用。想临时停一下用 `pause`（可恢复），别动不动 terminate。

---

# 六、活动审计：问责的落地

每一次变更（mutation）都会记进**活动审计日志（activity audit trail）**。这就是第 01 章「问责（accountability）」的技术落地——**谁、在什么时候、做了什么改动，全程留痕可查**。

配合第 07 章的 run record（每次心跳的运行记录），你能完整复盘：某个决策怎么来的、某笔花费花在哪、某个任务谁动过。

---

# 七、什么该开审批，什么该放权？

治理的艺术在于「闸门开在哪」。一般原则：

| 环节 | 建议 |
|------|------|
| **CEO 初始策略** | 必审（这是公司方向，影响最大） |
| **雇人** | 初期建议开审批（控制组织膨胀和预算），信任后可放 |
| **日常任务执行** | 放权（这是自动化的意义所在，审了就没效率了） |
| **高花费/高风险动作** | 用预算硬停 + 审批双重把关 |

> 经验：**越靠近「方向」和「钱」的决策越要把关，越靠近「执行」的越要放权**。审太多失去自动化意义，审太少则失控。

---

# 八、常见错误

- ❌ **公司不动，以为是 bug**
  → 多半是 CEO 策略在等你审批。先看 Approvals 页。

- ❌ **审批不看 payload 就批**
  → 雇人审批里藏着适配器配置和预算，闭眼批可能放进一个烧钱或配错的 Agent。

- ❌ **动不动 Terminate**
  → 不可逆。临时停用 `pause`，确认不要了再 terminate。

- ❌ **所有动作都开审批**
  → 失去自动化意义，你会被审批淹没。只在关键点设闸。

- ❌ **完全关掉审批图省事**
  → 失控风险。至少保留 CEO 策略审批和预算硬停。

---

# 九、最佳实践

- ✅ **CEO 策略审批一定开**：这是公司方向的人类签字关。
- ✅ **初期开雇人审批，跑顺后放权**：先控制组织膨胀，建立信任后再松。
- ✅ **审批当成「review 时刻」**：认真看 payload 和关联任务，这是你注入判断/品味的入口。
- ✅ **优先 pause 而非 terminate**：保留回旋余地。
- ✅ **定期看活动审计**：复盘团队行为，发现异常（比如某 Agent 反复 blocked 或异常烧钱）。

---

# 十、总结

- 治理 = **审批闸门 + 强制干预 + 活动审计**，让人类握方向盘。
- 两种审批：**雇人** 和 **CEO 策略**；工作流 `pending → approved/rejected/revision`。
- 审批被处理会**触发相关 Agent 心跳**自动跟进，闭环自动。
- 董事会能 **暂停/恢复/终止/改派/覆盖预算/直接建 Agent**（terminate 不可逆）。
- 原则：**靠近方向和钱的把关，靠近执行的放权**。

治理保证了「不失控」。但「钱花在哪、活干得怎样」还需要看得见——下一章讲技能系统，给 Agent 装外挂扩展能力。👉 [10 · 技能系统](../11-技能系统/chapter.md)
