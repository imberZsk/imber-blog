# Paperclip（11）- 实战：从 0 搭一家内容公司（OpenAgent）

> 本章目标：把前 10 章串成一条可复现的实操链路，亲手搭出一家「AI Agent 开发者学习与分享社区」公司，让 AI 团队自动协作产出。这一章是全书的「集大成」。

前面学的都是零件，这一章把它们装成一台能跑的机器。我们要建的公司叫 **OpenAgent**。

> 📌 本章是端到端走查。建议你边读边在自己的 Paperclip 里同步操作。涉及的每个概念，括号里标了对应章节，忘了就回去翻。

---

# 一、确定我们要建什么

| 项 | 内容 |
|----|------|
| **公司名** | OpenAgent |
| **使命/目标** | AI Agent 开发者学习与分享社区，提供课程、技术讨论和热文排行 |
| **初始团队** | CEO（规划委派）→ 工程师（建站/写功能）→ QA（质量把关） |
| **验收信号** | 测试后，工程师能自动改 bug；社区站点能产出内容 |

这个目标符合第 05 章的「好目标」标准：具体（社区 + 课程 + 讨论 + 热文排行）、可衡量（站点能跑、内容能产出）。

# 二、Step 1：启动平台、建公司

启动 Paperclip（第 02 章）：
```sh
npx paperclipai run
```
打开 `http://127.0.0.1:3100`，点「New Company」：
- **Name**：`OpenAgent`
- **Description**：`AI Agent 开发者学习与分享社区，提供课程、技术讨论和热文排行`

---

# 三、Step 2：设公司目标

到 Goals 区域，建顶层目标：

> **「打造 AI Agent 开发者学习与分享社区：上线一个含课程列表、技术讨论区、热文排行的网站，并持续产出内容。」**

这是所有任务的北极星（第 03 章）。CEO 会基于它拆任务。

---

# 四、Step 3：招 CEO（用 Claude Local）

招第一个 Agent（第 05、06 章）：
- **Name**：`CEO`
- **Role**：`ceo`
- **Adapter**：`claude_local`（CEO 要做规划和委派，必须用能 agentic 的大脑）
- **cwd**：给一个专属绝对路径，比如 `~/.paperclip/instances/default/projects/openagent`
- **Budget**：先保守，比如 `10000`（= $100/月）
- **Prompt template**：指示它「review 公司健康度、把目标拆成策略提交审批、批准后委派给下属、需要人就申请雇人」

配完点 **Test Environment**（第 06 章），确认 `claude` CLI 就绪再继续。

---

# 五、Step 4：启动，批准 CEO 策略

给 CEO 开启心跳。它第一次醒来会（第 07、09 章）：
1. 读公司目标
2. 制定一份策略（比如：先搭站点框架 → 做课程模块 → 做讨论区 → 做热文排行）
3. **提交 CEO 策略审批，等你点头**

到 Approvals 页，看 CEO 的策略 payload，觉得方向对就 **Approve**。觉得跑偏就 **Request revision** 让它改。

> 💡 如果公司「不动」，先来这页看有没有待审批（第 09 章最常见的「假死」）。

---

# 六、Step 5：让 CEO 组建团队

策略批准后，CEO 会发现「我需要工程师来建站」，于是提交**雇人审批**（第 09 章）。审批 payload 里你能看到拟雇 Agent 的配置：
- **工程师**：`role: engineer`，`adapter: claude_local`，独立 `cwd`，能力写「全栈开发、建站、写功能」
- 确认配置合理（适配器对、预算合理）→ **Approve**

同理，CEO 会再申请一个 **QA Agent**（`role: qa`），负责测试和质量把关。

> ⚠️ 确保新 Agent 开了 `wakeOnAssignment`（第 08 章），否则 CEO 派活给它，它不会自动醒。这是协作卡壳根因之一。

---

# 七、Step 6：看协作自动跑起来

团队齐了，CEO 开始委派（第 07 章 Step 9、第 08 章）。理想流程：

```
CEO 把「搭建站点框架」拆成任务 ──▶ 分配给工程师（设 parentId + goalId）
        │
工程师被自动唤醒 ──▶ 签出任务（第 08 章原子签出）──▶ 在 cwd 里建站、写代码
        │
工程师置 done + 评论「框架搭好，下一步做课程模块」
        │
子任务 done ──▶ 父任务被唤醒 ──▶ QA 的 review 任务自动解锁
        │
QA 被唤醒 ──▶ 签出 review 任务 ──▶ 跑测试，发现 bug
        │
QA 建一个修复子任务 @工程师 ──▶ 工程师被唤醒 ──▶ 自动改 bug ✅
```

最后那一步「**测试后工程师自动改 bug**」就是我们的验收信号——它能跑通，说明任务树、签出、@提及、wakeOnAssignment 这套协作机制全对了。

---

# 八、Step 7：在看板上监控

打开 Dashboard（第 12 章细讲），你能实时看到：
- 每个 Agent 当前在做哪个任务、什么状态
- 累计 token 花费、burn rate
- 任务树的整体进展

你（董事会）此刻该做的：**盯方向、批关键审批、必要时注入「品味」**（比如给工程师补一份品牌指南/参考站点，提升产出质量——第 01 章的护城河）。

---

# 九、Step 8：让它持续产出（例行任务）

社区要「持续产出内容」，可以配一个**例行任务（Routine）**（第 12/13 章会提到）。例行任务会按计划/webhook/API 触发，给指定 Agent 创建一次心跳：

```
POST /api/companies/{companyId}/routines
{
  "title": "每日热文排行更新",
  "description": "抓取并汇总当日 AI Agent 相关热门文章，更新到站点排行榜",
  "assigneeAgentId": "{运营或工程师AgentId}",
  "priority": "medium",
  "status": "active",
  "concurrencyPolicy": "coalesce_if_active",
  "catchUpPolicy": "skip_missed"
}
```

这样不用你每天手动催，公司自己「上班」。

# 十、常见错误（实战版）

- ❌ **公司建好就盯着等，结果一直不动**
  → 八成是 CEO 策略在等审批。去 Approvals 页。

- ❌ **CEO 派活了，工程师不动**
  → 查工程师有没有开 `wakeOnAssignment`；查任务 `parentId` 挂对没（第 08 章两大根因）。

- ❌ **工程师和 QA 互相等，卡死**
  → 多半任务树断了，子任务没挂到父任务，完成事件传不上去。

- ❌ **CEO 用了 process 适配器**
  → 不会规划。CEO/工程师/QA 都该用 `claude_local`。

- ❌ **预算太小，干到一半 Agent 被硬停**
  → 看板看到 Agent 变 `paused` 且 burn 到 100%，调高预算或优化任务粒度（第 12 章）。

- ❌ **产出质量差就猛改 prompt**
  → 先想想有没有给「品味输入」（品牌指南、参考资料）。输入决定上限。

# 十一、最佳实践（实战版）

- ✅ **从最小团队跑通闭环**：CEO + 工程师 + QA 三人就能验证整条链路，别一上来铺十个 Agent。
- ✅ **每个 Agent 独立 `cwd`**：隔离工作空间，利于 session 恢复。
- ✅ **关键审批认真看 payload**：这是你注入判断的入口。
- ✅ **先手动跑顺，再上例行任务**：确认协作正常了，再加 Routine 让它自动持续产出。
- ✅ **喂品味输入**：品牌指南、参考站点、风格要求——AI 团队产出的天花板就是你给的输入。
