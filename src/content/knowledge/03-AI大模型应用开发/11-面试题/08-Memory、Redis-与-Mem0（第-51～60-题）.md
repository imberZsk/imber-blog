# AI 大模型应用面试题（6）- Memory、Redis 与 Mem0（第 51～60 题）

> 读完你能：围绕“Memory、Redis 与 Mem0（第 51～60 题）”理解“题目与详细答案”与“第51题：LLM 的 Memory 本质是什么？”，并结合正文示例完成实践与排障。

> 重点考察短期状态、长期记忆和权威业务数据的边界，以及过期、冲突和删除治理。

# 一、题目与详细答案

## 第51题：LLM 的 Memory 本质是什么？

**答案：** 模型 API 默认无状态，Memory 是应用完成的保存、选择、压缩和注入。工作状态保存当前步骤，短期记忆保存线程上下文，长期记忆保存跨会话可复用事实；审计日志用于追责但不等于 Prompt 上下文。把全部 messages 每轮重发只是最简单实现，会带来成本、超长和噪声问题。

## 第52题：截断、总结和检索如何组合？

**答案：** 保留最近消息保证局部连贯，旧消息到阈值后生成带来源范围的滚动摘要，长期稳定事实进入可检索记忆库。新请求组装“系统规则 + 当前问题 + 近期消息 + 摘要 + 相关长期记忆”。截断要保持工具调用对完整；总结要防多次压缩失真；检索要处理权限、过期和冲突。

## 第53题：什么信息适合写入长期记忆？

**答案：** 用户明确表达、未来可能复用、允许持久化且可更新删除的偏好或事实，例如默认语言、长期项目和固定格式。不应保存临时指令、模型推测、密码/Token、可从权威数据库实时查询的易变事实。写入前要做价值、敏感性、重复、冲突和来源检查，并让用户可查看管理。

## 第54题：Redis 为什么适合 Agent 短期记忆？

**答案：** Redis 低延迟、支持 Hash/List/JSON、TTL、Stream 和原子操作，适合线程状态、最近消息、临时工具结果、限流与事件流。它也可借助 Search/HNSW 做长期语义召回。但订单、扣费、审批等不可丢业务事实必须落主库；Redis 是热路径状态层，不是默认权威事实源。

## 第55题：如何设计 Redis 会话键？

**答案：** 键至少包含应用命名空间、租户、用户和线程，如 `agent:session:{tenant}:{user}:{thread}`，并在业务层校验线程所有权。状态写入和 `EXPIRE` 用事务或 Lua 一起完成，避免有值无 TTL。大消息不要反复序列化为单个大 JSON；消息列表、摘要和工作状态可分结构存储并限制长度。

## 第56题：Redis 中 Agent 并发更新怎样防止覆盖？

**答案：** 用版本号、WATCH/MULTI、Lua 或事件追加模型，而不是用长锁包住 LLM 调用。请求先读取版本和快照，模型完成后比较版本再提交；冲突时重放或合并。工具副作用还需要主库幂等键。分布式锁必须有短 TTL、唯一 token，并用 Lua 校验 token 后释放。

## 第57题：短期记忆与长期记忆如何使用 TTL？

**答案：** 工作状态和会话有明确短 TTL；情节记忆可较长并随时间衰减；稳定语义偏好可无自动 TTL，但必须可更新删除和定期验证。Redis Stream 用 MAXLEN/XTRIM 控制长度，而不是只依赖 EXPIRE。TTL 到期策略要与产品预期一致，关键状态到期后应能从主库恢复或明确降级。

## 第58题：Mem0 的价值是什么？

**答案：** Mem0 在应用与存储之间提供记忆抽取、添加/更新/删除决策、按用户/Agent 范围搜索和存储适配，解决“哪些对话值得变成长期记忆”。它不是业务主库，也不能自动解决隐私和事实正确性。生产应封装其 API、固定用户边界、保存来源/版本，并对抽取精确率和删除传播做评测。

## 第59题：长期记忆冲突如何处理？

**答案：** 同一属性维护当前值和历史覆盖关系；用户明确新陈述高于旧陈述，权威业务数据高于模型推断。旧记忆标记 inactive/superseded，不再参与召回，但可按合规保留审计。时间敏感事实要有有效期。不能把互相冲突的 active 记忆都注入 Prompt，交给模型随机选择。

## 第60题：如何评估 Memory 系统？

**答案：** 看写入精确率、需要记忆时的 Recall、无关/过期/冲突注入率、摘要保真、Token 节省、任务成功率、删除传播时延和跨用户泄漏。构造跨会话测试：先写偏好，再修改，再删除，验证后续会话行为。只测试“能记住名字”不足以证明生产可用。

# 三、总结

Memory 的难点不在保存，而在选择、压缩、过期、冲突、删除和权限；Redis 与 Mem0 解决的是不同层级的问题。
