# 工程化工作流（08） - grill-me：用决策树把模糊需求问清楚

> grill-me 不是让 Agent “多问几个问题”，而是把设计拆成有依赖的决策树：能调查的事实由 Agent 调查，只有真实取舍才交给用户。

> 读完你能：主持一轮有结束条件的需求访谈，把答案整理成可交给 OpenSpec、Spec Kit 或实施计划的输入契约。

## 核心知识清单

- 决策树与问题前沿 Frontier
- 事实调查和用户决策的职责分离
- 每轮问题的依赖顺序与推荐答案
- 目标、非目标、约束、失败和验收
- 共享理解确认与访谈停止条件
- 从访谈记录到规范系统的交接

## 为什么普通“请先问我”仍会失败

无结构访谈常出现三类浪费：一次抛出 30 个互相依赖的问题；把仓库结构、框架版本等可查事实推给用户；只讨论正常路径，不问权限、失败、回滚和完成条件。结果是问题很多，决策仍然缺失。

grill-me 实际调用底层 `grilling` Skill。它先画出决策之间的依赖，当前置决策已经解决后，相关问题才进入本轮 **Frontier**。每个问题都给出推荐答案和理由，用户可以接受、修改或拒绝，而不是从空白开始设计。

## 一轮高质量访谈

以“自动修复失败 CI”为例，第一轮只问目标与风险边界：

```text
Q1 目标范围：只诊断，还是允许修改代码并提交 PR？
推荐：允许修改，但禁止直接推送 main；每次运行只创建一个待审查 PR。

Q2 成功标准：CI 变绿就算完成吗？
推荐：原失败消失、相关回归通过、没有新增失败，并附根因与 diff 摘要。

Q3 高风险动作：依赖升级、迁移和密钥变更怎么处理？
推荐：只生成方案并暂停，必须人工批准后执行。
```

范围确定后，第二轮才问触发来源、日志权限、修改目录、重试预算、超时和回滚。Agent 应先读取现有 CI、分支保护和测试脚本，不把“项目现在怎么配置”当作用户问答题。

## 交付物不是聊天记录

访谈结束时至少输出六项：问题陈述、目标与非目标、已确认决策、事实与来源、仍未解决的问题、可验证验收。对每个决策记录“为什么”，否则下一位 Agent 只看到结论，遇到新约束时无法判断是否应该调整。

停止条件是 Frontier 为空，且用户确认双方已形成共享理解。不能用“已经问了三轮”作为停止条件，也不能在用户确认前直接实现。随后将产物交给 OpenSpec 的 proposal/change 或 Spec Kit 的 specification，而不是让访谈内容只留在对话上下文里。

## 不适用和常见坑

- 拼写修复、明确的小范围改动不值得启动完整访谈。
- 推荐答案应暴露取舍，不应暗中替用户决定业务目标。
- 问题必须具体到可决策；“还有别的要求吗”无法关闭决策树。
- 用户改变上游决定后，要重新计算 Frontier，不能沿用已经失效的下游答案。

## 学完验收

- 能把一个需求拆成事实节点、决策节点及其依赖。
- 能解释为什么某个问题现在问，而另一个问题必须晚一轮。
- 访谈产物可被另一位 Agent 直接转成规格，且无需重新猜目标和边界。
