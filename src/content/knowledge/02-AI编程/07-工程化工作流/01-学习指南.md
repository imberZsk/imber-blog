# 工程化工作流（01） - 学习指南

> 这条路线解决的不是“再记几个命令”，而是如何把模糊意图变成可审查规格，再让 Agent 在受控循环中实现、验证和交付。

> 读完你能：按任务的不确定性、风险和规模选择访谈、规范、循环、图编排或角色化流水线，并为每一步留下可复核证据。

## 核心知识清单

- grill-me 的决策树、问题前沿与共享理解
- OpenSpec 的 change、delta spec、apply 与 archive
- GitHub Spec Kit 的 constitution、specify、plan、tasks 与 implement
- Superpowers 的设计、计划、TDD、审查和分支收尾
- loop-me 的 workflow spec、Trigger、Checkpoint、Brief 与 Push right
- Loop Engineering 的状态、进度、预算、停止条件和人工接管
- Graph Engineering 的节点、边、持久化、分支、审批与恢复
- gstack、PUA、GSD 与 BMAD 的定位、风险和组合边界

## 推荐顺序

1. 先读 `grill-me`，学会区分“能查到的事实”和“必须由人决定的取舍”。
2. 再从 OpenSpec 与 Spec Kit 二选一，把目标、非目标、场景、设计和任务落入仓库。
3. 用 Superpowers 完成隔离工作区、TDD、系统调试、审查和交付。
4. 任务需要多轮反馈时学习 Loop Engineering；存在显式分支、审批或恢复时再升级为 Graph Engineering。
5. 最后看 gstack、PUA、GSD 与 BMAD，判断应该复用一个完整流程，还是只引入某个缺失能力。

## 一条完整主线

```text
模糊意图
  -> grill-me 澄清决策
  -> OpenSpec / Spec Kit 固化规格
  -> Superpowers 设计、实现、测试与审查
  -> Loop 根据证据迭代
  -> Graph 管理分支、审批和恢复
  -> gstack / GSD / BMAD 扩展角色或生命周期
  -> 真实构建、测试、浏览器与发布证据验收
```

这些工具不是越多越好。小改动只需要目标、边界和验证命令；跨模块功能才值得维护规格；长时任务必须有预算和停止条件；部署、数据迁移、权限变更仍需人工批准。流程成本必须低于返工风险。

## 学完验收

- 给出一个模糊需求，能列出事实调查、用户决策、非目标和验收标准。
- 能解释 OpenSpec 与 Spec Kit 的差异，而不是把两者都叫“写文档工具”。
- 能设计一个含成功、失败、无进展、预算耗尽和人工接管的 Agent Loop。
- 能判断何时使用 Loop、何时使用 Graph，以及 gstack、PUA 是否值得引入。
- 完成声明包含真实命令、输出摘要、未验证项和剩余风险。
