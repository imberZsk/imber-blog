# 二、从模糊需求到可实施任务

先问“用户现在做不到什么”，再定义可观察结果。
对接口写请求、响应、错误和兼容性；
对 UI 写交互、空态、加载、错误和响应式边界；
对数据写来源、权限、迁移和回滚。
非目标能阻止 Agent 顺手扩大范围。

```markdown
## 目标
用户提交失败后保留表单内容，并看到可操作错误。
## 非目标
不重做表单组件，不改变后端错误码。
## 验收
- 400：显示字段错误并保留其他输入。
- 500：显示重试入口且只上报一次错误。
- 键盘和移动端流程通过浏览器测试。
```

规范发生变化时同步更新任务和验收，不让代码、测试、文档各自表达不同需求。
完成声明必须链接到测试、截图或运行记录。

# 三、工具分工

- **grill-me** 先构建决策树：Agent 自己调查事实，只把价值取舍、范围和风险选择交给用户。
- **OpenSpec** 适合已有系统的增量变更：当前 spec 表达现状，change 目录表达本次差异，验收后再归档合并。
- **GitHub Spec Kit** 适合从项目原则逐步推导规格、技术计划、任务和实现，并检查各阶段的追踪关系。
- **Superpowers** 不替代规格系统，它负责把设计、计划、隔离工作区、TDD、审查和收尾变成执行纪律。

具体命令、目录和失败处理见“工程化工作流”中的对应专篇。
本篇只负责建立选择边界，避免把四种不同职责压成一篇工具清单。

# 六、规范驱动开发与需求澄清 的结果解释

解释“规范驱动开发与需求澄清”实验时先看首个偏差，而不是最后一条错误。最后的异常通常只是上游状态错误的结果；从末端反推容易误把症状当根因。

| 观察结果 | 可以支持的判断 | 下一步 |
| --- | --- | --- |
| 主链路没有达到预期 | 条件缺失、结果不可复现或失败后责任不清 | 先执行：保留基线，缩小变量；根因确认前不扩大范围 |
| 异常链路无法恢复 | 条件缺失、结果不可复现或失败后责任不清 | 先执行：保留基线，缩小变量；根因确认前不扩大范围 |
| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

“规范驱动开发与需求澄清”只有同时满足“结果符合结论条件，异常输入可解释、可恢复”，并且没有出现“条件缺失、结果不可复现或失败后责任不清”，才可以认为主链路通过。这里的“通过”只对当前固定版本、样本和环境有效，不能外推到尚未测试的容量、权限或数据分布。

如果“规范驱动开发与需求澄清”候选方案与基线差异很小，先检查证据分辨率是否足够；如果差异很大，先排除数据泄漏、环境漂移和版本不一致。两种情况都不能只看一个汇总均值，需要回到逐样本输出和中间状态。

- **工具分工**：grill-me 先构建决策树：Agent 自己调查事实，只把价值取舍、范围和风险选择交给用户。
- **OpenSpec、Spec Kit 与规范驱动开发**：OpenSpec 适合已有系统的增量变更：当前 spec 表达现状，change 目录表达本次差异，验收后再归档合并。
- **验收标准、示例、边界和失败场景**：规范不是提前写完所有细节，而是把目标、边界和验收变成开发者与 Agent 都能检查的契约。
- **规范变更、追踪关系与完成证据**：GitHub Spec Kit 适合从项目原则逐步推导规格、技术计划、任务和实现，并检查各阶段的追踪关系。
