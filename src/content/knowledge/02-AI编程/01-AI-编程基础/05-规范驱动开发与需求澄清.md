# AI 编程基础（05） - 规范驱动开发与需求澄清

> 规范不是提前写完所有细节，而是把目标、边界和验收变成开发者与 Agent 都能检查的契约。

> 读完你能：把模糊需求整理成目标、非目标、边界和验收标准，并保持规范与实现可追踪。

## 核心知识清单

- 问题陈述、用户价值与非目标
- 需求澄清、歧义清单与决策记录
- OpenSpec、Spec Kit 与规范驱动开发
- 验收标准、示例、边界和失败场景
- 设计方案、实施计划与任务依赖
- 规范变更、追踪关系与完成证据

## 从模糊需求到可实施任务

先问“用户现在做不到什么”，再定义可观察结果。对接口写请求、响应、错误和兼容性；对 UI 写交互、空态、加载、错误和响应式边界；对数据写来源、权限、迁移和回滚。非目标能阻止 Agent 顺手扩大范围。

```markdown
## 目标
用户提交失败后保留表单内容，并看到可操作错误。
## 非目标
不重做表单组件，不改变后端错误码。
## 验收
- 400：显示字段错误并保留其他输入。
- 500：显示重试入口且只上报一次错误。
- 键盘和移动端流程通过浏览器测试。
```

规范发生变化时同步更新任务和验收，不让代码、测试、文档各自表达不同需求。完成声明必须链接到测试、截图或运行记录。

## 工具分工

- **grill-me** 先构建决策树：Agent 自己调查事实，只把价值取舍、范围和风险选择交给用户。
- **OpenSpec** 适合已有系统的增量变更：当前 spec 表达现状，change 目录表达本次差异，验收后再归档合并。
- **GitHub Spec Kit** 适合从项目原则逐步推导规格、技术计划、任务和实现，并检查各阶段的追踪关系。
- **Superpowers** 不替代规格系统，它负责把设计、计划、隔离工作区、TDD、审查和收尾变成执行纪律。

具体命令、目录和失败处理见“工程化工作流”中的对应专篇。本篇只负责建立选择边界，避免把四种不同职责压成一篇工具清单。
