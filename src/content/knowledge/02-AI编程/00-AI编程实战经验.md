# 一、背景

AI 编程工具已经没有技术壁垒，谁都能装上 Claude Code（CC）和 Codex。差距在于「会不会用」——配置、省 token、工作流、知识库沉淀，这些才是真正的硬技能。这篇把我实际在用的一套打法讲清楚。

# 二、CC 和 Codex

## 2.1 CC 的核心配置

https://code.claude.com/docs/zh-CN/settings

配置文件在 `~/.claude/settings.json`，最值钱的是三块：`env`（模型、base_url、鉴权）、`permissions`（默认模式 + deny 危险命令）、`hooks`（Notification / PostToolUse 挂钩）。用 `deny` 拦住 `git push --force`、`git reset --hard`、`git clean -f` 这类不可逆操作，比事后后悔靠谱。`defaultMode` 设 `bypassPermissions` 换免打扰，但一定要配合 deny 名单兜底。

`hooks` 里最实用的是挂一个「任务做完弹通知」的脚本：开了 bypass 模式挂机跑长任务时，AI 干完活或需要你时自动弹系统提示，不用一直盯着终端。下面 `Notification` 事件触发时调用一个 `notify.sh`（脚本里用 macOS 的 `osascript` 或 `terminal-notifier` 发通知即可，此处从略）。

```jsonc
{
  "env": { "ANTHROPIC_MODEL": "claude-opus-4-8", "ANTHROPIC_BASE_URL": "<你的中转地址>" },
  "permissions": {
    "deny": ["Bash(git push --force:*)", "Bash(git reset --hard:*)", "Bash(git clean -f:*)"],
    "defaultMode": "bypassPermissions"
  },
  "hooks": {
    // 任务完成 / 需要人工介入时弹系统通知，挂机跑长任务不用盯屏
    "Notification": [
      { "hooks": [{ "type": "command", "command": "~/.claude/hooks/notify.sh", "timeout": 10 }] }
    ]
  }
}
```

## 2.2 Codex 的核心配置

配置在 `~/.codex/config.toml`，关键字段是 `model`、`model_reasoning_effort`（推理强度，复杂任务开 `xhigh`）、`approval_policy`、`sandbox_mode`。`approval_policy = "never"` + `sandbox_mode = "danger-full-access"` 是全放开模式，效率高但要清楚自己在做什么。`[features]` 里可以按需打开 `goals`、`hooks` 等实验能力。

```toml
model = "gpt-5.5"
model_reasoning_effort = "xhigh"
approval_policy = "never"
sandbox_mode = "danger-full-access"
```

## 2.3 CC 的核心功能

`CLAUDE.md` 分级记忆（用户级 / 项目级 / 本地级）是灵魂，把约定写成「可检查、可执行」的规则，它每次都照办。`Esc Esc` 检查点回溯是后悔药，改错了一键回退到任意一步，放心大胆试。自定义 slash 命令（`.claude/commands/*.md`）把重复流程一键化，比如我用 `/polish-article`、`/lint-projects`。

## 2.4 Codex 的核心功能

`model_reasoning_effort` 可动态调，难题上 `xhigh`、琐事降下来省算力。skills（`~/.codex/skills/`）和 plugins 与 CC 打通，同一套 Superpowers 两边都能跑。goals + hooks 让它能记目标、在工具调用前后挂自动化。

# 三、节省 token

用 `/insights` 看自己的 token 花在哪，先量化再优化。大改动前用 Plan Mode 只出计划不动手，避免它一头扎进错误方向烧掉几万 token。把长任务拆给子代理（subagent）跑，主上下文只做协调，脏活的上下文不占用主窗口。

## 顾问工具（advisorModel）

https://code.claude.com/docs/zh-CN/advisor

在 `settings.json` 里配 `advisorModel`（或用 `/advisor` 命令），让主模型在关键节点——提交方案前、反复报错、声称完成前——咨询一个更强的顾问模型。它本身不省 token，省的是「返工的 token」：长任务里一次咨询几千 token，换掉主模型扎错方向、症状式打补丁反复重来烧掉的几万 token。注意它只在长任务、决策质量决定成败时划算，短任务上是净增成本；且顾问能力必须 ≥ 主模型（主模型 opus-4-8 时顾问只能选 opus/fable，设不了更便宜的档）。

## 把 skill 沉淀成 command

skill 的描述是常驻上下文的（模型得随时知道该不该触发它），装得越多常驻开销越大。如果某个 skill 你其实都是手动触发，就把它改写成自定义 command（`.claude/commands/*.md`），command 只在 `/命令` 调用时才加载，平时零占用。判断标准很简单：靠模型自动判断触发的留成 skill，你自己明确知道何时用的沉淀成 command。

## command + 脚本：确定性的活别让模型干

真正省 token 的杀招是「command 调脚本」——把流程里确定的步骤写成 shell/js 脚本，让 command 去调，模型只负责传参和读结果，不用一个 token 一个 token 地生成命令。我的 `work-auto-scripts` 就是这么干的：`comment-jira.sh` 追加 jira 评论、`upload-docs-to-feishu.sh` 上传文档到飞书，全是脚本跑，模型零推理。凡是能用代码稳定复现的活（找文件、拼接口、去重、发请求）都交给脚本，模型只在需要判断的地方出手。

# 四、软件辅助

## visual-worktree

我做的跨平台桌面应用，可视化管理多仓库和按「任务」组织的跨仓 worktree。核心场景：一个需求要改多个仓库时，按 `worktreesRoot/{任务名}/{项目名}` 批量建 worktree，还能批量切主分支、拉更新、查状态。技术栈 Electron + React + simple-git，配置和任务状态全存在本地 `~/.visualWorktree`，不上传任何仓库内容。

## visual-aicoding

同样是我做的，用图形界面统一管理散落在 `~/.claude`、`~/.codex` 下的配置、插件和市场。能可视化编辑 `settings.json` / `config.toml`（表单 + 语法校验 + 原始文本兜底），检查插件版本并一键更新。保存用「临时文件 + rename」原子写入，写一半崩溃也不会损坏原配置。

# 五、知识库

个人知识库用 Obsidian 管 Markdown，一个概念一篇短笔记，编号目录（`01-`、`02-`）按阶段排序，每个主题一篇 `course.md` 当索引。团队级用 AI 知识库三层模型：wiki-query 查、wiki-ingest/wiki-save 存、wiki-lint 巡检维护。核心原则是「单一事实来源」+「渐进式披露」——先给摘要，需要时再展开细节，省 token 又不丢信息。

# 六、工作流

## Superpowers

一套 skill（方法论）库，没有 slash 命令，工作时按需自动触发。管的是「每一步怎么做好」：TDD 先写测试再实现、systematic-debugging 先找根因禁止打补丁、verification-before-completion 声称完成前必须贴验证证据。类比就是「资深工程师的工作习惯」。

## OpenSpec

spec-driven 开发框架，用 slash 命令管「做什么、按什么顺序做」。5 个命令串起流程：`/opsx:explore`（只想不写）→ `/opsx:propose`（一次生成 proposal/design/tasks 三份文档）→ `/opsx:apply`（逐条实现）→ `/opsx:sync`（合并进主规范）→ `/opsx:archive`（归档）。强调「动作不是阶段」，apply 时发现设计错了随时回头改。

两者互补：OpenSpec 是流程的「轨道」，Superpowers 是跑在轨道上的「功力」，缺一不可。

## 通用知识库（g）

跨项目复用的全局知识层，放通用方法论、速查、可迁移的经验。AI 每次开工前先查这里，避免重复踩坑。对应 wiki-query 的通用检索路径。

## 项目知识库（p）

单个项目专属的业务知识层，用 areas-init 初始化，沉淀这个项目才有的领域规则和上下文。业务知识写在项目库、通用方法写在全局库，两层不混，检索时按需加载。

# 七、多 Agent 编排

把互不依赖的任务并行派给多个子代理（dispatching-parallel-agents），每个任务一个全新上下文实现 + 审查，主代理只做协调和汇总。配合 worktree 隔离工作区，多个代理并行改代码也不会互相污染。关键纪律：并行工作流汇报「全部完成」后，一定要在主分支独立跑一遍真实构建和完整测试再宣布成功，不要信任工作流自报的结果。
