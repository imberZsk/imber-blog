# 二、为什么扩展机制很重要

直接改核心循环来加功能，有几个大问题：

- **容易改崩**：核心循环是 Agent 的心跳，动一下满盘皆输。
- **耦合死**：每加个功能就塞进循环，循环越来越臃肿、没法维护。
- **不灵活**：不同用户/项目想要不同功能，全塞内核就没法按需启用。

扩展机制的思路是：

> **把核心循环做"薄"、做稳定，把可变的能力做成"插件"挂上去。** 内核只管驱动，扩展按需加载。

这跟软件工程里的"开闭原则"一个意思：**对扩展开放，对修改关闭。
** 你用的 Claude Code 能配 hooks、能加自定义命令，靠的就是这套机制。

# 三、Hooks：在循环的关键节点"拦一道"

Hook（钩子）是**挂在循环关键节点上的回调函数**。
循环跑到某个节点时，会"回头"调用你注册的 hook，让你有机会观察、修改、甚至拦截。

回忆第 02 章的循环，关键节点有这些可以挂 hook：

```text
用户输入 ──▶ [PreToolUse hook] ──▶ 执行工具 ──▶ [PostToolUse hook] ──▶ 喂回
                  ↑                              ↑
            工具执行前触发                    工具执行后触发
         （可审计/校验/拦截）              （可记日志/加工结果）
```

常见的 hook 时机和用途：

| Hook 时机 | 能干什么 |
| --- | --- |
| **工具执行前**（PreToolUse） | 审计、参数校验、**拦截危险操作**（第 08 章的门卫其实就是一种 hook！） |
| **工具执行后**（PostToolUse） | 记日志、统计、对结果做后处理 |
| **每轮结束** | 检查进度、注入提醒 |
| **会话开始/结束** | 加载配置、清理资源、归档日志 |

代码上，hook 机制朴素得很——就是在循环里留几个"回调点"：

```python
# hooks 注册表：把"时机"映射到一串回调函数
hooks = {"pre_tool": [], "post_tool": []}

def register(timing, fn):
    """注册一个 hook：在指定时机会被调用。timing: 时机名；fn: 回调函数。"""
    hooks[timing].append(fn)

def run_hooks(timing, context):
    """触发某个时机的所有 hook。context 携带当时的信息（工具名、参数、结果等）。"""
    for fn in hooks[timing]:
        # hook 可以观察、修改 context，甚至返回"拦截"信号
        context = fn(context) or context
    return context
```

然后在核心循环执行工具的前后，插一句 `run_hooks(...)` 即可。
**核心循环本身几乎不变，能力全靠注册进来的 hook。
**

> 💡 关键体会：第 08 章的"权限门卫"，本质就是一个注册在 `pre_tool` 时机的 hook。所以学到这里你会发现——**很多功能都能统一成"挂个 hook"**，这就是扩展机制的威力。

# 四、Skills / 命令：把"一套打法"封装起来复用

Hook 是"在节点上拦"，
Skill（技能 / 自定义命令）则是另一个方向——**把一套常用的"打法/流程"打包成一个可一键调用的能力。
**

比如你每次发布都要走："跑测试 → 打 tag → 构建 → 推镜像 → 通知群"。
与其每次都跟 Agent 啰嗦一遍这五步，
不如**封装成一个 `/release` 技能**，
里面写好流程和注意事项。
以后一句 `/release` 就触发整套。

Skill 通常长这样（一段结构化的指令 + 可选的脚本/工具）：

```markdown
---
name: release
description: 执行项目标准发布流程
---

当用户触发发布时，按顺序执行：
1. 跑全部测试，失败就停下报告
2. 给当前版本打 git tag
3. 构建产物
4. ……
注意：第 3 步失败必须回滚第 2 步的 tag。
```

它的价值：

- **复用**：常用流程沉淀下来，不用每次重复描述。
- **一致**：团队都用同一个 `/release`，流程标准化，少出错。
- **按需加载**：用到才加载进上下文，不占平时的窗口（呼应第 06 章）。

> Skill 和 Hook 的分工：**Hook 是"被动拦截"（循环跑到那儿自动触发），Skill 是"主动调用"（用户/Agent 显式触发一套流程）。** 一个管"过程管控"，一个管"能力封装"。

# 五、还有一种扩展：MCP（连接外部工具）

简单提一句更进阶的扩展——**MCP（Model Context Protocol）**。
前面工具都是你自己写的函数，
而 MCP 是一套**标准协议**，
让 harness 能即插即用地接上**别人做好的工具服务**（比如连数据库、连 GitHub、连某个 SaaS）。

你不用关心它的协议细节，记住这个定位即可：

> **MCP 之于工具，就像 USB 之于外设——一套标准接口，让 harness 能插上各种现成的外部能力，而不用为每个服务单独写适配代码。**

它本质上还是给 Agent 加工具，只不过工具来自外部、通过标准协议接入。

# 六、常见误区

❌ **误区 1：加功能就改核心循环。
** 循环要薄要稳。
能用 hook/skill 解决的，就别动内核。

❌ **误区 2：hook 里塞重逻辑、搞阻塞。
** hook 在循环关键路径上，里面干又慢又重的活会拖垮整个 Agent。
hook 要轻、要快。

❌ **误区 3：Skill 和 Hook 混为一谈。
** 一个是主动调用的能力封装，一个是被动触发的节点拦截，用途不同别混用。

❌ **误区 4：扩展太多太杂。
** 一堆 hook 互相影响、难以排查。
扩展也要克制，保持可维护。

---

# 七、最佳实践

✅ **核心循环做薄做稳**，可变能力做成可插拔的扩展（开闭原则）。
✅ **拦截/审计/记日志类用 Hook**，挂在合适的时机点，保持轻量快速。
✅ **常用流程/打法用 Skill 封装**，提升复用和一致性，按需加载省窗口。
✅ **接外部现成能力用 MCP**，享受"标准接口、即插即用"。
✅ **扩展也要克制**，别让一堆 hook/skill 变成新的维护负担。

# 八、动手实践：Hooks 与 Skills：不改内核给 Agent 加料

- **Hook**：注册一个"每次调用工具前后自动记日志"的钩子，挂在循环节点上被动触发。
- **Skill**：封装一个 `/summary` 技能，把"读文件 + 总结"这套打法打包成一键调用。

## 8.1 怎么跑

无需 API Key，直接跑：

```bash

```

输出会展示：

1. Agent 正常调用工具，但每次工具执行前后都被 hook 自动记了日志（带时间戳）

3. 最后打印完整的工具调用日志——这些日志完全由 hook 产生，核心循环一行没改

## 8.2 看点

1. **核心循环没改**：看 `agent_loop` 函数，它只在工具前后插了 `run_hooks(...)`，加日志能力完全来自外部注册的 hook。
2. **门卫也是 hook**：对照第 08 章，权限确认其实就能注册成一个 `pre_tool` hook。
3. **Hook 被动 vs Skill 主动**：hook 是循环自动触发的，skill 是显式调用的——对照第 10 章的区分。
4. 试着再注册一个 hook（比如"统计工具调用次数"），体会"加功能不动内核"的爽感。

| 恢复重放 | 执行：保留基线，缩小变量；根因确认前不扩大范围 | 原失败样本的复测证据 | 原样本恢复，正常样本没有回归 |

恢复动作不是简单重启。对于“Hooks 与 Skill 扩展加载机制”，第一步是：保留基线，缩小变量；根因确认前不扩大范围。完成后使用原始失败样本复测；只验证一个新样本成功，不能证明触发条件已经消失。

“Hooks 与 Skill 扩展加载机制”边界实验结束后，应把正常、临界、失败和恢复四类记录放在同一个运行批次中。这样才能区分“候选方案真的修复问题”和“环境变化让问题暂时没有出现”。

# 十三、总结

- **为什么扩展机制很重要**：容易改崩：核心循环是 Agent 的心跳，动一下满盘皆输。
- **Hooks：在循环的关键节点"拦一道"**：Hook（钩子）是挂在循环关键节点上的回调函数。
- **Skills / 命令：把"一套打法"封装起来复用**：Hook 是"在节点上拦"，Skill（技能 / 自定义命令）则是另一个方向——把一套常用的"打法/流程"打包成一个可一键调用的能力。
- **还有一种扩展：MCP（连接外部工具）**：前面工具都是你自己写的函数，而 MCP 是一套标准协议，让 harness 能即插即用地接上别人做好的工具服务（比如连数据库、连 GitHub、连某个 SaaS）。
- **常见误区**：一个是主动调用的能力封装，一个是被动触发的节点拦截，用途不同别混用。
- **最佳实践**：✅ 核心循环做薄做稳，可变能力做成可插拔的扩展（开闭原则）。
