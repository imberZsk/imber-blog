# 五、几个最坑的「反模式」

这些是新手反复栽跟头的地方，单独拎出来强调：

1. **「全能技能」反模式**：想做一个「啥都能干」的超级技能。结果触发不准、正文巨大、谁也维护不了。**拆开。**

2. **「沉默资源」反模式**：辛辛苦苦写了 reference、templates，却忘了在正文引用。Claude 根本不知道它们存在。**正文不点名 = 文件不存在。**

3. **「巨型正文」反模式**：把所有内容怕 Claude 看不到，全堆进 SKILL.md 正文。每次触发都烧巨量 token。**该外置的外置。**

4. **「干描述」反模式**：`description: 周报工具`。没有场景、没有用户语言，技能永远静静躺着不被触发。**用公式：当用户需要……时使用。**

5. **「AI 硬算」反模式**：明明该用脚本的精确计算/格式转换，非让 Claude 推理。又慢又错。**交给代码。**

# 六、心智模型：把技能当「同事的 SOP」来写

写技能时，想象你在给一位**新来的、很聪明但不了解你具体业务的同事**写工作手册：

- 你会先告诉他「这岗位是干嘛的、什么情况下找你」（description）。
- 你会给他「干活的标准流程」（正文）。
- 又厚又少用的资料，你会说「在那本手册里，要用再翻」（reference）。
- 容易算错的活，你会给他「一个计算器/工具」（脚本）。
- 你不会把整个公司的制度都背给他听（简洁优先）。

用这个视角，很多设计决策会自然变清晰。

| 主链路没有达到预期 | 条件缺失、结果不可复现或失败后责任不清 | 先执行：保留基线，缩小变量；根因确认前不扩大范围 |
| 异常链路无法恢复 | 条件缺失、结果不可复现或失败后责任不清 | 先执行：保留基线，缩小变量；根因确认前不扩大范围 |
| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

“Skill 最佳实践与常见问题”只有同时满足“结果符合结论条件，异常输入可解释、可恢复”，并且没有出现“条件缺失、结果不可复现或失败后责任不清”，才可以认为主链路通过。这里的“通过”只对当前固定版本、样本和环境有效，不能外推到尚未测试的容量、权限或数据分布。

如果“Skill 最佳实践与常见问题”候选方案与基线差异很小，先检查证据分辨率是否足够；如果差异很大，先排除数据泄漏、环境漂移和版本不一致。两种情况都不能只看一个汇总均值，需要回到逐样本输出和中间状态。

“Skill 最佳实践与常见问题”故障定位完成后，记录“现象、首个偏差、根因、改动、原样本复测”五项。缺少原样本复测时，只能标记为待观察，不能标记为已解决。

# 十六、Skill 最佳实践与常见问题 的发布判断

发布判断需要把“Skill 最佳实践与常见问题”的质量、失败边界和恢复能力放在同一份记录中。以下任一条件缺失，都应停止扩量，而不是用“基本正常”替代证据。

- [ ] “Skill 最佳实践与常见问题”的基线与候选只存在一个计划内变量。
- [ ] “Skill 最佳实践与常见问题”的输入、代码、依赖、配置和数据版本可以追溯。
- [ ] “Skill 最佳实践与常见问题”的正常、临界、失败和恢复样本使用同一套断言。
- [ ] “Skill 最佳实践与常见问题”的原始输出、中间状态和失败现场已经保留。
- [ ] “Skill 最佳实践与常见问题”的日志、Trace、截图和测试数据已经脱敏。
- [ ] “Skill 最佳实践与常见问题”的停止条件、负责人和回滚入口已经演练。
- [ ] “Skill 最佳实践与常见问题”尚未覆盖的输入、权限、容量和外部依赖已经登记。

最终记录至少包含基线版本、唯一变量、原始证据、首个偏差、恢复复测和发布责任人。没有参与本次修改的人如果不能据此重放“Skill 最佳实践与常见问题”的判断，就不能发布。

# 十七、总结

- **心智模型：把技能当「同事的 SOP」来写**：你会先告诉他「这岗位是干嘛的、什么情况下找你」（description）。
- **内容组织**：| 正文给「步骤 + 输出格式 + 示例」 | 只写一句模糊的「帮我做 xx」 |
- **脚本与安全**：| 脚本写清用法、校验输入、友好报错 | 缺参数就崩栈 |
- **调试与维护**：| 一次只改一处，开新会话验证 | 一次改一大片，无法定位 |
