# 二、持续演进：技能也要迭代

技能不是写完就完事，它会随业务变化。建立一个轻量的迭代习惯：

1. **收集反馈**：用的人觉得「触发不准」「产出漏了点」，就是迭代信号。
2. **小步改进**：一次改一处（第 10 章纪律），改完跑测试用例。
3. **记录变更**：重要修改在提交信息或 README 里写一句「为什么改」，方便回溯。
4. **定期回顾**：技能多了之后，定期看看有没有「职责重叠该合并」或「太大该拆分」的。

> 把技能当成「活的文档」：它和业务一起成长，越用越准、越用越好。

# 三、团队落地的一套简单方案

如果你想在团队推行技能，这套流程最省心：

1. **建一个共享目录**：在项目仓库的 `.claude/skills/` 下放团队公认的技能。
2. **定个简单规范**：命名用小写连字符、每个技能附测试用例、改动走 PR review。
3. **从一个高频痛点起步**：选团队最常重复的一件事（如代码审查、写周报）做成第一个技能，让大家尝到甜头。
4. **鼓励贡献**：谁有好用的个人技能，整理一下提进共享目录。
5. **定期清理**：淘汰没人用的、合并重复的，保持技能集精简。

# 四、常见错误

- **❌ 全用个人级，团队各搞各的**：同一个技能十个人写十遍，标准不统一。该共享的放项目级。
- **❌ 技能进了仓库却没文档**：新人看不懂、不敢改，慢慢变成没人维护的黑盒。
- **❌ 从不迭代**：业务变了技能没跟上，触发不准还在用，越用越糟。
- **❌ 改技能不走 review**：团队共享的技能被人随手改坏，影响所有人。
- **❌ 技能越堆越多不清理**：重复、过时的技能互相干扰，触发开始混乱。

# 五、最佳实践

- **按作用域选位置**：个人工具放个人级，团队标准放项目级（进 Git 仓库）。
- **技能自带文档**：description 清晰 + 正文首句说职责 + 必要时附 README。
- **改动走 PR**：团队共享技能和代码一样 review，防止被改坏。
- **从高频痛点起步推行**，让团队先尝到甜头再铺开。
- **定期回顾**：合并重复、拆分过大、淘汰过时。

## 7.2 看点

1. 技能放在**项目的 `.claude/skills/` 里**，而不是个人的 `~/.claude/skills/`。区别：
   - 个人级：只有你能用，跟着你的机器走。

2. 目录里有 `README.md` 写明团队规范——这让技能库可维护、新人能上手。

```bash
git add .claude/skills
git commit -m "feat: 添加团队共享技能 code-review 和 weekly-report"
```

队友 `git pull` 后，这些技能在该项目里自动可用。

| 恢复重放 | 执行：停止扩量，回滚制品与配置，数据采用前向修复 | 原失败样本的复测证据 | 原样本恢复，正常样本没有回归 |

恢复动作不是简单重启。对于“Skill 分享、版本与演进”，第一步是：停止扩量，回滚制品与配置，数据采用前向修复。完成后使用原始失败样本复测；只验证一个新样本成功，不能证明触发条件已经消失。

“Skill 分享、版本与演进”边界实验结束后，应把正常、临界、失败和恢复四类记录放在同一个运行批次中。这样才能区分“候选方案真的修复问题”和“环境变化让问题暂时没有出现”。

# 十、Skill 分享、版本与演进 的结果解释

解释“Skill 分享、版本与演进”实验时先看首个偏差，而不是最后一条错误。最后的异常通常只是上游状态错误的结果；从末端反推容易误把症状当根因。

| 观察结果 | 可以支持的判断 | 下一步 |
| --- | --- | --- |
| 主链路没有达到预期 | 版本不明、配置漂移、健康检查失真或数据不兼容 | 先执行：停止扩量，回滚制品与配置，数据采用前向修复 |
| 异常链路无法恢复 | 版本不明、配置漂移、健康检查失真或数据不兼容 | 先执行：停止扩量，回滚制品与配置，数据采用前向修复 |
| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

“Skill 分享、版本与演进”只有同时满足“版本可追溯，灰度不劣于基线，回滚路径已验证”，并且没有出现“版本不明、配置漂移、健康检查失真或数据不兼容”，才可以认为主链路通过。这里的“通过”只对当前固定版本、样本和环境有效，不能外推到尚未测试的容量、权限或数据分布。

如果“Skill 分享、版本与演进”候选方案与基线差异很小，先检查证据分辨率是否足够；如果差异很大，先排除数据泄漏、环境漂移和版本不一致。两种情况都不能只看一个汇总均值，需要回到逐样本输出和中间状态。

“Skill 分享、版本与演进”故障定位完成后，记录“现象、首个偏差、根因、改动、原样本复测”五项。缺少原样本复测时，只能标记为待观察，不能标记为已解决。

# 十一、Skill 分享、版本与演进 的发布判断

发布判断需要把“Skill 分享、版本与演进”的质量、失败边界和恢复能力放在同一份记录中。以下任一条件缺失，都应停止扩量，而不是用“基本正常”替代证据。

- [ ] “Skill 分享、版本与演进”的基线与候选只存在一个计划内变量。
- [ ] “Skill 分享、版本与演进”的输入、代码、依赖、配置和数据版本可以追溯。
- [ ] “Skill 分享、版本与演进”的正常、临界、失败和恢复样本使用同一套断言。
- [ ] “Skill 分享、版本与演进”的原始输出、中间状态和失败现场已经保留。
- [ ] “Skill 分享、版本与演进”的日志、Trace、截图和测试数据已经脱敏。
- [ ] “Skill 分享、版本与演进”的停止条件、负责人和回滚入口已经演练。
- [ ] “Skill 分享、版本与演进”尚未覆盖的输入、权限、容量和外部依赖已经登记。

最终记录至少包含基线版本、唯一变量、原始证据、首个偏差、恢复复测和发布责任人。没有参与本次修改的人如果不能据此重放“Skill 分享、版本与演进”的判断，就不能发布。

# 十二、总结

- **作用域**：个人 Skill 服务个人习惯，项目级 Skill 随仓库分发并接受团队约束，不能把机器私有路径写进共享能力。
- **版本演进**：根据触发错误和产出缺口小步修改，每次只改变一个可验证行为，并在提交或变更记录中说明原因。
- **质量门禁**：共享 Skill 的 description、正文、脚本和测试用例一起走 PR，成功、边界和失败样例都通过后才能合并。
- **生命周期**：定期统计使用情况，合并职责重复项、拆分过大项并删除过时项，避免多个 Skill 争抢同一触发场景。
