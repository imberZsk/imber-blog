# Claude Code（05） - 工作循环与检查点回溯：读—改—跑—验证 + 后悔药

> 本章目标：理解 Claude Code 的核心工作循环；学会用检查点把文件回退到任意一步。
> 学完你能：看懂它每步在做什么，改错了能一键回溯，放心大胆地试。

---

# 一、它干活的基本节奏：读—改—跑—验证

你下完指令，它不是「啪」一下吐出代码就完。一个完整的循环长这样：

```
   ┌─────────────────────────────────────────────┐
   │  1. 读：搜索 + 读相关文件，搞清现状           │
   │  2. 改：编辑文件（每次改动都展示给你看）       │
   │  3. 跑：执行命令（跑测试 / 构建 / lint）       │
   │  4. 验证：看结果。没过？回到第 2 步自己修      │
   └─────────────────────────────────────────────┘
                      ↓ 验证通过
                    交付给你审查
```

举个例子，你说「修复 cart.test.js 失败的用例」，你会依次看到：

1. **读**：它 grep 搜 `cart`、读 `cart.js` 和 `cart.test.js`；
2. **改**：它定位到 bug，编辑 `cart.js`（屏幕显示 diff）；
3. **跑**：它执行 `npm test`；
4. **验证**：测试全绿 → 交付；若还有红 → 它自己回去再改。

**看懂这个循环，你就知道任何时刻它在哪一步、该不该打断。**

---

# 二、每一步你都有控制权

- **它要改文件 / 跑命令时**，默认会**先问你**（权限机制第 06 章细讲）。你可以：
  - 同意这一次；
  - 同意并以后类似操作不再问；
  - 拒绝，并补充说明让它换个做法。
- **它跑偏了**：按 `Esc` 立刻打断，然后纠正方向。
- **想看它改了啥**：如果项目用 git，随时 `git diff` 看全部改动。

> 🔑 心法：**你是 reviewer，它是 executor。** 让它干活，但每一步的「准/不准」由你把关。

---

# 三、后悔药：检查点与回溯

试错难免。Claude Code 提供了「**检查点（checkpoint）**」——它会在对话推进中记录文件状态，让你能**把文件回退到之前任意一步**，就像游戏存档读档。

## 3.1 怎么用（交互式）

连按两次 **`Esc Esc`**，会弹出对话历史里的各个节点，选一个就能把**文件**回退到那一刻的状态。

适用场景：

- 它连续改了好几轮，越改越歪 → 回退到「还没歪」的那一步重来；
- 你想换个思路试试 → 先回到岔路口，再走另一条路；
- 改崩了不想手动一个个撤销 → 一键回到干净状态。

## 3.2 要分清：回退的是「文件」，不是「记忆」

回溯主要恢复的是**文件内容**。对话的上下文还在，所以你可以「回到那一步的文件 + 带着这一路的教训」重新出发。

> 💡 这和 `git` 不冲突。git 是你主动提交的版本；检查点是会话内的细粒度「即时存档」，更轻、更密。两者配合：大节点用 git 提交，会话内试错用检查点回溯。

---

# 四、常见错误

**错误 1：放着它自动跑一长串却从不看 diff**
它能力强，但不是永远对。养成看改动的习惯，尤其是它「连跑好几步」之后。

**错误 2：改崩了手动一行行撤**
没必要。`Esc Esc` 回溯到上一个好状态，比手动撤销快且不易漏。

**错误 3：把检查点当成 git 的替代品**
检查点是会话内的临时存档，关键里程碑还是要 `git commit` 落地。会话结束后，git 才是你长期可靠的版本记录。

**错误 4：它在「跑」的步骤卡住/报错，却没给它反馈**
它跑命令失败时，往往会自己尝试修。如果它卡住，把报错信息补给它，或 `Esc` 后换个思路。

---

# 五、最佳实践

1. **干活前先 `git commit` 一个干净基线**：万一要彻底推倒，`git` 兜底。
2. **大改之前，心里标个检查点**：知道「这步之前是好的」，出问题随时 `Esc Esc` 回去。
3. **盯住「验证」这一步**：它跑的是不是对的测试/命令？验证标准对了，结果才可信。
4. **它自我纠错时给点耐心**：测试没过它会自己再改，别急着插手；但若它在原地打转两次以上，就该介入换思路。

---

# 六、总结

- 它的核心节奏是**读 → 改 → 跑 → 验证**，没过会自己回到「改」再来一遍。
- 每一步你都有控制权：`Esc` 打断、看 diff、同意/拒绝它的操作。
- **`Esc Esc` 是后悔药**：把文件回退到对话中任意一步，大胆试错不怕崩。
- 检查点管会话内试错，git 管长期版本，两者配合最稳。

入门篇到此结束——你已经会装、会问、看得懂它干活、还能一键回退。下一篇进阶篇，我们从「给项目立规矩」开始，让它越用越懂你。👉 `06-CLAUDE.md与记忆分级.md`

# 动手实践：Demo 04 · 读—改—跑—验证 + 检查点回溯实战

这个 Demo 是一个**带测试、且故意留了一个 bug** 的小项目（购物车计价）。你将完整体验一遍 Claude Code 的工作循环，并练习用 `Esc Esc` 回溯。

## 怎么用

1. 先建一个干净基线（强烈建议）：
   ```bash
   cd 05-工作循环与检查点回溯-demo
   git init && git add -A && git commit -m "baseline"
   ```
2. 跑测试，亲眼看到失败：
   ```bash
   node cart.test.js
   ```
   你会看到「折扣计算」相关用例不通过。
3. 启动 Claude Code，下达带验证方式的指令：
   ```
   运行 `node cart.test.js`，有用例失败。
   帮我定位 @cart.js 里的 bug 并修复，修完重新跑测试，全绿才算完成。
   ```
4. **观察它的工作循环**：读 → 改（看 diff）→ 跑测试 → 没过就自己再改 → 全绿交付。

## 练习检查点回溯

- 等它改完后，故意说一句「换个写法重来」之类的，让它再改一版；
- 然后按 **`Esc Esc`**，把文件回退到之前某一步，体会「后悔药」。
- 对比：`git diff` 看的是相对 baseline 的总改动；检查点回退的是会话内的某一步。

## 文件说明

- `cart.js`：购物车计价逻辑，`applyDiscount` 里有个故意的 bug。
- `cart.test.js`：极简测试（用 Node 自带 assert，无需安装依赖）。
