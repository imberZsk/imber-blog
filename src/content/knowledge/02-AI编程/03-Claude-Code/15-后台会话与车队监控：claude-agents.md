# Claude Code（14）- 后台会话与车队监控：claude agents

> 本章目标：把任务丢后台跑，用 `claude agents` 一屏监控所有后台会话状态。
> 学完你能：同时派发多个后台任务，一眼看清谁在跑、谁要你拍板、谁完成了。

---

# 一、后台会话是什么

前面并行干活，你得开好几个终端盯着。但有些任务很长（跑一大轮重构、补一整套测试），你不想干等。**后台会话**让任务**脱离终端继续跑**——每个后台会话都是一个**完整的 Claude Code 对话**，只是没有终端挂在上面。

你派出去就能去忙别的，它在后台自己推进，需要你拍板时再来找你。

---

# 二、用 claude agents 一屏监控

任务一多，怎么知道哪个在跑、哪个卡住要你输入、哪个干完了？用 **agent view**：

```bash
claude agents
```

它打开一块**统一面板**，列出所有后台 Claude Code 会话，每个的状态一目了然：

- 🟢 **正在跑**：还在干活；
- 🟡 **需要你输入**：卡在某个要你拍板的地方；
- ✅ **已完成**：干完了，等你查收。

在这个面板里你还能**派发新会话**、切进某个会话看详情。按 `Esc` 退出回到 shell。

> 类比：你是车队调度员，`claude agents` 就是那块大屏，每辆车（会话）在哪、什么状态，尽收眼底。

---

# 三、典型用法：派发 + 巡检

```
# 1. 派几个后台任务（可结合 worktree 隔离）
#    比如分别让它们去补测试、修 bug、写文档

# 2. 随时巡检
claude agents
#    扫一眼：哪个跑完了？哪个卡住等我输入？

# 3. 进到"需要输入"的那个，给它指示，让它接着跑
```

这套流程让你从「盯着一个终端等」变成「调度一支车队」——**派活 → 巡检 → 只在必要时介入**。

---

# 四、和前几章的关系

到这里，「规模化」的拼图凑齐了：

- **子代理（11）**：一个会话内并行思考；
- **Agent Team（12）**：多会话协作沟通；
- **Worktree（13）**：并行任务文件不打架；
- **后台会话 + claude agents（14）**：把这些并行任务**丢后台跑，并统一监控**。

合起来，你能同时驱动一支「代理车队」干活，自己只做调度和关键决策。

> ⚠️ 注意：agent view 目前是研究预览（research preview）特性，不同版本表现可能有差异；它需要在交互式终端里打开。

---

# 五、常见错误

**错误 1：派了一堆后台任务从不巡检**
后台不等于「丢了不管」。有的会卡在「需要你输入」。→ 定期 `claude agents` 扫一眼。

**错误 2：把需要你频繁拍板的任务丢后台**
一步一确认的活放后台，反而老来打断你。→ 后台更适合「能自己跑一长段」的任务。

**错误 3：后台任务都挤在同一目录**
不隔离会互相覆盖。→ 配合 worktree（第 13 章）给每个后台任务独立工作区。

**错误 4：一次性派太多，自己管不过来**
车队也要量力。→ 从几个开始，熟悉调度节奏再加。

---

# 六、最佳实践

1. **长任务才丢后台**：能自己跑一大段的活适合后台，碎步确认的别放。
2. **定期巡检**：`claude agents` 当成你的「调度大屏」，常扫一眼。
3. **配合 worktree 隔离**：每个后台任务独立工作区，不打架。
4. **只在必要时介入**：让它们自己跑，卡住要输入时你再进去。
5. **控制并发量**：从少到多，匹配你能照看的范围。

---

# 七、总结

- 后台会话 = 任务**脱离终端继续跑**，每个都是完整的 Claude Code 对话。
- `claude agents` 打开**统一监控面板**：谁在跑、谁要输入、谁完成，一屏看清。
- 工作模式：**派活 → 巡检 → 必要时介入**，你当调度员。
- 与子代理/团队/worktree 合体，组成可监控的「代理车队」。

# 动手实践：Demo 14 · 后台车队调度演练

本章讲后台会话与 `claude agents` 监控面板。Demo 是一份「调度员巡检」操作清单。

## 文件
- `车队调度清单.md`：派活 → 巡检 → 介入 的标准流程与状态对照。

## 怎么用
照清单在真实项目里把几个长任务丢后台，再用 `claude agents` 巡检，体会「当调度员」的感觉。

## 实践目标

本 Lab 用最小输入验证“Demo 14 · 后台车队调度演练”的核心行为。先按上文命令运行基线，记录输入、关键中间状态和最终输出；再只修改一个参数或一个分支，比较结果差异。不要在第一次运行时同时更换依赖、模型和数据，否则失败后无法定位变量。

## 实践验收

1. 安装、启动或执行命令退出码为 0，输出与 README 描述一致。
2. 至少准备一个正常输入、一个边界输入和一个失败输入，并说明系统为什么得到该结果。
3. 涉及模型、检索或工具时，记录请求 ID、版本、候选或工具参数，保证结果可复现。
4. 涉及文件、网络或写操作时，验证路径、超时、权限和幂等边界；错误不能只打印后继续伪装成功。

## 常见问题

- 环境失败：先确认 Python/Node 版本、工作目录和依赖安装结果，再检查业务代码。
- 结果不稳定：固定样例、随机种子和配置版本，分别记录输入与输出。
- 示例能跑但无法解释：逐步打印或断言中间状态，直到能说清每个阶段的输入、处理和产物。
