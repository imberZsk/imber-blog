# Claude Code（15）- /loop：让任务循环跑

> 本章目标：用 `/loop` 让一段提示反复执行，可固定间隔或让它自定节奏。
> 学完你能：让它持续盯着某件事，直到你喊停。

---

# 一、什么是 /loop

到目前为止，都是「你说一句，它干一轮」。但有些事需要**反复做**：盯着部署有没有好、CI 过没过、有没有新的 review 评论要处理。一遍遍手动催它太累。

`/loop` 就是让一段提示**只要会话开着就反复执行**的命令。它还有个别名 `/proactive`。

---

# 二、三种用法

**用法 1：固定间隔**

给个时间间隔（`5m`、`2h`），它就按这个频率反复跑：

```
/loop 5m 检查部署是否完成，完成了就告诉我发生了什么
```

每 5 分钟跑一次这段提示。Claude 会把间隔转成 cron 表达式来调度。

**用法 2：动态间隔（让它自己定节奏）**

省略时间，让它**根据观察到的活动自己决定**下一次什么时候跑——通常更省 token：

```
/loop 检查 CI 是否通过，并处理任何 review 评论
```

它会自己判断「现在该多久后再看一眼」，而不是死板地固定频率。

**用法 3：什么都不给（内置维护）**

`/loop` 后面啥都不加，它会跑一个**内置的维护检查**；如果你项目里有 `.claude/loop.md`，它会跑里面定义的提示：

```
/loop
```

---

# 三、固定 vs 动态：怎么选

| | 固定间隔 `/loop 5m` | 动态间隔 `/loop` |
| --- | --- | --- |
| 何时下一轮 | 死板按周期 | 它根据活动自己判断 |
| Token 成本 | 可能浪费（没事也跑） | 更省（没动静就拉长间隔） |
| 适合 | 你明确要「每 X 分钟一次」 | 大多数「盯着直到完成」的场景 |

> 经验：**不确定就用动态**（不加间隔），让它聪明地自定节奏。明确需要固定频率时才写死。

---

# 四、典型场景

```
# 盯部署
/loop 5m 检查生产部署状态，部署成功或失败都立刻告诉我

# 盯 CI + 自动处理评论
/loop 检查这个 PR 的 CI，过了就告诉我；有 review 评论就帮我逐条处理

# 盯一个长任务的日志
/loop 3m 看一眼训练日志最后 50 行，有报错或异常就总结给我
```

共同点：**一件需要反复查看、直到某个状态出现的事。**

---

# 五、常见错误

**错误 1：把一次性任务硬套 /loop**
「帮我改个函数」不需要循环。`/loop` 是给**反复性**任务用的。

**错误 2：固定间隔设得过密**
`/loop 10s` 盯一个要十分钟才有结果的事，纯烧 token。→ 间隔匹配事情变化的节奏，或干脆用动态。

**错误 3：开了循环忘了关**
会话开着它就一直跑。事情办完记得停掉，别让它空转。

**错误 4：循环里塞会改东西的高危操作**
反复自动执行的提示，尽量是**只读/低风险**的检查。要改动的，让它「发现后告诉你」，由你决定。

---

# 六、最佳实践

1. **反复性任务才用**：一次性的别套循环。
2. **默认用动态间隔**：不加时间，让它自定节奏、省 token。
3. **间隔匹配节奏**：固定间隔时，频率对齐事情真实的变化速度。
4. **循环内容偏只读**：盯状态、看日志、报告；高危改动留给你拍板。
5. **办完即停**：别让循环空转。

---

# 七、总结

- `/loop`（别名 `/proactive`）= 让一段提示**反复执行**，会话开着就一直跑。
- 三种用法：**固定间隔**（`/loop 5m ...`）、**动态间隔**（`/loop ...`，自定节奏更省）、**纯 `/loop`**（内置维护或 `.claude/loop.md`）。
- 适合「盯着某件事直到出结果」，内容尽量只读，办完即停。

## 实践目标

本 Lab 用最小输入验证“Demo 15 · /loop 命令速查与场景脚本”的核心行为。先按上文命令运行基线，记录输入、关键中间状态和最终输出；再只修改一个参数或一个分支，比较结果差异。不要在第一次运行时同时更换依赖、模型和数据，否则失败后无法定位变量。

## 实践验收

1. 安装、启动或执行命令退出码为 0，输出与 README 描述一致。
2. 至少准备一个正常输入、一个边界输入和一个失败输入，并说明系统为什么得到该结果。
3. 涉及模型、检索或工具时，记录请求 ID、版本、候选或工具参数，保证结果可复现。
4. 涉及文件、网络或写操作时，验证路径、超时、权限和幂等边界；错误不能只打印后继续伪装成功。

## 常见问题

- 环境失败：先确认 Python/Node 版本、工作目录和依赖安装结果，再检查业务代码。
- 结果不稳定：固定样例、随机种子和配置版本，分别记录输入与输出。
- 示例能跑但无法解释：逐步打印或断言中间状态，直到能说清每个阶段的输入、处理和产物。
