# Skills（12）- 组织分享与演进


# 一、持续演进：技能也要迭代

技能不是写完就完事，它会随业务变化。建立一个轻量的迭代习惯：

1. **收集反馈**：用的人觉得「触发不准」「产出漏了点」，就是迭代信号。
2. **小步改进**：一次改一处（第 10 章纪律），改完跑测试用例。
3. **记录变更**：重要修改在提交信息或 README 里写一句「为什么改」，方便回溯。
4. **定期回顾**：技能多了之后，定期看看有没有「职责重叠该合并」或「太大该拆分」的。

> 把技能当成「活的文档」：它和业务一起成长，越用越准、越用越好。

# 二、团队落地的一套简单方案

如果你想在团队推行技能，这套流程最省心：

1. **建一个共享目录**：在项目仓库的 `.claude/skills/` 下放团队公认的技能。
2. **定个简单规范**：命名用小写连字符、每个技能附测试用例、改动走 PR review。
3. **从一个高频痛点起步**：选团队最常重复的一件事（如代码审查、写周报）做成第一个技能，让大家尝到甜头。
4. **鼓励贡献**：谁有好用的个人技能，整理一下提进共享目录。
5. **定期清理**：淘汰没人用的、合并重复的，保持技能集精简。

# 三、常见错误

- **❌ 全用个人级，团队各搞各的**：同一个技能十个人写十遍，标准不统一。该共享的放项目级。
- **❌ 技能进了仓库却没文档**：新人看不懂、不敢改，慢慢变成没人维护的黑盒。
- **❌ 从不迭代**：业务变了技能没跟上，触发不准还在用，越用越糟。
- **❌ 改技能不走 review**：团队共享的技能被人随手改坏，影响所有人。
- **❌ 技能越堆越多不清理**：重复、过时的技能互相干扰，触发开始混乱。

# 四、最佳实践

- **按作用域选位置**：个人工具放个人级，团队标准放项目级（进 Git 仓库）。
- **技能自带文档**：description 清晰 + 正文首句说职责 + 必要时附 README。
- **改动走 PR**：团队共享技能和代码一样 review，防止被改坏。
- **从高频痛点起步推行**，让团队先尝到甜头再铺开。
- **定期回顾**：合并重复、拆分过大、淘汰过时。

# 五、总结

- 技能有三种作用域：**个人级（跟你走）、项目级（随仓库走、最适合团队）、打包分发**。
- 团队共享的最佳方式是**把技能提进项目 Git 仓库**：人人同步、版本可控、就地维护。
- 技能要**自带文档**、**持续迭代**、**改动走 review**，当成「活的文档」来养。
- 推行落地：共享目录 + 简单规范 + 从高频痛点起步 + 鼓励贡献 + 定期清理。
