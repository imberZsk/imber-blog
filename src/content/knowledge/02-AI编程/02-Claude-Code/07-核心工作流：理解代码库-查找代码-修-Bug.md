# 二、快速理解一个代码库

接手陌生项目，别自己一头扎进去翻文件。
让 Claude Code 先给你「导游」。

**技巧：从宽到窄，逐层下钻。**

```text
# 第一层：要个全局概览
给我这个仓库的概览

# 第二层：问架构和关键设计
这里用的主要架构模式是什么？
关键的数据模型有哪些？
认证是怎么处理的？

# 第三层：要术语表（项目黑话）
给我一份这个项目特定术语的词汇表
```

> 💡 提示：用项目里的语言提问（它叫「工单」你就别说「ticket」），它定位得更准。

# 三、查找相关代码

知道「想找啥」但不知道「在哪」，正是它的强项。

```text
# 1. 先找到文件
找到处理用户认证的文件

# 2. 再问它们怎么协作
这些认证文件是如何协同工作的？

# 3. 追踪一条完整链路
追踪从前端到数据库的登录流程
```

第 3 步特别有用——**让它把一条业务链路从头到尾串给你**，比你自己跳着读快得多。

> 关键习惯：**明确说要找什么 + 用项目里的词**。「找登录相关代码」比「找 auth 那块」更不容易跑偏。

# 四、修复 Bug（最核心的闭环）

修 Bug 是验证「读—改—跑—验证」循环的最佳场景。
给它的信息越足，它修得越准。

**关键：把「怎么复现」和「怎么算修好」都告诉它。**

```text
# 1. 给它报错和复现方式
我运行 `npm test` 时看到一个错误，堆栈如下：[贴报错]。
这个错误是稳定复现的。

# 2. 让它先诊断（可结合 Plan Mode）
先别改，告诉我这个 bug 的根因在哪、你打算怎么修。

# 3. 安全地修，并保持行为
修复它，注意不要改动 sum 之外的函数行为。

# 4. 让它自己验证
修完重新跑 `npm test`，全绿才算完成。
```

第 4 步是灵魂——**带上验证方式**，它改完会自己跑测试确认，没过会自己再改，形成闭环。

> 💡 间歇性 bug 要特别说明：「这个错误是偶发的，不是每次都出现」。它会据此采取不同的排查策略（比如找竞态、找未初始化状态）。

# 五、三件套串起来：一个完整例子

> 场景：新接手项目，下单偶尔丢优惠券。

```text
1.（理解）给我这个仓库的概览，重点说说下单流程怎么走。
2.（查找）追踪从「点击下单」到「优惠券核销」的完整代码路径。
3.（定位）优惠券偶尔没被核销。先别改，分析可能的根因。
4.（修复）按你说的根因修复，改完跑 `npm test`，并补一个能覆盖这个场景的测试。
```

这就是一次真实的工作闭环：**理解全局 → 锁定链路 → 诊断根因 → 修复并验证。

# 六、常见错误

**错误 1：直接「修一下这个 bug」，啥背景都不给**
它只能猜复现方式。→ 给报错、给复现步骤、说清是稳定还是偶发。

**错误 2：不给验证方式，它「改了就交」**
没有「跑什么算修好」，它无法自我确认。→ 永远附上验证命令。

**错误 3：让它「读完整个仓库」**
大项目这样既慢又抓不住重点。→ 从概览开始，按需下钻到具体模块。

**错误 4：复杂 bug 不先诊断就让它改**
容易头痛医头。
→ 先让它（最好在 Plan Mode 下）分析根因，认可了再动手。

# 七、最佳实践

1. **理解从宽到窄**：概览 → 架构 → 具体模块，别一上来钻细节。
2. **查找用项目术语**：说它的「黑话」，定位更准。
3. **修 Bug 给全三件套**：复现方式 + 根因诊断 + 验证命令。
4. **先诊断后动手**：复杂 bug 先让它讲根因，再修。
5. **修完必验证**：让它自己跑测试，并尽量补一个覆盖该场景的测试。

“核心工作流：理解代码库 / 查找代码 / 修 Bug”边界实验结束后，应把正常、临界、失败和恢复四类记录放在同一个运行批次中。这样才能区分“候选方案真的修复问题”和“环境变化让问题暂时没有出现”。

# 十一、核心工作流：理解代码库 / 查找代码 / 修 Bug 的结果解释

解释“核心工作流：理解代码库 / 查找代码 / 修 Bug”实验时先看首个偏差，而不是最后一条错误。最后的异常通常只是上游状态错误的结果；从末端反推容易误把症状当根因。

| 观察结果 | 可以支持的判断 | 下一步 |
| --- | --- | --- |
| 主链路没有达到预期 | 文本直通执行、状态不可重放或重试重复写入 | 先执行：关闭副作用入口，恢复检查点，补充失败契约测试 |
| 异常链路无法恢复 | 文本直通执行、状态不可重放或重试重复写入 | 先执行：关闭副作用入口，恢复检查点，补充失败契约测试 |
| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

“核心工作流：理解代码库 / 查找代码 / 修 Bug”只有同时满足“模型只提议；执行受代码约束；失败不重复副作用”，并且没有出现“文本直通执行、状态不可重放或重试重复写入”，才可以认为主链路通过。这里的“通过”只对当前固定版本、样本和环境有效，不能外推到尚未测试的容量、权限或数据分布。

如果“核心工作流：理解代码库 / 查找代码 / 修 Bug”候选方案与基线差异很小，先检查证据分辨率是否足够；如果差异很大，先排除数据泄漏、环境漂移和版本不一致。两种情况都不能只看一个汇总均值，需要回到逐样本输出和中间状态。

“核心工作流：理解代码库 / 查找代码 / 修 Bug”故障定位完成后，记录“现象、首个偏差、根因、改动、原样本复测”五项。缺少原样本复测时，只能标记为待观察，不能标记为已解决。

# 十二、核心工作流：理解代码库 / 查找代码 / 修 Bug 的发布判断

发布判断需要把“核心工作流：理解代码库 / 查找代码 / 修 Bug”的质量、失败边界和恢复能力放在同一份记录中。以下任一条件缺失，都应停止扩量，而不是用“基本正常”替代证据。

- [ ] “核心工作流：理解代码库 / 查找代码 / 修 Bug”的基线与候选只存在一个计划内变量。
- [ ] “核心工作流：理解代码库 / 查找代码 / 修 Bug”的输入、代码、依赖、配置和数据版本可以追溯。
- [ ] “核心工作流：理解代码库 / 查找代码 / 修 Bug”的正常、临界、失败和恢复样本使用同一套断言。
- [ ] “核心工作流：理解代码库 / 查找代码 / 修 Bug”的原始输出、中间状态和失败现场已经保留。
- [ ] “核心工作流：理解代码库 / 查找代码 / 修 Bug”的日志、Trace、截图和测试数据已经脱敏。
- [ ] “核心工作流：理解代码库 / 查找代码 / 修 Bug”的停止条件、负责人和回滚入口已经演练。
- [ ] “核心工作流：理解代码库 / 查找代码 / 修 Bug”尚未覆盖的输入、权限、容量和外部依赖已经登记。

最终记录至少包含基线版本、唯一变量、原始证据、首个偏差、恢复复测和发布责任人。没有参与本次修改的人如果不能据此重放“核心工作流：理解代码库 / 查找代码 / 修 Bug”的判断，就不能发布。

# 十三、总结

- **快速理解一个代码库**：接手陌生项目，别自己一头扎进去翻文件。
- **查找相关代码**：知道「想找啥」但不知道「在哪」，正是它的强项。
- **修复 Bug（最核心的闭环）**：修 Bug 是验证「读—改—跑—验证」循环的最佳场景。
- **三件套串起来：一个完整例子**：这就是一次真实的工作闭环：理解全局 → 锁定链路 → 诊断根因 → 修复并验证。
- **常见错误**：→ 给报错、给复现步骤、说清是稳定还是偶发。
- **最佳实践**：理解从宽到窄：概览 → 架构 → 具体模块，别一上来钻细节。 -> 查找用项目术语：说它的「黑话」，定位更准。 -> 修 Bug 给全三件套：复现方式 + 根因诊断 + 验证命令。 -> 先诊断后动手：复杂 bug 先让它讲根因，再修。
