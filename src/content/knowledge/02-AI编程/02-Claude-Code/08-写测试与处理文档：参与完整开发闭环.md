# 二、为什么是这一章

如果只用它「生成代码」，价值大打折扣。
真实开发里，一段代码能不能被接受，取决于它**有没有通过测试、符不符合规范、经没经过审查**。
让它参与**完整开发闭环**，才是正确用法：

```text
实现修改 → 编写/更新测试 → 跑测试 → 跑 lint/类型检查 → 审查 diff
```

它从「代码生成器」变成「开发循环里的执行节点」。
本章讲其中两环：**测试**和**文档**。

# 三、写测试：四步法

**第 1 步：找出没被测到的代码**
```text
在 @notification.js 中查找未被测试覆盖的函数
```

**第 2 步：生成测试骨架**
```text
为通知服务添加测试用例
```

**第 3 步：补边界情况（最有价值的一步）**
```text
为通知服务补充边界条件的测试：空收件人、超长内容、发送失败重试
```
> 💡 普通用例它生成得又快又好，**真正的价值在边界情况**——明确点名让它覆盖异常路径。

**第 4 步：跑测试并修失败**
```text
运行新写的测试，修复任何失败项
```

这一步闭环：它跑测试 → 没过 → 自己改 → 再跑，直到全绿。

# 六、常见错误

**错误 1：只让它写「正常路径」测试**
正常用例价值有限，**点名让它覆盖边界和异常**才值。

**错误 2：生成测试不跑**
没跑过的测试可能本身就是错的。→ 永远让它「跑新测试并修失败」。

**错误 3：文档不指定风格**
不说 JSDoc 还是 docstring，风格会乱。
→ 明确风格 + 要示例。

**错误 4：把文档当一次性任务**
代码改了文档没改 = 误导。
→ 把「改代码同步改文档」写进 `CLAUDE.md`。

---

# 七、最佳实践

1. **测试重点压在边界**：异常、空值、并发、失败重试，明确点名。
2. **测试必跑必验证**：让它「跑新测试并修复失败」。
3. **文档指定风格 + 带示例**：JSDoc/docstring 选一种，要求给用法示例。
4. **闭环写进 CLAUDE.md**：让补测试、补文档成为它的默认动作。

| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

“写测试与处理文档：参与完整开发闭环”只有同时满足“结果符合结论条件，异常输入可解释、可恢复”，并且没有出现“条件缺失、结果不可复现或失败后责任不清”，才可以认为主链路通过。这里的“通过”只对当前固定版本、样本和环境有效，不能外推到尚未测试的容量、权限或数据分布。

如果“写测试与处理文档：参与完整开发闭环”候选方案与基线差异很小，先检查证据分辨率是否足够；如果差异很大，先排除数据泄漏、环境漂移和版本不一致。两种情况都不能只看一个汇总均值，需要回到逐样本输出和中间状态。

“写测试与处理文档：参与完整开发闭环”故障定位完成后，记录“现象、首个偏差、根因、改动、原样本复测”五项。缺少原样本复测时，只能标记为待观察，不能标记为已解决。

# 十二、写测试与处理文档：参与完整开发闭环 的发布判断

发布判断需要把“写测试与处理文档：参与完整开发闭环”的质量、失败边界和恢复能力放在同一份记录中。以下任一条件缺失，都应停止扩量，而不是用“基本正常”替代证据。

- [ ] “写测试与处理文档：参与完整开发闭环”的基线与候选只存在一个计划内变量。
- [ ] “写测试与处理文档：参与完整开发闭环”的输入、代码、依赖、配置和数据版本可以追溯。
- [ ] “写测试与处理文档：参与完整开发闭环”的正常、临界、失败和恢复样本使用同一套断言。
- [ ] “写测试与处理文档：参与完整开发闭环”的原始输出、中间状态和失败现场已经保留。
- [ ] “写测试与处理文档：参与完整开发闭环”的日志、Trace、截图和测试数据已经脱敏。
- [ ] “写测试与处理文档：参与完整开发闭环”的停止条件、负责人和回滚入口已经演练。
- [ ] “写测试与处理文档：参与完整开发闭环”尚未覆盖的输入、权限、容量和外部依赖已经登记。

最终记录至少包含基线版本、唯一变量、原始证据、首个偏差、恢复复测和发布责任人。没有参与本次修改的人如果不能据此重放“写测试与处理文档：参与完整开发闭环”的判断，就不能发布。

# 十三、总结

- **为什么是这一章**：真实开发里，一段代码能不能被接受，取决于它有没有通过测试、符不符合规范、经没经过审查。
- **写测试：四步法**：第 3 步：补边界情况（最有价值的一步）
- **处理文档：四步法**：第 2 步：生成文档（指定风格）
- **串进日常：让它成为习惯**：把「实现完顺手补测试和文档」写进 CLAUDE.md（第 05 章），它每次改完业务逻辑就会主动补：
- **常见错误**：正常用例价值有限，点名让它覆盖边界和异常才值。
- **最佳实践**：测试重点压在边界：异常、空值、并发、失败重试，明确点名。 -> 测试必跑必验证：让它「跑新测试并修复失败」。 -> 文档指定风格 + 带示例：JSDoc/docstring 选一种，要求给用法示例。 -> 闭环写进 CLAUDE.md：让补测试、补文档成为它的默认动作。
