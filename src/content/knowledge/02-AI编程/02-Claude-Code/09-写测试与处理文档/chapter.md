# Claude Code（8）- 写测试与处理文档：参与完整开发闭环

> 本章目标：让 Claude Code 补测试、跑测试、生成与校对文档。
> 学完你能：为代码补齐测试与文档，每次改动都「实现—验证—审查」一气呵成。

---

# 一、为什么是这一章

如果只用它「生成代码」，价值大打折扣。真实开发里，一段代码能不能被接受，取决于它**有没有通过测试、符不符合规范、经没经过审查**。让它参与**完整开发闭环**，才是正确用法：

```
实现修改 → 编写/更新测试 → 跑测试 → 跑 lint/类型检查 → 审查 diff
```

它从「代码生成器」变成「开发循环里的执行节点」。本章讲其中两环：**测试**和**文档**。

---

# 二、写测试：四步法

**第 1 步：找出没被测到的代码**
```
在 @notification.js 中查找未被测试覆盖的函数
```

**第 2 步：生成测试骨架**
```
为通知服务添加测试用例
```

**第 3 步：补边界情况（最有价值的一步）**
```
为通知服务补充边界条件的测试：空收件人、超长内容、发送失败重试
```
> 💡 普通用例它生成得又快又好，**真正的价值在边界情况**——明确点名让它覆盖异常路径。

**第 4 步：跑测试并修失败**
```
运行新写的测试，修复任何失败项
```

这一步闭环：它跑测试 → 没过 → 自己改 → 再跑，直到全绿。

---

# 三、处理文档：四步法

**第 1 步：找出没文档的代码**
```
在 @auth 模块里找出没有 JSDoc 注释的函数
```

**第 2 步：生成文档（指定风格）**
```
给 @auth.js 里没注释的函数补上 JSDoc，包含参数说明和一个使用示例
```
> 关键：**指定风格**（JSDoc / docstring / TSDoc…）并**要求带示例**，产出才好用。

**第 3 步：审查增强**
```
给这些文档补充更多上下文和边界说明
```

**第 4 步：对照规范校验**
```
检查这些文档是否符合我们项目的注释规范（见 CLAUDE.md）
```

---

# 四、串进日常：让它成为习惯

把「实现完顺手补测试和文档」写进 `CLAUDE.md`（第 05 章），它每次改完业务逻辑就会主动补：

```markdown
# 开发闭环要求
- 改动业务逻辑后必须补/更新对应测试，并运行 `pnpm test`
- 新增公共函数必须带 JSDoc，包含参数说明和使用示例
```

---

# 五、常见错误

**错误 1：只让它写「正常路径」测试**
正常用例价值有限，**点名让它覆盖边界和异常**才值。

**错误 2：生成测试不跑**
没跑过的测试可能本身就是错的。→ 永远让它「跑新测试并修失败」。

**错误 3：文档不指定风格**
不说 JSDoc 还是 docstring，风格会乱。→ 明确风格 + 要示例。

**错误 4：把文档当一次性任务**
代码改了文档没改 = 误导。→ 把「改代码同步改文档」写进 `CLAUDE.md`。

---

# 六、最佳实践

1. **测试重点压在边界**：异常、空值、并发、失败重试，明确点名。
2. **测试必跑必验证**：让它「跑新测试并修复失败」。
3. **文档指定风格 + 带示例**：JSDoc/docstring 选一种，要求给用法示例。
4. **闭环写进 CLAUDE.md**：让补测试、补文档成为它的默认动作。

---

# 七、总结

- 别只让它生成代码，让它参与**实现→测试→跑→lint→审查**完整闭环。
- 测试四步：找空白 → 生成 → **补边界** → 跑并修。
- 文档四步：找空白 → **按指定风格生成+示例** → 增强 → 对照规范校验。
- 把闭环要求写进 `CLAUDE.md`，让它成为习惯。
