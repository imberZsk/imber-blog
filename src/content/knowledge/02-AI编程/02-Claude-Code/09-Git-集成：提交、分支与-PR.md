# 二、它能帮你做的 Git 活

日常 Git 操作大多可以用一句话交给它：

```text
# 总结改动并提交
把我这次的改动总结一下，写一条规范的 commit message 并提交

# 开分支干活
基于 main 开一个 feature/user-pagination 分支

# 建 PR
把当前分支推上去，创建一个 PR，标题简洁、描述里说明改了什么、怎么测的
```

它会先看 `git diff` / `git status` 搞清你改了啥，
再生成贴切的提交信息或 PR 描述——**不是套模板，
而是基于真实改动**。

---

# 三、写好 commit 和 PR 的小技巧

**提交信息**：让它基于实际 diff 总结，比你手写「fix bug」之类的强。
可以要求遵循团队规范：
```text
按 Conventional Commits 规范写这条 commit message
```

**PR 描述**：好的 PR 描述包含三块——**改了什么、怎么测的、有什么注意事项**。
可以让它先生成再增强：
```text
创建 PR
# 看完它的初稿后
在 PR 描述里补充这次安全相关改动的背景说明
```

> 💡 PR 标题保持简洁（70 字以内），细节放描述里。

# 四、重点：它的安全边界（不会擅自干的事）

这是本章最该记牢的。
Claude Code 在 Git 上**默认偏保守**，因为有些操作不可逆、影响协作：

- **不会直接推到 main/master**：默认推到新分支，除非你明确要求。
- **破坏性操作默认不做**：`push --force`、`reset --hard`、`clean -f`、`branch -D` 这类会丢东西的，需要你**明确授权**。
- **提交要你发话**：它不会动不动就自作主张提交，通常等你说「提交吧」。
- **会提醒敏感文件**：发现 `.env`、密钥文件之类，提交前会提示你。
- **不乱改 git 配置**：你的 `git config` 它不碰。

> 🔑 一句话：**它把「可能丢代码 / 影响别人」的操作的决定权留给你。** 这是保护，不是缺陷。

# 五、典型工作流：从改完到 PR

```text
1. 我改完了用户分页功能，帮我看一下 git diff，确认没有遗漏。
2. 基于 main 开个分支 feature/user-pagination。
3. 把改动提交，commit message 按 Conventional Commits 写。
4. 推到远程并创建 PR，描述里写清功能点和测试方式。
```

一条龙下来，你只需审查它的 diff 和 PR 描述。

# 六、常见错误

**错误 1：让它「提交所有改动」却没先看 diff**
可能把不相关的改动、调试代码一起提交了。
→ 先 `git diff` 审查，或让它分文件提交。

**错误 2：指望它 `--force` push 救场**
破坏性操作它默认不做，且你也不该随手用。真要用，想清楚后果再明确授权。

**错误 3：把密钥提交上去**
它会提醒，但最终是你点的确认。
→ 留意它的敏感文件提示，配好 `.gitignore`。

**错误 4：在 main 上直接干**
养成开分支的习惯，让它「基于 main 开新分支」，别在主干上乱来。

---

# 七、最佳实践

1. **提交前看 diff**：让它总结改动，你扫一眼再放行。
2. **遵循团队提交规范**：明确告诉它用 Conventional Commits 之类。
3. **善用它的保守默认**：它不擅自推 main、不做破坏性操作，顺着这个安全习惯走。
4. **PR 描述三件套**：改了什么 / 怎么测 / 注意事项。
5. **敏感文件配好忽略**：别依赖事后提醒，`.gitignore` 先行。

| 主链路没有达到预期 | 条件缺失、结果不可复现或失败后责任不清 | 先执行：保留基线，缩小变量；根因确认前不扩大范围 |
| 异常链路无法恢复 | 条件缺失、结果不可复现或失败后责任不清 | 先执行：保留基线，缩小变量；根因确认前不扩大范围 |
| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

“Git 集成：提交、分支与 PR”只有同时满足“结果符合结论条件，异常输入可解释、可恢复”，并且没有出现“条件缺失、结果不可复现或失败后责任不清”，才可以认为主链路通过。这里的“通过”只对当前固定版本、样本和环境有效，不能外推到尚未测试的容量、权限或数据分布。

如果“Git 集成：提交、分支与 PR”候选方案与基线差异很小，先检查证据分辨率是否足够；如果差异很大，先排除数据泄漏、环境漂移和版本不一致。两种情况都不能只看一个汇总均值，需要回到逐样本输出和中间状态。

“Git 集成：提交、分支与 PR”故障定位完成后，记录“现象、首个偏差、根因、改动、原样本复测”五项。缺少原样本复测时，只能标记为待观察，不能标记为已解决。

# 十二、Git 集成：提交、分支与 PR 的发布判断

发布判断需要把“Git 集成：提交、分支与 PR”的质量、失败边界和恢复能力放在同一份记录中。以下任一条件缺失，都应停止扩量，而不是用“基本正常”替代证据。

- [ ] “Git 集成：提交、分支与 PR”的基线与候选只存在一个计划内变量。
- [ ] “Git 集成：提交、分支与 PR”的输入、代码、依赖、配置和数据版本可以追溯。
- [ ] “Git 集成：提交、分支与 PR”的正常、临界、失败和恢复样本使用同一套断言。
- [ ] “Git 集成：提交、分支与 PR”的原始输出、中间状态和失败现场已经保留。
- [ ] “Git 集成：提交、分支与 PR”的日志、Trace、截图和测试数据已经脱敏。
- [ ] “Git 集成：提交、分支与 PR”的停止条件、负责人和回滚入口已经演练。
- [ ] “Git 集成：提交、分支与 PR”尚未覆盖的输入、权限、容量和外部依赖已经登记。

最终记录至少包含基线版本、唯一变量、原始证据、首个偏差、恢复复测和发布责任人。没有参与本次修改的人如果不能据此重放“Git 集成：提交、分支与 PR”的判断，就不能发布。

# 十三、总结

- **它能帮你做的 Git 活**：它会先看 git diff / git status 搞清你改了啥，再生成贴切的提交信息或 PR 描述——不是套模板，而是基于真实改动。
- **写好 commit 和 PR 的小技巧**：PR 描述：好的 PR 描述包含三块——改了什么、怎么测的、有什么注意事项。
- **重点：它的安全边界（不会擅自干的事）**：Claude Code 在 Git 上默认偏保守，因为有些操作不可逆、影响协作：
- **典型工作流：从改完到 PR**：一条龙下来，你只需审查它的 diff 和 PR 描述。
- **常见错误**：错误 2：指望它 --force push 救场
- **最佳实践**：提交前看 diff：让它总结改动，你扫一眼再放行。 -> 遵循团队提交规范：明确告诉它用 Conventional Commits 之类。 -> 善用它的保守默认：它不擅自推 main、不做破坏性操作，顺着这个安全习惯走。 -> PR 描述三件套：改了什么 / 怎么测 / 注意事项。
