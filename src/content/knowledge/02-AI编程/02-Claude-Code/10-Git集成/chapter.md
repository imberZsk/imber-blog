# Claude Code（9）- Git 集成：提交、分支与 PR

> 本章目标：让 Claude Code 帮你写提交信息、管分支、建 PR，并理解它的安全边界。
> 学完你能：用自然语言完成日常 Git 操作，知道哪些破坏性操作它不会擅自做。

---

# 一、它能帮你做的 Git 活

日常 Git 操作大多可以用一句话交给它：

```
# 总结改动并提交
把我这次的改动总结一下，写一条规范的 commit message 并提交

# 开分支干活
基于 main 开一个 feature/user-pagination 分支

# 建 PR
把当前分支推上去，创建一个 PR，标题简洁、描述里说明改了什么、怎么测的
```

它会先看 `git diff` / `git status` 搞清你改了啥，再生成贴切的提交信息或 PR 描述——**不是套模板，而是基于真实改动**。

---

# 二、写好 commit 和 PR 的小技巧

**提交信息**：让它基于实际 diff 总结，比你手写「fix bug」之类的强。可以要求遵循团队规范：
```
按 Conventional Commits 规范写这条 commit message
```

**PR 描述**：好的 PR 描述包含三块——**改了什么、怎么测的、有什么注意事项**。可以让它先生成再增强：
```
创建 PR
# 看完它的初稿后
在 PR 描述里补充这次安全相关改动的背景说明
```

> 💡 PR 标题保持简洁（70 字以内），细节放描述里。

---

# 三、重点：它的安全边界（不会擅自干的事）

这是本章最该记牢的。Claude Code 在 Git 上**默认偏保守**，因为有些操作不可逆、影响协作：

- **不会直接推到 main/master**：默认推到新分支，除非你明确要求。
- **破坏性操作默认不做**：`push --force`、`reset --hard`、`clean -f`、`branch -D` 这类会丢东西的，需要你**明确授权**。
- **提交要你发话**：它不会动不动就自作主张提交，通常等你说「提交吧」。
- **会提醒敏感文件**：发现 `.env`、密钥文件之类，提交前会提示你。
- **不乱改 git 配置**：你的 `git config` 它不碰。

> 🔑 一句话：**它把「可能丢代码 / 影响别人」的操作的决定权留给你。** 这是保护，不是缺陷。

---

# 四、典型工作流：从改完到 PR

```
1. 我改完了用户分页功能，帮我看一下 git diff，确认没有遗漏。
2. 基于 main 开个分支 feature/user-pagination。
3. 把改动提交，commit message 按 Conventional Commits 写。
4. 推到远程并创建 PR，描述里写清功能点和测试方式。
```

一条龙下来，你只需审查它的 diff 和 PR 描述。

---

# 五、常见错误

**错误 1：让它「提交所有改动」却没先看 diff**
可能把不相关的改动、调试代码一起提交了。→ 先 `git diff` 审查，或让它分文件提交。

**错误 2：指望它 `--force` push 救场**
破坏性操作它默认不做，且你也不该随手用。真要用，想清楚后果再明确授权。

**错误 3：把密钥提交上去**
它会提醒，但最终是你点的确认。→ 留意它的敏感文件提示，配好 `.gitignore`。

**错误 4：在 main 上直接干**
养成开分支的习惯，让它「基于 main 开新分支」，别在主干上乱来。

---

# 六、最佳实践

1. **提交前看 diff**：让它总结改动，你扫一眼再放行。
2. **遵循团队提交规范**：明确告诉它用 Conventional Commits 之类。
3. **善用它的保守默认**：它不擅自推 main、不做破坏性操作，顺着这个安全习惯走。
4. **PR 描述三件套**：改了什么 / 怎么测 / 注意事项。
5. **敏感文件配好忽略**：别依赖事后提醒，`.gitignore` 先行。

---

# 七、总结

- 提交信息、分支、PR 都能用一句话交给它，且**基于真实 diff** 生成。
- 它的**安全边界**：不擅自推 main、破坏性操作要授权、提交要你发话、提醒敏感文件。
- 这些限制是保护你和团队，顺着用最稳。
