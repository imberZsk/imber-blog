# 二、CPU、内存、I/O 与负载的关系

CPU 饱和看运行队列与 user/system/steal，
内存压力看 available、swap 和回收，
而不是只看 free。
load average 包含可运行和不可中断睡眠任务，磁盘或网络文件系统阻塞也会抬高负载；
必须结合 vmstat、iostat 和进程级指标判断。

# 三、从系统趋势下钻到进程

先确认异常开始时间和版本，
再看整体资源分位趋势，
随后用 pidstat、top、lsof 或 perf 下钻到进程、线程和系统调用。
日志要用 request_id、PID、错误类型和持续时间关联，
不把密码、Token 或无限基数正文写入集中日志。

# 四、基线、容量与修复验证

性能结论必须和正常基线、请求量及业务成功率一起比较。
修复后重复相同负载，观察吞吐、P95/P99、队列、错误率和资源；
只看到 CPU 降低可能是请求被拒绝或功能降级，不能单独证明优化成功。

# 五、十分钟性能快照

这些命令分别观察运行队列、内存、块设备和进程。

```bash
uptime
vmstat 1 10
iostat -xz 1 10
pidstat -dur -p ALL 1 10
free -h
df -hT
journalctl -p warning --since '10 min ago'
```

不要只截最后一行；
连续样本才能看出趋势。
iostat 的高 await 需结合设备利用率和队列判断，虚拟磁盘指标还要对照云平台。

# 九、日志、资源与性能排查 的结果解释

解释“日志、资源与性能排查”实验时先看首个偏差，而不是最后一条错误。最后的异常通常只是上游状态错误的结果；从末端反推容易误把症状当根因。

| 观察结果 | 可以支持的判断 | 下一步 |
| --- | --- | --- |
| 主链路没有达到预期 | 环境漂移、探针失真、权限错误、发布扩大故障或回滚不可用 | 先执行：停止扩量，按制品、配置、运行时和依赖顺序定位并恢复 |
| 异常链路无法恢复 | 环境漂移、探针失真、权限错误、发布扩大故障或回滚不可用 | 先执行：停止扩量，按制品、配置、运行时和依赖顺序定位并恢复 |
| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

“日志、资源与性能排查”只有同时满足“成功路径达标，失败被及时阻断，恢复与回滚结果经过复测”，并且没有出现“环境漂移、探针失真、权限错误、发布扩大故障或回滚不可用”，才可以认为主链路通过。这里的“通过”只对当前固定版本、样本和环境有效，不能外推到尚未测试的容量、权限或数据分布。
