# Python（9）- 异常处理与上下文管理

> 读完你能：围绕“异常处理与上下文管理”理解“先给锚点：try/except/finally 和 JS 几乎一一对应”与“边界一：except 要声明类型，且可以接多种”，并结合正文示例完成实践与排障。

> 你在 JS 里写过 `try/catch/finally`，Python 的异常处理八成长得一样，迁移成本很低。但有几个"看着像、其实多了点东西"的地方：`catch` 要写成 `except` 还得声明类型、多了一个 JS 没有的 `else` 子句、`throw` 改叫 `raise`。另外本篇还要讲一个前端没有直接对应物的语法——`with`（上下文管理器），它专门解决"资源用完一定要关掉"这件事，比你手写 `finally` 优雅得多。

# 一、先给锚点：try/except/finally 和 JS 几乎一一对应

你在前端写过的 `try/catch/finally`，Python 里有等价物，结构基本平移：

```javascript
// JS / TS
try {
  const result = 10 / 0          // JS 里除零不报错，得 Infinity；这里只是占位
  JSON.parse("非法 json")         // 真正会抛错的地方
} catch (error) {                 // catch 不用声明类型，啥都接
  console.error(error)
} finally {
  console.log("无论成败都执行")
}
```

```python
# Python
try:
    result = 10 / 0              # Python 除零会直接抛 ZeroDivisionError
except ZeroDivisionError as e:   # except 要声明异常类型，as e 把异常对象绑到 e
    print(f"出错了: {e}")        # e 里存着这次异常的信息
finally:
    print("无论成败都执行")       # 清理逻辑，和 JS 的 finally 一模一样
```

先用对照表建立直觉：

| JS / TS | Python | 说明 |
|---------|--------|------|
| `try { }` | `try:` | 一致 |
| `catch (e) { }` | `except SomeError as e:` | Python 要声明异常类型 |
| `finally { }` | `finally:` | 一致 |
| `throw new Error(...)` | `raise SomeError(...)` | 关键字不同 |
| （无） | `else:` | Python 独有，见第三节 |
| `e instanceof TypeError` | `except TypeError` | 类型匹配 Python 直接写在 except 上 |

最大的体感差异：**JS 一个 `catch` 啥都接，Python 习惯按异常类型分开接**——这点更像你在 Java 里见过的 `catch (XxxException e)`。

---

# 二、边界一：except 要声明类型，且可以接多种

JS 里 `catch (e)` 是"一网打尽"，再在里面 `if (e instanceof XXX)` 分流。Python 把这个分流前置到了 `except` 上，可以写多个 `except` 分支，从上往下匹配，命中第一个就停：

```python
def parse_age(text):
    """把字符串转成年龄整数，演示多种异常分别处理。

    text: 用户输入的年龄字符串，比如 "18"
    """
    try:
        age = int(text)          # 转换失败会抛 ValueError
        return 100 // age        # 若 age 为 0 会抛 ZeroDivisionError
    except ValueError:           # 业务场景：用户输入的不是数字
        print("请输入数字")
    except ZeroDivisionError:    # 业务场景：年龄填了 0，除法没意义
        print("年龄不能为 0")
    except (TypeError, KeyError):  # 一个 except 用元组接多种异常
        print("类型或键错误")
```

```javascript
// JS 对比：只能在一个 catch 里手动 if 分流
function parseAge(text) {
  try {
    const age = Number(text)
    if (Number.isNaN(age)) throw new TypeError("不是数字")
    return Math.floor(100 / age)
  } catch (e) {
    if (e instanceof TypeError) console.log("请输入数字")
    else console.log("其他错误")
  }
}
```

> ⚠️ 顺序坑：`except` 从上往下匹配，**子类异常要写在父类前面**。如果把 `except Exception`（万能父类）写在最上面，下面所有具体的 `except` 都永远轮不到。这和 JS 里 `if/else if` 的顺序是一个道理。

# 三、边界二：多了一个 JS 没有的 else 子句

Python 的 `try` 可以跟一个 `else`，它在 **try 块没抛任何异常时才执行**。作用是把"正常后续逻辑"和"可能出错的逻辑"分开，让 try 块尽量只包住真正会抛错的那一两行：

```python
def read_config(path):
    """读取配置文件并解析，演示 else 的用法。

    path: 配置文件路径
    """
    try:
        f = open(path)          # 只有这行可能抛 FileNotFoundError
    except FileNotFoundError:
        print("配置文件不存在")
        return None
    else:
        # try 没出错才走这里：把"读内容"放这而非 try 里，
        # WHY: 避免误把 read 阶段的异常也被上面的 except 接住，职责更清晰
        content = f.read()      # content 存文件全部文本
        f.close()
        return content
```

记忆口诀：`try` 放"可能炸的"，`else` 放"没炸之后才做的"，`finally` 放"炸不炸都要做的"（通常是清理）。JS 没有 `else`，等价写法是在 try 末尾继续写，但那样不好区分"哪行可能抛异常"。

# 四、raise：抛异常（对应 JS 的 throw）

```python
# Python
raise ValueError("网点 id 不能为空")
```

```javascript
// JS
throw new Error("网点 id 不能为空")
```

几乎一样，只是关键字从 `throw` 变成 `raise`，且 Python 习惯用语义化的内置异常类型（`ValueError` / `TypeError` / `KeyError`…）而不是笼统的 `Error`。

## 4.1 异常链：raise ... from

捕获一个异常后想重新抛一个更贴业务的异常，用 `from` 保留原始原因，排查时能看到完整因果链：

```python
def load_user(uid):
    """根据 id 加载用户，把底层异常包装成业务异常。

    uid: 用户 id
    """
    try:
        return db.query(uid)     # 假设底层抛 ConnectionError
    except ConnectionError as e:
        # from e: 把原始异常挂上去，报错时会显示"The above exception was the direct cause of..."
        # （注：不写 from、直接在 except 里 raise 是隐式链接，那种才显示"During handling of the above exception..."）
        raise RuntimeError("加载用户失败") from e
```

# 五、自定义异常：继承内置异常即可

和 Java 的 `BusinessException extends RuntimeException` 思路一致，Python 自定义异常只要继承 `Exception`（或其子类）：

```python
class BusinessError(Exception):
    """业务异常：携带一个错误码，供上层统一处理。"""

    def __init__(self, message, code=1):
        # message: 错误描述文本；code: 业务错误码，默认 1
        super().__init__(message)   # 把消息交给父类存着
        self.code = code            # 额外存一个错误码字段

# 使用：和内置异常用法完全一样
def get_company(cid):
    """根据网点 id 查公司，参数非法时抛业务异常。

    cid: 网点 id
    """
    if cid is None:
        raise BusinessError("网点 id 不能为空", code=400)
    # 下面只写正常逻辑，干净——出错就 raise，由全局处理器接住
```

```javascript
// JS 对比：继承 Error，概念完全一样
class BusinessError extends Error {
  constructor(message, code = 1) {
    super(message)
    this.code = code
  }
}
```

> 和你在 Java 笔记里见过的套路相同：Service 层只管 `raise`，由一个统一的地方（比如 Web 框架的全局异常处理器）捕获 `BusinessError`，转成 `{ code, msg }` 返回前端。后续学 FastAPI 时会用到（详见后面的框架篇）。

## 5.1 常见内置异常对照

| Python 异常 | 何时出现 | JS 类比 |
|-------------|----------|---------|
| `ValueError` | 类型对但值不合法，如 `int("abc")` | `Number("abc")` → NaN |
| `TypeError` | 类型不对，如对 None 调方法 | `Cannot read property of undefined` |
| `KeyError` | 字典里取不存在的键 `d["x"]` | 访问对象不存在的属性返回 undefined |
| `IndexError` | 列表越界 `arr[99]` | JS 越界返回 undefined（不报错） |
| `FileNotFoundError` | 打开不存在的文件 | Node 的 `ENOENT` |

注意一个差异：JS 里访问越界数组或不存在的对象属性会**静默返回 undefined**，Python 会**直接抛 `IndexError` / `KeyError`**——这点对前端是个高频惊吓，养成判断或用 `dict.get(key, 默认值)` 的习惯。

# 六、with 语句：本篇的重点，前端没有直接对应物

很多操作"用完必须收尾"：文件用完要 `close`、数据库连接用完要释放、锁用完要解锁。如果手写，你得用 `finally` 保证收尾一定执行：

```python
# 手写 finally 版（能用但啰嗦）
f = open("data.txt")             # f 存打开的文件对象
try:
    content = f.read()           # content 存文件内容
finally:
    f.close()                    # 不管读没读成功，都要关掉文件
```

Python 提供了 `with` 语句，把"获取资源 + 保证释放"打包成一行，**离开 with 代码块时自动收尾，哪怕中途抛异常也照样收尾**：

```python
# with 版（推荐）：等价于上面那段 try/finally，但自动 close
with open("data.txt") as f:      # 进入时 open，f 绑定文件对象
    content = f.read()           # content 存文件内容
# 走到这里（缩进结束）文件已被自动关闭，无需手写 f.close()
```

类比前端帮你定位它的位置：

| 场景 | JS / 前端做法 | Python |
|------|---------------|--------|
| 用完自动清理 | `try { } finally { cleanup() }` | `with` 自动调用清理 |
| TS 5.2 新语法 | `using f = openFile()`（块结束自动 dispose） | `with` 思路完全一致 |
| React 副作用清理 | `useEffect` 里 return 一个 cleanup 函数 | 概念相近：声明"怎么收尾"，由运行时负责调 |

> 边界提醒：`with` 不是 try/catch 的替代品。它只负责"保证收尾"（相当于 finally），**不负责吞掉异常**。with 块里抛的异常该往上抛还是会往上抛，你想处理还得套 try/except。

可以同时管理多个资源，逗号分隔：

```python
# 同时打开两个文件：读 in.txt，写 out.txt，块结束时两个都自动关闭
with open("in.txt") as fin, open("out.txt", "w") as fout:
    fout.write(fin.read())       # 把输入文件内容写到输出文件
```

# 七、自定义上下文管理器：with 背后的机制

`with` 能作用于一个对象，是因为该对象实现了两个魔术方法：`__enter__`（进入时调，返回值给 `as` 后面的变量）和 `__exit__`（离开时调，负责收尾）。

```python
class Timer:
    """一个计时器上下文管理器：测量 with 块的执行耗时。"""

    def __enter__(self):
        # 进入 with 块时自动调用：记录起始时间，返回值会赋给 as 后面的变量
        import time
        self.start = time.time()    # start 存进入时的时间戳
        return self                 # 返回值会赋给 with ... as 后面的变量

    def __exit__(self, exc_type, exc_val, exc_tb):
        # 离开 with 块时自动调用（正常或异常都会调）：计算并打印耗时
        # 三个参数：异常类型/异常值/堆栈；块内无异常时三者都是 None
        import time
        cost = time.time() - self.start   # cost 存这段代码耗时(秒)
        print(f"耗时 {cost:.3f} 秒")
        # WHY: 返回 False(或不返回) 表示"不吞异常"，让块内异常正常往上抛；
        #      返回 True 才会吞掉异常，一般不要这么干
        return False

with Timer():                       # 不需要 as，因为我们不用返回值
    sum(range(1_000_000))           # 被测量的代码
```

更省事的写法是用标准库 `contextlib`，把上面一坨简化成一个带 `yield` 的函数（`yield` 你在生成器那篇见过）：

```python
from contextlib import contextmanager

@contextmanager                     # 这个装饰器把生成器函数变成上下文管理器
def timer():
    """同样是计时器，但用 yield 写更简洁。"""
    import time
    start = time.time()             # start 存开始时间
    try:
        yield                       # yield 之前 = __enter__，之后 = __exit__
    finally:
        # 放 finally 里，保证块内抛异常也能打印耗时
        print(f"耗时 {time.time() - start:.3f} 秒")

with timer():
    sum(range(1_000_000))
```

记忆：`yield` 那一行就是"分界线"——上半段是进入时跑的，下半段（放进 `finally`）是离开时跑的。

# 八、易踩坑清单（前端新手高频）

```python
# ❌ 坑 1：裸 except 吞掉一切，包括 Ctrl+C 和 SystemExit，问题被掩盖
try:
    do_something()
except:                  # 不写类型 = 接住所有东西，极难排查
    pass

# ✅ 至少接 Exception（它不含 KeyboardInterrupt/SystemExit）
try:
    do_something()
except Exception as e:   # 接住常规异常，且把对象绑到 e 方便打日志
    print(f"出错: {e}")
```

- **坑 2：`except` 顺序写反**。`except Exception` 写在具体异常前面，会让后面的分支永远命中不到（同第二节）。
- **坑 3：忘了用 `with`**，文件/连接没关，量大时会耗尽文件句柄。能用 `with` 就别手写 `open` + `close`。
- **坑 4：在 `finally` 里 `return`**。`finally` 的 return 会**覆盖**前面的返回值、甚至吞掉正在往上抛的异常，制造诡异 bug，别在 finally 里 return。
- **坑 5：拿索引/键当 JS 用**。`arr[99]`、`d["不存在的键"]` 在 Python 会抛异常而非返回 undefined，记得用 `dict.get(k, 默认值)` 或先判断。

# 九、总结

Python 的异常处理可以直接套你的 JS `try/catch/finally` 心智模型，重点补两块：按类型分 `except` + 多出来的 `else`，以及前端没有的 `with`。

✅ 该掌握
- `try / except 类型 as e / else / finally` 四件套，`raise` 抛异常
- 自定义异常继承 `Exception`，Service 只管 raise、交全局统一处理
- `with open(...) as f:` 自动收尾，是管理文件等资源的标准姿势
- 自定义上下文管理器：类写 `__enter__`/`__exit__`，或用 `@contextmanager` + `yield`

⚠️ 易混淆
- `except` 要声明类型且**子类在前父类在后**，别让 `except Exception` 挡住后面分支
- `else` 是 Python 独有，放"没出错才执行"的逻辑
- `with` 只保证收尾（≈ finally），**不吞异常**，要处理异常仍需 try/except
- 别用裸 `except:`，至少 `except Exception`；别在 `finally` 里 `return`
- 索引/键越界 Python 抛异常，不像 JS 返回 undefined
