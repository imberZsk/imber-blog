# Python（16）- 数据库操作

> 读完你能：围绕“数据库操作”理解“先给前端的「最小 SQL 集」”与“先给锚点：ORM ≈ Prisma / TypeORM”，并结合正文示例完成实践与排障。

> 接口收到数据后总得存进数据库。前端时代你大概率没手写过 SQL，而是用 Prisma / TypeORM 这类 ORM：定义一个 model，然后 `prisma.user.create(...)` 就完事。Python 后端最主流的 ORM 叫 **SQLAlchemy**，思路一模一样——**把数据表映射成 class，把每行数据映射成对象，增删改查全用 Python 代码表达，不手写 SQL**。本篇帮你把 Prisma 的直觉平移过来，同时讲清一个前端 ORM 里很弱、但 SQLAlchemy 里极其核心的概念：**Session（会话/工作单元）**。

# 一、先给前端的「最小 SQL 集」

ORM 是把 SQL 包了一层，但你至少得知道它在背后生成什么。下面四句覆盖 90% 日常操作，看懂即可，不用背：

```sql
-- 查：从 users 表取 name 等于 'Tom' 的行
SELECT * FROM users WHERE name = 'Tom';

-- 增：插入一行
INSERT INTO users (name, email) VALUES ('Tom', 't@x.com');

-- 改：把 id=1 的行的 name 改掉
UPDATE users SET name = 'Tom2' WHERE id = 1;

-- 删：删掉 id=1 的行
DELETE FROM users WHERE id = 1;
```

记住对应关系即可：**查=SELECT、增=INSERT、改=UPDATE、删=DELETE**。下面 SQLAlchemy 的每个操作，本质都是帮你生成上面这几句。

# 二、先给锚点：ORM ≈ Prisma / TypeORM

如果你用过 Prisma，下面这段几乎是逐行对应：

```typescript
// Prisma（前端熟悉的 ORM）
// schema 里定义 model
model User {
  id    Int    @id @default(autoincrement())
  name  String
  email String?
}

// 业务代码里直接用对象操作，不写 SQL
const user = await prisma.user.create({ data: { name: "Tom" } })
const found = await prisma.user.findMany({ where: { name: "Tom" } })
```

```python
# SQLAlchemy（Python 主流 ORM），2.0 现代写法
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

# Base：所有模型的基类，相当于 Prisma 里 schema 的命名空间
class Base(DeclarativeBase):
    pass

# User 类映射到数据库的 users 表，一个类 = 一张表
class User(Base):
    __tablename__ = "users"                              # 表名
    id: Mapped[int] = mapped_column(primary_key=True)    # 主键，自增
    name: Mapped[str] = mapped_column()                  # 必填字符串列
    email: Mapped[str | None] = mapped_column()          # 可空列(对应 String?)
```

对照表先建立直觉：

| Prisma / TypeORM | SQLAlchemy | 说明 |
|---|---|---|
| `model User {}` | `class User(Base)` | 一个模型 = 一张表 |
| `@id` | `primary_key=True` | 主键 |
| `String?`（可空） | `Mapped[str \| None]` | 可空列 |
| `prisma.user.create` | `session.add(User(...))` | 新增 |
| `findMany / findUnique` | `select(User)` / `session.get` | 查询 |
| 自动连接池 / client | `engine` + `Session` | 连接与会话 |

> **关键边界（最重要）**：Prisma 里你 `await prisma.user.create(...)` 一行就直接写库了。SQLAlchemy **不是**——你对对象的增删改，是先攒在一个叫 **Session** 的"暂存区"里，最后统一 `commit()` 才真正落库。这个 Session 概念是前端 ORM 里几乎没有、但 SQLAlchemy 里绕不开的核心，第三节专门讲。先记住：**SQLAlchemy = 模型映射(像 Prisma) + 显式的工作单元(Session)**。

# 三、三个地基对象：Engine、Model、Session

SQLAlchemy 有三个你必须分清的角色，用前端类比一句话各自定位：

| 对象 | 作用 | 前端类比 |
|---|---|---|
| **Engine** | 数据库连接的总入口，管连接池 | 像 `new Pool()` / 数据库连接配置 |
| **Model（模型类）** | 表 ↔ 类、行 ↔ 对象的映射定义 | Prisma 的 `model` 定义 |
| **Session** | 一次"对话"，暂存改动、最后提交 | 一个事务 / 一批待保存的草稿 |

## 3.1 Engine：连一次，全局复用

```python
from sqlalchemy import create_engine

# create_engine：创建数据库引擎(连接池)，通常整个应用只建一次
# 第一个参数是连接串：协议://用户:密码@主机/库名；这里用 sqlite 本地文件演示
# echo=True：把生成的 SQL 打印到控制台，学习期强烈建议开，能看清 ORM 背后干了啥
engine = create_engine("sqlite:///app.db", echo=True)

# 根据所有 Model 定义，在数据库里建好对应的表(已存在则跳过)
# 相当于 Prisma 的 migrate / db push，但这是最朴素的建表方式
Base.metadata.create_all(engine)
```

> 连接串换数据库只改前缀：SQLite 用 `sqlite:///文件名`；MySQL 用 `mysql+pymysql://user:pwd@host/dbname`；PostgreSQL 用 `postgresql+psycopg://...`。学习期用 SQLite（零部署、单文件），上生产再换 MySQL/PG，模型代码一行不用改——这正是 ORM 屏蔽数据库差异的价值。

## 3.2 Session：所有增删改查都在它上面进行

```python
from sqlalchemy.orm import Session

# 用 with 打开一个 Session(会话)，with 块结束自动关闭、释放连接
# with 是 Python 的资源管理语法(见第 9 篇)，类比 try-with-resources / using
with Session(engine) as session:
    # 在这个块里做增删改查……
    ...
```

记住这条主线：**Engine 建一次全局共享；Session 每个请求/每段业务开一个，用完就关**。在 FastAPI 里，Session 通常通过依赖注入按请求创建（见第 18 篇 `Depends`）。

# 四、核心心智模型：Session 是"工作单元"，commit 才落库

这是前端过来最该停下来理解的一节。Prisma 每个方法都是"说了就直接执行"，而 SQLAlchemy 的 Session 像 **Git 的暂存区**：

- `session.add(obj)` ≈ `git add`：把改动放进暂存区，**还没写库**
- `session.commit()` ≈ `git commit`：把这一批改动**一次性真正写入数据库**
- `session.rollback()` ≈ `git checkout .`：放弃这一批改动

```python
with Session(engine) as session:
    user = User(name="Tom", email="t@x.com")  # 只是个内存里的对象，库里还没有
    session.add(user)                          # 放进暂存区，仍未落库
    # 如果程序在这里崩了，库里不会有这行数据
    session.commit()                           # 此刻才真正 INSERT 进数据库
    print(user.id)                             # commit 后主键 id 才被数据库回填
```

> **为什么要这么设计（WHY）**：把"多次改动攒成一批一次提交"，天然就是**事务**——要么全成功，要么全回滚。比如"扣库存 + 创建订单"两步，放在一个 Session 里 commit，中途失败就整体回滚，不会出现扣了库存却没下单的脏数据。Prisma 要用 `prisma.$transaction([...])` 显式包起来，而 SQLAlchemy 的 Session **本身就是一个事务单元**，这是它更"重"但也更强的地方。

边界提醒：**别每次操作都 new 一个 Session，也别全局共享一个 Session**。正确姿势是"一段业务/一个请求一个 Session"。Session 不是线程安全的，全局共享会出并发问题。

# 五、增删改查（CRUD）完整对照

下面四个操作是日常 95% 的工作，每个都给出等价的 Prisma 写法并排看。

## 5.1 增（Create）

```python
# 新增一条用户记录
def create_user(session: Session, name: str, email: str) -> User:
    user = User(name=name, email=email)  # 构造对象，字段按模型注解传
    session.add(user)                    # 放入会话暂存区
    session.commit()                     # 提交，真正 INSERT
    session.refresh(user)                # 从库里刷新，拿到数据库生成的 id 等字段
    return user                          # 返回带 id 的完整对象
```

```typescript
// Prisma 对比：一行搞定，没有 add/commit 两步
const user = await prisma.user.create({ data: { name, email } })
```

## 5.2 查（Read）—— 2.0 的 select 写法

SQLAlchemy 2.0 统一用 `select()` 构造查询，再用 `session.scalars()` 执行：

```python
from sqlalchemy import select

# 按主键查单条：最快捷，等价 Prisma 的 findUnique
def get_user(session: Session, uid: int) -> User | None:
    return session.get(User, uid)        # 找不到返回 None

# 条件查询：构造 select 语句再执行
def find_by_name(session: Session, name: str) -> list[User]:
    # select(User)：要查 User 整行；.where(...)：加过滤条件(对应 SQL 的 WHERE)
    stmt = select(User).where(User.name == name)
    # scalars()：把结果取成 User 对象序列；.all() 转成列表
    return list(session.scalars(stmt).all())

# 取第一条(可能没有)
def find_first(session: Session, name: str) -> User | None:
    stmt = select(User).where(User.name == name)
    return session.scalars(stmt).first()  # 没有则返回 None
```

```typescript
// Prisma 对比
const user = await prisma.user.findUnique({ where: { id: uid } })
const list = await prisma.user.findMany({ where: { name } })
```

> 小坑：过滤条件写的是 `User.name == name`（用 `==`），**不是** Python 的关键字。SQLAlchemy 重载了 `==`，让 `User.name == name` 这个表达式生成 SQL 片段 `name = ?`，而不是返回布尔值。这点和 Prisma 用对象 `{ where: { name } }` 风格不同，初看会有点怪，习惯就好。

## 5.3 改（Update）

最直观的方式：**先查出对象，直接改属性，commit**。Session 会自动追踪哪些字段变了（这叫"脏检查"）：

```python
# 修改用户名：查出来 → 改属性 → 提交
def rename_user(session: Session, uid: int, new_name: str) -> User | None:
    user = session.get(User, uid)        # 先查出受 Session 跟踪的对象
    if user is None:                     # 业务场景：目标用户不存在，直接返回 None
        return None
    user.name = new_name                 # 直接改属性，Session 自动记下这个改动
    session.commit()                     # 提交，自动生成 UPDATE 语句
    return user
```

```typescript
// Prisma 对比
const user = await prisma.user.update({ where: { id: uid }, data: { name: newName } })
```

> 这就是 ORM 的"魔法"：你只是改了个 Python 对象的属性，commit 时 SQLAlchemy 对比对象的新旧值，发现 `name` 变了，自动生成 `UPDATE users SET name=? WHERE id=?`。前端 ORM 里没有这种"改对象=改库"的隐式追踪，这是 Session 跟踪对象带来的能力。

## 5.4 删（Delete）

```python
# 删除用户：查出来 → delete → 提交
def delete_user(session: Session, uid: int) -> bool:
    user = session.get(User, uid)        # 先按主键查出要删的对象
    if user is None:                     # 业务场景：要删的用户不存在
        return False
    session.delete(user)                 # 标记删除，放入暂存区
    session.commit()                     # 提交，真正 DELETE
    return True
```

```typescript
// Prisma 对比
await prisma.user.delete({ where: { id: uid } })
```

# 六、表关系：一对多（外键 + relationship）

真实业务里表是有关系的：一个用户有多篇文章。SQLAlchemy 用 `ForeignKey`（外键，数据库层面的关联）+ `relationship`（Python 层面的对象导航）两件套：

```python
from sqlalchemy import ForeignKey
from sqlalchemy.orm import relationship

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column()
    # relationship：让 user.posts 直接拿到该用户的所有文章对象(对象导航，不是数据库列)
    # back_populates 指向 Post 那边的属性名，双向关联保持同步
    posts: Mapped[list["Post"]] = relationship(back_populates="author")

class Post(Base):
    __tablename__ = "posts"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column()
    # ForeignKey：真实写进数据库的外键列，指向 users 表的 id
    author_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    # relationship：让 post.author 直接拿到作者对象
    author: Mapped["User"] = relationship(back_populates="posts")
```

```typescript
// Prisma 对比：relation 字段 + 外键标量字段，思路完全一致
model User { id Int @id; posts Post[] }
model Post { id Int @id; authorId Int; author User @relation(fields: [authorId], references: [id]) }
```

定义好后，访问关联数据就像访问普通属性：

```python
with Session(engine) as session:
    user = session.get(User, 1)
    for post in user.posts:          # 直接遍历这个用户的所有文章
        print(post.title)
    # 反向也行：从文章拿作者
    post = session.get(Post, 1)
    print(post.author.name)          # 拿到作者名
```

> **N+1 查询坑（前端用 ORM 也会踩）**：上面 `for post in user.posts` 默认是"用到才查"（懒加载）。如果你在循环里对一批 user 逐个访问 `.posts`，会变成 1 次查用户 + N 次查文章，共 N+1 条 SQL，量大时很慢。解决办法是查询时显式预加载：
> ```python
> from sqlalchemy.orm import selectinload
> # selectinload：一次性把关联的 posts 也批量查出来，避免逐个再查
> stmt = select(User).options(selectinload(User.posts))
> users = session.scalars(stmt).all()
> ```
> 这等价于 Prisma 的 `include: { posts: true }`。把 `echo=True` 打开看 SQL 条数，是验证有没有踩 N+1 的最直接办法。

# 七、放进 FastAPI：按请求开 Session

把 Session 接到 FastAPI 接口上，标准做法是用依赖注入（`Depends` 见第 18 篇），保证**每个请求一个独立 Session、请求结束自动关闭**：

```python
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session

app = FastAPI()

# get_db：依赖函数，每个请求调一次，yield 出一个 Session 给接口用
# yield 之后的 close 在请求处理完后执行(生成器特性，见第 6 篇)
def get_db():
    db = Session(engine)  # db：本次请求专用的数据库会话对象
    try:
        yield db          # 把 Session 交给接口
    finally:
        db.close()        # 请求结束(无论成功失败)都关闭，归还连接

# 接口：根据 id 查用户。db 由 Depends 注入，每个请求独立
@app.get("/users/{uid}")
def read_user(uid: int, db: Session = Depends(get_db)):
    user = db.get(User, uid)                          # user：按 id 查到的用户对象，查不到为 None
    if user is None:                                  # 查不到：返回 404
        raise HTTPException(status_code=404, detail="用户不存在")
    return user
```

> 这里 `db: Session = Depends(get_db)` 就是 FastAPI 的依赖注入：你不用自己 `Session(engine)`，框架按请求帮你建好、用完帮你关。这套"每请求一个会话"是后端铁律——和前端 React 里"每个组件一份 state、卸载时清理"的生命周期直觉一脉相承。

# 八、总结

SQLAlchemy 可以直接套用你的 Prisma 直觉：**类映射表、对象映射行、增删改查写 Python 不写 SQL**。但务必记住那条前端 ORM 里没有的核心边界——**Session 是显式的工作单元，`add/delete` 只是暂存，`commit()` 才真正落库，整个 Session 就是一个事务**。

✅ 该掌握
- 三件套定位：`engine`（全局连接池）、`Model`（表↔类映射）、`Session`（每请求一个的会话/事务）
- CRUD：增 `add`、查 `select(...).where(...)` + `scalars()` 或 `session.get`、改 `查出来改属性`、删 `delete`，最后都要 `commit()`
- 表关系：`ForeignKey`（真实外键列）+ `relationship`（对象导航），预加载用 `selectinload` 避免 N+1
- FastAPI 里用 `Depends(get_db)` 按请求注入 Session

⚠️ 易混淆
- **Session 不是 Prisma**：改动先进暂存区，`commit()` 才落库；忘了 commit 数据不会保存
- 过滤条件用 `User.name == name`（重载的 `==`，生成 SQL），不是普通布尔判断
- 一段业务/一个请求开一个 Session，**别全局共享**（非线程安全），也别每次操作都新建
- 懒加载关系在循环里访问会触发 **N+1 查询**，需 `selectinload` / `joinedload` 预加载（≈ Prisma `include`）
- 学习期开 `echo=True` 看背后真实 SQL，是理解 ORM、排查慢查询最有效的手段
