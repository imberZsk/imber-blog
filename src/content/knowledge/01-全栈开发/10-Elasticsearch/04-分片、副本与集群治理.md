# 二、分片是独立 Lucene 索引

每个主分片和副本都是独立 Lucene 索引。
写请求先路由到主分片，再复制到副本；
搜索由协调节点把请求 Fan-out 到相关分片并 Fan-in 合并结果。
更多分片能增加并行度，但也增加协调、内存、文件句柄和段合并成本，绝不是越多越快。

副本提升读取并发和故障容忍，但不会替代 Snapshot。
误删除或错误 Mapping 会同步到副本；
节点故障期间集群重新分配分片还会消耗网络和磁盘。

# 三、节点角色与容量

生产集群至少要避免 Master-eligible 节点和高负载数据查询完全争抢资源。
专用 Master 节点维护 Cluster State，不承载业务数据；
Data Tier 可按 Hot、Warm、Cold 生命周期放置时序数据；
Ingest 节点执行 Pipeline，但复杂处理应评估 CPU。

容量不能只看磁盘占用。
还要预算 Heap、Page Cache、段合并、恢复流量、副本、故障后剩余节点承载能力和高水位。
JVM Heap 通常不应挤占文件系统缓存，
聚合、Fielddata 和大量 Bucket 会增加堆压力。

# 四、集群健康与维护

```bash
curl -sS "$ES/_cluster/health?pretty"
curl -sS "$ES/_cat/shards?v&s=state,index"
curl -sS "$ES/_cluster/allocation/explain?pretty"
```

Green 表示主副本均分配，
Yellow 表示主分片可用但有副本未分配，
Red 表示至少一个主分片不可用。
状态只是入口，
必须继续用 Allocation Explain 查磁盘水位、过滤规则、节点离线、版本不兼容或无可用副本。

滚动升级一次只处理一个节点：先确认兼容矩阵与 Snapshot，
控制分片重分配，
停止节点，
升级并重新加入，
等待稳定后再继续。
一次重启多个数据节点可能让恢复流量和副本缺失叠加。

# 五、故障边界与治理

Cluster State 过大通常来自索引、分片、字段或 Alias 数量失控，
会拖慢发布和选主。
磁盘高水位可能阻止分配，洪水水位会给索引加只读保护；
清理空间后还要确认写 Block 是否解除。
网络分区和长 GC 会触发节点离开，排障要关联 JVM、磁盘和传输层指标。

恢复速度由分片大小、并发恢复、网络和磁盘共同决定。
调大恢复并发可能挤压线上查询，应在故障演练中找到可接受平衡，而不是事故时临时猜参数。

## 验收清单

- 集群在任一数据节点故障后仍满足容量和查询 SLO。
- 分片数、大小和副本有可测依据，Cluster State 增长受控。
- Yellow、Red、磁盘水位和节点离开均有明确 Runbook。
- Snapshot 恢复和滚动升级在非生产环境完成过演练。

# 十、总结

- **分片是独立 Lucene 索引**：每个主分片和副本都是独立 Lucene 索引。
- **节点角色与容量**：生产集群至少要避免 Master-eligible 节点和高负载数据查询完全争抢资源。
- **集群健康与维护**：状态只是入口，必须继续用 Allocation Explain 查磁盘水位、过滤规则、节点离线、版本不兼容或无可用副本。
- **故障边界与治理**：清理空间后还要确认写 Block 是否解除。
