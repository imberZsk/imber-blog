# 二、Project、Service 与声明式依赖

Compose project 把 services、networks、volumes 和 configs 组成一个环境。
depends_on 表达启动依赖，
只有结合 service_healthy 才能等待健康状态，
但应用仍需对数据库启动和网络抖动执行有界重试。

# 三、环境覆盖与开发数据

基础 compose.yaml 保存通用服务，开发覆盖文件只添加源码挂载、调试端口和本地依赖。
Secret 不提交到仓库，.env 仅用于非敏感插值；
数据库数据使用命名 Volume，并提供显式 reset 命令，不能在普通启动时自动清空。

# 四、可复现启动与故障演练

新开发者从空环境执行 config、pull/build 和 up 后应得到一致服务。
验收包括健康检查、日志关联、停止重启、Volume 恢复和依赖断开；
Compose 适合本地与单机编排，不代表生产多节点高可用。

# 五、带健康依赖的 Compose

API 只在数据库健康后启动，同时仍由应用负责重试。

```yaml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 12
    volumes: [db-data:/var/lib/postgresql/data]
    secrets: [db_password]
  api:
    build: .
    depends_on:
      db: { condition: service_healthy }
secrets:
  db_password: { file: ./secrets/db_password.txt }
volumes:
  db-data:
```

示例密钥文件必须加入 .gitignore 并只用于本地。
生产环境应使用平台 Secret 与托管数据库，不直接照搬本地拓扑。

# 六、故障边界与验证


| 现象 | 常见根因 | 验证与处理 |
| --- | --- | --- |
| API 启动时数据库拒绝连接 | 只配置启动顺序或健康检查过浅 | 增加真实 healthcheck，并让应用执行有上限的退避重试 |
| 不同开发者端口冲突 | 固定发布宿主端口或残留 project | 使用 project name 隔离并只暴露必要入口 |
| down 后业务数据消失 | 使用匿名卷、tmpfs 或执行了 down -v | 使用命名 Volume 并把清理动作设为显式危险命令 |
