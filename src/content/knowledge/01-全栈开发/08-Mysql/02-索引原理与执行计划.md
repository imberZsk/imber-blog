# 二、B+Tree 索引如何工作

InnoDB 聚簇索引的叶子节点保存整行，二级索引叶子保存索引列和主键。通过二级索引查非覆盖列时，需要先定位主键再回聚簇索引取行，这就是回表。主键过大会膨胀所有二级索引，因此主键不仅影响一棵树。

联合索引按列顺序排序。等值过滤列通常放在前面，范围、排序列放后面，但最终顺序要结合选择性、查询组合和排序需求。最左前缀不是“SQL 必须写最左列”，而是优化器能否在有序索引中确定连续范围；跳过中间列通常不能继续缩小扫描区间。

# 三、从查询反推索引

```sql
SELECT id, order_no, amount, created_at
FROM orders
WHERE tenant_id = ?
  AND status = 'PENDING'
  AND created_at >= ?
ORDER BY created_at DESC
LIMIT 50;

CREATE INDEX idx_order_tenant_status_created
  ON orders (tenant_id, status, created_at DESC);
```

该索引先固定租户和状态，再扫描时间范围，并可直接提供排序。若查询只返回索引中已有的列和主键，可形成覆盖索引减少回表；但为了覆盖所有页面不断追加列会增加存储和写放大。索引设计应围绕高频、昂贵且有稳定契约的查询，不围绕单个字段列表。

低选择性字段单列索引通常收益有限，但与租户、时间等字段组成联合索引后可能有效。`LIKE '%keyword%'` 无法利用普通 B+Tree 前缀定位，应考虑全文索引或 Elasticsearch，而不是继续堆索引。

# 四、读懂执行计划

```sql
EXPLAIN ANALYZE
SELECT id, order_no, amount, created_at
FROM orders
WHERE tenant_id = 42 AND status = 'PENDING'
ORDER BY created_at DESC
LIMIT 50;
```

检查实际行数与估算行数、访问类型、使用的 Key、扫描行数、过滤比例、排序和临时表。估算严重偏差可能来自统计信息过旧、列相关性或参数分布倾斜。看到 `Using index` 不等于整体查询快，仍要看返回行数、循环次数和真实耗时。

优化前后使用相同数据规模和参数分布对比 P50、P95、逻辑读与返回行数。测试库只有几百行时，全表扫描可能比索引更快，不能代表生产计划。

# 五、常见失败与治理

重复索引和前缀重叠索引会增加写入成本；索引失效常见原因包括对索引列做函数计算、隐式类型转换、排序方向或列顺序不匹配。分页到很深时 `OFFSET` 仍需跳过大量行，改用基于稳定排序键的 Seek Pagination。

删除“未使用索引”前要覆盖完整业务周期，确认监控包含低频报表和故障流程，并准备可回滚 DDL。写入骤降时检查索引数量、页分裂、锁和磁盘 I/O，不能只看查询延迟。

## 验收清单

- 每个新增索引都有对应查询、预期扫描范围和删除条件。
- `EXPLAIN ANALYZE` 的实际扫描行数、排序方式和耗时符合预算。
- 覆盖索引收益大于写放大与存储成本。
- 慢查询使用真实参数分布回归，避免只测一个理想值。

# 十、总结

- **B+Tree 索引如何工作**：通过二级索引查非覆盖列时，需要先定位主键再回聚簇索引取行，这就是回表。
- **从查询反推索引**：低选择性字段单列索引通常收益有限，但与租户、时间等字段组成联合索引后可能有效。
- **读懂执行计划**：测试库只有几百行时，全表扫描可能比索引更快，不能代表生产计划。
- **常见失败与治理**：删除“未使用索引”前要覆盖完整业务周期，确认监控包含低频报表和故障流程，并准备可回滚 DDL。
