# 二、复制不是备份

主库把已提交变更写入 Binary Log，
从库 I/O 线程获取并写入 Relay Log，
再由应用线程重放。
GTID 为事务提供全局身份，简化故障切换和定位。
复制可以扩展读取与提高可用性，
但误删除、错误 DDL 和逻辑污染也会被快速复制，
所以它不能替代独立备份。

异步复制允许主库提交后立即返回，故障时可能丢失尚未传到从库的事务；
半同步只提高至少一个从库收到日志的概率，仍要理解超时退化和应用语义。
读写分离会产生“写后读旧值”，关键链路需要读主、等待位点或使用会话一致性策略。

# 三、复制拓扑与切换边界

```sql
SHOW REPLICA STATUS\G
SELECT @@global.gtid_executed;
```

监控不能只看 `Seconds_Behind_Source`，
还要看接收位点与执行位点差距、复制线程状态、错误事务和磁盘余量。
大事务、无主键更新、DDL 和从库资源不足都会造成延迟。

故障切换前应停止或隔离写流量，
选择数据最新且健康的候选从库，
确认 GTID 集合，
再提升为新主并更新服务发现。
旧主恢复后必须以只读或隔离状态重新加入，不能自动接受写入，否则会形成脑裂。

# 四、备份策略与恢复目标

先定义 RPO（最多能丢多少数据）和 RTO（多久恢复服务），
再组合全量备份、增量或 Binlog。
物理备份适合大库快速恢复，逻辑备份便于对象级迁移但恢复较慢。
备份文件要加密、跨故障域保存、限制权限并设置保留周期。

点时间恢复流程是：恢复最近一次可用全量备份，
校验一致性，
再按顺序重放 Binlog 到误操作前的位置。
Binlog 必须和备份快照位点关联；
只有一堆备份文件但不知道从哪个位点续放，无法形成可执行恢复方案。

```bash
mysqlbinlog --start-position=123456 \
  --stop-datetime='2026-08-14 10:29:59' mysql-bin.000321 \
  | mysql --host=recovery-db
```

命令必须先在隔离恢复环境执行并核对目标时间，不能直接向生产主库重放。

# 五、恢复演练与常见失败

备份成功日志不等于可恢复。
定期在隔离环境恢复，记录实际 RTO、数据校验结果、应用冒烟测试和缺失依赖。
恢复后校验表数量、关键业务聚合、用户权限、时区、字符集和存储过程，并让应用以只读方式先验收。

常见失败包括备份与 Binlog 位点不匹配、加密密钥不可用、从库长期延迟却仍被选为新主、DNS/连接池缓存仍指向旧主，
以及旧主未经重建直接回归。
Runbook 应明确负责人、决策门槛、停止条件和回退路径。

## 验收清单

- RPO、RTO 与业务等级一致，并有最近一次恢复演练证据。
- 复制延迟、线程状态、GTID 差异和磁盘容量均有告警。
- 备份跨故障域、加密且权限最小化，密钥恢复流程已演练。
- 故障切换能够阻止双写，并确认应用连接全部转向新主。

# 十、总结

- **复制不是备份**：复制可以扩展读取与提高可用性，但误删除、错误 DDL 和逻辑污染也会被快速复制，所以它不能替代独立备份。
- **复制拓扑与切换边界**：监控不能只看 Seconds_Behind_Source，还要看接收位点与执行位点差距、复制线程状态、错误事务和磁盘余量。
- **备份策略与恢复目标**：物理备份适合大库快速恢复，逻辑备份便于对象级迁移但恢复较慢。
- **恢复演练与常见失败**：常见失败包括备份与 Binlog 位点不匹配、加密密钥不可用、从库长期延迟却仍被选为新主、DNS/连接池缓存仍指向旧主，以及旧主未经重建直接回归。
