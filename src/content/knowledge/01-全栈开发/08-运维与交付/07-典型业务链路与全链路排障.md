# 运维与交付（07） - 典型业务链路与全链路排障

> 用相同的数据流方法排查列表、登录、订单、缓存、搜索、配置和定时任务，而不是为每种业务背一套命令。

> 读完你能：沿入口、服务、数据和异步链路收集证据，区分存储成功、接口成功和页面成功。

## 核心知识清单

- Web 查询列表：参数、SQL、分页与序列化
- 登录链路：授权码、会话、Token 与权限
- 创建订单：事务、幂等、消息与最终一致性
- 缓存查询：命中、穿透、击穿与失效
- 全文搜索：写入、索引刷新与查询一致性
- 配置变更：版本、灰度、回滚与审计
- 定时任务：调度、锁、重试与对账
- trace_id 驱动的跨层证据链

## 通用排障框架

先固定一个失败请求，记录输入、身份、租户、版本、时间和 trace_id。沿着“入口 → 业务服务 → 缓存/数据库/搜索 → 消息或外部依赖”寻找第一个与预期不同的事实。列表空要分别验证请求参数、权限过滤、SQL、映射和前端渲染；订单重复要检查幂等键、事务提交与消息消费；搜索旧数据要检查数据库变更是否成功进入索引，而不是直接刷新页面。

## 证据表

| 阶段 | 必须保留的证据 | 常见误判 |
| --- | --- | --- |
| 入口 | request_id、用户、参数、版本 | HTTP 200 就等于业务成功 |
| 服务 | 首个异常 Span、错误类型 | 最后一个报错就是根因 |
| 数据 | SQL/缓存键/索引文档及版本 | 数据库有值就证明页面会显示 |
| 异步 | message_id、幂等键、重试次数 | 重跑一次成功就算修复 |
| 恢复 | 同一请求、指标恢复、无副作用 | 服务重启等于问题解决 |
