# 二、联合索引为什么强调最左前缀，如何验证是否有效？

**简洁答案：** B+Tree 按索引列顺序排序，查询只有利用连续前缀才能高效缩小扫描范围。

**深入说明：** 范围条件之后的列通常难以继续用于定位，但可能用于索引下推过滤；
是否命中不能只看 key，还要看 EXPLAIN ANALYZE 的实际行数、循环和耗时。
索引设计应从高频查询、选择性、排序与覆盖需求出发，同时承担写放大和存储成本。

**继续追问：** 为什么对低选择性状态列建立单列索引可能比全表扫描更慢？

# 三、InnoDB 的 MVCC 与隔离级别如何协作？

**简洁答案：** MVCC 通过隐藏版本信息和 undo 构造一致性读，
锁用于当前读和写冲突。

**深入说明：** READ COMMITTED 通常每条语句创建 Read View，
REPEATABLE READ 在事务内复用一致性视图；
select for update 属于当前读，会读取最新版本并加锁。
幻读控制还涉及 next-key lock，
锁范围受索引和查询条件影响，
无索引更新可能扩大锁定范围。

**继续追问：** 如何从 performance_schema 和死锁日志还原等待图与加锁顺序？

# 四、MyBatis 的 #{} 与 ${} 有什么本质区别？

**简洁答案：** #{} 使用预编译参数绑定，
${} 做原始文本替换，
后者存在 SQL 注入风险。

**深入说明：** 值参数应始终使用 #{}；
动态表名、列名或排序方向无法作为普通参数绑定时，
必须从服务端白名单枚举映射，
不能透传用户字符串。
resultMap 应明确复杂映射与延迟加载边界，避免 N+1 查询和隐式类型转换。

**继续追问：** 批量查询和嵌套映射怎样在可读性、网络往返和结果膨胀之间权衡？

# 五、缓存旁路模式如何处理数据库与 Redis 一致性？

**简洁答案：** 读未命中查库再回填，
写通常先提交数据库再删除缓存，
并接受短窗口内的最终一致。

**深入说明：** 先删缓存再写库会在并发读下回填旧值；
写库后删缓存失败则需要重试、消息或订阅变更日志补偿。
热点 Key 要处理击穿、雪崩和过期抖动，负缓存需短 TTL。
涉及余额和库存等强不变量时不能把缓存当最终事实源。

**继续追问：** 延迟双删能解决哪些竞态，又为什么不能替代可靠失效机制？

# 六、Redis 分布式锁怎样才算基本正确？

**简洁答案：** 使用唯一随机值和带过期时间的原子 SET NX，
释放时通过脚本校验持有者后删除。

**深入说明：** 锁 TTL 必须覆盖操作或具备受控续期，
客户端暂停、网络分区和主从故障仍可能产生并发持有者。
因此关键写入还需数据库唯一约束、版本号或 fencing token 防止旧持有者提交，
不能把锁当作唯一一致性保障。

**继续追问：** Redlock 的假设与 fencing token 分别解决什么问题？
