# 二、打包、代码签名与发布链

Electron 发布链通常分四步：打包应用代码与运行时，
生成目标平台安装格式，
使用平台证书签名，
最后把制品和更新元数据发布到可信渠道。
Electron Forge 可以组织 `package`、`make` 与 `publish`；
不同 Maker 产生 DMG、ZIP、Squirrel、deb、rpm 等格式。

Windows 信任 Authenticode 签名；
macOS 分发通常需要 Developer ID 签名、Hardened Runtime 与 Apple Notarization。
签名证明制品发布者和完整性，不会自动修复应用漏洞。
证书私钥必须放在 CI Secret 或专用签名服务，不能提交仓库或烘焙进镜像。

```mermaid
flowchart LR
  SOURCE["源码与锁文件"] --> BUILD["锁定环境构建"]
  BUILD --> PACKAGE["Electron Package"]
  PACKAGE --> MAKE["平台安装器"]
  MAKE --> SIGN["代码签名 / 公证"]
  SIGN --> SBOM["哈希、SBOM、更新清单"]
  SBOM --> CANARY["灰度发布"]
  CANARY --> PROD["正式渠道"]
```

# 三、配置必须显式区分平台

```ts
// forge.config.ts
import type { ForgeConfig } from '@electron-forge/shared-types'
import { MakerDMG } from '@electron-forge/maker-dmg'
import { MakerSquirrel } from '@electron-forge/maker-squirrel'
import { MakerZIP } from '@electron-forge/maker-zip'

/** Electron Forge 的跨平台制品配置。 */
const forgeConfig: ForgeConfig = {
  packagerConfig: {
    asar: true // 将应用资源打包为 ASAR，减少散文件但不把它当安全加密。
  },
  makers: [
    new MakerSquirrel({}), // Windows 安装与更新制品。
    new MakerDMG({}), // macOS 图形化安装镜像。
    new MakerZIP({}, ['darwin']) // macOS 更新常用 ZIP 制品。
  ]
}

export default forgeConfig
```

ASAR 只是归档格式，用户仍可读取，不应存密钥。
原生 Node 模块必须与 Electron ABI 和目标架构匹配；
Apple Silicon、Intel、Windows x64/arm64 应分别构建或明确生成 Universal 包。
最可靠的方式是在目标操作系统 runner 上构建和签名，而不是依赖未经验证的跨平台交叉构建。

# 四、CI 产物和发布策略

构建输入包括 Git commit、锁文件、Node/Electron 版本和平台工具链。
每个制品记录 SHA-256、大小、签名身份、构建时间与 SBOM。
发布前先把不可变制品上传暂存区，
完成安装与更新验证后再提升到 stable Channel，
不能重新构建“相同版本”。

更新元数据与二进制必须使用 HTTPS，并防止降级到已知不安全版本。
灰度可以按 Channel、组织或百分比推进；
监控新版本启动成功率、崩溃率和更新失败码。
回滚通常是发布更高版本号的修复包或撤回更新清单，而不是指望客户端自动安装更低版本。

# 五、跨平台验收与失败边界

- 未签名开发包能启动，不代表用户机器不会被 Gatekeeper 或 SmartScreen 拦截。
- 证书过期不一定使历史签名失效，但时间戳、公证和更新链必须实际验证。
- 只测试全新安装会遗漏覆盖安装、自动更新、旧数据迁移和卸载残留。
- 原生模块在开发机可用但目标架构崩溃，通常是 ABI 或架构不匹配。
- 发布更新元数据早于二进制同步完成，会让客户端拿到不可下载版本。

最低验收矩阵包括：干净机器安装、首次启动、协议/文件关联、自动更新、保留用户数据、降级阻止、离线启动、卸载和重新安装。
macOS 使用 `codesign`/`spctl` 检查签名与公证，
Windows 检查数字签名和安装器来源；
Linux 验证包依赖、桌面入口与沙盒权限。

# 十、总结

- **打包、代码签名与发布链**：证书私钥必须放在 CI Secret 或专用签名服务，不能提交仓库或烘焙进镜像。
- **配置必须显式区分平台**：ASAR 只是归档格式，用户仍可读取，不应存密钥。
- **CI 产物和发布策略**：构建输入包括 Git commit、锁文件、Node/Electron 版本和平台工具链。
- **跨平台验收与失败边界**：证书过期不一定使历史签名失效，但时间戳、公证和更新链必须实际验证。
