# 二、监控三层成功

调度成功表示 Trigger 已产生，
执行成功表示 Worker 无异常结束，
业务成功表示预期数据或外部结果正确。
三者必须分开：一个任务可能准时运行并返回 0，却因为查询条件错误处理了零条数据。

执行记录至少包含 `job_id`、`execution_id`、计划时间、实际开始/结束、节点、分片、状态、重试次数、处理数量、水位和 `trace_id`。
指标按任务和环境聚合，租户等高基数字段放日志或 Trace，避免把监控系统打爆。

# 三、核心指标与告警

- 调度延迟：实际开始减计划时间。
- 运行时长与 P95/P99：识别逐步变慢和卡死。
- 成功、失败、重试、超时和取消数量。
- 待处理、处理成功、跳过、死信和业务对账差异。
- 上次成功时间与连续失败次数。

告警应基于业务时间窗口。
例如“每日 03:00 前必须完成对账”比单次异常更接近用户影响；
同时保留异常率和卡死告警以便提前介入。
告警包含任务、执行 ID、影响范围、Dashboard、日志和 Runbook 链接。

# 四、故障恢复流程

1. 止损：暂停新调度或限制并发，保护数据库和下游。
2. 定位：区分未触发、未领取、运行失败、卡住和结果错误。
3. 评估：确定受影响时间、租户、分片和副作用。
4. 修复：部署代码/配置或修复数据，在隔离样本验证。
5. 补跑：指定业务窗口和幂等键，限速执行并持续对账。
6. 收尾：恢复调度、确认水位、关闭临时开关并复盘。

补跑不能默认“从头再来”。
保存 Checkpoint 和业务水位，选择失败范围；
涉及通知、扣款等副作用时启用 Dry-run 或审批，并记录操作人和原因。

# 五、恢复边界与演练

调度平台数据库也需要备份和恢复，但执行状态可能已与真实业务分叉。
恢复后先对账任务状态与业务事实，再决定哪些 Execution 可继续、重试或标记终止。
不能把备份中的 Running 任务直接当成仍有执行者。

演练包括调度中心不可用、执行器批量离线、数据库限流、消息积压和错误版本发布。
衡量检测时间、止损时间、恢复时间和数据差异，复盘产出具体门禁与自动化，而不是只写“加强监控”。

## 验收清单

- 每个关键任务有完成时限、业务结果指标和最近成功时间。
- 告警能直接定位 Execution、日志、Trace 与 Runbook。
- 补跑支持范围、限速、Dry-run、审批和幂等。
- 调度平台恢复后会与业务数据对账，不盲信旧状态。

# 八、任务监控与故障恢复 的结果解释

解释“任务监控与故障恢复”实验时先看首个偏差，而不是最后一条错误。最后的异常通常只是上游状态错误的结果；从末端反推容易误把症状当根因。

| 观察结果 | 可以支持的判断 | 下一步 |
| --- | --- | --- |
| 主链路没有达到预期 | 计划退化、死锁、热点击穿、消息重复丢失或恢复后数据不一致 | 先执行：从数据入口、存储状态、复制消费链路和恢复步骤定位根因 |
| 异常链路无法恢复 | 计划退化、死锁、热点击穿、消息重复丢失或恢复后数据不一致 | 先执行：从数据入口、存储状态、复制消费链路和恢复步骤定位根因 |
| 新样本成功但原样本仍失败 | 修复没有覆盖原始触发条件 | 固定原失败输入，恢复基线后重新比较 |
| 指标改善但证据无法回链 | 数据、版本或中间状态没有固定 | 暂停发布，补齐可追溯记录后重跑 |

# 十、总结

- **监控三层成功**：三者必须分开：一个任务可能准时运行并返回 0，却因为查询条件错误处理了零条数据。
- **核心指标与告警**：成功、失败、重试、超时和取消数量。
- **故障恢复流程**：止损：暂停新调度或限制并发，保护数据库和下游。 -> 定位：区分未触发、未领取、运行失败、卡住和结果错误。 -> 评估：确定受影响时间、租户、分片和副作用。 -> 修复：部署代码/配置或修复数据，在隔离样本验证。
- **恢复边界与演练**：恢复后先对账任务状态与业务事实，再决定哪些 Execution 可继续、重试或标记终止。
