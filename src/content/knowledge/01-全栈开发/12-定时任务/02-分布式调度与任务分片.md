# 二、调度与执行分离

分布式调度通常由调度中心计算触发、选择执行器并保存状态，执行器负责领取分片、运行和回报。
调度中心必须高可用且避免同一 Trigger 被多个节点重复派发，
常用数据库唯一约束、Leader 或共识机制控制；
执行器则应被视为可能随时崩溃的临时工作者。

调度请求至少包含 `job_id`、`execution_id`、计划时间、分片号、总分片数、参数版本和超时。
执行器不能只靠进程内状态判断是否执行过。

# 三、任务分片方法

数据可按稳定哈希、ID 范围、时间区间或数据库游标分片。
简单的 `id % shardTotal` 分布稳定，但增加总分片数会改变归属；
范围分片便于检查进度，但数据倾斜会让尾部很慢；
动态 Worker 拉取小批任务能改善均衡，但需要可靠认领和 Lease。

```sql
UPDATE reconciliation_item
SET owner = :workerId,
    lease_until = NOW() + INTERVAL 2 MINUTE,
    status = 'RUNNING'
WHERE status IN ('READY', 'RETRY')
  AND (lease_until IS NULL OR lease_until < NOW())
ORDER BY id
LIMIT 100;
```

不同数据库对带 Limit 的更新和并发锁语义不同，
生产可使用 `SELECT ... FOR UPDATE SKIP LOCKED` 后再更新。
Lease 过期允许其他 Worker 接管，因此单条业务仍必须幂等。

# 四、节点故障与状态机

任务状态至少区分 Scheduled、Running、Succeeded、Retry、Failed、Cancelled。
Heartbeat 只能说明执行器近期活跃，不能证明某个业务步骤完成。
调度中心在 Lease 超时后重新分配，
旧执行器恢复时应通过 Fencing Token 或状态条件被拒绝。

分片任务的总状态由全部分片聚合；
部分成功不能简单标为整体失败后全量重跑。
保存每个分片水位和错误，重试仅处理失败或未完成范围。

# 五、容量与故障边界

并行度受数据库、缓存、消息和第三方 API 最小容量限制。
把 10 个分片扩成 100 个可能只让下游连接池排队。
调度器应支持租户公平、优先级和最大并发，防止一个大任务占满全部 Worker。

故障演练包括调度中心切主、执行器运行中被终止、网络分区、Heartbeat 丢失和数据倾斜。
排障查看分片分配、Lease、Heartbeat、处理速率和下游等待，而不是只看总任务状态。

## 验收清单

- 分片算法对扩缩容、倾斜和重跑的影响已说明。
- 执行器崩溃后分片可接管，旧执行器无法提交过期结果。
- 聚合状态能区分部分成功并只重试失败范围。
- 全局并发受下游容量与租户公平策略限制。

# 十、总结

- **调度与执行分离**：分布式调度通常由调度中心计算触发、选择执行器并保存状态，执行器负责领取分片、运行和回报。
- **任务分片方法**：Lease 过期允许其他 Worker 接管，因此单条业务仍必须幂等。
- **节点故障与状态机**：Heartbeat 只能说明执行器近期活跃，不能证明某个业务步骤完成。
- **容量与故障边界**：调度器应支持租户公平、优先级和最大并发，防止一个大任务占满全部 Worker。
