# 二、锁只减少并发执行

多实例应用中的 `@Scheduled` 会在每个实例触发。
可以通过数据库唯一记录、`SELECT ... FOR UPDATE`、Redis 租约或调度平台单点派发控制并发，
但锁不能替代业务幂等。
持锁节点暂停超过租约后，新节点可能接管，旧节点恢复后仍可能继续运行。

数据库锁适合同库短事务，语义清晰但不能长时间占用连接；
Redis 锁适合低延迟协调，需要所有者、TTL、原子释放和最终存储约束；
调度平台能减少重复派发，但网络超时后仍可能无法判断执行器是否已经开始。

# 三、错过执行的业务语义

服务停机、调度器故障或资源不足都会错过触发。
补跑策略必须按任务定义：报表生成可补最近一次，
逐小时账单可能逐段补齐，
缓存预热可直接跳过旧周期。
Misfire 策略若只依赖框架默认值，升级或更换调度器时可能改变业务结果。

```yaml
apiVersion: batch/v1
kind: CronJob
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 1800
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
```

`Forbid` 防止同一 CronJob 并发，
但控制器仍可能在特定故障窗口创建重复 Job，
业务代码必须幂等。
`startingDeadlineSeconds` 表示超过多长时间不再补启动，
需要与业务补跑策略一致。

# 四、执行所有权与 Fencing

任务领取时生成递增 Token，提交结果时要求 Token 仍是当前版本。
Heartbeat 续租只能延长所有权，不能让过期执行者重新有效。
长任务按 Checkpoint 分段提交，接管者从已确认水位继续，而不是全部重跑。

锁粒度要对应业务资源。
全局锁实现简单但会阻塞所有租户；
按租户或日期分锁提高并行度，但需要限制总并发和热点租户。
锁 Key 与执行记录都要有可观测名称和脱敏标识。

# 五、故障注入与排查

主动验证实例在任务中途被杀、GC 暂停超过 TTL、调度器重复回调、网络分区和数据库提交后回报失败。
检查最终业务记录是否唯一、旧执行者是否被拒绝、漏跑是否能检测和补偿。

发现重复结果时不要只调大锁 TTL，应回溯幂等键、租约、Token 和提交条件。
发现漏跑时核对计划触发、派发、领取、开始、Checkpoint 和结束六个阶段，明确缺口所在。

## 验收清单

- 锁类型、粒度、租约和失效行为有明确依据。
- Misfire 和重复触发策略与业务时间窗口一致。
- 旧执行者在租约失效后无法提交结果。
- 系统能自动发现漏跑，并通过受控补跑恢复。

# 十、总结

- **锁只减少并发执行**：可以通过数据库唯一记录、SELECT ... FOR UPDATE、Redis 租约或调度平台单点派发控制并发，但锁不能替代业务幂等。
- **错过执行的业务语义**：补跑策略必须按任务定义：报表生成可补最近一次，逐小时账单可能逐段补齐，缓存预热可直接跳过旧周期。
- **执行所有权与 Fencing**：任务领取时生成递增 Token，提交结果时要求 Token 仍是当前版本。
- **故障注入与排查**：主动验证实例在任务中途被杀、GC 暂停超过 TTL、调度器重复回调、网络分区和数据库提交后回报失败。
