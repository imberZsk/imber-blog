# 二、集群内 DNS 与 Service 路由

CoreDNS 为 Service 和 Pod 提供名称解析，
Service 通过 EndpointSlice 表达后端。
DNS 成功只证明名称可解析，不能证明端口、NetworkPolicy 或应用健康；
排障要分别验证名称、路由、TCP、TLS 和 HTTP。

# 三、Ingress Controller 与路由契约

Ingress 是路由声明，真正执行由 Ingress Controller 完成；
不同控制器的 annotation 行为不同。
Host、Path、TLS Secret 和后端 Service 构成入口契约，
生产要明确超时、请求体限制、转发头和默认拒绝路由。

# 四、NetworkPolicy 与最小网络权限

NetworkPolicy 依赖 CNI 实现，默认没有策略时通常允许通信。
先按命名空间和 workload 建立默认拒绝，再开放 DNS、入口、依赖和监控流量；
策略上线前记录现有连接并灰度，避免一次阻断控制面或健康检查。

# 五、入口与网络验证命令

从临时调试 Pod 验证 DNS、Service 和 HTTP，再检查入口对象。

```bash
kubectl run netcheck --rm -it --restart=Never --image=curlimages/curl -- sh
nslookup api.default.svc.cluster.local
curl -sv --connect-timeout 2 http://api.default.svc.cluster.local/health
kubectl get ingress,service,endpointslice -A
kubectl describe ingress api
```

生产集群应使用受控调试镜像与短期权限。
若 Service 直连成功但域名入口失败，
重点检查 Ingress Controller、TLS、Host 和外部负载均衡。

# 六、故障边界与验证

下面三类现象覆盖本主题最常见的错误路径；
证明结果可复现且没有引入新的副作用。

| 现象 | 常见根因 | 验证与处理 |
| --- | --- | --- |
| DNS 解析成功但连接超时 | NetworkPolicy、端口或路由阻断 | 检查端点、目标端口、策略和 CNI 流日志 |
| Ingress 返回默认 404 | Host/Path 未匹配或对象由另一 Controller 管理 | 核对 ingressClassName、Host 和控制器事件 |
| 策略上线后 DNS 全失败 | 默认拒绝未放行 CoreDNS UDP/TCP 53 | 按命名空间选择器显式允许 DNS 并验证 TCP fallback |
