# 运维与可观测性（03） - CI/CD、灰度与回滚

> CI 证明提交满足质量门槛，CD 把同一不可变产物安全推进环境；重新构建一份“看起来一样”的包会破坏可追溯性。

## 学习目标

- 设计从检查、测试、构建到灰度发布的流水线阶段。
- 选择滚动、蓝绿、金丝雀和 Feature Flag 的适用边界。
- 用指标阈值、版本摘要和迁移策略验证暂停与回滚。

## 一、流水线分层

```text
提交 -> 格式/静态检查 -> 单测 -> 集成测试 -> 构建一次 -> 安全扫描
     -> 部署测试环境 -> 冒烟/E2E -> 人工或策略门禁 -> 灰度 -> 全量
```

每一步保存提交 SHA、依赖锁、构建产物摘要和测试报告。敏感凭据使用短期身份或专用 Secret，不把长期密钥写入仓库和普通 CI 日志。

## 二、发布策略

- 滚动发布适合向后兼容变更，控制 maxUnavailable 与 maxSurge。
- 蓝绿发布切换清晰但资源成本高，仍需处理数据库兼容。
- 金丝雀按稳定用户/租户分桶，比较错误率、延迟和业务指标。
- Feature Flag 分离代码部署与功能开放，但需要所有者和清理期限。

## 三、回滚触发

上线前定义自动暂停/回滚阈值：错误率、P95/P99、关键业务成功率和安全事件。回滚动作包含应用、配置、模型、Schema 与缓存策略；不可逆数据迁移必须有前向修复方案。

## 四、质量门禁

单测通过不代表端到端正确。接口契约、数据库迁移、浏览器路径、权限负例和真实构建应按风险进入流水线。Flaky Test 应隔离并修复，不能无限重跑掩盖不确定性。

## 五、验收

- 使用同一产物从测试推进生产，摘要一致。
- 模拟灰度错误率超阈值，流水线自动暂停并保留证据。
- 回滚后用同一冒烟集确认恢复，而不是只看 Pod Running。
