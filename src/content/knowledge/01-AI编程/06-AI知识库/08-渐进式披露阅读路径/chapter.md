# 渐进式披露阅读路径

## 本篇你能学到

- 为什么不能把整个知识库塞给 AI：上下文窗口、噪声、成本三笔账怎么算
- 四级阅读路径（hot.md → _index.md → 分区 _index → 具体页）的设计逻辑
- hot.md 热缓存与 _index.md「按意图导航」的设计原理

---

## 先聊聊一个反直觉的事

很多人第一次给 AI 搭知识库，思路是这样的：把所有 markdown 拼成一个大文件，或者干脆把整个目录扔进上下文，然后说「你都看完，回答我的问题」。

听起来很合理，AI 看得越多答得越准嘛。

但实际跑起来你会发现三个问题同时找上门：

> **AI 读知识库，从来不是「读得越多越好」，而是「读到刚好够用就停」。**

第一，**上下文窗口是有上限的**。哪怕是大窗口模型，把几百篇 references 全塞进去，也会挤掉真正重要的对话历史和当前任务上下文。窗口被知识库填满了，AI 反而忘了你最初问的是什么。

第二，**噪声会拖垮判断**。你问的是「Tailwind 选哪个版本」,结果上下文里同时躺着 React 路由、TypeScript 配置、Git 工作流几十个无关主题。AI 要在一堆干扰里捞出那一行答案，准确率不升反降。

第三，**成本是真金白银**。每次查询都全量读取，token 消耗按整个知识库的体量计费。知识库越大越值钱，但你的查询账单也跟着线性膨胀，这显然不可持续。

所以正确的设计不是「让 AI 看全部」，而是**给它一条由浅入深的路径，让它自己决定走到哪一步就够了**。这就是渐进式披露（Progressive Disclosure）。

## 四级阅读路径：从薄到厚

`frontend-knowledge` 知识库里，这条路径被写死在约定里，AI 查询时必须按顺序走：

```text
1. wiki/hot.md          会话热缓存（最薄，时间性缓存）
        ↓ 没命中
2. wiki/_index.md       按意图路由（定位到哪个分区）
        ↓ 进入分区
3. 分区 _index.md        分组导航（定位到哪个页面）
        ↓ 锁定页面
4. references/<topic>.md  具体页面（最厚，真正的细则）
```

🎯 关键在于「**信息足够即停止，不多读一个文件**」。这句话不是口号，它直接写在 `wiki-query` 技能的执行流程里：

> 信息足够即停止，不多读一个文件。所有步骤限定在前端知识库内，不跨仓库、不跨方向查找。

每一级都比上一级更厚、更具体，但也更窄。AI 沿着路径往下走，一旦在某一级拿到了能回答问题的信息，立刻停下，**不会为了「保险」继续往下读**。

来看每一级各自的职责。

### 第一级：hot.md —— 时间性热缓存

`hot.md` 是整条路径里最薄的一层，本质是「最近高频问题的速查表」。它不承载完整知识，只放指针和结论摘要。

看一眼 `frontend-knowledge` 里真实的 `hot.md` 结构（节选）：

```markdown
## 常见问题

| 问题                         | 快速解决                      | 详细说明                                    |
| ---------------------------- | ----------------------------- | ------------------------------------------- |
| 解构 reactive 对象丢失响应性 | 用 `toRefs(state)` 保持连接   | vue3/reactivity-pitfalls.md                 |
| Tailwind 版本选择            | 默认选 3.x（浏览器兼容更好）  | conventions/adr/tech-stack-selection.md     |

## 核心文档导航

| 场景           | 文档                          |
| -------------- | ----------------------------- |
| React 组件开发 | stacks/react/.../\_index.md   |
| 测试规范       | conventions/references/testing.md |
```

它的价值在于：**高频问题一次命中，跳过后面所有递归**。如果你问的是「Tailwind 选哪个版本」，AI 在第一级就拿到了「默认 3.x」的结论和源页面链接，直接结束，连 `_index.md` 都不用打开。

为什么强调它是「时间性」缓存？因为 `hot.md` 的条目是会过期的。不同 section 有不同的过期阈值：

| Section          | 过期阈值                       |
| ---------------- | ------------------------------ |
| 当前焦点 / 环境状态 | 7 天，超期删除                 |
| 活跃线程         | 7 天，超期删除                 |
| 近期变更         | 14 天，超期删除                |
| 关键决策         | 不自动过期，被新决策覆盖时替换 |
| 常见坑 / 快速链接 | 不自动过期，源页面变动时重新验证 |

> `hot.md` 记录的是「当前焦点」，不是「永久真理」。它像浏览器的缓存，命中就快，过期就刷新，永远跟着团队最近在折腾的事走。

还有一个容易忽略的设计：**读写分离**。查询通用知识库（wiki 分区）时，读的是团队级的 `wiki/hot.md`，但写回缓存时写的是当前项目的 `knowledge/hot.md`。原因很实在：通用知识库是团队级资产，应由架构组维护，不该被某个项目的查询自动改写；而且不同项目的高频问题差异大，项目级缓存更贴近实际，也避开了多项目并发写入的冲突。

### 第二级：_index.md —— 按意图路由

如果 `hot.md` 没命中，AI 进入 `wiki/_index.md`。这一级只干一件事：**判断问题该去哪个分区**。

它的导航表设计有个反常识的地方 —— **不按目录结构排，而按「意图」排**：

```markdown
## 按意图查找

| 常见意图                                  | 优先入口                          |
| ----------------------------------------- | --------------------------------- |
| 新项目技术选型 / 团队规范基线             | 团队技术选型规范                  |
| 已有项目开发规范 / 质量门禁 / 技术债      | 协作与约定                        |
| 初始化 React 项目 / 项目脚手架            | React 项目脚手架模板              |
| 鉴权、交互模式（如渐进披露、加载态）      | Patterns                          |
| Tailwind CSS v3/v4 配置与迁移             | CSS Frameworks                    |
```

差别在哪？对比一下就清楚了：

| 维度       | ✅ 按意图设计的导航表                       | ❌ 按目录树罗列的导航                       |
| ---------- | ------------------------------------------ | ------------------------------------------ |
| 左列内容   | 用户真实会问的问题（「新项目选什么栈」）   | 文件夹名（`conventions/`、`stacks/`）      |
| AI 匹配方式 | 语义匹配意图，一眼定位                     | 得先猜「选型」属于哪个文件夹               |
| 维护视角   | 站在「别人会怎么问」的角度                 | 站在「我怎么存的」角度                     |
| 命中率     | 高，问题和入口同语言                       | 低，需要 AI 二次翻译                       |

> 导航表的左列写的应该是「**用户嘴里的话**」，不是「文件系统里的路径」。AI 拿着问题做语义匹配，意图对得上，路由就准。

注意 `_index.md` 顶部那行藏起来的注释，它直接给 AI 下了指令：

```markdown
<!-- AI: 读本页前先读 hot.md，有实质内容则以其为当前现场；
     为空或不存在则忽略，直接用下方意图表导航。 -->
```

这就是把渐进式披露的顺序**显式写进了文档本身**，而不是只靠技能脚本约束。文档自己会告诉 AI 「先看缓存，再看我」。

### 第三级：分区 _index.md —— 分组导航

路由确定后，AI 进入分区的 `_index.md`，做更细一层的定位。比如进了 `conventions/_index.md`：

```markdown
## 立项与结构 <!-- 必读 -->

| 文档              | 说明                                              |
| ----------------- | ------------------------------------------------- |
| 团队技术选型规范  | 新项目默认栈（React + Vite + Tailwind 3.x ...）   |
| 仓库结构          | 按 feature 组织、目录深度 ≤ 4                      |

## 代码与评审 <!-- 必读 -->

| 文档              | 说明                                              |
| ----------------- | ------------------------------------------------- |
| 文件命名          | 组件 PascalCase、hooks camelCase、其他 kebab-case |
| Code Review       | PR ≤ 400 行、拆分顺序、评论前缀                    |
```

这一级把分区内的页面按「立项 / 评审 / 质量 / 技术债」分组，每个链接配一句话说明。AI 扫一眼说明就能判断该点哪个，**不需要把页面打开才知道里面讲啥**。说明写得好，本身就是一层过滤。

### 第四级：references/<topic>.md —— 真正的细则

走到这一级，AI 才真正读完整页面。但即便到了这里，**也不是整页全读**。页面用 HTML 注释给 section 标了深度：

| 标记            | 行为                                                        |
| --------------- | ----------------------------------------------------------- |
| `<!-- 必读 -->` | 始终读取                                                    |
| `<!-- 按需 -->` | 仅当问题涉及该段主题时才读                                  |
| `<!-- 专项 -->` | 默认跳过；只在用户明确追问或高度匹配时才展开                |
| 无标记          | 整体阅读                                                    |

举个例子，一篇「React Query 怎么用」的页面：

```markdown
## 基础用法 <!-- 必读 -->
React Query 的核心是 useQuery hook...

## 缓存策略 <!-- 按需 -->
staleTime 和 gcTime 的区别在于...

## 源码分析 <!-- 专项 -->
QueryClient 内部维护了一个 QueryCache 实例...
```

问「怎么用」时：基础用法（必读）读、缓存策略（按需且相关）读、源码分析（专项非追问）跳过。**渐进式披露不只发生在文件之间，连一篇文档内部也在分层。** 你不追问源码，AI 就不为你读源码那段。

## 用 8 步流程反证这条路径

光说设计还不够，看 `wiki-query` 技能真实的 8 步执行流程，会发现整条路径就是它的骨架：

| 步骤   | 名称                        | 对应路径级别            |
| ------ | --------------------------- | ----------------------- |
| Step 1 | 读根 `_index.md`，确定路由   | 第二级：按意图路由      |
| Step 2 | 读分区 `hot.md`             | 第一级：热缓存（命中则直接跳 Step 7）|
| Step 3 | 递归读 `_index.md` 定位页面 | 第三级：分组导航        |
| Step 4 | 读目标页面                  | 第四级：具体页面        |
| Step 5 | Grep 关键词搜索（降级）     | 路径失效时的兜底        |
| Step 6 | AI 训练知识补充（兜底）     | 知识库未覆盖时的最后手段|
| Step 7 | 更新 `hot.md` 缓存（可选）  | 把这次结果沉淀回第一级  |
| Step 8 | 组织答案 + 引用来源表       | 输出                    |

几个细节值得拎出来说：

**Step 2 命中即跳转。** 一旦 `hot.md` 里找到答案，流程直接从 Step 2 跳到 Step 7，中间的 Step 3-6 全部跳过。这就是「信息足够即停止」最直白的体现 —— 不为了流程完整而多读文件。

**Step 4 命中也跳转。** 同理，目标页面里信息够了，Step 5（Grep）和 Step 6（AI 兜底）都跳过。每一步都在问「够了吗」，够了就走 Step 7/8 收尾。

**Step 5/6 是安全网，Step 7 让缓存自我成长**：前两步仅在路径失效时降级兜底，Step 7 则把本次查询结论写回 `knowledge/hot.md`，下次同类问题 Step 2 直接命中。

> 整个流程像一个漏斗：从最薄的缓存开始，逐级加深，每一级都设了「够了就停」的出口，只有漏到底都没接住，才动用兜底手段。

## 小结

渐进式披露的本质，是承认「AI 的上下文是稀缺资源」这件事。与其把整个知识库砸给它让它自己捞，不如铺一条由薄到厚的路：`hot.md` 接住高频问题，`_index.md` 按意图路由，分区索引做分组定位，具体页面才展开细则 —— 而且每一级、甚至每一篇文档内部，都允许 AI「够用就停」。

这套设计同时解了三道题：上下文窗口不被无关内容挤爆，噪声在路由阶段就被过滤，成本随查询深度按需付费而不是全量买单。`wiki-query` 的 8 步流程里那些「命中即跳转」「降级才 Grep」的分支，全是这条路径的工程化落地。

下次你给团队搭 AI 知识库，先别急着堆内容。先想清楚两件事：**入口怎么按意图组织**，以及**怎么让 AI 知道哪一步可以停**。这两件事做对了，知识库才是真能被 AI 用起来的知识库，而不是一个塞满 markdown 的大仓库。
