# 渐进式披露阅读路径设计

## 本篇你能学到

- 为什么「大文件平铺」是反模式：多主题混杂导致 AI token 浪费、命中率下降，人也要通读才能建立心智模型
- `_index` 导航层 → 详情页两层结构的落地方式，以及 `<!-- 必读 -->` / `<!-- 按需 -->` / `<!-- 专项 -->` 三个章节标记的用法
- 拆分阈值背后的原理：以单页信息密度和检索意图独立性为判断依据的设计决策框架

---

## 一个真实的痛点

你有没有遇到过这种情况：把所有规范、最佳实践、踩坑记录都堆在一个 `README.md` 里，打开一看 800 行，问 AI 一个问题，它把整个文件都读了一遍，然后给你一个"综合了多个因素"的模糊回答？

这不是 AI 的问题，是信息架构的问题。

大文件平铺有几个硬伤：

1. **AI 读取成本高**：token 是有限资源，每次都全量读取，浪费在无关内容上
2. **噪声干扰命中率**：文件里混了太多主题，AI 很难精准定位你问的那个点
3. **命中后难以定位**：找到了关键词，但上下文混乱，AI 还要花时间理解"这段到底是说哪种情况"
4. **维护成本爆炸**：一个人改了某块内容，另一个人不知道，整个文件成了随机修改的战场

第 08 篇讲过"读取顺序"，那是战术层面的——告诉 AI 先读哪、后读哪。本篇要往上一层：**架构层面，你的知识应该怎么组织，才能让"读取顺序"策略真正发挥效果**。

## 渐进式披露是什么

这个词来自 UX 设计领域：只在用户需要的时候展示相关信息，不一次性把所有内容砸给用户。

搬到知识库里，逻辑完全一样：

> **AI 查询知识库时，应该像人翻目录一样——先看摘要，找到位置，再翻到具体页，不是从第一页读到最后一页。**

核心原则就一句话：**信息足够即停止，不多读一个文件。**

这不只是对 AI 友好，对人也友好。你找东西的时候，宁愿看一个清晰的目录页，还是翻一本没有目录的厚书？

---

## 两层结构：导航层 + 详情层

最实用的落地结构是两层：

```text
wiki/
├── _index.md          ← 导航层：路由表，告诉你去哪找
├── stacks/
│   ├── _index.md      ← 子导航层：stacks 分区的路由
│   └── react/
│       ├── _index.md  ← React 专区导航
│       └── references/
│           ├── project-scaffold.md  ← 详情页：只讲脚手架
│           └── state-management.md  ← 详情页：只讲状态管理
└── engineering/
    ├── _index.md
    └── git-workflow/
        └── _index.md
```

`_index.md` 只做一件事：**路由**。它列出"这个目录下有什么，各自解决什么问题，入口在哪"，不承载具体细则。

以真实的 `wiki/_index.md` 为例，它的意图表长这样：

```markdown
| 常见意图                        | 优先入口                              |
| ------------------------------- | ------------------------------------- |
| 新项目技术选型 / 团队规范基线   | conventions/adr/references/tech-stack-selection.md |
| 初始化 React 项目 / 项目脚手架  | stacks/react/references/project-scaffold.md        |
| 包管理、构建、测试、Monorepo    | engineering/_index.md                 |
```

AI 读完这张表，就知道"你说的 React 脚手架问题，去 `stacks/react/references/project-scaffold.md` 找"，然后直接跳过去。**完全不需要读其他任何文件**。

这就是渐进式披露的威力：一次路由，精准命中，最小读取。

## 三个深度标记

导航层解决了"去哪找"，详情页内部还有一个问题：**一篇详情页本身也可能很长，不同问题只需要读其中一部分**。

这时候用 section 深度标记：

```markdown
## 基础用法 <!-- 必读 -->

React Query 的核心是 useQuery hook...

## 缓存策略 <!-- 按需 -->

staleTime 和 gcTime 的区别在于...

## 源码分析 <!-- 专项 -->

QueryClient 内部维护了一个 QueryCache 实例...
```

| 标记 | 行为 |
|------|------|
| `<!-- 必读 -->` | 始终读取，这是理解页面的最小必要信息 |
| `<!-- 按需 -->` | 仅当问题涉及该段主题时读取 |
| `<!-- 专项 -->` | 默认跳过；仅在用户明确追问、高度匹配时展开 |
| 无标记 | 整体阅读 |

**标记影响范围**：从当前标题到下一个同级或更高级标题。

举个例子，用户问"React Query 怎么用"：

- **基础用法**（必读）→ 读 ✅
- **缓存策略**（按需，与问题相关）→ 读 ✅
- **源码分析**（专项，没人追问）→ 跳过 ⛔
- **常见问题**（无标记）→ 读 ✅

这个问题用了 75% 的页面内容，节省了 25%。如果页面有 10 个 section，其中 3 个是专项，节省比例更高。

> 💡 这些标记不只是给 AI 看的。新人翻文档时，看到 `<!-- 必读 -->` 也知道"这段我必须理解，其他先跳过"。

## 拆分阈值：单页信息密度控制

什么时候该把一篇文档拆开？这是很多人拿不准的问题。

背后的原理是**单页信息密度**：一个页面承载的"独立主题数"越多，精准命中率越低。

判断标准可以用这几个维度：

**按主题独立性**：如果一个 H2 section 单独拿出来就能成为一篇独立文章，那它就应该是独立文件。

**按检索意图**：用户会单独搜这个话题吗？如果"React Query 缓存策略"和"React Query 乐观更新"是两种完全不同的检索意图，就拆成两个文件。

**按长度**：经验值，超过 500 行的文件基本都有拆分的必要。但长度只是结果，不是原因。

**按修改频率**：经常单独修改的内容，拆出来能减少协作冲突。

一个实用的决策问题：

> 如果我只需要知道 A，我非得看 B 不可吗？如果不需要，B 就应该在另一个文件里。

## 正反对比

| 维度 | ✅ 渐进式分层结构 | ❌ 大杂烩单文件 |
|------|-----------------|----------------|
| **AI 读取成本** | 按需读取，最小 token 消耗 | 每次全量读取，成本随文件增长线性上升 |
| **命中精准度** | 路由直达目标页，噪声极低 | 多主题混杂，AI 难以精准定位 |
| **维护协作** | 各页独立，改 A 不影响 B | 多人同时改一个文件，冲突频发 |
| **新人上手** | 看 `_index` 就知道全局结构 | 需要通读全文才能建立心智模型 |
| **内容扩展** | 新增主题加新文件，不污染已有结构 | 越堆越大，越来越难维护 |
| **检索降级** | Grep 搜索目标明确，命中文件少 | Grep 命中 N 个位置，还要逐个过滤 |

## 设计一个知识库的思路

如果让你从零搭一个新方向的知识库，怎么做？

先列出团队的检索意图清单，按相关性分组，每组对应一个子目录和 `_index.md` 路由骨架——导航先建好，详情页可以后补。详情页写完后，给每个 H2/H3 打上深度标记，再约定拆分阈值（如单文件超 300 行触发 review），防止文件悄悄膨胀。

---

## 为什么「信息足够即停止」是一个好原则

这个原则对 AI 和人都有一个共同的好处：**减少认知负荷**。

AI 读完必读 section 就够回答问题了，就没必要继续读专项内容。继续读不会让答案更准，只会引入更多可能干扰判断的细节。

对人来说，看完"基础用法"能解决 80% 的日常问题，看"缓存策略"解决剩下 15%，只有极少数情况才需要去读"源码分析"。**大部分时间，你不需要知道全部**。

这是一种尊重读者时间的设计哲学。

---

## 小结

渐进式披露的本质是：**在正确的时机，给出正确粒度的信息**。

两层结构（`_index` 导航 + 详情页）解决了"去哪找"的问题；三个深度标记（必读/按需/专项）解决了"读多少"的问题；拆分阈值控制了单页信息密度，避免文件膨胀成新的大杂烩。

知识库的架构不是一次设计好就永远不动的。随着内容积累，你会发现某些文件越来越臃肿、某些 `_index` 的路由越来越长——这些都是需要重构的信号。**定期整理知识架构，和定期重构代码一样重要**。
