# 整体架构：三层模型

> 📌 **本篇你能学到**
>
> - 三层架构各管什么、为什么要分层——看懂这张骨架，全书其余内容都有了落脚点
> - 用「图书馆」类比 + 目录结构图，一次性建立三层空间感
> - 三层的写入约束与职责边界，避免内容污染
>
> 这一篇是全书的地基。后面所有技能、命令、写入规范，都是在这张三层骨架上长出来的。读慢一点，值得。

---

## 先抛结论：三层是哪三层

如果你只能记住一句话，记这句：**一手证据、团队共识、项目落地，三件事必须分开放。**

落到目录上，就是三层：

| 层 | 路径 | 装什么 | 一句话定位 |
| --- | --- | --- | --- |
| 原始层 | `raw/` | React/Vue 官方 docs、RFC 的一手快照 | 只存证据，不下结论 |
| 通用层 | `wiki/` | 团队通用前端知识（与业务解耦） | 团队的共识沉淀 |
| 项目层 | 各业务仓库的 `knowledge/` | 项目架构、业务、踩坑 | 这个项目怎么干的 |

注意最后一栏：**三层互不强绑，职责严格分离**。这不是一句口号，而是后面所有写入约束的源头。先把这个印象刻进去，下面慢慢拆。

---

## 🏛️ 一个图书馆的类比

抽象的「层」不好记，换成图书馆你立刻就懂了。

**原始层 = 档案库房。** 这里放的是一手档案的原件——官方文档的快照、RFC 提案的原文。库房有一条铁规矩：**只许借阅，不许涂改**。你不能在档案上写批注、画重点、夹自己的便签。它存在的唯一意义，是当有人质疑「你这个结论哪来的」时，你能把人领到库房，指着原件说：「喏，在这。」

**通用层 = 公共藏书区。** 这里是馆员整理过的、面向所有读者的通用读物——「我们团队为什么选 Zustand 而不是 Redux」「鉴权流程的标准写法」。这些是**结论**，是从档案库房里读完原件后提炼出来的团队共识。它和具体哪个项目无关，谁来都能用。

**项目层 = 各科室的专柜。** 财务科有财务科的专柜，研发科有研发科的专柜。专柜里放的是「我们这个项目的架构图」「这个业务域的流转规则」「上次那个诡异的 bug 是怎么填的坑」。这些东西**只对本科室有意义**，搬到公共藏书区只会污染别人。

> 💡 关键洞察：档案库房的原件不会因为某个项目结束而失效，公共藏书也不会因为某个项目的特殊踩坑而被污染。**层与层之间没有强依赖**——删掉某个项目的专柜，公共藏书区毫发无损；公共藏书更新了选型结论，档案库房的原件一个字都不用动。

## 📂 目录结构图：建立空间感

光说不画，永远记不住。把三层摊开看一眼：

```text
frontend-knowledge/                 # 通用知识库仓库（原始层 + 通用层同居一处）
├── _index.md                       # 仓库总入口，只做路由到 wiki
├── raw/                            # 【原始层】证据，不下结论
│   ├── README.md
│   ├── docs/
│   │   ├── react/                  # react.dev 源码快照（git clone --depth 1）
│   │   └── vue/                    # vuejs.org 源码快照
│   └── rfcs/
│       ├── react/                  # React 设计提案
│       └── vue/                    # Vue 设计提案
└── wiki/                           # 【通用层】团队通用知识
    ├── _index.md                   # 按意图导航的总目
    ├── hot.md                      # 会话热缓存（读 _index 前先读）
    ├── wiki-schema.md              # 文档格式规范（写入前必读）
    ├── conventions/                # 团队约定
    ├── engineering/                # 工具链（构建/质量/Git/TS/Monorepo…）
    ├── foundations/                # 性能、安全等跨框架原则
    ├── patterns/                   # 通用交互模式
    └── stacks/react · stacks/vue   # 技术栈最佳实践


your-business-repo/                 # 你的某个业务仓库（项目层独立寄居在这里）
└── knowledge/                      # 【项目层】用 areas-init 技能初始化，不进通用仓库
    ├── _index.md                   # 知识库入口：概述 + 导航
    ├── hot.md                      # 项目热点上下文
    ├── areas/                      # 结构化知识
    │   ├── architecture/           # 这个项目怎么实现的
    │   ├── business/               # 这个项目在做什么业务
    │   ├── components/             # 有哪些组件、怎么复用
    │   ├── best-practices/         # 有哪些经验、坑和推荐做法
    │   └── conventions/            # 项目内部怎么约定
    └── raw/                        # 项目级原始素材（会议纪要、截图…）
```

看清楚两个仓库的边界了吗？**原始层和通用层住在 `frontend-knowledge` 这一个仓库里**；**项目层完全不在这个仓库**，它通过 `frontend-knowledge:areas-init` 技能，在你各自的业务仓库根目录下就地生成一个 `knowledge/`。

> ⚠️ 这是新人最容易搞错的一点：项目知识**不要往通用仓库塞**。业务组件、业务流程、项目架构决策、业务域强绑的状态流转，这些一律去项目自己的 `areas/`。通用仓库的 `wiki/` 只收「与业务解耦」的东西。

## 为什么非得分层？

如果你嫌三层麻烦，问自己一个问题：**不分层会怎样？** 答案是会得「知识库癌症」——所有东西混在一坨，三个月后没人敢动，因为分不清哪条是官方说的、哪条是团队定的、哪条只是某个项目的临时妥协。

分层精确地解决三件事。

### 1️⃣ 职责分离：每层只回答一类问题

| 层 | 回答的问题 | 典型内容 |
| --- | --- | --- |
| 原始层 `raw/` | 「官方原文是怎么说的？」 | React 学习文档、Vue API、RFC 提案 |
| 通用层 `wiki/` | 「我们团队的共识是什么？」 | 为何选 Zustand、ESLint 团队配置、鉴权标准写法 |
| 项目层 `areas/` | 「这个项目具体怎么干的？」 | 业务域地图、项目架构、已知坑与排障 |

一个问题进来，先想它属于哪一类，就知道该去哪层找、该往哪层写。脑子里不再打架。

### 2️⃣ 避免污染：内容边界划死

这是分层最值钱的地方。看看通用层 `wiki/` 的红线：

| ✅ 放进 `wiki/` | ❌ 不放进 `wiki/` |
| --- | --- |
| 技术选型决策与团队约定 | React/Vue 的基础用法与 API 文档（AI 已知，无增量价值） |
| 团队场景踩出的写法约定（带 ✅/❌） | 项目业务组件、业务流程、业务踩坑 |
| 工具链的团队配置（ESLint/Vite/pnpm） | 项目架构决策、文件约定 |
| 通用交互模式的团队实现（鉴权、加载态） | 业务域强绑的状态流转、业务规则 |

右边那一列要是漏进了 `wiki/`，通用层立刻被项目细节稀释——别的项目来查通用约定，搜出一堆和自己无关的业务噪声。**边界划死，才能保证每层的信噪比。**

### 3️⃣ 写入约束不同：各层有各层的规矩

三层不仅装的东西不同，**连「能怎么写」都不一样**：

```text
raw/    →  只读快照。git clone --depth 1 引入，git pull 更新。
           严禁在此编辑或添加派生内容。引用时用相对路径 ../raw/...

wiki/   →  最严格。frontmatter 必填（title/type/status/created/updated），
           kebab-case 命名，对比必须用 ✅/❌，决策必须用表格，
           代码块必须标语言，文档超 300 行要拆分。

areas/  →  结构固定（architecture/business/components/best-practices/conventions），
           遵循同一套 frontmatter 与内容规则，但落在各业务仓库内独立演进。
```

原始层动都不让你动，通用层管得最严，项目层在自己仓库里相对自由。**约束强度的差异，本身就是分层价值的体现**——越靠近「事实源」，越不许随意改写。

> 📎 单一事实来源（防漂移）：`wiki/` 引用 `raw/` 的证据时**只链接不复制**，源页才是真相。同理，项目特定内容沉到 `areas/`，绝不反向倒灌进 `wiki/`。一份事实只存一处，改的时候才不会顾此失彼。

## 三层是怎么联动的

分层不等于老死不相往来。它们之间有一条清晰的**信息流**：

```text
raw/（一手证据）
  │  读原文、做提炼
  ▼
wiki/（团队共识）  ←── 引用时只链接不复制，用 ../raw/... 相对路径
  │  通用经验下沉到具体项目
  ▼
areas/（项目落地）  ←── 项目里反复踩的通用坑，可回提炼成 wiki 共识
```

往下是「证据 → 共识 → 落地」的提炼链，往上是「项目经验反哺通用共识」的回流。但无论哪个方向，**都靠引用和提炼连接，绝不靠复制粘贴**。这就是「互不强绑」的真正含义:可以互相引用,但谁也不依赖谁的内部实现而存活。

---

## 小结

三层模型说穿了就一件事:**把「证据」「共识」「落地」三种性质完全不同的知识,按职责拆开存放。**

- `raw/` 是档案库房,只存一手证据,只读不改,需要时供溯源
- `wiki/` 是公共藏书,沉淀与业务解耦的团队共识,写入约束最严
- `areas/` 是项目专柜,寄居在各业务仓库,记录这个项目特有的架构、业务和踩坑

它们职责严格分离、互不强绑:删一层不伤另一层,改一层不动另一层,层间只靠引用和提炼连接。记住这张骨架,后面所有的技能和命令,你都能立刻定位到它在哪一层、解决哪类问题。
