# 知识库写入规范 wiki-schema

## 本篇你能学到

- wiki 写入规范的六条硬规则：frontmatter、kebab-case 命名、`_index.md + references/` 目录结构、✅/❌ 对比、决策必用表格、代码块必标语言
- 为什么强制用 ✅/❌ 而非「好/坏」：AI 需要离散、无歧义的信号，自然语言中「好」「坏」的语义边界模糊，会让 AI 无法确定该学哪个结论
- 不守规范会给 AI 检索带来什么麻烦，以及触发文档拆分的量化阈值判断标准

---

## 知识库也需要「代码规范」

写代码时，大家习惯了 ESLint、Prettier 来统一风格。但写知识库的时候，很多团队的态度是「随便，能看懂就行」。

这个「随便」，在只有人读的时候还能凑合。一旦 AI 要读、要检索、要基于知识库生成答案，问题就暴露了。

我们在 `frontend-knowledge` 仓库里把这套规范沉淀成了 CLAUDE.md 里的「写入约束」，每一条都是踩过坑以后补上去的。下面逐条拆开讲。

---

## 📋 Frontmatter：必填字段不能少

每个 `wiki/` 下的 `.md` 文件，开头的 frontmatter 必须包含这五个字段：

```yaml
---
title: 鉴权流程
type: guide
status: stable
created: 2026-03-10
updated: 2026-05-20
---
```

`type` 的合法值：`convention` / `guide` / `reference` / `decision` / `pattern` / `index` / `rule`。

有一个特殊规则：**`type: rule` 的文档还需要额外带 `impact` 字段**，比如：

```yaml
---
title: 禁止直接操作 DOM
type: rule
impact: high
status: stable
created: 2026-04-01
updated: 2026-05-15
---
```

**为什么要这些字段？**

AI 检索知识库时，第一步往往是过滤文档类型——「找决策类文档」和「找规范类文档」对应的阅读策略是不同的。没有 `type`，AI 就得全文读完才能判断这是不是它要找的内容，白白消耗上下文窗口。

`status` 字段让 AI 知道这条内容是否稳定可信。`draft` 状态的文档，AI 在引用时应该保守一些；`stable` 的内容可以直接作为结论输出。如果没有这个字段，AI 会把一篇还在草稿阶段的内容当成团队共识——这会产生错误的引导。

`created` 和 `updated` 则帮助 AI 判断时效性。两个月没更新的「最新实践」，AI 应该提示用户核实，而不是照单全收。

> 不带 frontmatter 的文档，相当于给 AI 递了一份没有目录、没有日期、不知道作者的 Word 文档。它能读，但很痛苦。

## 📁 文件命名：kebab-case + 两个保留名

文件名一律 kebab-case：

| ✅ | ❌ |
|---|---|
| `auth-flow.md` | `AuthFlow.md` |
| `react-query-setup.md` | `reactQuerySetup.md` |
| `vite-config.md` | `vite_config.md` |

两个**保留名**有特殊含义，不能随便用于其他用途：

- `_index.md`：目录的导航入口，只做路由，不承载实质内容
- `hot.md`：会话热缓存，存放当前焦点、关键决策、快速链接

如果你把自己的内容写成了一个叫 `_index.md` 的文件，AI 在渐进式阅读时会把它当成目录页跳过，里面的实质内容就被漏掉了。这种 bug 排查起来非常隐蔽。

---

## 🗂 目录结构：`_index.md + references/` 模式

只要一个目录下有多个子文件，就必须走这个结构：

```text
conventions/
├── _index.md          # 导航表格，列出下面所有文件的入口
└── references/
    ├── naming-files.md
    ├── code-review.md
    └── testing.md
```

**不允许**在目录下散落 `.md` 文件，也不允许直接在根目录平铺内容文件。

这个模式的本质是「渐进式披露」：AI 读 `_index.md` 就能拿到导航表，知道要去哪里找什么，不需要把整个目录的文件全读一遍。当知识库规模增长到几十个文件时，这个结构的价值才真正体现出来。

反例：我们早期有一段时间直接在 `wiki/` 根目录下建了十几个 `.md` 文件，没有任何分组。AI 检索「命名规范」时，需要逐个打开文件才能找到目标，最终的回答往往只命中了部分内容，漏掉了分散在其他文件里的补充说明。

## ✅/❌ 对比：为什么 AI 需要明确信号

这是整套规范里我认为最值得单独解释的一条。

规范要求：**对比必须用 ✅/❌，不用「好/坏」「正确/错误」等文字表述。**

很多人第一反应是：「这不就是格式风格问题吗？」不是的，这是一个**语义信号**问题。

自然语言里，「好的做法」「推荐方式」「建议用」「更好的选择」——这些表述对人类读者够用，因为我们有上下文推断能力。但对 AI 来说，它在解析你的文档时，需要识别「哪个是推荐的，哪个是要避免的」。

「好」和「坏」的语义边界模糊：

> 用 `any` 是坏的做法，但在某些场景下是可接受的权宜之计。

这句话里，「坏」和「可接受」同时出现，AI 就不知道该学哪个结论。

而 ✅/❌ 是**离散的、无歧义的信号**：

```text
✅ 用 unknown 替代 any，收窄类型后再操作
❌ 直接用 any 绕过类型检查
```

这两行，AI 可以直接识别成「推荐模式」和「反模式」，无需上下文推断。在知识库规模大了之后，AI 可以批量索引所有 ✅ 条目，生成一份团队推荐实践摘要；也可以在代码 review 时，把 ❌ 模式当作检测规则来匹配。

这是**写给 AI 读的格式**，而不只是写给人读的格式。

---

## 📊 决策/对比必须用表格，代码块必须标语言

对比信息用表格，原因和 ✅/❌ 类似：结构化数据比散文更容易被解析。

```markdown
| 方案 | 适用场景 | 缺点 |
|---|---|---|
| ✅ Zustand | 简单全局状态 | 无 devtools 原生支持 |
| ❌ Redux | 小项目 | 模板代码过多 |
```

代码块必须标注语言类型：

````markdown
```
// ✅ 用泛型约束类型
function getFirst<T>(arr: T[]): T | undefined {
  return arr[0]
}
```text
```

不标语言的代码块，AI 需要猜测这是 TypeScript、JavaScript 还是伪代码，会影响它对代码语义的理解。尤其是团队内 TS 和 JS 混用的场景，一个没有语言标注的代码块，AI 可能用错误的类型推断逻辑来解读它。

## ✂️ 拆分阈值：文档什么时候该拆

触发拆分的三个条件，满足任意一个就该行动：

| 触发条件 | 阈值 |
|---|---|
| 文档总行数 | > 300 行 |
| 同一 H2 下的条目数 | > 15 条 |
| 文档内代码块数量 | > 20 个 |

拆分的方式是：原文件降级为 `_index.md`（只保留导航表格），具体内容按 H2 拆到 `references/` 下的独立文件。

这个阈值不是拍脑袋的。AI 的上下文窗口是有限的，一次能「完整理解」的文档长度有上限。超过 300 行的文档，AI 往往只能命中前半部分或后半部分，无法把整篇内容综合起来回答问题。而且长文档意味着多个主题混在一起，检索「命名规范」的时候不应该把「测试规范」也一并加载进来。

## 💥 反例：一个不守规范的页面会怎样

来看一个真实的「问题页面」长什么样（简化版）：

```markdown
# 前端规范

这里是我们团队的前端规范，大家按照这个来写代码。

## 命名

组件用大写开头，文件名用小驼峰，hooks 用 use 开头，其他的随意。
好的例子：UserCard.tsx，坏的例子：usercard.tsx

## 状态管理

我们用 Zustand，不要用 Redux，太麻烦了。以后新项目都统一用 Zustand。

    const useStore = create((set) => ({
      count: 0,
      increment: () => set((state) => ({ count: state.count + 1 })),
    }))

这个代码可以直接用。
```

这个页面有以下问题：

1. **无 frontmatter**：AI 不知道这是什么类型的文档，也不知道最后更新时间。「以后新项目都统一用 Zustand」——这是什么时候写的？还有效吗？
2. **用「好的例子/坏的例子」**：AI 需要把「好」映射到「推荐」、把「坏」映射到「避免」，语义不够直接
3. **代码块没标语言**：这段 Zustand 代码是 JS 还是 TS？有没有类型定义？AI 无法确定
4. **散文混杂规则**：「太麻烦了」「随意」这类主观表述，AI 不知道该不该学进去

当 AI 基于这个页面回答「我们团队用什么状态管理方案」时，它能给出「Zustand」，但无法判断这条规范是否还有效，也无法告诉你具体的使用约定和注意事项，因为这些都没有结构化地写出来。

改造后的版本应该是：有 frontmatter、有 ✅/❌ 对比表格、代码块标 typescript、条目列表清晰分组——AI 可以直接把它索引成团队技术选型决策的权威来源。

## 章节标注层级注释

最后一个细节：文档内的章节需要用注释标注阅读优先级：

```markdown
## 核心规则 <!-- 必读 -->

## 进阶用法 <!-- 按需 -->

## 特殊场景处理 <!-- 专项 -->
```

这让 AI 在上下文有限时，知道优先读哪些章节。「必读」的内容会被优先加载进上下文，「专项」的内容只在相关问题被问到时才读取。

**反例对比：错误的层级注释写法**

| ❌ 错误写法 | 问题所在 | ✅ 正确写法 |
|---|---|---|
| `## 命名规范（重要）` | 用中文括号，AI 无法识别为结构化优先级标记 | `## 命名规范 <!-- 必读 -->` |
| `## 特殊场景 <!-- 可选 -->` | `可选` 不在合法值集合内，语义与`按需`重叠但不统一 | `## 特殊场景 <!-- 专项 -->` |
| `## 进阶用法 <!--按需-->` | 缺少空格，部分解析器无法识别 | `## 进阶用法 <!-- 按需 -->` |
| 全篇章节不加注释 | AI 无从判断优先级，上下文受限时随机裁剪，可能跳过核心规则 | 每个 H2 章节都标注 |

层级注释只有三个合法值：`必读` / `按需` / `专项`。团队内必须统一，不能各自造词。AI 在处理多文档检索时，会把所有 `<!-- 必读 -->` 章节优先装入上下文，自由发挥的写法会使这套机制完全失效。

## 📋 Frontmatter 字段错误写法对比

frontmatter 是 AI 过滤文档最依赖的元数据入口，字段写错比不写更危险——AI 会基于错误的元数据做出错误的判断。

| 字段 | ❌ 错误写法 | 问题所在 | ✅ 正确写法 |
|---|---|---|---|
| `type` | `type: 指南` | 中文值不在合法枚举内，AI 类型过滤时无法命中 | `type: guide` |
| `type` | `type: Guide` | 大写开头，枚举区分大小写，匹配失败 | `type: guide` |
| `status` | `status: 稳定` | 同上，必须用英文枚举值 | `status: stable` |
| `status` | `status: ok` | `ok` 不在合法值内，AI 会按无字段处理 | `status: stable` |
| `created` | `created: 2026/03/10` | 斜杠格式，部分解析器不认，应用连字符 | `created: 2026-03-10` |
| `updated` | `updated: 今天` | 自然语言无法排序，AI 无法判断时效性 | `updated: 2026-05-20` |
| `impact`（rule 类型缺失）| 无 `impact` 字段 | `type: rule` 文档缺少 `impact`，AI 无法评估规范的影响范围 | `impact: high` |

`type` 的合法值只有七个：`convention` / `guide` / `reference` / `decision` / `pattern` / `index` / `rule`。任何不在列表内的值，等同于没有这个字段。`status` 的合法值是：`draft` / `review` / `stable` / `deprecated`。

一个 frontmatter 写成这样：

```yaml
---
title: 鉴权流程
type: 指南
status: ok
created: 2026/3/10
---
```

AI 读取这份文档时，`type` 和 `status` 过滤均失效，`created` 可能解析报错——实际上等同于一个完全没有元数据的裸文档，和那些「随便写」的文档没有任何区别。

---

## 小结

wiki-schema 的本质不是「整洁」，而是**让 AI 能够可靠地读懂你的知识库**。

frontmatter 给 AI 提供元数据过滤能力；kebab-case 和保留名避免检索冲突；`_index.md + references/` 结构支持渐进式阅读；✅/❌ 是 AI 能识别的离散信号；表格和语言标注让结构化内容可解析；拆分阈值控制单文档的认知负担。

每一条规范背后都有「不这样做会怎样」的代价。在知识库只有几十个文件的时候，代价不明显。等到几百个文件、十几个人共同维护、AI 每天被问几十个问题的时候，这些规范的价值才真正显现出来。

从第一个文件开始就守规范，比等出了问题再回来修要省力得多。
