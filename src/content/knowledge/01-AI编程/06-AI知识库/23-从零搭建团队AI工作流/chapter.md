# 从零搭建团队 AI 工作流

> **本篇你能学到**
> - 一个可执行的三阶段落地路线图：第一周、第一个月、三个月后的里程碑与验收标准
> - 飞轮效应如何形成：知识越沉淀，AI 越好用，越好用越愿意沉淀
> - 本书从第 01 篇痛点到此的闭环：AI 终于「懂你」的团队长什么样

从 01 篇到这里，我们走了一整圈。开篇说的那个痛——换了 Zustand 但 AI 还在给你 Redux、团队黑话 AI 一个字都不懂、每次对话都要从头解释一遍背景——这篇是结束，也是真正意义上的开始。

下面是我见过落地成功的团队，实际走过的路线图。不是理想化蓝图，是可以直接抄作业的执行清单。

## 🗓️ 第一周：跑通最小闭环

第一周的目标只有一个：**让团队里至少一个人用 `wiki-query` 问出来了一个有用的答案**。别想着一步到位，先跑通这条最短路径。

### 具体动作

**Day 1-2：安装插件、初始化通用 wiki 骨架**

```bash
# 1. 在通用知识库仓库（或新建一个）执行，生成 wiki/ 骨架
# 在 Claude Code 里触发：
# 「初始化知识库」

# 2. 设置环境变量，让所有 skill 能找到知识库根目录
export FRONTEND_KNOWLEDGE_WIKI_ROOT=/path/to/your/frontend-knowledge
# 建议写进团队的 .zshrc 模板或 onboarding 文档
```

`areas-init` 不需要外部环境变量，直接在业务仓库里跑就行。但通用 wiki 需要这个环境变量——这是第一周最容易卡住的地方，先把它配好。

**Day 3：把团队核心约定写进去**

挑 3-5 条最影响日常的团队约定，用 `wiki-save` 沉淀进去。选哪些？就选那些你每次让 AI 生成代码都得手动纠正的东西。比如：

- 数据请求统一走 `useRequest`，不用裸 `fetch`
- 状态管理用 Zustand，不用 Redux
- 组件库用内部的 `@xxx/ui`，不用 antd 直接引

不用多，三五条「被遗忘成本最高」的约定就够了。在 Claude Code 里说：「把刚才这个决策沉淀到知识库」，`wiki-save` 会帮你走完整个流程。

**Day 4-5：跑通一次 `wiki-query`**

知识库有内容后，找一个你们最常问 AI 的问题，用 `wiki-query` 试一次：

```text
# 在 Claude Code 里说：
「查一下我们的数据请求规范」
「按知识库，怎么做状态管理」
```

如果答案能命中刚才沉淀的约定，并在末尾输出了引用来源表——第一周的目标达成了。

### ✅ 第一周验收标准

| 验收项 | 怎么算通过 |
|--------|-----------|
| 插件安装 & 环境变量 | `wiki-query` 能正常启动，不报环境变量缺失 |
| 通用 wiki 骨架 | `wiki/` 目录存在，有至少一个 `_index.md` |
| 核心约定写入 | 至少 3 条团队约定已沉淀，有 frontmatter |
| 跑通一次查询 | `wiki-query` 返回了命中知识库的答案，有引用来源 |

## 📅 第一个月：建立沉淀习惯

跑通了最小闭环之后，接下来要做的事是让这个体系在各业务仓库里生根，然后把「沉淀」变成团队的日常习惯而不是运动式冲刺。

### 各业务仓库用 `areas-init` 建项目知识库

优先级：挑团队最复杂、新人最容易迷失的那个仓库先做。

```bash
# 切到业务仓库根目录，在 Claude Code 里触发：
# 「初始化知识库」
# areas-init 会自动探索 package.json、扫项目结构、生成 knowledge/ 骨架
```

生成完之后，`knowledge/areas/` 下会有 5 个子域：`architecture`、`business`、`components`、`best-practices`、`conventions`。不用全部填满，先把「新人入职第一周最需要知道的东西」填到 `architecture` 和 `conventions` 里。

### 养成 `wiki-save` / `wiki-ingest` 的沉淀习惯

这是第一个月最关键的事，也是最容易被跳过的事。

沉淀的触发时机就两个：

**1. 对话结束时**
每次和 AI 的对话产出了有价值的决策或方案，在关闭之前说一句「把这次讨论沉淀到知识库」。`wiki-save` 会帮你提炼对话里的结论，写成规范的知识页，不保留对话痕迹。

**2. 有外部素材时**
PRD 来了、官方文档有了新的迁移指南、某次故障复盘出了结论——这类有文件依据的素材走 `wiki-ingest`：

```text
# 在 Claude Code 里说：
「整理 raw/react-19-migration.md 这份文档，归档到知识库」
「把这次复盘的结论沉淀到 areas」
```

> 别等「内容完善了再存」。哪怕是 draft 状态的半成品也要存，因为「存进去」和「没存」之间的差距，远大于「完善」和「半成品」之间的差距。

### 定期 `wiki-lint` 巡检

每两周跑一次巡检，养成习惯：

```text
# 在 Claude Code 里说：
「巡检知识库」
```

`wiki-lint` 会输出一份分级报告，CRITICAL 必须修、WARNING 建议修、SUGGESTION 按需处理。重点关注：

- **死链**：导航表里有但文件不存在，影响 AI 检索准确性
- **孤立页面**：文件存在但未在任何 `_index.md` 登记，AI 永远找不到它
- **developing 停滞**：状态标了 developing 但超过 90 天没更新，应该要么完善要么降级为 draft

### ✅ 第一个月验收标准

| 验收项 | 怎么算通过 |
|--------|-----------|
| 业务仓库覆盖 | 至少 1 个核心业务仓库有 `knowledge/` 目录 |
| 知识页数量 | 团队累计沉淀 15 页以上（wiki + areas 合计） |
| 沉淀来源多样 | wiki-save 和 wiki-ingest 都有人用过 |
| 巡检通过 | wiki-lint 跑完，CRITICAL 问题清零 |
| 日常触达 | 团队成员自发用 `wiki-query` 查询过至少一次 |

## 🚀 三个月后：知识库成为事实标准

如果第一周和第一个月都扎实执行了，三个月后你会看到一个明显的质变：**团队不再需要提醒大家「用知识库」，因为不用的代价已经自己显现出来了。**

### 新人靠知识库快速上手

三个月的沉淀之后，`knowledge/areas/architecture/` 里已经有了项目的整体设计、关键技术决策、和「为什么这么做而不是那么做」的来龙去脉。`conventions/` 里有代码规范、命名约定、Review 时最常被打回来的那些点。

新人入职，不用再拉着老人口口相传，直接让 AI 帮他查：

```text
「根据知识库，这个项目的鉴权方案是怎么做的」
「按约定，数据请求应该怎么写」
```

老人对新人最值钱的输出，从「解释背景」变成了「解释为什么」——因为 what 和 how 已经在知识库里了。

半年后，一个新人入职第三天就能独立完成第一个需求的 PR，Review 时被打回的低级错误（「这里要用 useRequest」「状态不要放 Redux」）几乎消失——不是他/她特别聪明，是知识库里有足够多的先例和约定，AI 在生成代码时已经自动对齐了团队口味。带教老人第一次感受到：新人上手这件事，不再是「一对一传帮带」，而是「知识库 + AI 兜底，老人只做答疑」。

### AI 输出质量的肉眼可见提升

这是最直接的回报。三个月前你让 AI 加个功能，它给你 Redux；三个月后，因为 `wiki-query` 先命中了技术选型页面，它直接给你 Zustand 的写法，代码能过 Review 的概率大幅提升。

不是 AI 变聪明了，是它终于「懂你」了。这正是 01 篇说的那件事。

### ✅ 三个月验收标准

| 验收项 | 怎么算通过 |
|--------|-----------|
| 新人入职 | 新成员可以靠知识库 + AI 自助解决 80% 的入门问题 |
| 日常使用 | 每周有新内容沉淀，不需要专门提醒 |
| AI 对齐 | AI 生成代码符合团队约定的比例明显高于三个月前 |
| 知识规模 | 全库 50 页以上，wiki-lint 健康度 ≥ 90% |
| 体系覆盖 | 核心业务仓库（3 个以上）都有 `knowledge/` |

## 🔄 飞轮效应：为什么这件事值得持续投入

我想在这里说一件很多落地文章会跳过的事：**为什么这个体系会自我增强，而不是某个人走了之后就慢慢烂掉。**

原因是飞轮。

```text
知识越沉淀
    ↓
AI 输出越准确
    ↓
用 AI 的效率越高
    ↓
越愿意用 AI
    ↓
越愿意把结论沉淀回知识库
    ↓
知识越沉淀（回到起点）
```

关键是**第一圈**。飞轮启动需要外力推——这就是第一周那个最小闭环的意义。一旦有人用 `wiki-query` 查到了一个准确答案，他/她就会记住「这个东西真的有用」，下次讨论完自然会想「要不顺手 save 一下」。

反过来也成立：如果知识库里什么都没有，`wiki-query` 永远 fallback 到 AI 训练知识，和没有知识库没区别，自然没人愿意维护。这就是为什么第一周的「先写 3-5 条核心约定进去」那么重要——它是飞轮的第一圈。

> 知识库的竞争力不来自某个工具有多强，而来自沉淀了多久。沉淀时间越长，知识密度越高，AI 协作的护城河就越宽。这是一个后发劣势极强的资产——越晚开始，追赶成本越高。

## 回到起点

01 篇说：AI 很强，但对你的项目天生失明。

这本小册走了 23 篇，从体系架构到三层模型，从插件安装到 skill 定制，从通用 wiki 到项目 areas，说的都是同一件事：**怎么把你团队的私有现场，一页一页地喂给 AI，让它终于「懂你」。**

这不是一个工具的问题，是一套工作方式的问题。工具会迭代，skill 可以定制，但「把团队知识沉淀成可检索结构」这个方向，在 AI 协作这个赛道上，不会过时。

现在轮到你了。第一步很简单：打开你最复杂的那个业务仓库，跑一次 `areas-init`。

## 小结

三个阶段，每个阶段有具体动作和验收标准：

- **第一周**：装好插件、配好环境变量、写入 3-5 条核心约定、跑通一次 `wiki-query`
- **第一个月**：各业务仓库跑 `areas-init`、养成 `wiki-save` / `wiki-ingest` 的沉淀习惯、定期 `wiki-lint` 巡检
- **三个月后**：知识库成为事实标准，新人靠它自助上手，AI 输出符合团队约定的比例大幅提升

飞轮的核心逻辑：知识越沉淀，AI 越好用，越好用越愿意沉淀。第一圈最难，只要跑起来，后面靠惯性。

01 篇问的那个问题——AI 怎么才能懂你的项目——到这里，你已经有了完整的答案。
