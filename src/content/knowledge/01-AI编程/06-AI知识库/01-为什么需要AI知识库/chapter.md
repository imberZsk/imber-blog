# 为什么需要 AI 知识库

> **本篇你能学到**
> - 为什么「装了 Claude Code」≠「AI 懂你的项目」
> - 没有知识库时，AI 会犯的 4 类具体错误（不是泛泛而谈，是你天天在踩的坑）
> - 知识库到底沉淀的是什么，以及它和「往对话框里粘一堆背景」的本质区别

先说个让我自己挺扎心的场景。

我所在的团队半年前把状态管理从 Redux 切到了 Zustand，技术选型文档写得明明白白。结果上个月我让 Claude 帮我加一个全局登录态，它张口就给我 `createStore` + `combineReducers` + 一坨 `mapStateToProps`。代码本身没毛病，跑也能跑，但它给的是我们团队三年前就抛弃的写法。

我当时的第一反应不是「AI 真笨」，而是——**它怎么可能知道？** 它又没参加过我们那场吵了两小时的选型会。

这就是这本小册想先讲清楚的事：AI 很强，但它对你的项目一无所知。强和「懂你」是两件完全不同的事。

## 🤔 先破一个误区：AI 不是不知道，是「不知道你」

很多人对 Claude Code 的期待是：它读过全世界的代码，所以它什么都懂。

前半句对，后半句错。它确实读过海量公开代码，所以它知道 React 怎么写、Zustand 的 API 长什么样、qiankun 怎么接微应用。这些是**公共知识**，AI 自带，你不需要为此建任何东西。

但它不知道的是这一类东西：

| ✅ 它知道的（公共知识）        | ❌ 它不知道的（你的现场）                          |
| --------------------------- | ----------------------------------------------- |
| Zustand 和 Redux 的 API     | 你们团队为什么选了 Zustand 而不是 Redux         |
| `useEffect` 的依赖项规则     | 你们约定数据请求必须走 `useRequest` 而不是裸 `fetch` |
| 微前端的几种主流方案        | 你们线上跑的是 qiankun，主应用注册逻辑在哪个文件 |
| 「鉴权」这个词的通用含义     | 你们说的「灰度白名单」具体指哪套配置             |

右边这一列，才是真正决定「AI 生成的代码能不能直接用」的东西。而它,默认全是空白。

> AI 知识库要解决的，从来不是「让 AI 更聪明」，而是「把你团队的私有现场喂给它」。

## ❌ 没有知识库，AI 会犯的 4 类错

这部分我尽量讲具体的,因为泛泛说「AI 不了解项目」没用,你得能对上号才行。

**第一类：用了你早就废弃的技术选型。**

就是开头那个例子。AI 倾向于给「最主流、最常见」的写法,而主流不等于你团队的当下选择。它会给你 class 组件、会给你 Redux、会给你 Moment.js——这些在公开语料里出现频率极高,但你的团队可能两年前就换成了函数组件、Zustand、dayjs。每次都要你手动纠正一遍。

**第二类：代码能跑,但不符合团队约定。**

这是最隐蔽的一类。AI 给的代码逻辑完全正确,但:

```tsx
// ❌ AI 默认给的:裸 fetch + 自己处理 loading
function UserList() {
  const [data, setData] = useState([]);
  const [loading, setLoading] = useState(false);
  useEffect(() => {
    setLoading(true);
    fetch("/api/users")
      .then((r) => r.json())
      .then(setData)
      .finally(() => setLoading(false));
  }, []);
  // ...
}
```

```tsx
// ✅ 团队约定:统一走封装好的 useRequest,自动处理 loading / 错误 / 缓存
function UserList() {
  const { data, loading } = useRequest(getUserList);
  // loading 态、错误兜底、重试都由 hook 统一接管,组件里不重复造
}
```

两段代码都「对」,但下面那段才是能过 Code Review 的那段。AI 不知道你们有 `useRequest` 这个内部封装,自然不会用。

**第三类:对业务黑话一无所知。**

每个团队都有自己的「黑话」。你说「帮我在车务模块加个维保字典」,AI 完全不知道「车务」是哪块业务、「字典」在你们这指的是后端枚举映射表还是前端的 i18n 文案。它只能按字面意思猜,猜错的概率极高。这些词在任何公开语料里都查不到,因为它们是你们公司内部造的。

**第四类:每次对话都得从头解释一遍。**

这是最耗人的。今天你花十分钟跟 AI 讲清楚「我们用 pnpm monorepo、主应用叫 portal、组件库是内部的 @xxx/ui」,明天开一个新对话,这些上下文全部清零,你得再讲一遍。一周下来,你光在「重新介绍项目」上花的时间,可能比写代码还多。

## 💡 那「把背景粘进对话框」不行吗

会有人说:那我每次把项目背景复制一大段粘进去不就行了?

短期能用,长期是灾难。我们对比一下:

| ❌ 临时粘贴背景                          | ✅ 沉淀成知识库                              |
| ---------------------------------------- | ------------------------------------------- |
| 每次对话重新粘,时间成本永远存在          | 写一次,所有对话、所有人复用                 |
| 你粘的版本和同事粘的版本不一样,各说各话  | 单一事实来源,全团队对齐                     |
| 选型变了,你得记得去更新那段「祖传话术」  | 改一个文件,下次检索自动是新的               |
| 粘太多撑爆上下文,粘太少 AI 又抓不到重点  | 渐进式披露,按需检索,只喂相关的那几页        |

最后一条是关键。知识库不是「把所有背景一股脑塞给 AI」,而是建一套能**按需检索**的结构。比如团队这套通用知识库,就是分了三层来管:

- **原始层**(`raw/`):React/Vue 官方文档的快照,只存证据不下结论
- **通用层**(`wiki/`):与具体业务解耦的团队约定、技术选型、工程配置
- **项目层**(各业务仓库的 `knowledge/`):项目架构、业务踩坑、那些「黑话」

> 三层互不强绑,职责严格分离。AI 回答前按 `hot.md → _index.md → 具体页面` 的顺序读,任意一层拿到足够信息就停——这样既不会漏,也不会把上下文撑爆。

这套结构怎么落地、每一层放什么、怎么让 AI 自动检索,是后面几章要展开的。这里你只需要记住一件事:**知识库的价值不在「存了多少」,而在「能不能在对的时机被喂给 AI」。**

## 小结

AI 强,但它对你的项目天生失明。没有知识库时,它会给你废弃的技术选型、不符合约定的代码、读不懂的业务黑话,还逼着你每次对话从头解释一遍背景。

把背景临时粘进对话框只是止血,真正的解法是把团队的私有现场沉淀成一套**可检索、单一事实来源、全团队复用**的知识库。它不让 AI 更聪明,而是让 AI 终于「懂你」。
