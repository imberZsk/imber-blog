# 核心概念速查

> 📑 这一篇是工具书，不是故事会。前两篇讲清了「为什么要搭这套体系」和「它长什么样」，但真正动手时，你脑子里会冒出一堆名词：plugin 和 skill 啥区别？raw、wiki、areas 到底各管什么？status 写 draft 还是 developing？这一篇就把这些词一次性铺平，建好书签，随时回来翻。

## 本篇你能学到

- 分清 plugin / skill / agent / subagent 这几个容易混的角色
- 三层结构 raw / wiki / areas 及文件约定（frontmatter / _index.md / hot.md）的真实作用
- 三条设计原则速查：渐进式披露、单一事实来源、status 状态机

读法建议：第一遍通读混个脸熟，之后当字典用，Ctrl+F 搜词直接跳。

## 一、Claude Code 生态角色

这一组是最容易糊在一起的，因为它们是层层嵌套的关系。先记一句话：**Claude Code 是宿主，plugin 是安装包，skill 是包里的能力，agent 是干活的执行体。**

| 概念 | 一句话定义 | 什么时候会遇到它 |
| --- | --- | --- |
| **Claude Code** | Anthropic 官方的命令行 AI 编程环境，是整套体系运行的宿主 | 你在终端敲 `claude` 启动会话、用 `/` 调命令的时候 |
| **插件 plugin** | 一组 skill + 配置打包成的可安装单元，从插件市场装到 Claude Code 里 | 安装 `frontend-knowledge` 这个插件、`/plugin` 管理已装插件时 |
| **技能 Skill** | 一段写在 `SKILL.md` 里的结构化指令，定义「遇到某类意图时该怎么一步步做」 | 用 `/wiki-query` 查知识、说「整理到知识库」触发 `wiki-ingest` 时 |
| **Agent** | 执行任务的 AI 实体，能读写文件、跑命令、调 skill | 任何一次 Claude Code 会话本身就是一个 agent 在干活 |
| **subagent** | 主 agent 派生出去的子执行体，独立上下文，跑完把结果汇报回来 | 让 AI「并行读 50 个文件」「深度调研某主题」时它会自动 fan-out 出 subagent |

> 💡 plugin 和 skill 的关系，类比一下：plugin 像手机上的一个 App，skill 像 App 里的一个个功能页。你装的是 `frontend-knowledge`（一个 plugin），但实际用的是它内部的 `wiki-query`、`wiki-save` 这些 skill。

subagent 这个概念新手最容易忽略，但它是性能关键。主 agent 的上下文窗口是有限资源，与其自己串行读一堆文件把上下文塞爆，不如丢给 subagent 去读、只把结论拿回来。后面讲查询和巡检时你会反复见到它。

## 二、三层知识结构

这是整套体系的骨架，也是你每天都要打交道的部分。三层**互不强绑、职责严格分离**，记住每一层「能写什么、不能写什么」比记路径更重要。

| 层 | 路径 | 一句话定义 | 什么时候会遇到它 |
| --- | --- | --- | --- |
| **原始层 raw** | `raw/` | 一手来源的快照（官方 docs、RFC、PRD、会议纪要），只存证据不下结论 | 想引入 React 官方文档做依据、归档一份 PRD 原文时 |
| **通用层 wiki** | `wiki/` | 与业务解耦的团队通用前端知识（选型决策、编码约定、工具链配置） | 沉淀「为什么团队选 Zustand 不选 Redux」这类跨项目共识时 |
| **项目层 areas** | 各业务仓库的 `knowledge/areas/` | 项目落地知识（架构、业务、组件、约定、踩坑），不进通用库 | 在某个业务仓库里记录它的认证流程、业务域地图时 |

三层最关键的纪律，是这张「放 / 不放」对照表：

| 内容类型 | ✅ 放这里 | ❌ 不放这里 |
| --- | --- | --- |
| React/Vue 基础 API 用法 | 哪都不放（AI 已知，无增量） | wiki |
| 团队选型决策、编码约定 | `wiki/` | areas |
| 项目业务组件、业务踩坑 | 项目 `areas/` | `wiki/`（会污染通用库） |
| 官方文档原文快照 | `raw/`，引用时只链不抄 | `wiki/` 正文里手抄一遍 |

> ⚠️ 最常见的翻车点：把项目特定的业务知识写进了 `wiki/`。通用库一旦混进业务内容，就失去了「跨项目复用」的价值，别的项目读到一堆看不懂的业务名词。判断标准很简单——这条知识换个项目还成立吗？不成立就进 areas。

`raw/` 层还有个反直觉的约束：**只存证据，不下结论，也不在里面编辑派生内容**。它就是个证据柜，用 `git clone --depth 1` 拉进来、`git pull` 更新。要下结论、做提炼，是 `wiki-ingest` 把它加工成 wiki 页的事。

## 三、文件与目录约定

进了任意一层，你会反复见到这几个固定文件名。它们不是随便起的，每个都有明确职责。

| 概念 | 一句话定义 | 什么时候会遇到它 |
| --- | --- | --- |
| **frontmatter** | 每篇知识页开头的 YAML 元数据块，记录 title / type / status / 时间等 | 新建或修改任何 wiki/areas 页面时，开头必须有它 |
| **`_index.md`** | 每个目录的导航页，用表格路由到下级页面，是「按意图找路」的入口 | 进入任何含子文件的目录、AI 决定往哪读时 |
| **`hot.md`** | 会话热缓存，记当前焦点、关键决策、常见坑、快速链接 | 每次查询前 AI 第一个读的文件，命中就不用往深处翻了 |
| **`references/`** | 存放具体内容页的目录，所有详细文档都收纳在这里 | 一个主题被拆成多页、或单页超过拆分阈值时 |

frontmatter 的最小必填字段长这样，照抄即可：

```yaml
---
title: "认证流程"           # 与正文 H1 严格一致，不加副标题
description: "登录、Token 刷新与权限守卫的实现约定"  # 1-2 句，80 字内
type: architecture          # 等于文件所在的分区目录名
status: developing          # draft / developing / stable 三选一
created: 2026-06-09         # 首次创建日期，update 时保留不动
updated: 2026-06-09         # 任何改动都要刷新成当天
tags: [auth, token]         # 可选，全小写 kebab-case，2-5 个
---
```

> 📌 记两条铁律：`type` 永远等于文件所在的目录名（`_index.md` 一律是 `type: index`）；`updated` 改一个字都要刷新。这两条是 `wiki-lint` 巡检时最常揪出来的问题。

目录约定也有条硬规则：**任何含子文件的目录，必须走「`_index.md` + `references/`」模式，目录根下不许散落其他 `.md`**。也就是说，详细内容统统进 `references/`，目录根只留导航页。这样 AI 才能靠 `_index.md` 一层层往下找，而不是面对一堆平铺文件抓瞎。

文件命名统一 kebab-case（`auth-flow.md`），保留名只有两个：`_index.md` 和 `hot.md`。

## 四、三条设计原则

这一组是「为什么这么设计」的答案。理解了它们，你就能在没有明文规定的场景里自己做对决定。

| 概念 | 一句话定义 | 什么时候会遇到它 |
| --- | --- | --- |
| **渐进式披露** | 按 `hot.md → _index.md → 分区 _index.md → 具体页` 顺序读，拿到够用信息就停 | AI 回答问题时的标准读取路径，每次查询都在用 |
| **单一事实来源** | 同一知识只有一个权威出处，别处只链接不复制 | 想在两个页面写同一段内容、或发现内容对不上时 |
| **status 状态** | 标记一篇知识的成熟度：`draft` / `developing` / `stable` | 新建页面填 frontmatter、或判断某页可不可信时 |

渐进式披露解决的是「上下文不能无限读」的问题。完整路径：

```text
1. wiki/hot.md          ← 会话热缓存，时间性薄缓存，可能命中也可能为空
2. wiki/_index.md       ← 按意图路由，表格形式快速定位分区
3. 分区/_index.md        ← 分组导航
4. references/<topic>.md ← 最终的具体内容页
```

任意一层拿到足够信息就停下，**不多读一个文件**。这就是为什么 `hot.md` 要放最热的内容——大部分高频问题在第一步就该被命中。

单一事实来源防的是「内容漂移」。举个具体场景：`conventions/` 里要提到某个工程约定，而详细内容在 `engineering/`，这时只写一个链接指过去，**不把那段话复制一遍**。一旦复制，两处迟早改得对不上，读者不知道信哪个。

status 三态的判断标准（这是 areas-init 内置的强制规则，照着判不会错）：

| status | 判断标准 | ✅ 典型场景 | ❌ 误用 |
| --- | --- | --- | --- |
| `draft` | < 30% 实质内容，只有章节框架 | 含「待补充 / TODO / 暂无」占位文字、空表格 | 内容已完整却还挂着 draft |
| `developing` | 30-70% 实质内容，有框架待补充 | 从代码提取了部分真实信息，关键逻辑待人工梳理 | 只有空模板却标 developing |
| `stable` | > 70% 实质内容，可作权威参考 | 内容完整、无占位符、可直接引用 | 还有 TODO 残留却标 stable |

> 💡 一条速记规则：文档里只要还出现「待补充 / TODO / 暂无」，无论写了多少，都必须降级为 `draft`。status 不是写心情，是给读者的可信度信号。

## 五、技能触发速查

知道有哪些 skill，更要知道「该说什么话能触发对应的 skill」。这套体系的 skill 都靠自然语言里的触发词命中，下面这张表直接对照你的意图去用。

| 技能 | 一句话定义 | 什么时候会遇到它（触发场景） |
| --- | --- | --- |
| **wiki** | 兜底调度层，意图模糊时识别意图再路由到具体子技能 | 你说的话不明确命中某个子技能、需要跨技能编排时 |
| **wiki-query** | 从知识库查询并回答，按渐进式披露读取后内联引用来源 | 说「查一下 / 解释一下 / 在知识库里找 / 按约定」时 |
| **wiki-ingest** | 把**外部素材**（raw、PRD、会议纪要、文档快照）沉淀成规范知识页 | 说「整理这份文档 / 归档这份 PRD / 整理 raw」时 |
| **wiki-save** | 把**当前会话**里的结论、决策、踩坑整理成知识页，一次只存一页 | 说「保存这次讨论 / 沉淀刚才的分析 / 记录这个决策」时 |
| **wiki-lint** | 知识库健康检查：结构合规、死链、孤页、frontmatter 缺失、导航同步 | 说「巡检知识库 / 清理 wiki / 做健康检查」时 |
| **areas-init** | 在业务仓库根目录生成 `knowledge/` 项目级骨架，调用即生成不依赖外部环境 | 在某个前端项目里说「初始化知识库 / 搭知识库结构」时 |

> ⚠️ 注意书里前面提到的「五技能」指 wiki 那一组（wiki / wiki-query / wiki-ingest / wiki-save / wiki-lint），它们都作用在通用知识库；而 `areas-init` 是独立的，作用在**业务仓库**里，用来开项目级知识库的局，别在通用库里调它。

ingest 和 save 是最容易混的一对，记住分水岭就一条：**有没有现成的文件/素材**。

| 场景 | ✅ 用哪个 | ❌ 别用 |
| --- | --- | --- |
| 手上有 raw 资料 / PRD 文件 / 文档快照 | `wiki-ingest` | wiki-save |
| 想沉淀刚才对话里讨论出的结论 | `wiki-save` | wiki-ingest |
| 不确定该用哪个、意图很模糊 | `wiki`（兜底调度） | 自己手工改文件 |

最后提一句调用习惯：表达意图时**优先靠触发词命中 skill，而不是手工读写文件**。skill 内部封装了渐进式披露顺序、frontmatter 规范、导航同步这些细节，手工操作很容易漏掉一环——比如新建了页面却忘了在父 `_index.md` 登记，下次就成了孤页。

## 小结

这一篇没有故事线，就是一本随身字典。真正要你记住的其实是三组心智模型：**角色上**，plugin 装能力、skill 是能力、agent/subagent 干活；**结构上**，raw 存证据、wiki 存通用、areas 存项目，三层别串味；**原则上**，渐进式披露管「读多少」、单一事实来源管「写在哪」、status 管「信不信」。

文件约定（frontmatter / `_index.md` / `hot.md` / `references/`）和技能触发词，遇到具体操作再回来查表就行。从下一章开始我们就动真格——从零搭起通用知识库，那时这张速查表会成为你最常翻的一页。
