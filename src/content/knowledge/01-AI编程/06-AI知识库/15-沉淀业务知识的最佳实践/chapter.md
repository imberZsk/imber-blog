# 沉淀业务知识的最佳实践

> **本篇你能学到**
>
> - 一套立刻上手的判断标准：什么值得沉淀，什么纯属浪费时间
> - 用真实场景拆解：表格分页踩坑、被反复问到的状态流转，该不该记、记去哪
> - 三个黄金沉淀时机和「一页一主题」原则，以及 wiki-save/wiki-ingest 在 areas 层的用法差异

知识库写不好，八成不是因为不会写，而是因为不知道「什么不该写」。

我见过太多团队的知识库最后变成垃圾场：今天存一个 console.log 调试记录，明天存一段「这个接口报 500 了我重启就好了」，三个月后没人敢点开。真正有价值的那几页业务流转图，淹没在一堆一次性内容里。

所以这篇不讲怎么写得漂亮，先讲清楚一件事：**沉淀是有成本的，每一页都要为它的存在付租金。** 写的时候花十分钟，但它会占据后来每一个搜索它、读到它、需要判断它是否过期的人的注意力。值不值，得算账。

## 先立判断标准：这页知识的「保质期」有多长

判断一条知识该不该沉淀，我只问一个问题：

> **三个月后，还会有人需要它，并且那时它依然成立吗？**

这一个问题能筛掉八成噪音。它同时考了两个维度——「会不会被再次需要」和「会不会过期」。两个都过关才值得写。

把它展开成一张表：

| 维度 | ✅ 值得沉淀 | ❌ 不值得沉淀 |
| --- | --- | --- |
| 复用频率 | 会被反复问到 / 反复踩到 | 一次性的、问完就忘 |
| 获取成本 | 不读半天代码 / 不问人就搞不清 | 一查代码、一看接口文档就知道 |
| 稳定性 | 业务规则、架构决策，半年内不变 | 临时 workaround、马上要重构的方案 |
| 隐性程度 | 藏在脑子里、口口相传的经验 | 已经写在 README / 注释里的 |
| 因果价值 | 解释了「为什么这么设计」 | 只描述了「现在是什么样」 |

注意最后一行。**「为什么」几乎永远值得沉淀，「是什么」大多数时候不值得。** 因为「是什么」代码里就有，AI 一读就懂；但「为什么当初选了这个方案、踩过哪些坑才定下来」，代码里一个字都没有，这才是知识库真正的护城河。

## 实战场景一：表格分页踩坑，到底记不记？

来个真实的。你接了个需求，给一个列表加分页。联调时发现后端的分页是从第 0 页开始的，而前端组件库默认从第 1 页开始，导致每次都少请求一页、最后一页数据还重复。你调了一下午，最后在请求层做了个 `page - 1` 的转换搞定。

这事该不该记？**分情况，而且关键在于「记什么」。**

❌ 不该记的版本（调试流水账）：

```text
2026-06-09 调试分页 bug
试了改组件 current 默认值，没用
试了在 onChange 里 +1，数据还是重复
最后发现是后端从 0 开始
改了请求层的 page 参数，好了
```

这是典型的「一次性调试过程」，问题解决了它就没价值了，没人会回头看你试错的顺序。

✅ 该记的版本（沉淀成一条规则）：

```markdown
## 列表分页：前后端页码基准不一致

**结论**：本项目所有分页接口，后端页码从 0 开始计数，
前端组件库（Ant Design Table）从 1 开始。请求层统一做 `page - 1` 转换，
业务组件内不要自己处理偏移。

**为什么**：转换收口在 request 层，业务侧拿到的永远是「人类直觉」的页码（第 1 页就是第 1 页），
避免每个列表各写一套偏移逻辑、各踩一次坑。

✅ 正确：业务传 page=1，request 层转成 0 发给后端
❌ 错误：业务组件内自己 page-1，导致全站口径不统一
```

差别在哪？前者记的是「我怎么 debug 的」，后者记的是「这个项目的页码约定 + 为什么这么定」。后者是一条会被下一个做列表需求的人反复需要、且半年不会变的规则。

这条该落到哪？它是**本项目的请求层约定**，跨项目不通用（别的项目后端可能从 1 开始）。按 areas 分区规则，请求层相关的踩坑和约定落在：

```text
knowledge/areas/best-practices/references/pitfalls.md
```

> 判断落位的小窍门：先问「这条换个项目还成立吗」。成立 → 进通用层 wiki；只在本仓库成立 → 进 areas。页码基准这种事高度依赖后端实现，毫无疑问是 areas。

## 实战场景二：被反复问到的业务状态流转

第二个场景更典型。你们做的是一个运单系统，运单有「待派车 → 已派车 → 运输中 → 已签收 → 已结算」这么一条主流转。新人每次接需求都来问你：「这个状态能不能直接跳到那个？」「已签收还能回退吗？」你一个月被问了五遍。

这就是教科书级别的「值得沉淀」——高频被问、藏在老人脑子里、且业务规则相对稳定。

❌ 不要这样记（光画个图就完事）：

```text
待派车 → 已派车 → 运输中 → 已签收 → 已结算
```

这种「是什么」级别的信息，价值有限——光看状态名连不成完整认知，真正会卡住人的是流转的**约束和例外**。

✅ 要把「约束」和「例外」一起记下来，这才是别人脑子里那部分：

```markdown
## 运单状态流转

**主流转**：待派车 → 已派车 → 运输中 → 已签收 → 已结算

**关键约束**（这些是新人最常踩的）：
- 「已签收」是单向终态分支，不可回退到「运输中」；
  签收后发现问题走「异常签收」子流程，不走状态回退
- 「已派车」可以取消回退到「待派车」，但「运输中」之后不行
- 只有「已签收」满 24h 才能进「已结算」，由定时任务推进，前端不能手动触发

✅ 正确：前端按 allowedTransitions 配置控制操作按钮的显隐
❌ 错误：前端 hardcode 各状态能点哪些按钮，业务规则一改就全错
```

落位上，状态流转属于**业务流程**，按 areas 分区规则进：

```text
knowledge/areas/business/references/core-flows.md
```

> 一个反直觉但重要的点：状态流转这种东西，很多人觉得「PRD 里都有，没必要记」。但 PRD 是按需求拆的、散在十几个文档里，而知识库是按领域聚合的。把散落各处的流转规则收拢成一页完整的 `core-flows.md`，本身就是巨大的价值。

## 什么坚决不值得沉淀

反过来,这几类东西见到就别存,存了是负债:

| 类型 | 例子 | 为什么不存 |
| --- | --- | --- |
| 一查就知道的 | 「useState 怎么用」「这个组件有哪些 props」 | 代码 / 官方文档里直接有,AI 一读就懂 |
| 一次性调试 | 「今天这个 bug 我是怎么定位的」 | 问题解决就失效,试错顺序没人看 |
| 马上会变的 | 「临时把超时改成 30s 顶一下,下周重构」 | 写下来下周就是错的,误导比没有更糟 |
| 纯环境问题 | 「我本地 node 版本不对,nvm 切一下就好」 | 个人环境,不是团队知识 |
| 重复已有的 | README 已经写了的部署步骤 | 同一信息两处维护,迟早不一致 |

最后一类要特别警惕。**知识库最大的敌人不是空,而是重复和过期。** 一条信息只该有一个权威出处,在知识库里再抄一遍,等于给自己埋了个「两处不一致」的雷。需要关联时用链接指过去,别复制。

## 什么时候动手沉淀

知识沉淀最怕「等有空再说」,因为永远不会有空。我的经验是抓住三个天然的时间窗口,趁记忆还热乎:

**① 联调结束后。** 联调是踩坑密度最高的时刻——前后端字段对不上、页码基准不一致、状态枚举值和文档不符,这些坑刚踩完印象最深。联调一结束,趁热把「踩了什么坑、最后怎么约定的」记进 `pitfalls.md`,十分钟的事。

**② 故障复盘后。** 线上出过事的地方,是知识库含金量最高的内容。复盘会上聊清楚的「根因 + 怎么防」,直接沉淀成一条 pitfall。这类知识的复用价值极高,因为同一个坑团队往往会换个人再踩一次。

**③ 做完一个需求后。** 不是每个需求都值得,但凡是「过程中需要搞懂一段没文档的业务逻辑」「做了个非显而易见的技术决策」的需求,收尾时花十分钟沉淀,是对未来的自己最好的投资。

> 别等到「攒一波一起写」。攒着写的下场就是细节全忘光,最后写出来的是含糊的回忆,不是准确的知识。**热乎的时候记,这是颗粒度和准确度的前提。**

## 颗粒度：一页一主题

沉淀时最容易犯的错是「一页装下整个项目」。正确的颗粒度是**一页只讲一个主题**:

- 「运单状态流转」是一页,「结算规则」是另一页,别揉一起
- 一页超过 300 行 / 一个二级标题下超过 15 条,就是该拆的信号

这不只是为了好读。一页一主题,搜索时才能精准命中;AI 检索时才能只把相关的那一页喂进上下文,而不是拖进一大坨噪音。颗粒度细,检索质量才高——这是知识库能不能被 AI 用好的关键。

## 用 wiki-save 还是 wiki-ingest

落到工具上,frontend-knowledge 插件提供了两个沉淀技能,区别就一条:**知识从哪来。**

| 技能 | 输入来源 | 典型场景 |
| --- | --- | --- |
| `wiki-save` | 当前对话 | 刚和 AI 讨论清楚了状态流转,「保存这次讨论」 |
| `wiki-ingest` | 外部素材文件 | 「把这份 PRD / 联调纪要 / 复盘文档归档到知识库」 |

两个场景对应上面的实战:

场景二的状态流转,通常是你和 AI 一边翻代码一边聊清楚的,结论在对话里——用 `wiki-save`:

```text
保存这次讨论,沉淀到当前项目的业务流程
```

它会提炼对话要点、判定落到 `areas/business/`、写成知识页(注意它会**去掉对话痕迹**,不会写「用户问了 X,AI 答了 Y」,而是直接写「运单签收后不可回退,因为……」)。

场景一的分页坑,如果你手里有一份联调纪要文件,用 `wiki-ingest`:

```text
把这份联调纪要 raw/liantiao-0609.md 归档,重点是分页页码的坑
```

它会读取素材、提取要点、落到 `areas/best-practices/pitfalls.md`。

> 两个技能都遵守同一条铁律:**只沉淀有持久价值的洞察,一次只产出一页,且不自动 commit。** 写完会给你一份待提交清单,提交时机由你决定。这个设计很关键——它逼你 review 一遍再入库,而不是让 AI 往知识库里乱塞。

还有个前提别忘了:areas 是项目级知识库,得先在业务仓库根目录跑过 `areas-init` 生成 `knowledge/` 骨架,`wiki-save` / `wiki-ingest` 才有地方落。当前目录没有 `knowledge/`,技能会直接终止并提示你先初始化。

## 小结

业务知识沉淀的核心不是「多记」,而是「记对」。

- **判断标准就一句话**:三个月后还有人需要、且那时依然成立,才值得记
- **记「为什么」不记「是什么」**:代码能回答的别记,代码回答不了的(决策理由、踩坑约束、状态流转的例外)才是知识库的护城河
- **抓三个时机**:联调后、故障复盘后、做完需求后,趁热记,别攒
- **一页一主题**:颗粒度细,搜索和 AI 检索才精准
- **工具按来源选**:对话结论用 `wiki-save`,外部文档用 `wiki-ingest`,都落在项目层 areas,都要先 `areas-init`

记住,知识库的每一页都在付租金。让那些真正会被反复需要、又不会很快过期的内容留下来,把一次性的噪音挡在门外——这才是知识库三个月后还有人敢点开的唯一原因。
