# 为什么要有项目知识库

> 本篇你能学到：
> - 通用知识库已够用，为什么还要每个业务仓库单建 `knowledge/`
> - 通用知识 vs 项目知识的边界到底划在哪——一条具体知识该往哪放
> - 一张 ✅/❌ 判断表 + `areas/` 五个子域分工速查

前三章我们一直在搞通用知识库 wiki。建好之后我自信满满，觉得团队所有前端知识都能往里塞了。结果第一个真实场景就把我打回原形。

## 一个把我问住的场景

那天有个新同事接手了我们的「车务维保」项目，问我：

> 这个 `<VehicleStatusTag>` 组件，`status` 传 `3` 是「维修中」还是「已完工」？为啥还有个 `legacy` 的 prop，传 `true` 之后行为完全变了？

我下意识想：查 wiki 啊。然后我愣住了——这玩意儿根本不该在 wiki 里。

wiki 里我们写的是「为什么团队选 Zustand 而不是 Redux」「ESLint 该怎么配」这种**跨项目复用**的东西。而 `status: 3` 这个魔法数字、`legacy` 这个为了兼容老车队接口留下的后门，**只在这一个仓库里有意义**。我要是把它写进 wiki，下一个查 wiki 的人看到一堆「车务维保项目的 status 枚举」，只会一脸懵：这跟我有啥关系？

这就是项目知识库存在的全部理由：**有一类知识，离开了它所在的那个仓库就毫无价值，硬塞进通用 wiki 只会污染它。**

## wiki 的洁癖：与业务解耦

回去翻我们 frontend-knowledge 仓库的 `CLAUDE.md`，「内容边界」那一节写得很清楚。我把原文摘出来（这是真实规则，不是我编的）：

**放入 `wiki/`：**

- 技术选型决策与团队约定（为何选 Zustand 而非 Redux）
- 团队场景下踩出的 React/Vue 写法约定
- 工程工具链的团队配置（ESLint / Vite / pnpm / Turborepo）
- 团队编码约定（命名、目录、Code Review）

**不放入 `wiki/`：**

- React/Vue 的基础用法与 API 文档
- 项目业务组件、业务流程、业务踩坑
- 项目架构决策、文件约定
- 业务域强绑的状态流转、业务规则

最后一条还专门补了一句：

> 项目特定内容（业务组件、业务踩坑、项目架构决策）**不进 `wiki/`**，去项目自己的 `areas/`。

wiki 是有「洁癖」的——它要保持与具体业务解耦，才能被所有项目复用。一旦你把 A 项目的业务黑话、B 项目的接口坑都倒进去，wiki 就退化成了一个谁也不想查的杂物间。AI 读 wiki 的时候，也会被这些噪声干扰，给出张冠李戴的答案。

## 项目知识长什么样

那些「离开仓库就没意义」的知识，恰恰是新人最需要、AI 最容易答错的。我把它们归了四类：

🔹 **业务组件的 props 约定**
`<VehicleStatusTag status={3} legacy />` 这种。status 的枚举映射、legacy 的历史包袱，文档里查不到，只能口口相传。

🔹 **某个内部 API 的坑**
比如「`/api/maintenance/list` 这个接口，`pageSize` 传超过 50 会静默返回空数组，后端不报错」。这种坑写进 wiki 毫无意义，但项目里的人天天踩。

🔹 **项目特有的目录结构**
为什么 `src/biz/` 和 `src/modules/` 看起来重复却不能合并？因为一个是新架构、一个是迁移期的过渡产物。这是**项目架构决策**，只对这个仓库成立。

🔹 **业务黑话 / 状态流转**
「待派单 → 已派单 → 在途 → 已签收」这套状态机，还有团队内部管退货叫「回头车」。新人不懂这些黑话，连需求都看不懂。

这四类知识有个共同特征：**强绑业务域，跨项目不可复用。** 它们就该待在项目自己的 `knowledge/areas/` 里。

## 边界判断表：这条该放哪

光说原则太虚，上真实案例。下面每一条都是我团队里实际纠结过的：

| 这条知识 | 放 wiki ✅ / 放 areas ❌ | 为什么 |
| --- | --- | --- |
| 团队统一用 Zustand 做状态管理 | ✅ wiki | 跨项目的技术选型，所有新项目都该遵守 |
| 车务项目用 Zustand 存了一棵「车辆状态树」，结构是 XXX | ❌ areas | 业务域强绑，换个项目这棵树就不存在 |
| ESLint + Prettier 的团队基线配置 | ✅ wiki | 工具链团队约定，可直接复制到新仓库 |
| 本项目 `vite.config.ts` 为啥要 alias 一个 `@legacy` | ❌ areas | 项目架构决策，因历史迁移而生 |
| React 列表渲染必须加 key（团队写法约定） | ✅ wiki | 通用写法约定，带 ✅/❌ 范例 |
| `<VehicleStatusTag>` 的 status 枚举映射 | ❌ areas | 业务组件 props 约定，离开本仓库无意义 |
| 鉴权流程：登录拿 Token、刷新、权限守卫的**团队通用模式** | ✅ wiki | 通用交互模式的团队实现 |
| 本项目对接的「老车队 SSO」那套魔改鉴权 | ❌ areas | 业务踩坑 + 项目架构决策 |
| `/api/maintenance/list` 的 pageSize > 50 静默返回空 | ❌ areas | 内部 API 的坑，强绑这个后端服务 |
| pnpm workspace 在 monorepo 里的团队配置规范 | ✅ wiki | 工程工具链团队配置 |

> 一个屡试不爽的判断口诀：**「把这条知识原封不动复制到另一个新项目，还成立吗？」**
> 成立 → 进 wiki；只在当前仓库成立 → 进 areas。

我自己卡壳的时候就默念这一句，基本不会放错。

## areas/ 不是一个文件，是五个抽屉

知道该放项目层之后，下一个问题是：项目知识库长啥样？跑一下 `frontend-knowledge:areas-init` 技能，它会在仓库根目录生成 `knowledge/`。核心是 `areas/` 下的五个子域，每个接住一类知识：

```text
knowledge/
├── _index.md              # 入口：概述 + 导航
├── hot.md                 # 热点上下文：最常用的核心知识
├── areas/
│   ├── architecture/      # 这个项目「怎么实现」的
│   ├── business/          # 这个项目「在做什么业务」
│   ├── components/        # 有哪些组件、怎么复用
│   ├── best-practices/    # 有哪些经验、坑和推荐做法
│   └── conventions/       # 项目内部「怎么约定」
└── raw/                   # 原始素材（会议纪要、截图、导出文档）
```

对照前面那四类项目知识，归位就很清楚了：

| 项目知识 | 该进哪个抽屉 |
| --- | --- |
| `<VehicleStatusTag>` 的 props 约定 | `areas/components/` |
| `/api/...` 接口坑 | `areas/best-practices/`（已知坑） |
| `src/biz` vs `src/modules` 为啥并存 | `areas/architecture/` |
| 「待派单 → 在途 → 已签收」状态流转 | `areas/business/` |
| 项目内 API 命名/目录约定 | `areas/conventions/` |

> 注意一个写入规则：每个子目录下**只允许** `_index.md` 和 `references/` 目录，所有详细内容统一放进 `references/`，不能散落在子目录根下。`_index.md` 只做导航和必读摘要，通过表格链接到 `references/` 里的具体文件。

这个约束一开始我嫌麻烦，后来真香——因为它和 wiki 的结构完全一致，AI 读项目库和读 wiki 用的是同一套「渐进式披露」路径，不用学两套规矩。

## 两层各司其职，AI 才不会乱答

最后说回那个新同事的问题。如果两层知识各就各位，会发生什么：

- 他问「team 为什么用 Zustand」→ AI 读 wiki，给出技术选型决策
- 他问「`status: 3` 是啥」→ AI 读项目 `areas/components/`，给出枚举映射
- 两个问题**各有归属，互不污染**

反过来，如果我当初偷懒把业务枚举塞进 wiki，AI 在回答任何一个项目的状态管理问题时，都可能把「车务维保的车辆状态树」当成通用方案推给你。这就是边界失守的代价。

## 小结

通用知识库回答「我们团队这么做」，项目知识库回答「这个仓库这么做」。前者要解耦、要复用，所以业务细节必须挡在门外；后者专门接住那些**离开仓库就失效**的业务组件、接口坑、架构决策和状态流转。

判断一条知识往哪放，记住那句口诀就够：复制到新项目还成立吗？成立进 wiki，不成立进 areas。剩下的交给 `areas-init` 把五个抽屉摆好，让每条业务知识都有自己的位置——下一篇我们就动手跑这个初始化流程。
