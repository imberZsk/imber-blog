# ElasticSearch 全文检索：倒排索引表 + IK 分词器 + BM25 算法

> 读完你能：理解关键词全文检索为什么仍然重要，以及 ES 在混合检索中的位置。

## 本篇定位

这是 RAG 检索进阶篇，补上向量检索之外的关键词召回能力。

## 一个真实场景

用户问“E17 报错怎么处理”。向量检索可能觉得 E17 只是一个孤立编号，不一定召回准确；关键词检索却能精准命中文档里的 E17。企业 RAG 不能只靠语义，编号、产品名、法条、接口名都需要全文检索。

## 核心拆解

- 倒排索引是从词到文档的映射。搜索一个词时，系统直接找到包含这个词的文档，而不是全库扫描。
- 中文检索需要分词。IK 分词器会把句子切成词，分词质量直接影响能不能搜到。
- BM25 是关键词相关性排序算法，会综合词频、逆文档频率和文档长度，判断哪个文档更相关。

## 工程链路

- 文档入 ES 前分词。
- 建立倒排索引。
- 查询时对 query 分词。
- 用 BM25 打分召回候选。
- 和向量召回结果融合。
- 再进入 rerank。

## 落地建议

- 把错误码、型号、接口名加入自定义词典。
- 关键词检索适合精确名词和编号。
- ES 结果要保留 score，方便和向量召回融合。

## 常见坑

- 以为向量检索能替代所有关键词搜索。
- 中文不配分词器，搜索效果很差。
- 不维护业务词典，专有名词被切碎。

## 设计判断

判断一个 RAG 项目是否需要 ES，可以看问题里专有名词多不多。如果用户经常问型号、错误码、合同条款号、法规编号、接口名、人员姓名，关键词检索几乎必不可少。向量检索擅长同义表达，但对精确符号不一定稳定；ES 则能把这些“必须一字不差”的线索拉回来。成熟方案不是二选一，而是让 ES 负责精确召回，让向量负责语义召回。

## 复述答法

> ES 的核心是倒排索引和 BM25：先分词建索引，查询时按关键词相关性召回。它特别适合错误码、型号、接口名等精确词。生产 RAG 常把 ES 的关键词召回和向量召回融合。
