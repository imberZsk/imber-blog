# 混合检索 RAG：多路召回 + 重排模型

> 读完你能：掌握企业 RAG 常用的检索漏斗：关键词、向量、多路融合、rerank。
> 来源：`吃透 AI Agent 开发` 截图目录第 27 篇，2026/05/02，可试读 9%
> 导入与重写日期：2026/07/07

## 本篇定位

这是检索调优的核心篇，承接 24 和 78。

## 一个真实场景

用户问“合同里的不可抗力条款怎么写”，向量检索能找到语义相近段落；用户问“第 12.3 条付款条件”，关键词检索更稳。单一路线总有盲区，混合检索就是用多路召回互补，再用重排模型精排。

## 核心拆解

- 多路召回通常包括 BM25、向量检索、标题/标签召回、历史点击召回。每一路负责不同类型的问题。
- 融合阶段要把不同分数体系合并，常见做法是 RRF，用排名而不是原始分数做融合。
- rerank 阶段对融合后的候选做精排，把真正能回答问题的证据排到前面。

## 工程链路

- query 同时走 BM25 和向量检索。
- 各取 topK 候选。
- 按 doc_id 或 chunk_id 去重。
- 用 RRF 融合排名。
- 用 rerank 模型精排。
- 取 topN 拼 prompt。

## 落地建议

- 不同问题类型可动态调整召回权重。
- 融合后要保留来源路由，方便分析哪一路有效。
- rerank 只处理小候选集，别对全库精排。

## 常见坑

- 直接把 BM25 分数和向量分数相加。
- 召回越多越好，结果 prompt 噪声爆炸。
- 没有评测集，无法判断混合检索是否真的提升。

## 和已有主线的关系

24 是初排+重排基础，78 补关键词召回；79 是企业 RAG 检索链路的推荐形态。

## 设计判断

混合检索上线后要看每一路召回的贡献，而不是只看最终答案。可以在 trace 里记录命中文档来自 BM25、向量、标题、标签还是图谱路径。坏 case 复盘时，如果正确证据只被 BM25 找到，说明关键词链路有价值；如果只被向量找到，说明语义召回不能删。长期看这些统计，才能决定召回路由和权重，而不是靠感觉保留一堆昂贵链路。

## 复述答法

> 混合检索是多路召回再融合精排：BM25 适合关键词，向量适合语义，RRF 按排名融合，rerank 对候选精排。关键是去重、保留路由信息，并用评测集证明提升。
