# Redis：实现 Agent 短期记忆存储的最佳方案

> 读完你能：理解 Redis 在 Agent 会话、短期记忆、缓存和限流中的作用。
> 来源：`吃透 AI Agent 开发` 截图目录第 33 篇，2026/06/01
> 导入与重写日期：2026/07/07

## 本篇定位

这是短期状态篇，和 63 的 Memory 策略形成工程落点。

## 一个真实场景

Agent 会话中有很多短期数据：最近几轮消息、流式响应状态、任务执行锁、验证码、限流计数、临时工具结果。这些数据访问频繁、生命周期短，不适合都写主数据库。Redis 正好适合做短期记忆和临时状态层。

## 核心拆解

- 短期记忆一般和 session 绑定，保留最近消息、摘要、当前任务状态。Redis 的 TTL 可以让它自然过期。
- Redis 也适合做语义缓存或普通缓存，把相同问题、相同检索结果、工具返回缓存起来。
- 分布式锁和限流计数能防止同一任务重复执行、同一用户刷爆模型接口。

## 工程链路

- 会话创建时分配 session_id。
- 最近 messages 写 Redis list 或 hash。
- 设置 TTL。
- 每轮请求读取短期上下文。
- 超过长度后摘要并覆盖。
- 会话结束或过期自动清理。

## 落地建议

- 短期记忆不要永久化，默认设置过期时间。
- 关键业务结论要同步写 PostgreSQL。
- 模型缓存要包含 prompt 版本和模型版本，避免错用旧结果。

## 常见坑

- 把 Redis 当唯一数据库。
- 不设 TTL，短期记忆越堆越多。
- 缓存 key 不含用户和权限，导致数据串用。

## 设计判断

Redis 里的短期记忆要按“丢了是否可接受”分类。正在流式输出的临时状态、最近几轮对话、限流计数，丢了最多影响体验，可以放 Redis；订单创建结果、任务执行记录、扣费记录，丢了会造成业务错误，必须写主库。这个判断能避免一个常见错误：因为 Redis 好用，就把所有状态都塞进去，最后服务重启或淘汰策略触发时难以恢复。

## 复述答法

> Redis 适合 Agent 短期记忆：最近消息、会话状态、临时工具结果、限流和锁。它快、支持 TTL，但不能替代主数据库；长期结论和审计仍要落 PostgreSQL。
