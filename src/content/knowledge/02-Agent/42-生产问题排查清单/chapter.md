# 生产问题排查清单

> 读完你能：面对线上 AI 应用的超时、空回答、召回失败、幻觉，按一套结构化清单逐段定位根因，而不是靠猜；并理解为什么「同样答不出」可能是完全不同的两个根因。

## 一个真实场景

周一早上，群里炸了：用户反馈知识库助手"一问就转圈""答了等于没答""明明有的文档说查不到"。三个现象，你得快速判断各是什么问题、改哪里。

新手的反应是打开代码一行行看、凭感觉猜。老手的反应是：**调出这几次请求的观测记录，按字段逐段定位。** 超时看耗时分布在哪一步，空回答看检索命中没有，召回失败看 query 和 chunk。有结构化日志（第 40 篇）打底，排查就是走一遍决策树，不是玄学。

这一篇给你这套决策树。

## 最常见的几类故障和它们的"指纹"

每类故障在观测记录里都有特定的"指纹"——哪个字段异常，基本就锁定了根因：

| 故障现象 | 指纹（哪个字段异常） | 根因方向 |
|---|---|---|
| 超时转圈 | `model_ms` 或 `retrieve_ms` 很大 | 模型/检索慢，定位是哪一步 |
| 拒答"资料不足" | `hit_count == 0` | 检索没命中（召回失败） |
| 空回答 | `answer` 空但 `hit_count > 0` | 检索好的，生成端出问题 |
| 答非所问/编造 | `hit_count > 0` 但答案与资料无关 | 幻觉，prompt 或 grounding 问题 |
| 报错 500 | `error` 非空 | 链路异常，看错误日志 |

关键洞察：**"超时"和"空回答"和"召回失败"是三个不同的故障，指纹不同、改的地方也不同。** 把它们混为一谈"AI 不好用"，就永远修不对。

## 看延迟别只看平均值

线上排查要看 P50/P90/P99：

- P50：一半用户的体感，代表常规体验。
- P90：大多数用户的慢请求边界。
- P99：最差 1% 请求，常暴露模型排队、向量库索引、外部工具慢调用。

如果平均耗时没变但 P99 飙升，说明不是整体慢，而是少数请求卡住。排查要看 trace：是 retrieve、rerank、generate、tool 还是 judge 阶段拖慢。

## 排查决策树：逐段定位，别跳步

诊断要有固定顺序，从"是否崩了"到"慢在哪"再到"质量问题在检索还是生成"：

```python
def diagnose(trace):
    """对一次请求记录走诊断决策树，返回排查结论。"""
    findings = []

    # 1. 先看异常：抛错了优先级最高，直接定位
    if trace.error:
        findings.append(f"[异常] 链路报错：{trace.error} -> 查错误日志和重试/降级")

    # 2. 看耗时：定位慢在模型还是检索
    if trace.model_ms > TIMEOUT_MS:
        findings.append("[超时] 模型调用超时 -> 流式返回、超时重试、降级小模型")
    if trace.retrieve_ms > TIMEOUT_MS:
        findings.append("[超时] 检索超时 -> 查向量库索引和并发，加缓存")

    # 3. 看命中：0 命中是召回失败
    if trace.hit_count == 0:
        findings.append("[召回失败] -> 查 query 改写、chunk 切分、相似度阈值")

    # 4. 区分空回答和召回失败：命中了却没回答，问题在生成端
    if not trace.answer and trace.hit_count > 0:
        findings.append("[空回答] 检索命中但没回答 -> 查 prompt、安全拦截、max_tokens")

    return findings or ["[正常] 各项指标在阈值内"]
```

第 3、4 步是最容易出错的地方：都是"没给出有效答案"，但 `hit_count == 0` 是检索的锅，`hit_count > 0 但 answer 为空` 是生成的锅。**改错地方就是因为没区分这两个。**

## 几类故障的具体排查方向

**召回失败（hit_count=0）**最常见，按这个顺序查：

1. query 太口语化？→ 加 query 改写（第 36 篇 LangGraph 的循环就是干这个）
2. chunk 切太大/太小？→ 调切分粒度
3. 相似度阈值太高？→ 适当放宽
4. 知识库真有这资料吗？→ 别排查半天发现压根没入库

**超时**按耗时分布定位：是检索慢（向量库索引、并发）还是模型慢（服务负载、网络、prompt 太长）。模型慢的缓解手段是流式返回（先吐字降低体感延迟）、超时重试、降级到小模型。

**幻觉（答非所问）**最隐蔽，因为指标看着都正常。要靠 prompt 强约束"只基于资料回答"、回答附引用来源让人能核对、以及评测集兜底（第 26 篇）。

## 工程上真正会踩的坑

- **没有观测数据就开始猜**。没记 `hit_count`、`model_ms`，排查只能靠复现和猜。排查能力的上限是可观测性的上限——这也是为什么第 40 篇排在这之前。
- **把所有问题归为"模型不行"**。召回失败是检索的锅、空回答是 prompt 的锅，甩给模型既修不对也甩锅。先定位是哪一段。
- **线上不能复现就放弃**。AI 输出有随机性，但请求记录是确定的。抓住那次请求的 `request_id`，调出它的完整 trace，比反复复现高效得多。
- **修了不验证**。改了 chunk 切分或阈值，凭感觉觉得好了。要用评测集（第 26 篇）跑一遍命中率，确认是真变好不是错觉。

## 一句话面试答法

> **线上 AI 应用出问题你怎么排查？** 我不靠猜，靠观测记录逐段定位。先看有没有抛异常，再看各阶段耗时定位慢在检索还是模型，再看检索命中数和回答区分质量问题。关键是同样"答不出"根因可能完全不同：检索命中 0 条是召回失败，要查 query 改写、chunk 切分、相似度阈值；检索命中了但回答为空是生成端问题，要查 prompt、安全拦截、max_tokens。这套排查能落地的前提是结构化日志记了 requestId、耗时、命中数这些字段，可观测性是排查的地基。改完我会用评测集验证是真的修好了。
