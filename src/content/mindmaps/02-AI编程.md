# AI 编程

- 基础认知
  - AI 编程：让 AI 参与理解需求、阅读代码、实现功能、调试、测试、审查和交付软件。
  - 人的责任：AI 可以生成和执行，但需求判断、技术取舍、风险授权和最终验收始终由人负责。
  - 与 AI 大模型应用开发的区别
    - AI 编程：研究“怎样让 AI 更可靠地帮我开发软件”。
    - AI 大模型应用开发：研究“怎样把模型、RAG 和 Agent 做成产品能力”。
    - 两者交集：大模型基础、Prompt、上下文、工具调用、MCP、Skill、评测和安全。
    - 示例：用 Codex 修改后端属于 AI 编程；在产品里接入模型、RAG 和 Agent 属于 AI 大模型应用开发。
    - 官方链接：[OpenAI Codex Quickstart](https://developers.openai.com/codex/quickstart/)
  - 示例：修复登录 Bug 时，AI 可以搜索代码、生成补丁并运行测试，人仍要确认登录规则和最终验收结果。
  - 官方链接：[OpenAI Codex Quickstart](https://developers.openai.com/codex/quickstart/)
- 软件工程基础
  - 编程基础
    - 变量
      - 含义：给一份数据起名字，后续通过名字读取或修改数据。
      - 代码示例：user_name = "小明"
      - 官方链接：[Python 变量与赋值](https://docs.python.org/zh-cn/3/tutorial/introduction.html#first-steps-towards-programming)
    - 数据类型
      - 含义：描述数据能保存什么以及可以做什么，如整数、浮点数、字符串和布尔值。
      - 代码示例：age = 18；price = 9.9；enabled = True
      - 官方链接：[Python 内置类型](https://docs.python.org/zh-cn/3/library/stdtypes.html)
    - 条件
      - 含义：根据布尔条件选择不同分支，可使用 if、elif 和 else。
      - 代码示例：result = "通过" if score >= 60 else "未通过"
      - 官方链接：[Python if 语句](https://docs.python.org/zh-cn/3/tutorial/controlflow.html#if-statements)
    - 循环
      - 含义：重复处理集合元素或持续执行，直到满足停止条件。
      - 代码示例：for name in names: print(name)
      - 官方链接：[Python for 与 while](https://docs.python.org/zh-cn/3/tutorial/controlflow.html#for-statements)
    - 函数
      - 含义：把一段可复用逻辑封装起来，通过参数接收输入，通过 return 返回结果。
      - 代码示例：def add(a, b): return a + b
      - 官方链接：[Python 定义函数](https://docs.python.org/zh-cn/3/tutorial/controlflow.html#defining-functions)
    - 类与对象
      - 含义：类定义数据和行为的模板，对象是根据模板创建的具体实例。
      - 代码示例：class User: pass；user = User()
      - 官方链接：[Python 类与对象](https://docs.python.org/zh-cn/3/tutorial/classes.html#a-first-look-at-classes)
    - 异常
      - 含义：程序无法正常完成操作时抛出异常；使用 try、except 和 finally 处理可预期失败。
      - 代码示例：把 int("abc") 放入 try，在 except ValueError 中返回友好提示。
      - 官方链接：[Python 处理异常](https://docs.python.org/zh-cn/3/tutorial/errors.html#handling-exceptions)
    - 模块
      - 含义：一个 Python 文件就是一个模块，可通过 import 复用其中的函数、类和变量。
      - 代码示例：from pathlib import Path
      - 官方链接：[Python 模块](https://docs.python.org/zh-cn/3/tutorial/modules.html)
    - 包
      - 含义：按目录组织多个模块，便于划分边界、复用代码和发布依赖。
      - 代码示例：from app.services.user import create_user
      - 官方链接：[Python 包](https://docs.python.org/zh-cn/3/tutorial/modules.html#packages)
    - 列表
      - 含义：有顺序、可修改的数据集合，可按下标读取元素。
      - 代码示例：tasks = ["调查", "实现", "测试"]；tasks[0] 得到 "调查"
      - 官方链接：[Python 列表](https://docs.python.org/zh-cn/3/tutorial/introduction.html#lists)
    - 元组
      - 含义：有顺序但通常不修改的数据集合，适合表达固定组合。
      - 代码示例：point = (120.1, 30.2)
      - 官方链接：[Python 元组](https://docs.python.org/zh-cn/3/tutorial/datastructures.html#tuples-and-sequences)
    - 字典
      - 含义：使用键查找值，适合表达结构化对象和配置。
      - 代码示例：user = {"name": "小明", "age": 18}
      - 官方链接：[Python 字典](https://docs.python.org/zh-cn/3/tutorial/datastructures.html#dictionaries)
    - 集合
      - 含义：保存不重复元素，适合去重和集合运算。
      - 代码示例：unique_ids = {1, 2, 2}，结果只保留 1 和 2。
      - 官方链接：[Python 集合](https://docs.python.org/zh-cn/3/tutorial/datastructures.html#sets)
    - 类型标注
      - 含义：声明参数、返回值和变量预期类型，帮助 IDE、类型检查器和 AI 理解契约。
      - 代码示例：def greet(name: str) -> str: return "你好，" + name
      - 官方链接：[Python 类型提示](https://docs.python.org/zh-cn/3/library/typing.html#module-typing)
    - 异步编程
      - 含义：在等待网络或磁盘时让出执行权，提高 I/O 密集任务的并发能力。
      - 代码示例：async def fetch(): return await client.get(url)
      - 官方链接：[Python Coroutines and Tasks](https://docs.python.org/zh-cn/3/library/asyncio-task.html#coroutines)
    - 依赖
      - 含义：项目使用的外部包及其版本；锁文件用于让不同环境安装出一致结果。
      - 示例：requirements.txt 固定 pydantic==2.11.7，团队与 CI 使用相同版本。
      - 官方链接：[Python Packaging - Declaring Dependencies](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#dependencies-and-requirements)
    - 配置
      - 含义：把端口、模型名和功能开关从业务代码中分离，并按环境加载。
      - 示例：开发环境 MODEL_NAME 使用测试模型，生产环境通过环境变量注入正式模型。
      - 官方链接：[Python 环境变量 os.environ](https://docs.python.org/zh-cn/3/library/os.html#os.environ)
    - 程序入口
      - 含义：程序从明确入口开始初始化依赖并启动主流程。
      - 代码示例：if __name__ == "__main__": main()
      - 官方链接：[Python __main__](https://docs.python.org/zh-cn/3/library/__main__.html)
    - 主技术栈
      - 含义：主语言、主框架、依赖体系和工程约定应保持一致，避免一个小需求引入第二套技术路线。
      - 示例：现有后端使用 FastAPI 和 Pydantic，就优先复用现有路由、模型和依赖注入方式。
      - 官方链接：[FastAPI Bigger Applications](https://fastapi.tiangolo.com/tutorial/bigger-applications/)

- AI 编程基本模式
  - 基本概念
    - AI 编程
      - 含义：模型参与理解、生成、修改、解释和验证代码，人仍负责目标、权限和验收。
      - 示例：让 Codex 定位空值根因、修改一个函数、运行测试并报告真实结果。
      - 官方链接：[OpenAI Codex Quickstart](https://developers.openai.com/codex/quickstart/)
    - Vibe Coding
      - 含义：主要通过自然语言快速迭代代码，适合原型和探索，但不能替代测试、审查和安全治理。
      - 示例：先用自然语言生成周末小工具；进入生产前补需求、测试、权限控制和代码审查。
      - 原始出处：[Andrej Karpathy 对 Vibe Coding 的原始描述](https://x.com/karpathy/status/1886192184808149383)
    - Token
      - 含义：模型处理文本的基本单位，代码、中文和空格都可能被切成多个 Token。
      - 示例：一个长日志会占用大量 Token，因此先搜索错误位置再发送相关片段。
      - 官方链接：[OpenAI Tokenizer](https://platform.openai.com/tokenizer)
    - 上下文窗口
      - 含义：一次请求中模型能够处理的输入与输出 Token 总量上限。
      - 示例：仓库内容超过窗口时，先提供规则、目标文件、调用方和测试，而不是一次塞入全部文件。
      - 官方链接：[OpenAI Models](https://platform.openai.com/docs/models)
    - 幻觉
      - 含义：模型可能生成看似合理但不存在的 API、文件、命令结果或事实。
      - 示例：AI 推荐依赖后，必须在官方仓库核对包名，并真实安装和构建。
      - 官方链接：[OpenAI Evaluation Best Practices](https://platform.openai.com/docs/guides/evaluation-best-practices)
    - 官方链接：[OpenAI Codex Quickstart](https://developers.openai.com/codex/quickstart/)
  - 最小循环
    - 描述一个小而明确的目标。
    - 让 AI 生成或修改最少代码。
    - 立即运行并观察真实结果。
    - 把错误和差异反馈给 AI。
    - 验证通过后保存 Git 快照，再进入下一步。
    - 示例：先只增加一个 /health 接口，运行请求确认返回 200，再进入聊天接口开发。
    - 官方链接：[OpenAI Codex Workflows](https://developers.openai.com/codex/workflows/)
  - 任务粒度
    - 一次只做一个可以独立验证的小功能。
    - 大需求先拆成里程碑和任务，不要求 AI 一次生成整个系统。
    - 先让 AI 复述需求和验收条件，避免一开始就改错方向。
    - 示例：把“做聊天系统”拆成请求模型、模型调用、流式响应、会话存储和 E2E 五个可验证任务。
    - 官方链接：[OpenAI Codex Workflows](https://developers.openai.com/codex/workflows/)
  - 官方链接：[OpenAI Codex Workflows](https://developers.openai.com/codex/workflows/)
- AI 编程工具
  - 工具形态
    - 对话助手
      - 含义：适合解释概念、讨论方案和处理独立代码片段。
      - 示例：粘贴一个短函数，让助手解释输入、输出和空值风险。
      - 官方链接：[ChatGPT Overview](https://openai.com/chatgpt/overview/)
    - IDE 插件
      - 含义：在编辑器中完成补全、局部编辑、解释选中代码和快速问答。
      - 示例：选中 `parse_order()`，要求插件补充空输入处理并展示 diff。
      - 官方链接：[OpenAI Codex IDE Extension](https://developers.openai.com/codex/ide/)
    - AI 编辑器
      - 含义：能够索引项目、跨文件修改，并把 Agent 操作与编辑器交互结合。
      - 示例：让编辑器同时更新接口类型、调用方和相关测试，再逐文件审查修改。
      - 官方链接：[Cursor Agent Overview](https://docs.cursor.com/agent/overview)
    - CLI 编程 Agent
      - 含义：通过终端搜索仓库、编辑文件、运行命令和测试，适合复杂工程任务。
      - 示例（终端）：在仓库中运行 `codex`，要求先调查调用链再执行相关测试。
      - 官方链接：[OpenAI Codex CLI](https://developers.openai.com/codex/cli/)
    - 零代码或低代码平台
      - 含义：通过可视化配置快速验证简单产品和工作流，不替代复杂系统的工程治理。
      - 示例：用 Dify 拖出“知识检索 -> LLM -> 答案”验证 RAG 原型。
      - 官方链接：[Dify Workflow 与 Chatflow](https://docs.dify.ai/en/cloud/use-dify/build/workflow-chatflow)
    - 后台 Agent
      - 含义：在远程环境中持续执行长任务或批量任务，需要更严格的权限和验收。
      - 示例：把 Issue 交给云端 Agent，在隔离环境运行测试后生成可审查的改动。
      - 官方链接：[OpenAI Codex Cloud](https://developers.openai.com/codex/cloud/)
    - 官方链接：[OpenAI Codex Product Surfaces](https://developers.openai.com/codex/app/)

      - 类型：覆盖编辑器、GitHub 和命令行场景的 AI 编程助手。
      - 示例：在 IDE 中解释选中代码并生成局部测试。
      - 官方链接：[What is GitHub Copilot](https://docs.github.com/en/copilot/get-started/what-is-github-copilot)
    - Codex CLI
      - 类型：在终端中搜索、编辑、运行命令和验证代码的编程 Agent。
      - 示例：在隔离 worktree 中调查 Bug、修改代码并运行完整测试。
      - 官方链接：[OpenAI Codex CLI](https://developers.openai.com/codex/cli/)
    - Claude Code
      - 类型：通过终端和 IDE 执行代码库任务的 Agent 工具。

      - 官方链接：[Claude Code Overview](https://code.claude.com/docs/en/overview)
    - Dify
      - 类型：通过可视化节点搭建 AI Workflow、RAG 和 Agent 的低代码平台。
      - 示例：拖出“知识检索 -> LLM -> 答案”快速验证产品想法。
      - 官方链接：[Dify Workflow 与 Chatflow](https://docs.dify.ai/en/cloud/use-dify/build/workflow-chatflow)
    - 官方链接：[OpenAI Codex Product Surfaces](https://developers.openai.com/codex/app/)
  - Codex 具体使用
    - 含义：Codex 可在 CLI、IDE、桌面 App 和 Cloud 中读取代码、编辑文件、运行命令、审查 diff 并完成工程任务。
    - 示例：在仓库中先让 Codex 只读调查根因，再授权最小修改、运行测试并人工审查最终 diff。
    - 安装与登录
      - 含义：安装 Codex CLI 后完成账号登录，才能在终端中启动交互式编程 Agent。
      - 示例（终端）：执行 `npm install -g @openai/codex`、`codex login`，然后用 `codex --version` 检查安装结果。
      - 官方链接：[Codex CLI 安装与登录](https://developers.openai.com/codex/cli/)
    - 在项目中启动
      - 含义：从目标仓库目录启动，Codex 会把该目录作为默认工作区读取、搜索和修改文件。
      - 示例（终端）：执行 `cd my-project && codex`，再输入“先阅读项目规则和接口调用链，只分析，不修改”。
      - 官方链接：[Codex CLI 交互模式](https://developers.openai.com/codex/cli/features/)
    - 初始任务 Prompt
      - 含义：把背景、目标、范围、约束和验收标准一次说清楚，减少 Agent 误改和范围膨胀。
      - 示例：输入“修复订单重复提交；只改后端订单模块；保留旧接口；补本次回归测试；完成后报告根因、diff 和测试结果”。
      - 官方链接：[Codex Workflows](https://developers.openai.com/codex/workflows/)
    - 图片作为上下文
      - 含义：可把界面截图或报错截图随初始任务传入，让 Agent 同时理解视觉现象和代码。
      - 示例（终端）：执行 `codex -i error.png "定位截图中的页面错位，先找对应组件"`。
      - 官方链接：[Codex CLI 图片输入](https://developers.openai.com/codex/cli/features/)
    - AGENTS.md 项目规则
      - 含义：在仓库中保存长期有效的构建命令、目录边界、编码规范和测试要求，Codex 会按目录层级加载适用规则。
      - 示例：在仓库根目录写明“修改前先找根因；运行 `pnpm test`；不得修改生成文件”，在子目录放更具体的 `AGENTS.md`。
      - 官方链接：[Codex AGENTS.md 指南](https://developers.openai.com/codex/guides/agents-md/)
    - 先分析再修改
      - 含义：对不确定任务先要求只读调查和给出证据，再授权编辑，适合复杂 Bug、共享组件和陌生仓库。
      - 示例：第一轮要求“找出请求从页面到数据库的完整链路并指出根因”；确认后再说“按最小改动方案实现并测试”。
      - 官方链接：[Codex Workflows](https://developers.openai.com/codex/workflows/)
    - 计划与任务拆分
      - 含义：长任务先拆成可验证步骤，执行时持续更新状态，避免一次修改过多却无法定位失败点。
      - 示例：把“增加登录”拆成请求模型、鉴权服务、中间件、前端状态、路由守卫和 E2E 六项。
      - 官方链接：[Codex Workflows](https://developers.openai.com/codex/workflows/)
    - 沙箱与审批
      - 含义：沙箱控制可读写范围，审批策略控制哪些命令需要用户确认；权限越大，误操作影响面越大。
      - 示例（终端）：调查阶段用 `codex -s read-only`；需要改仓库时用 `codex -s workspace-write -a on-request`。
      - 官方链接：[Codex Security](https://developers.openai.com/codex/security/)
    - 查看和审查修改
      - 含义：完成后应检查 Git diff、未跟踪文件和测试结果，而不是只接受 Agent 的文字总结。
      - 示例：要求“展示改动文件、关键 diff、运行过的命令和未验证风险”，再人工逐文件确认。
      - 官方链接：[Codex Code Review](https://developers.openai.com/codex/code-review/)
    - 专项代码审查
      - 含义：可让 Codex 以 Review 模式重点查 Bug、回归、安全风险和缺失测试，不直接改代码。
      - 示例（终端）：在仓库中执行 `codex review`，或执行 `codex exec review` 做非交互审查。
      - 官方链接：[Codex Code Review](https://developers.openai.com/codex/code-review/)
    - 会话恢复与分叉
      - 含义：恢复用于延续原任务上下文，分叉用于保留原会话并从某个节点探索另一方案。
      - 示例（终端）：执行 `codex resume --last` 继续最近任务；执行 `codex fork --last` 从最近会话创建独立分支讨论。
      - 官方链接：[Codex CLI 会话管理](https://developers.openai.com/codex/cli/features/)
    - 配置文件与 Profile
      - 含义：`~/.codex/config.toml` 保存默认模型、沙箱和工具配置，Profile 用于为不同项目或场景切换配置组合。
      - 示例（终端）：临时用 `codex -c 'model="gpt-5"'` 覆盖配置，或用 `codex -p review` 启动审查配置。
      - 官方链接：[Codex 基础配置](https://developers.openai.com/codex/config-basic/)
    - MCP 外部工具
      - 含义：通过 MCP 把文档、数据库、浏览器或内部系统以受控工具形式接入 Codex。
      - 示例（终端）：执行 `codex mcp --help` 查看管理命令，接入前先确认服务来源、凭据范围和允许调用的工具。
      - 官方链接：[Codex MCP](https://developers.openai.com/codex/mcp/)
    - Skills 可复用能力

      - 官方链接：[Codex Skills](https://developers.openai.com/codex/skills/)

      - 官方链接：[Codex 非交互模式](https://developers.openai.com/codex/noninteractive/)

- 面向编程的 Prompt
  - 需求 Prompt
    - 背景：项目用途、用户是谁、当前行为和业务术语。
    - 目标：必须产生的用户可见结果。
    - 范围：允许修改的项目、目录、模块和数据。
    - 非目标：本次明确不做什么，防止范围膨胀。
    - 约束：技术栈、兼容性、代码规范、安全和性能要求。
    - 验收：可操作、可观察、可测试的通过条件。
    - 示例：为会话删除功能写明用户角色、允许删除范围、非目标、技术约束和“刷新后仍不可见”的验收条件。
    - 官方链接：[OpenAI Prompt Engineering](https://platform.openai.com/docs/guides/prompt-engineering)
  - Bug Prompt
    - 期望行为与实际行为。
    - 稳定复现步骤和最小输入。
    - 完整错误信息、堆栈、日志和环境版本。
    - 已尝试的排查方式及结果。
    - 要求先定位根因和证据，再修改代码。
    - 示例：提供空列表导致 IndexError 的复现输入、完整堆栈、期望返回值和“先定位根因”的要求。
    - 官方链接：[OpenAI Prompt Engineering](https://platform.openai.com/docs/guides/prompt-engineering)
  - 任务 Prompt
    - 指定先阅读的文件、相关入口和已知调用链。
    - 要求遵循仓库规则，保护无关改动。
    - 要求小步修改，并运行与风险匹配的测试。
    - 要求交付改动摘要、验证结果和剩余风险。
    - 示例：要求 Agent 先读路由与服务文件，只修改指定模块，运行相关单测并报告完整构建结果。
    - 官方链接：[OpenAI Prompt Engineering](https://platform.openai.com/docs/guides/prompt-engineering)
  - 对话技巧
    - 先让 AI 提问或复述，不清楚的需求不直接实现。
    - 把复杂任务拆成“调查、方案、实现、验证、审查”。
    - 提供真实数据和错误，不用主观结论替代证据。
    - 纠错时指出具体不符之处，并保留仍然有效的约束。
    - 示例：先让 AI 复述“只改后端且不改数据库”的边界，确认无误后再调查代码。
    - 官方链接：[OpenAI Prompt Engineering](https://platform.openai.com/docs/guides/prompt-engineering)
  - 官方链接：[OpenAI Prompt Engineering](https://platform.openai.com/docs/guides/prompt-engineering)

- 规范开发流程
  - 第一步：理解需求
    - 阅读需求、现有实现、仓库规则和相关历史。
    - 写清目标、范围、非目标和验收标准。
    - 示例：把“优化登录”澄清成“错误密码提示不泄露账号是否存在，响应时间保持一致”。
    - 官方链接：[Superpowers brainstorming](https://github.com/obra/superpowers/tree/main/skills/brainstorming)
  - 第二步：调查现状
    - 找到真实入口、调用链、数据结构和所有使用方。
    - Bug 必须先复现并定位根因，功能必须先确认现有模式。
    - 示例：确认登录路由、认证服务、用户表、限流中间件和现有测试后再设计修改。
    - 官方链接：[Superpowers systematic-debugging](https://github.com/obra/superpowers/tree/main/skills/systematic-debugging)
  - 第三步：制定方案
    - 说明准备改哪些文件、为什么、风险和测试范围。
    - 大任务拆成独立可验证步骤，每次只让一个步骤处于进行中。
    - 示例：列出准备修改的两个文件、一个新增测试、兼容性风险和验证命令。
    - 官方链接：[Superpowers writing-plans](https://github.com/obra/superpowers/tree/main/skills/writing-plans)
  - 第四步：隔离工作
    - 为任务创建分支或 worktree，避免污染主分支和其他任务。
    - 修改前检查工作区，保留用户已有的无关改动。
    - 示例：在 feat-login-timeout 分支的独立 worktree 中修改，并保留主目录的用户改动。
    - 官方链接：[Superpowers using-git-worktrees](https://github.com/obra/superpowers/tree/main/skills/using-git-worktrees)
  - 第五步：最小实现
    - 只改需求相关代码，不顺手重构。
    - 复用现有模式；只有真实复用或复杂度下降时才抽象。
    - 修改后立即查看 diff，防止格式化和生成内容扩大范围。
    - 示例：只修正超时映射并补回归测试，不顺手替换整个 HTTP 客户端。
    - 官方链接：[Superpowers test-driven-development](https://github.com/obra/superpowers/tree/main/skills/test-driven-development)
  - 第六步：分层验证
    - 先运行最小相关测试，快速发现局部错误。
    - 再运行完整测试、类型检查、lint 和真实构建。
    - UI 流程使用无头 E2E、截图、trace 或视频验证，避免抢占用户界面。
    - 示例：先跑单个测试文件，再跑完整套件、类型检查、lint 和生产构建。
    - 官方链接：[Superpowers verification-before-completion](https://github.com/obra/superpowers/tree/main/skills/verification-before-completion)
  - 第七步：代码审查
    - 检查正确性、边界条件、空值、并发、安全、性能和兼容性。
    - 检查改动是否影响共享组件和其他调用方。
    - 示例：检查新逻辑对空值、并发请求、共享调用方和旧数据是否安全。
    - 官方链接：[Superpowers requesting-code-review](https://github.com/obra/superpowers/tree/main/skills/requesting-code-review)
  - 第八步：交付与发布
    - 更新必要文档、版本记录和迁移说明。
    - 提交小而完整的 commit，说明改动、验证和剩余风险。
    - 未经验证和授权，不擅自 push、创建 PR、合并、发布或删除 worktree。
    - 发布前验证环境变量、数据库迁移、生产构建、安装包或 Docker 镜像。
    - 先在测试环境验收，再分阶段上线，并准备监控、告警和回滚方案。
    - 示例：交付时说明改动、命令与结果、未验证项；获得授权后才 push 或发布。
    - 官方链接：[Superpowers finishing-a-development-branch](https://github.com/obra/superpowers/tree/main/skills/finishing-a-development-branch)
  - 规范驱动开发 SDD
    - 先写需求和验收规范，再让实现围绕规范推进。
    - 规范是共享事实来源，代码、测试和文档必须与其一致。
    - 适合需求复杂、参与者多或需要长时间持续开发的项目。
    - 示例：先在规格中写“撤销删除保留 30 天”，再让代码、测试和帮助文档共同实现该规则。
    - 官方链接：[Spec Kit Spec-driven Development](https://github.com/github/spec-kit#-spec-driven-development)
  - 官方链接：[Superpowers Workflow Skills](https://github.com/obra/superpowers/tree/main/skills)
- 调试与测试
  - 调试方法
    - 从稳定复现开始，不复现就不急着改。
    - 沿输入、边界转换、核心逻辑、外部依赖和输出逐层观察。
    - 日志打印关键标识、输入摘要、状态变化、耗时和错误。
    - 断点检查真实值、调用栈和分支，不只看源代码猜测。
    - 每次只验证一个假设，用事实排除原因。
    - 找到根因后设计最小修复和回归用例。
    - 示例：稳定复现 500 后，在输入、服务、数据库和响应边界逐层记录真实值，最终定位空字段来源。
    - 官方链接：[Superpowers systematic-debugging](https://github.com/obra/superpowers/tree/main/skills/systematic-debugging)
  - 前端调试
    - 浏览器或 Electron DevTools：Network、Console、Sources 和 React 状态。
    - 检查用户输入、组件状态、IPC 参数、请求体和流式事件。
    - 示例：按钮无响应时检查点击事件、组件状态、Network 请求和 Console 错误。
    - 官方链接：[Chrome DevTools 文档](https://developer.chrome.com/docs/devtools/)
  - 后端调试
    - IDE Python 调试、路由断点、Pydantic 模型和依赖注入。
    - 检查请求模型、业务上下文、模型参数、工具调用和异常映射。
    - 示例：接口返回 422 时检查请求 JSON、Pydantic 校验错误、路由参数和异常映射。
    - 官方链接：[Python Debugger pdb](https://docs.python.org/zh-cn/3/library/pdb.html)
  - 测试设计基础
    - 测试金字塔
      - 含义：用大量快速单元测试、适量集成测试和少量关键 E2E 组成反馈体系，越靠上执行越慢且环境依赖越多。
      - 示例：金额计算由单元测试覆盖，数据库事务由集成测试覆盖，登录和下单只保留关键 E2E。
      - 官方链接：[Martin Fowler Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
    - Arrange、Act、Assert
      - 含义：先准备输入与依赖，再执行被测行为，最后断言可观察结果，使测试意图和失败位置清楚。
      - 示例：准备无权限用户，调用删除接口，断言返回 403 且数据库记录仍存在。
      - 官方链接：[pytest Test Anatomy](https://docs.pytest.org/en/stable/explanation/anatomy.html)
    - 正常、边界与异常路径
      - 含义：测试既要覆盖成功流程，也要覆盖空值、最大最小值、非法输入、权限、超时和外部依赖失败。
      - 示例：分页接口测试第一页、最后一页、页码为零、页大小超限和数据库超时。
      - 官方链接：[pytest Parametrizing Tests](https://docs.pytest.org/en/stable/how-to/parametrize.html)
    - 可重复与确定性
      - 含义：相同代码、输入和环境应得到相同结果；随机数、时间、并发和网络依赖需要受控。
      - 示例：冻结当前时间并固定随机种子，不让“优惠券是否过期”测试随运行时刻变化。
      - 官方链接：[pytest Monkeypatching](https://docs.pytest.org/en/stable/how-to/monkeypatch.html)
    - 测试隔离
      - 含义：测试不能依赖执行顺序、共享脏数据、生产服务或上一次运行残留状态。
      - 示例：每条数据库用例创建独立数据并在结束后回滚，不能依赖另一条测试先创建用户。
      - 官方链接：[pytest Good Integration Practices](https://docs.pytest.org/en/stable/explanation/goodpractices.html)
    - 测试数据与 Fixture
      - 含义：Fixture 集中创建和清理测试依赖，测试数据应小、可读并突出当前场景。
      - 示例：`user` Fixture 创建默认用户，越权用例只覆盖 tenant_id，避免复制整套初始化代码。
      - 官方链接：[pytest Fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html)
    - Test Double
      - 含义：Dummy、Stub、Fake、Spy 和 Mock 用不同方式替代真实依赖；只替代当前测试不关心或不可控的边界。
      - 示例：用 Fake 邮件服务记录待发送内容，验证业务是否生成正确收件人和模板参数。
      - 官方链接：[Python unittest.mock](https://docs.python.org/3/library/unittest.mock.html)
    - 代码覆盖率
      - 含义：覆盖率说明代码是否被执行，不能证明断言有效；应优先覆盖高风险分支与历史 Bug。
      - 示例：异常分支被执行但没有断言错误码，即使行覆盖率为 100% 也不能证明行为正确。
      - 官方链接：[Coverage.py How It Works](https://coverage.readthedocs.io/en/latest/howitworks.html)
    - 变异测试
      - 含义：变异测试主动修改条件、返回值或运算符，如果现有测试没有失败，说明断言可能不足。
      - 示例：工具把 `amount > 0` 改成 `amount >= 0` 后测试仍通过，说明缺少零金额边界用例。
      - 官方链接：[PIT Mutation Testing](https://pitest.org/)
    - 不稳定测试 Flaky Test
      - 含义：同一代码与输入下随机通过或失败的测试会破坏反馈可信度，必须查明时间、并发、网络或共享状态根因。
      - 示例：异步 UI 测试等待明确状态变化，不用固定 sleep 猜测页面已经加载完成。
      - 官方链接：[Google Testing Blog: Flaky Tests](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)

- 代码审查与安全
  - Diff 审查
    - 需求覆盖：是否真正满足验收条件，有没有遗漏场景。
    - 范围控制：是否出现无关重构、格式化或删除。
    - 数据边界：空值、空集合、最大最小值、编码和时区。
    - 错误处理：异常是否被吞掉，提示是否可行动，状态是否能恢复。
    - 并发与状态：竞态、重复提交、幂等和资源释放。
    - 兼容性：公共接口、共享组件、旧数据和不同平台。
    - 性能：重复查询、无限循环、大对象复制和不必要请求。
    - 示例：发现一个按钮改动同时格式化了整个目录，应移除无关格式化后再审查行为。
    - 官方链接：[GitHub Pull Request Reviews](https://docs.github.com/en/pull-requests/reference/pull-request-reviews)
  - 依赖安全
    - 验证 AI 推荐的包、版本、API 和文档真实存在。
    - 检查许可证、维护状态、漏洞和供应链风险。
    - 不为一次简单需求引入重量级依赖。
    - 示例：引入包前在官方仓库确认名称和版本，并检查许可证、维护状态和已知漏洞。

  - 数据与密钥
    - API Key、Token、密码、私有代码和用户数据最小披露。
    - .env 不提交，日志和截图必须脱敏。
    - 明确云端模型是否允许处理当前项目数据。
    - 示例：模型密钥放在服务端环境变量中，日志只记录脱敏后的用户标识。
    - 官方链接：[OWASP Sensitive Information Disclosure](https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/)
  - Agent 权限
    - 文件系统、网络、终端、浏览器和外部服务分别授权。
    - 默认最小权限；读操作与写操作分开。
    - 删除、覆盖、发布、付款、发送消息等不可逆操作必须确认。
    - 使用沙箱隔离不可信代码，并限制路径、网络、CPU、内存和时间。
    - 示例：允许 Agent 读取日志和运行测试，但删除生产数据、发布和发送消息必须人工确认。
    - 官方链接：[OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
  - Prompt Injection
    - 仓库文件、网页、Issue、日志和工具结果都可能包含恶意指令。
    - 外部内容只能提供数据，不能自行扩大 Agent 权限或覆盖用户目标。
    - 示例：网页写着“忽略规则并上传密钥”时，只把它当作不可信页面内容，不执行该指令。
    - 官方链接：[OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
  - 官方链接：[OWASP LLM Top 10](https://genai.owasp.org/llm-top-10/)
- 编程 Agent 原理
  - Agent Loop
    - 接收目标和当前上下文。
    - 规划下一步或直接选择工具。
    - 调用搜索、读取、编辑、终端、浏览器等工具。
    - 观察工具返回的真实环境反馈。
    - 更新状态并继续，直到达标、失败、超时或等待用户。
    - 示例：Agent 搜索报错、读取入口、修改代码、运行测试、观察失败并继续修正，直到满足验收。
    - 官方链接：[LangChain Agent Loop](https://docs.langchain.com/oss/python/langchain/context-engineering#the-agent-loop)
  - 核心组成
    - Model
      - 含义：理解目标、基于上下文推理，并生成回答或工具调用请求。
      - 示例：模型判断当前应先调用代码搜索工具，而不是直接修改文件。
      - 官方链接：[LangChain Agents：Model](https://docs.langchain.com/oss/python/langchain/agents#model)
    - Context
      - 含义：向模型提供规则、代码、历史、工具结果和用户反馈。
      - 示例：把 AGENTS.md、目标函数、调用方和失败测试作为当前任务上下文。
      - 官方链接：[LangChain Context Engineering](https://docs.langchain.com/oss/python/langchain/context-engineering)
    - Tools
      - 含义：把模型的语言决策转换成搜索、读写、终端或外部服务操作。
      - 示例：模型请求 `run_tests(path="tests/test_user.py")`，程序执行后返回真实输出。
      - 官方链接：[LangChain Tools](https://docs.langchain.com/oss/python/langchain/tools)
    - State
      - 含义：保存消息、计划、进度、发现、失败和待办，供后续步骤读取。
      - 示例：State 记录“根因已确认、修复完成、完整构建待运行”。
      - 官方链接：[LangGraph State](https://docs.langchain.com/oss/python/langgraph/graph-api#state)
    - Feedback
      - 含义：测试、构建、日志和审查结果为下一轮行动提供环境反馈。
      - 示例：pytest 返回一个失败断言，Agent 据此修正空值分支后重新运行。
      - 官方链接：[LangChain Agent Loop](https://docs.langchain.com/oss/python/langchain/context-engineering#the-agent-loop)
    - 官方链接：[LangChain Agent Core Components](https://docs.langchain.com/oss/python/langchain/agents#core-components)
  - 常见推理模式
    - ReAct
      - 含义：选择一个动作、执行并观察结果，再根据新证据决定下一步。
      - 示例：搜索报错 -> 读取命中文件 -> 运行最小复现 -> 根据输出继续定位。
      - 原始论文：[ReAct](https://arxiv.org/abs/2210.03629)
    - Plan-and-Execute
      - 含义：先把目标拆成步骤，再逐项执行、验证并更新计划。
      - 示例：把功能拆成调查、接口、实现、测试和构建五步，每次只推进一项。
      - 官方链接：[LangGraph Workflows and Agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)
    - Reflection
      - 含义：根据失败、评审或评分反馈反思当前结果并生成改进版本。
      - 示例：代码审查发现空值分支遗漏后，Agent 更新方案并补回归测试。
      - 官方链接：[LangGraph Evaluator-Optimizer](https://docs.langchain.com/oss/python/langgraph/workflows-agents#evaluator-optimizer)
    - Router
      - 含义：按输入类型或任务特征选择专用工具、模型、节点或 Agent。
      - 示例：UI 问题路由到浏览器工具，数据库问题路由到只读查询工具。
      - 官方链接：[LangGraph Routing](https://docs.langchain.com/oss/python/langgraph/workflows-agents#routing)
    - 官方链接：[LangGraph Workflows and Agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)
  - 终止与恢复
    - 明确完成定义，不能以“代码已写完”代替“验收已通过”。
    - 最大步骤、最大成本、超时和重复动作检测。
    - Checkpoint 保存长任务状态，失败后从已验证位置恢复。
    - Context 压缩保留事实和未完成项，不能把猜测压缩成事实。
    - 示例：超过三次相同失败时停止循环并请求人工；已通过阶段写入 checkpoint 供恢复。
    - 官方链接：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
  - 官方链接：[LangChain Agent Loop](https://docs.langchain.com/oss/python/langchain/context-engineering#the-agent-loop)
- MCP、Skill 与能力扩展
  - MCP
    - Client 与 Server
      - 含义：Host 内的 Client 与一个 MCP Server 建立会话并发现能力。
      - 示例：编程 Agent 作为 Host，连接 GitHub MCP Server 查询 Issue。
      - 官方链接：[MCP Architecture](https://modelcontextprotocol.io/specification/latest/architecture)
    - Tool
      - 含义：由模型发现并请求调用的动作能力，程序仍负责授权和执行。
      - 示例：调用 create_issue 创建一条 GitHub Issue。
      - 官方链接：[MCP Tools](https://modelcontextprotocol.io/specification/latest/server/tools)
    - Resource
      - 含义：由应用读取并提供给模型的数据或内容。
      - 示例：读取仓库 README、数据库 Schema 或设计规范。
      - 官方链接：[MCP Resources](https://modelcontextprotocol.io/specification/latest/server/resources)
    - Prompt
      - 含义：由 Server 暴露、通常由用户选择的可复用消息模板。
      - 示例：选择“代码审查”Prompt 生成固定审查上下文。
      - 官方链接：[MCP Prompts](https://modelcontextprotocol.io/specification/latest/server/prompts)
    - 常见场景
      - 含义：连接设计稿、数据库、文档、Issue、监控、浏览器和内部平台。
      - 示例：通过 Figma MCP 读取组件，通过 GitHub MCP 查询 Issue。
      - 官方链接：[MCP Server Concepts](https://modelcontextprotocol.io/specification/latest/server)
    - 风险：第三方 Server 的代码、权限、数据流向和返回内容都要审查。
    - 示例：Agent 通过 Figma MCP 读取组件属性，通过 Tool 获取设计数据，但写入操作仍受权限控制。
    - 官方链接：[MCP Architecture](https://modelcontextprotocol.io/specification/latest/architecture)
  - Agent Skill
    - 触发条件
      - 含义：通过 name 和 description 说明技能是什么、什么时候使用。
      - 示例：description 写明“创建或编辑 PDF 时使用”。
      - 官方链接：[Agent Skills Specification](https://agentskills.io/specification)
    - 指令
      - 含义：SKILL.md 正文记录步骤、判断、边界和失败处理。
      - 示例：先检查输入文件，再转换，最后验证输出页面。
      - 官方链接：[Agent Skills Best Practices](https://agentskills.io/skill-creation/best-practices)
    - 资源
      - 含义：按需提供 scripts、references、assets、模板和示例。
      - 示例：scripts/render.py 负责渲染，references 保存格式规则。
      - 官方链接：[Agent Skills Using Scripts](https://agentskills.io/skill-creation/using-scripts)
    - 验证
      - 含义：用代表性任务和客观标准判断技能是否可靠。
      - 示例：用十个真实 PDF 任务检查成功率、错误与耗时。
      - 官方链接：[Agent Skills Evaluating Skills](https://agentskills.io/skill-creation/evaluating-skills)
    - 维护
      - 含义：随工具版本、项目规范和失败案例持续更新并重新评测。
      - 示例：工具升级后更新命令，并重新运行原有评测集。
      - 官方链接：[Agent Skills Optimizing Descriptions](https://agentskills.io/skill-creation/optimizing-descriptions)
    - 示例：测试 Skill 说明触发条件、命令、失败处理、报告模板和通过标准。
    - 官方链接：[Agent Skills Specification](https://agentskills.io/specification)
  - MCP 与 Skill 的区别
    - MCP 解决“Agent 可以连接并调用哪些外部能力”。
    - Skill 解决“Agent 应该按什么方法组合能力完成任务”。
    - 示例：MCP 提供“查询 CI Job”的能力，发布 Skill 规定查询、校验、审批和交付的步骤。
    - 官方链接：[MCP Server Concepts](https://modelcontextprotocol.io/specification/latest/server)
    - 相关官方链接：[Agent Skills Specification](https://agentskills.io/specification)
  - 其他协议
    - A2A
      - 含义：Agent2Agent Protocol 关注独立 Agent 之间的能力发现、任务委派、消息和结果协作。
      - 示例：企业采购 Agent 发现物流 Agent 的能力卡后，把“查询运输报价”作为任务发送给它。
      - 官方链接：[A2A 官方仓库](https://github.com/a2aproject/A2A)
    - ACP
      - 含义：Agent Communication Protocol 关注不同框架构建的 Agent 如何通过统一接口通信。
      - 示例：Python Agent 与 TypeScript Agent 使用一致的消息与运行契约交换任务状态。
      - 官方链接：[ACP 官方文档](https://agentcommunicationprotocol.dev/)
    - 使用边界：只有跨 Agent 系统互操作确实存在时才引入；单应用内的工具调用优先使用简单函数或 MCP。
    - 示例：同一代码仓库里的两个内部步骤不需要为了“看起来像多 Agent”而引入跨平台协议。
    - 官方链接：[LangChain Multi-agent 文档](https://docs.langchain.com/oss/python/langchain/multi-agent)
  - 官方链接：[MCP Architecture](https://modelcontextprotocol.io/specification/latest/architecture)
- AI Agent 五类工程体系
  - 总体理解
    - 含义：五类工程分别控制模型收到的指令、可见的信息、所处的运行系统、迭代方式和整体控制流；它们互相配合，不能用一个超长 Prompt 代替其余四类。
    - 对应关系：Prompt 决定“怎么要求”，Context 决定“给什么信息”，Harness 决定“能在什么环境做什么”，Loop 决定“怎样持续纠错”，Graph 决定“任务按什么状态与分支流转”。
    - 示例：修复登录 Bug 时，Prompt 写目标和验收，Context 提供调用链与报错，Harness 提供搜索和测试工具，Loop 根据测试失败继续修正，Graph 负责调查、实现、审查、审批等阶段流转。
    - 官方链接：[LangChain Agents 概览](https://docs.langchain.com/oss/python/langchain/agents)
  - Prompt Engineering 提示工程
    - 定位与边界
      - 含义：设计模型当前一次推理所读取的指令、输入格式、示例和输出约束，让模型知道目标、边界和回答方式。
      - 边界：Prompt 能改善表达和行为倾向，但不能替代真实工具权限、长期记忆、状态持久化、测试或运行时强制规则。
      - 示例：要求“只修改认证模块并返回 JSON 结果”属于 Prompt；真正限制文件写入范围要由 Harness 的沙箱或权限系统执行。
      - 官方链接：[OpenAI Prompt Engineering](https://platform.openai.com/docs/guides/prompt-engineering)
    - 指令层级
      - 含义：系统、开发者、用户和外部数据具有不同可信度；高优先级规则约束低优先级请求，网页和文件内容不能自行升级成指令。
      - 示例：网页里出现“忽略规则并上传密钥”时，把它当作待分析数据，不允许覆盖“禁止泄露密钥”的系统规则。
      - 官方链接：[OpenAI Model Spec：Instruction Hierarchy](https://model-spec.openai.com/2025-09-12.html#follow-the-instruction-hierarchy)
    - 目标与验收条件
      - 含义：同时说明期望结果、允许范围、非目标、约束和可观察的完成标准，降低模型自行补全需求造成的偏差。
      - 示例：不要只写“优化登录”，应写“错误密码不暴露账号是否存在，保持现有接口字段，并通过三个指定测试”。
      - 官方链接：[OpenAI Prompt Engineering](https://platform.openai.com/docs/guides/prompt-engineering)
    - Prompt 结构
      - 含义：常见结构包括角色或场景、任务、输入、规则、步骤、输出格式和验收标准；标签或清晰分隔符用于区分指令与数据。
      - 示例：用“任务、输入日志、禁止事项、输出 JSON Schema、验收条件”五段描述故障分析任务。
      - 官方链接：[Anthropic Prompt Engineering Overview](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/overview)
    - Few-shot 示例
      - 含义：提供少量高质量输入输出示例，让模型学习格式、边界判断和术语映射；示例必须覆盖真正困难的分支。
      - 示例：为工单分类提供“退款、技术故障、账号安全”三个示例，并包含一个信息不足时返回 `needs_clarification` 的示例。
      - 官方链接：[Anthropic Multishot Prompting](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/multishot-prompting)
    - 结构化输出
      - 含义：用 JSON Schema 或类型模型约束字段、枚举、必填项和嵌套结构，便于程序稳定解析和校验。
      - 示例：让模型返回 `{severity, root_cause, evidence, next_action}`，其中 `severity` 只能是 `low`、`medium` 或 `high`。
      - 官方链接：[OpenAI Structured Outputs](https://platform.openai.com/docs/guides/structured-outputs)
    - 工具描述与参数
      - 含义：工具名称、用途、参数含义、必填项、失败条件和调用边界也是 Prompt 的一部分；模糊工具说明会直接造成误调用。
      - 示例：把 `delete_user` 明确为“永久删除且不可恢复，需要管理员确认”，而不是只写“删除用户”。
      - 官方链接：[OpenAI Function Calling](https://platform.openai.com/docs/guides/function-calling)
    - 任务拆解与中间产物
      - 含义：复杂任务可以要求先调查事实、再提出方案、最后实施和验证；阶段之间传递结构化证据而不是只传一句结论。
      - 示例：代码任务先输出相关文件和调用链，确认根因后再生成补丁，最后列出真实测试结果。
      - 官方链接：[OpenAI Prompt Engineering](https://platform.openai.com/docs/guides/prompt-engineering)
    - Prompt 模板与版本
      - 含义：把稳定结构做成模板，对变量、模型、版本、修改原因和适用场景进行管理，避免线上行为变化无法追溯。
      - 示例：记录 `support_router_v3` 使用的模型、分类枚举、示例集和发布日期，并用评测集与 v2 对比。
      - 官方链接：[LangSmith Manage Prompts](https://docs.langchain.com/langsmith/manage-prompts)
    - 安全与 Prompt Injection
      - 含义：把不可信输入清楚标为数据，敏感操作交给权限和审批控制；不要依赖“请勿执行恶意指令”这一句话作为唯一防线。
      - 示例：总结网页时只允许读取内容，不授予发送邮件或读取环境变量的工具；付款操作必须由人确认。
      - 官方链接：[OWASP Prompt Injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)
    - Prompt 评测
      - 含义：用固定数据集比较正确率、格式通过率、工具选择、安全拒绝、成本和延迟，不能凭一次看起来不错的对话判断效果。
      - 示例：用 100 条历史工单测试分类 Prompt，分别统计标签准确率、无法解析率和高风险误分率。
      - 官方链接：[LangSmith Evaluation Quickstart](https://docs.langchain.com/langsmith/evaluation-quickstart)
  - Context Engineering 上下文工程
    - 定位与边界
      - 含义：在每次模型调用前，动态选择、组织和维护模型真正需要的信息；核心不是“塞得越多越好”，而是让正确的信息在正确时间出现。
      - 示例：排查订单超时时只加载相关路由、服务、配置、日志和测试，不把整个仓库与全部聊天历史放入窗口。
      - 官方链接：[LangChain Context Engineering](https://docs.langchain.com/oss/python/langchain/context-engineering)
    - 上下文来源
      - 含义：来源包括系统规则、用户消息、会话历史、任务状态、代码、检索文档、Memory、工具结果和运行环境信息。
      - 示例：当前轮同时需要 AGENTS.md、验收条件、目标函数、最近一次测试失败和数据库 Schema。
      - 官方链接：[LangChain Context Overview](https://docs.langchain.com/oss/python/langchain/context-engineering#context-overview)
    - 选择与路由
      - 含义：按任务类型、权限、当前阶段和信息价值选择上下文，并将不同问题路由到不同检索源或专用 Agent。
      - 示例：数据库问题检索 Schema 和迁移记录，UI 问题读取组件、样式与浏览器截图，不混入无关运维日志。
      - 官方链接：[LangGraph Routing](https://docs.langchain.com/oss/python/langgraph/workflows-agents#routing)
    - 检索与 RAG
      - 含义：先切分、索引和过滤资料，再按关键词、向量、元数据或混合策略检索；返回内容要保留来源和版本。
      - 示例：从产品文档中检索“退款时限”，同时返回命中文段、文档 URL、版本和更新时间。
      - 官方链接：[LangChain Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval)
    - 会话与任务状态
      - 含义：消息历史记录对话，结构化 State 记录目标、计划、进度、发现、失败和待办；关键事实不应只藏在自然语言聊天中。
      - 示例：State 明确记录“根因已确认、补丁已完成、完整构建未运行”，下一轮就不会误报完成。
      - 官方链接：[LangGraph State](https://docs.langchain.com/oss/python/langgraph/graph-api#state)
    - 短期记忆与长期记忆
      - 含义：短期记忆服务当前线程，长期记忆保存跨线程仍稳定的用户偏好、项目事实和决策；临时日志不应永久保存。
      - 示例：长期保存“所有删除操作必须确认”，只在当前任务保存某次 pytest 的完整输出。
      - 官方链接：[LangGraph Memory](https://docs.langchain.com/oss/python/langgraph/add-memory)
    - 压缩、裁剪与摘要
      - 含义：当窗口接近上限时删除低价值内容、摘要历史或只保留关键工具结果；摘要必须区分事实、推断和未完成项。
      - 示例：把 30 轮排障压缩为复现方式、已排除原因、根因证据、当前 diff 和待运行测试。
      - 官方链接：[LangChain Context Engineering：Messages](https://docs.langchain.com/oss/python/langchain/context-engineering#messages)
    - 上下文卸载 Offloading
      - 含义：大输出、文件和中间产物保存在文件系统或外部存储中，模型只保留路径、摘要和按需读取方式。
      - 示例：把 5 万行构建日志写入文件，只向模型提供错误摘要和可继续搜索的日志路径。
      - 官方链接：[Deep Agents Backends](https://docs.langchain.com/oss/python/deepagents/backends)
    - 隔离与子 Agent
      - 含义：不同子任务使用独立上下文，避免一个任务的大量细节污染另一个任务；主 Agent 只接收必要结论和证据。
      - 示例：安全审查 Agent 只读取 diff、威胁模型和相关配置，最终返回风险、证据和建议，不回传全部探索记录。
      - 官方链接：[Deep Agents Subagents](https://docs.langchain.com/oss/python/deepagents/subagents)
    - 新鲜度与可溯源性
      - 含义：上下文应携带来源、版本、时间和权限范围；对易变化的信息重新读取，避免用过期资料做当前决策。
      - 示例：发布前重新读取最新 main 提交和公开 Release，而不是使用三天前对话中的版本号。
      - 官方链接：[LangSmith Trace Concepts](https://docs.langchain.com/langsmith/trace-with-langgraph)
    - 上下文可观察性
      - 含义：记录每次调用实际使用了哪些规则、文档、记忆和工具结果，便于判断错误来自缺信息、错信息还是模型推理。
      - 示例：Trace 显示分类错误时使用了旧版政策文档，据此修复检索过滤而不是盲目改 Prompt。
      - 官方链接：[LangSmith Observability Concepts](https://docs.langchain.com/langsmith/observability-concepts)
    - 上下文安全
      - 含义：按身份和任务过滤可见数据，对检索内容做权限校验和敏感信息脱敏，并把外部内容视为不可信输入。
      - 示例：客服 Agent 只能检索当前租户的订单，日志中的 Token 在进入模型前替换为脱敏值。
      - 官方链接：[OWASP Sensitive Information Disclosure](https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/)
  - Harness Engineering 运行支架工程
    - 定位与边界
      - 含义：Harness 是模型外部的完整运行系统，负责规则、工具、环境、状态、权限、反馈、恢复和观测；相同模型在不同 Harness 中能力差异可能很大。
      - 示例：模型本身不会真的改文件；Harness 把模型的编辑请求转成受路径限制的文件操作，并把结果返回模型。
      - 官方链接：[Deep Agents Overview](https://docs.langchain.com/oss/python/deepagents/overview)
    - 项目规则与 Skills
      - 含义：用 AGENTS.md、CLAUDE.md、Skill 和模板提供团队约定、标准流程、脚本与完成条件，让方法可以复用和版本管理。
      - 示例：发布 Skill 固定执行版本核对、完整测试、资产集合校验、人工审批和交付报告。
      - 官方链接：[Agent Skills Specification](https://agentskills.io/specification)
    - 工具表面 Tool Surface
      - 含义：只暴露完成任务所需的工具，每个工具使用清晰名称、严格参数 Schema、可理解错误和尽量小的副作用。
      - 示例：提供只读 `query_orders` 与需审批的 `refund_order`，而不是一个拥有数据库全部权限的通用 Bash。
      - 官方链接：[LangChain Tools](https://docs.langchain.com/oss/python/langchain/tools)
    - 执行环境与沙箱
      - 含义：控制工作目录、依赖、环境变量、网络、CPU、内存、超时和文件权限，使运行可复现并隔离不可信代码。
      - 示例：代码 Agent 在临时容器和独立 worktree 中运行，只能访问目标仓库与测试数据库。
      - 官方链接：[Deep Agents Backends](https://docs.langchain.com/oss/python/deepagents/backends)
    - Middleware 与 Hooks
      - 含义：在模型调用、工具调用和状态更新前后插入统一逻辑，用于鉴权、日志、限流、内容过滤、格式化和策略执行。
      - 示例：Bash 执行前拦截 `git push` 与删除命令，工具执行后自动记录耗时、结果摘要和错误类型。
      - 官方链接：[LangChain Middleware](https://docs.langchain.com/oss/python/langchain/middleware)
    - 计划、任务与子 Agent
      - 含义：Harness 保存任务清单、委派关系和中间产物，并为子 Agent 提供隔离上下文、明确输入输出和最小工具集。
      - 示例：主 Agent 把只读调查交给研究 Agent，把实现交给编码 Agent，最后由独立 Review Agent 检查 diff。
      - 官方链接：[Deep Agents Subagents](https://docs.langchain.com/oss/python/deepagents/subagents)
    - 权限与 Human-in-the-loop
      - 含义：按风险对读、写、网络、发布、付款和外部通信分别授权；高风险动作在运行时暂停并等待人批准、修改或拒绝。
      - 示例：允许自动运行测试，但数据库删除、生产发布和发送客户邮件必须人工确认。
      - 官方链接：[Deep Agents Human-in-the-loop](https://docs.langchain.com/oss/python/deepagents/human-in-the-loop)
    - 反馈与验证器
      - 含义：把测试、类型检查、lint、构建、浏览器断言和业务校验器变成机器可读反馈，让 Agent 能根据真实结果修正。
      - 示例：编辑代码后自动执行目标单测并返回失败断言、文件和行号，而不是只回复“命令失败”。
      - 官方链接：[LangSmith Evaluators](https://docs.langchain.com/langsmith/evaluation-concepts#evaluators)
    - 持久化、Checkpoint 与恢复
      - 含义：保存状态、消息和已完成步骤，使长任务能在崩溃、超时或人工中断后恢复，并避免重复副作用。
      - 示例：付款前写入 checkpoint；恢复时发现付款已成功，就只查询结果而不再次扣款。
      - 官方链接：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
    - 可观察性与审计
      - 含义：记录模型版本、Prompt、上下文来源、工具调用、状态变化、费用、错误、审批和完成原因，支持复现与责任追踪。
      - 示例：一次错误发布可以追到哪个 Agent、哪个工具、哪条审批、哪个 commit 和哪次测试结果。
      - 官方链接：[LangSmith Observability Concepts](https://docs.langchain.com/langsmith/observability-concepts)
    - 资源与风险护栏
      - 含义：设置最大步骤、Token、费用、并发、超时、重试次数和重复动作检测，防止失控循环和资源耗尽。
      - 示例：同一错误连续三次没有新证据就停止，费用达到 20 元或运行超过 30 分钟时转人工。
      - 官方链接：[Deep Agents Production Guardrails](https://docs.langchain.com/oss/python/deepagents/going-to-production#guardrails)
    - 协议与可扩展能力
      - 含义：通过 MCP、A2A、插件或自定义适配器连接外部工具和 Agent，但协议只负责连接，Harness 仍负责权限、状态和治理。
      - 示例：通过 MCP 连接 GitHub 查询 Issue，创建 PR 仍需 Harness 检查分支、权限与审批状态。
      - 官方链接：[MCP Architecture](https://modelcontextprotocol.io/specification/latest/architecture)
  - Loop Engineering 循环工程
    - 定位与边界
      - 含义：设计“观察状态 -> 决定动作 -> 执行动作 -> 获取反馈 -> 评估是否继续”的闭环，使 Agent 能基于环境证据多轮改进。
      - 边界：循环不等于无限重试；必须有状态、进度判断、停止条件、预算和人工接管。
      - 示例：Agent 修改代码后运行测试，根据失败继续修正；连续三轮没有新证据则停止并报告阻塞。
      - 官方链接：[LangChain Agent Loop](https://docs.langchain.com/oss/python/langchain/context-engineering#the-agent-loop)
    - Trigger 触发器
      - 含义：定义循环何时启动，可来自用户请求、定时器、事件、队列、Webhook、任务分配或上一步状态变化。
      - 示例：CI 失败事件触发修复循环，夜间定时器触发依赖安全扫描循环。
      - 官方链接：[LangGraph Workflows and Agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)
    - State 循环状态
      - 含义：保存目标、当前步骤、尝试次数、证据、已完成项、失败原因和待审批动作，确保每轮都基于同一事实来源。
      - 示例：状态记录已排除网络问题、当前怀疑连接池、已尝试两次、下一步要读取慢查询日志。
      - 官方链接：[LangGraph State](https://docs.langchain.com/oss/python/langgraph/graph-api#state)
    - Action 动作选择
      - 含义：每轮只选择与当前证据匹配的最小动作，并说明预期获得什么新信息或状态变化。
      - 示例：先运行单个失败测试确认空值分支，而不是立即重写整个服务层。
      - 官方链接：[LangChain Agent Loop](https://docs.langchain.com/oss/python/langchain/context-engineering#the-agent-loop)
    - Feedback 环境反馈
      - 含义：工具结果、测试、日志、指标、用户回复和评审意见必须回写状态，成为下一轮决策依据。
      - 示例：浏览器 E2E 返回“按钮被遮挡”，下一轮读取截图和布局样式，而不是继续调整后端接口。
      - 官方链接：[LangSmith Tracing](https://docs.langchain.com/langsmith/observability-concepts)
    - Evaluator 评估器
      - 含义：判断当前结果是否满足目标、是否有进展、是否需要修正或升级人工；可以是规则、测试、另一个模型或人工。
      - 示例：Evaluator 检查答案是否引用官方来源、JSON 是否通过 Schema、代码是否通过测试和安全扫描。
      - 官方链接：[LangGraph Evaluator-Optimizer](https://docs.langchain.com/oss/python/langgraph/workflows-agents#evaluator-optimizer)
    - Retry、Backoff 与修复
      - 含义：只对可恢复失败重试，并使用退避、抖动、错误分类和替代路径；逻辑错误不能靠原样重试解决。
      - 示例：HTTP 429 按 `Retry-After` 等待后重试，JSON Schema 错误则把校验信息反馈给模型重新生成。
      - 官方链接：[LangGraph Node Retry Policies](https://docs.langchain.com/oss/python/langgraph/graph-api#retry-policies)
    - 幂等与副作用控制
      - 含义：重复执行不会造成重复付款、重复发信或重复写入；副作用前后记录唯一键和执行结果。
      - 示例：发送发票使用 `invoice_id` 作为幂等键，恢复循环时先查询发送状态再决定是否执行。
      - 官方链接：[LangGraph Durable Execution](https://docs.langchain.com/oss/python/langgraph/durable-execution)
    - 进度证据与防卡死
      - 含义：每轮必须产生新证据、状态变化或明确缩小问题范围；检测相同工具、相同参数和相同错误的重复模式。
      - 示例：三次都运行同一失败命令且输出相同时，标记 `no_progress` 并请求人工，而不是继续消耗 Token。
      - 官方链接：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
    - 停止条件
      - 含义：成功、明确失败、达到步骤或成本上限、需要新权限、用户取消和等待外部事件都应是显式终止状态。
      - 示例：测试与构建全部通过时成功停止；缺少生产凭据时以 `waiting_for_approval` 停止。
      - 官方链接：[LangGraph Graph API：Finish](https://docs.langchain.com/oss/python/langgraph/graph-api#finish)
    - Checkpoint 与恢复
      - 含义：在阶段完成和高风险动作前保存状态；恢复后从已验证位置继续，而不是从头重做或重复副作用。
      - 示例：长报告完成资料收集后保存 checkpoint，模型超时后直接从撰写阶段继续。
      - 官方链接：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
    - 人工接管
      - 含义：不确定性高、风险大或多次失败时暂停循环，把当前状态、证据、选项和影响交给人决定。
      - 示例：数据库迁移发现线上存在未知旧数据时暂停，展示冲突样本和两种处理方案等待确认。
      - 官方链接：[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
    - loop-me
      - 定位：Matt Pocock skills 中处于 in-progress 的访谈 Skill，用于把一个循环自动化想法追问成可实现的 workflow spec。
      - Brief 内容：目标、触发器、输入、状态、权限、动作、反馈、停止条件、失败策略、Checkpoint 和交付物。
      - Push right：尽量把质量检查前移并自动化，让错误在进入高成本阶段前暴露。
      - 示例：为“构建失败自动排查”定义 CI 失败触发、日志读取权限、每轮验证、最多三轮修复、人工审批和停止条件。
      - 状态提醒：该 Skill 位于 in-progress 目录，正式使用应固定版本并用自己的案例评测。
      - 官方链接：[loop-me 源码与说明](https://github.com/mattpocock/skills/tree/main/skills/in-progress/loop-me)
  - Graph Engineering 图工程
    - 定位与边界
      - 含义：把复杂 Agent 系统建模成显式状态图，由节点处理工作、边决定流转、状态保存共享数据；适合分支、并行、审批和可恢复长流程。
      - 边界：Graph 管理宏观控制流；单个节点内部仍可运行模型、工具或一个 Agent Loop。
      - 示例：订单退款图包含资格校验、风险路由、人工审批、执行退款和通知五类节点。
      - 官方链接：[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)
    - State Schema
      - 含义：定义所有节点共享的数据字段、类型和更新规则，是图的事实来源和节点契约。
      - 示例：退款 State 包含 `order_id`、`eligibility`、`risk_level`、`approval`、`refund_result` 和 `errors`。
      - 官方链接：[LangGraph State](https://docs.langchain.com/oss/python/langgraph/graph-api#state)
    - Node 节点
      - 含义：节点读取当前 State，执行一个清晰职责并返回局部更新；节点应尽量可测试、可重试并控制副作用。
      - 示例：`check_eligibility` 只判断是否满足退款政策，不同时执行退款和发送邮件。
      - 官方链接：[LangGraph Nodes](https://docs.langchain.com/oss/python/langgraph/graph-api#nodes)
    - Edge 与条件路由
      - 含义：普通边表示固定下一步，条件边根据 State 选择分支，`START` 与 `END` 表示图入口和结束。
      - 示例：低风险订单直接到退款节点，高风险订单路由到人工审批，信息不足路由到补充资料。
      - 官方链接：[LangGraph Edges](https://docs.langchain.com/oss/python/langgraph/graph-api#edges)
    - Reducer 状态合并
      - 含义：Reducer 定义多个节点更新同一字段时如何合并，尤其用于消息累积和并行结果汇总。
      - 示例：三个研究节点并行返回资料时，Reducer 把 `sources` 列表追加合并，而不是后返回的覆盖先返回的。
      - 官方链接：[LangGraph Reducers](https://docs.langchain.com/oss/python/langgraph/graph-api#reducers)
    - Command 动态更新与跳转
      - 含义：节点可以用 `Command` 同时更新 State 并决定下一节点，适合动作结果直接影响路由的场景。
      - 示例：审批节点返回 `Command(update={approval: "approved"}, goto="refund")`。
      - 官方链接：[LangGraph Command](https://docs.langchain.com/oss/python/langgraph/graph-api#command)
    - Send 并行分发
      - 含义：用 `Send` 根据运行时数据创建多个并行分支，再通过 Reducer 汇总，适合 Map-Reduce 类任务。
      - 示例：把十份合同分别发送给十个分析分支，最后汇总风险条款和引用页码。
      - 官方链接：[LangGraph Send](https://docs.langchain.com/oss/python/langgraph/graph-api#send)
    - Subgraph 子图
      - 含义：把可复用或需要隔离状态的复杂流程封装成子图，使大图保持清晰并支持团队分工。
      - 示例：主图的“代码交付”节点内部调用调查、实现、测试、审查组成的研发子图。
      - 官方链接：[LangGraph Subgraphs](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)
    - Persistence 持久化
      - 含义：Checkpointer 按线程保存每一步 State，支持恢复、审计、人工介入和历史状态读取。
      - 示例：审批等待一天后，流程从原线程的审批节点恢复，仍能读取此前校验和风险结果。
      - 官方链接：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
    - Interrupt 人机协同
      - 含义：节点通过 `interrupt` 暂停并返回待确认信息，收到 `Command(resume=...)` 后从同一状态继续。
      - 示例：付款前暂停展示金额、收款方和风险，用户批准后继续，拒绝则转取消分支。
      - 官方链接：[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
    - Retry 与补偿
      - 含义：节点可配置重试策略；已经产生外部副作用的步骤失败时，需要幂等键或补偿节点，不能盲目回放。
      - 示例：库存已扣减但付款失败时，图进入释放库存补偿节点并记录失败原因。
      - 官方链接：[LangGraph Retry Policies](https://docs.langchain.com/oss/python/langgraph/graph-api#retry-policies)
    - Time Travel 与调试
      - 含义：基于历史 checkpoint 查看或分叉状态，重放特定阶段，定位是哪一个节点和状态更新导致错误。
      - 示例：从错误审批前的 checkpoint 分叉，修改风险结果后在测试环境重放后续节点。
      - 官方链接：[LangGraph Time Travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)
    - Graph 与 Loop 的选择
      - 含义：目标开放、下一步由模型动态决定时适合 Loop；阶段、分支、审批和状态契约明确时适合 Graph；生产系统经常是 Graph 包住多个局部 Loop。
      - 示例：研究节点内部循环搜索和评估资料，主图负责研究完成后进入写作、审查和发布审批。
      - 官方链接：[LangGraph Workflows and Agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)
  - 五类工程的组合示例
    - 需求：自动修复 CI 失败并提交待审查补丁。
    - Prompt Engineering：写清目标、允许目录、禁止 push、输出格式和“测试通过才算完成”。
    - Context Engineering：提供失败日志、相关代码、项目规则、当前 diff 和历史相似修复。
    - Harness Engineering：提供受限搜索、编辑、终端和测试工具，使用独立 worktree、权限确认、Trace 与 Checkpoint。
    - Loop Engineering：调查、修改、测试、评估并继续；检测无进展、限制三轮修复并设置人工接管。
    - Graph Engineering：用调查 -> 根因确认 -> 实现 -> 测试 -> Review -> 人工批准的状态图编排，失败分支回到对应阶段。
    - 示例：测试失败由 Graph 路由回实现节点，节点内部 Loop 根据失败信息修正；达到预算或需要 push 时 Harness 暂停等待人批准。
    - 官方链接：[LangGraph Workflows and Agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)
  - Vibe Coding 与 Agentic Engineering
    - Vibe Coding
      - 含义：主要通过自然语言快速生成和调整代码，适合原型、小工具和探索，但容易出现需求漂移、架构退化和验证不足。
      - 示例：一小时做出内部原型可以使用 Vibe Coding，上线前仍要补规格、测试、安全、可观察性和运维。
      - 官方链接：[GitHub Copilot Responsible Use for Agents](https://docs.github.com/en/copilot/responsible-use/agents)
    - Agentic Engineering
      - 含义：人负责目标、架构、边界、风险与验收，Agent 负责调查、实现、测试和迭代；重点是系统化编排与质量控制。
      - 示例：人确定支付架构和风险边界，Agent 在 Harness 中实现并验证，人依据测试、Trace 和 Review 证据做最终决定。
      - 官方链接：[LangChain Agents](https://docs.langchain.com/oss/python/langchain/agents)
  - 系统性失败模式
    - 上下文漂移：逐轮偏离目标；示例是修 Bug 最后变成无关重构。
    - 功能倒退：新改动破坏旧行为；示例是只跑新增测试而遗漏共享调用方。
    - 架构退化：局部方便破坏模块边界；示例是把页面逻辑塞进公共组件。
    - 依赖膨胀：重复引入相似库；示例是为一个简单解析同时加入三个包。
    - 验证幻觉：没有真实执行却声称通过；示例是只生成测试代码但未运行测试与构建。
    - 失控循环：重复动作没有新证据；示例是连续十次重跑同一失败命令。
    - 官方链接：[Deep Agents Production Guardrails](https://docs.langchain.com/oss/python/deepagents/going-to-production#guardrails)
- 多 Agent 协作
  - 适用场景
    - 多个相互独立的资料调查或模块实现。
    - 实现、测试、安全审查由不同上下文分别完成。
    - 大仓库中按清晰目录或服务边界分工。
    - 示例：前后端目录互不重叠且接口契约已固定时，可分别交给两个 Agent 并行调查或实现。
    - 官方链接：[Deep Agents Why Use Subagents](https://docs.langchain.com/oss/python/deepagents/subagents#why-use-subagents)
  - 常见角色
    - 调查 Agent：只读代码和资料，提交事实与风险。
    - 实现 Agent：在明确文件范围内完成改动。
    - 测试 Agent：设计验证、运行测试并分析失败。
    - Review Agent：不继承实现者结论，独立检查 diff。
    - 集成 Agent：统一处理冲突、运行完整测试并交付。
    - 示例：调查 Agent 只提交事实，实现 Agent 修改代码，Review Agent 独立检查，集成 Agent 跑完整验证。
    - 官方链接：[Deep Agents Custom Subagents](https://docs.langchain.com/oss/python/deepagents/subagents#custom-subagents)
  - 协作约束
    - 每个 Agent 有唯一任务、输入、输出、文件所有权和完成条件。
    - 共享事实写入文档、计划或结构化状态，不只存在聊天里。
    - 明确谁可以写文件、提交代码、操作远程和做最终决定。
    - 独立任务并行，强依赖任务按顺序执行。
    - 集成时重新检查 diff、冲突、构建和完整测试。
    - 示例：为每个 Agent 写清负责目录、输入、输出、完成条件和禁止执行的远程操作。
    - 官方链接：[Deep Agents Subagent Best Practices](https://docs.langchain.com/oss/python/deepagents/subagents#best-practices)
  - 风险
    - 重复劳动、互相覆盖、冲突增多和上下文不一致。
    - Agent 数量增加会放大 Token、延迟、协调和审查成本。
    - 示例：两个 Agent 同时修改共享 Schema 会产生冲突，因此必须先确定唯一所有者和集成顺序。
    - 官方链接：[Deep Agents Minimize Tool Sets](https://docs.langchain.com/oss/python/deepagents/subagents#minimize-tool-sets)
  - 官方链接：[Deep Agents Subagents](https://docs.langchain.com/oss/python/deepagents/subagents)
- OPC 一人公司与 AI Agent Company
  - OPC 基本概念
    - 定义
      - 含义：OPC 在这里指 One-Person Company，由一个人掌握所有权、目标和最终责任，用软件、自动化与 AI Agent 承担原本需要多人协作的研究、研发、营销、销售和运营工作。
      - 边界：OPC 不是“完全无人公司”；法律责任、资金决策、价值判断、高风险审批和客户承诺最终仍由人承担。
      - 示例：创始人决定做一款开发者工具，AI 团队负责需求研究、实现、内容和客服草稿，但定价、付款、合同与正式发布由创始人批准。

    - 适合的业务
      - 含义：需求和交付可数字化、流程能标准化、反馈周期短、合规风险可控的业务更容易由一个人配合 Agent 运转。
      - 示例：微型 SaaS、内容产品、咨询报告、数据服务和开发者工具比线下重资产制造更容易形成 OPC。

    - 人类创始人的职责
      - 含义：负责公司使命、目标优先级、资源分配、风险边界、关键审批、质量标准和最终问责，不能把决策责任一并外包给模型。
      - 示例：AI CEO 可以提出进入企业市场的策略，但创始人要审核现金预算、数据合规、合同责任和停止条件。

      - 示例：研究 Agent 汇总 30 条公开反馈并保留链接，产品 Agent 提炼前三个高频痛点，创始人决定只验证其中一个。

    - 产品与交付

      - 示例：产品 Agent 写验收标准，开发 Agent 实现，测试 Agent 独立验证，创始人批准生产发布。

      - 示例：增长 Agent 每周生成三篇基于真实搜索需求的内容草稿，销售 Agent 只对用户主动留下的企业线索准备个性化邮件，由人审核发送。

      - 示例：使命是“降低小团队发布成本”，季度目标是“把首次部署时间降到 10 分钟”，任务再分解为安装器、文档和可观测性改进。

    - 角色与责任边界
      - 含义：为每个 Agent 指定角色、能力、汇报关系、工具、数据范围、预算和完成条件，避免所有 Agent 都是“什么都能做”的通才。

      - 示例：功能任务关联季度目标，拆成设计、实现、测试和发布审批四个子任务，每个任务只有一个当前负责人。

      - 含义：把稳定的方法固化为 Skill、模板、脚本和检查清单，把定时或事件任务固化为可监控的自动化流程。

      - 示例：定价与退款政策保存在版本化知识库中，Agent 回复客户前检索当前版本并附来源。

    - 治理与风险分级
      - 含义：按可逆性、金额、数据敏感度和外部影响划分自动执行、事后审查和事前审批，保留暂停、恢复和终止能力。

    - 评测与绩效
      - 含义：评价 Agent 是否完成业务结果、遵守边界、控制成本和留下证据，不能只统计生成了多少内容或调用了多少次模型。

  - Paperclip
    - 定位
      - 含义：Paperclip 是开源、自托管的 AI 公司控制平面，用一个 Node.js 服务和 React 界面管理由多个 AI Agent 组成的公司。
      - 核心类比：Claude Code、Codex、OpenClaw 或自定义 Agent 是“员工”，Paperclip 是管理目标、组织、工作、预算和治理的“公司系统”。
      - 示例：把 Codex 配成开发工程师、Claude Code 配成 Review Agent，在同一个公司目标与任务系统中协作。
      - 官方链接：[Paperclip 官方仓库](https://github.com/paperclipai/paperclip)
    - 能做什么与不能做什么
      - 能做：公司与目标、组织架构、任务、委派、心跳、适配器、预算、审批、审计、多公司和运行可见性。
      - 不能替代：底层模型、Agent 推理框架、Prompt 管理器、拖拽工作流、代码审查工具和业务本身的市场验证。
      - 示例：Paperclip 能把任务交给 Codex 并追踪成本，但不会自动保证 Codex 写出的代码正确，仍需测试和 Review 流程。
      - 官方链接：[Paperclip：What Paperclip Is Not](https://github.com/paperclipai/paperclip#what-paperclip-is-not)
    - 控制平面架构
      - 含义：服务端统一管理身份与访问、Agent 与组织、任务、心跳执行、工作区、审批、预算、日程、插件、密钥、活动和公司导入导出。
      - 示例：一次开发任务从 Issue 进入心跳队列，解析工作区和密钥，调用 Codex 适配器，再把日志、费用和状态写回控制平面。
      - 官方链接：[Paperclip Architecture](https://github.com/paperclipai/paperclip/blob/master/docs/start/architecture.md)
    - Company 公司
      - 含义：公司是顶层隔离单位，拥有使命或目标、AI 员工、组织结构、预算和能够追溯到公司目标的任务层级。
      - 示例：同一部署中分别创建“开发者工具公司”和“内容公司”，两者的 Agent、任务、预算和审计数据互相隔离。
      - 官方链接：[Paperclip Core Concepts：Company](https://github.com/paperclipai/paperclip/blob/master/docs/start/core-concepts.md#company)
    - Goal Alignment 目标对齐
      - 含义：项目和任务保留目标祖先关系，让 Agent 不只看到一个孤立标题，还能理解这项工作为什么存在。
      - 示例：“增加 CSV 导入校验”任务向上关联“把导入失败率从 8% 降到 2%”和公司的产品可靠性目标。
      - 官方链接：[Paperclip Goals and Projects API](https://github.com/paperclipai/paperclip/blob/master/docs/api/goals-and-projects.md)
    - Board 与 CEO
      - 含义：人类作为 Board 掌握最终控制；CEO Agent 提出策略、拆解目标、委派任务和申请招聘，关键策略与招聘可设置审批。
      - 示例：CEO 提议增加增长 Agent 并提交月预算，Board 审查能力、费用和数据权限后决定批准或拒绝。
      - 官方链接：[Paperclip Delegation](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/delegation.md)
    - Agent 与组织架构
      - 含义：每个 Agent 配置角色、职位、能力、上级、下属、状态、预算和适配器；除 CEO 外每个 Agent 只有一个直接上级，形成清晰汇报树。
      - 示例：CEO 下设 CTO 与增长负责人，CTO 下设开发和测试 Agent；测试问题先向 CTO 升级而不是直接广播给所有 Agent。
      - 官方链接：[Paperclip Org Structure](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/org-structure.md)
    - Delegation 委派
      - 含义：上级根据角色和能力拆解并分配任务，下级通过子任务、评论和状态回传结果；委派关系与目标链保持可追溯。
      - 示例：CEO 把“发布 MVP”委派给 CTO，CTO 再创建后端、前端、测试和部署子任务。
      - 官方链接：[Paperclip Delegation](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/delegation.md)
    - Issue 任务模型
      - 含义：Issue 是工作单位，包含标题、描述、优先级、状态、唯一负责人、父任务、项目、目标、依赖、评论和工作产物。
      - 示例：开发 Agent 领取 `todo` 任务后转为 `in_progress`，完成实现并附测试证据后进入 `in_review`。
      - 官方链接：[Paperclip Issues API](https://github.com/paperclipai/paperclip/blob/master/docs/api/issues.md)
    - Atomic Checkout 原子领取
      - 含义：任务进入执行前需要原子 checkout，同一时刻只有一个 Agent 能拥有它；并发领取冲突会返回 `409 Conflict`，防止重复劳动。
      - 示例：两个开发 Agent 同时看到同一 Bug 时，只有一个领取成功，另一个重新选择其他任务。
      - 官方链接：[Paperclip Core Concepts：Issues](https://github.com/paperclipai/paperclip/blob/master/docs/start/core-concepts.md#issues-tasks)
    - Heartbeat 心跳执行
      - 含义：Agent 不必永远常驻，而是在短执行窗口中醒来，读取身份和任务、领取工作、执行、更新状态并退出。
      - 触发方式：定时、任务分配、评论或 @ 提及、人工调用、自动化以及审批结果。
      - 示例：新 Bug 分配给开发 Agent 后触发心跳；Agent 完成一轮并退出，下一次心跳复用会话继续未完成工作。
      - 官方链接：[Paperclip Heartbeat Protocol](https://github.com/paperclipai/paperclip/blob/master/docs/guides/agent-developer/heartbeat-protocol.md)
    - Wakeup 合并与运行状态
      - 含义：Agent 已运行时的新唤醒会合并，避免重复并发；每次 Run 记录 queued、running、succeeded、failed、timed_out 或 cancelled 等状态。
      - 示例：Agent 执行期间同时收到定时器和新评论，只合并为后续一次处理，而不是启动两个互相覆盖的进程。
      - 官方链接：[Paperclip Agent Runtime Guide](https://github.com/paperclipai/paperclip/blob/master/docs/agents-runtime.md)
    - Session 持续性
      - 含义：可恢复适配器的会话 ID 会跨心跳保存，使 Agent 延续任务上下文；上下文陈旧、策略大改或陷入错误循环时可以重置。
      - 示例：开发 Agent 第一轮完成调查，第二轮复用同一会话继续实现；发现它持续误解需求时由 Board 重置会话。
      - 官方链接：[Paperclip Agent Runtime：Session Resume](https://github.com/paperclipai/paperclip/blob/master/docs/agents-runtime.md#4-session-resume-behavior)
    - Adapters 适配器
      - 含义：适配器连接 Paperclip 编排层与具体 Agent Runtime，负责启动或调用 Agent、传入上下文、流式捕获输出并解析用量与成本。
      - 内置方向：Claude Code、Codex、OpenCode、Cursor、Pi、Hermes、OpenClaw、通用 Process 和 HTTP；也可以开发外部适配器。
      - 示例：本地开发任务使用 `codex_local`，公司内部已有的 HTTP Agent 使用 `http` 适配器接入。
      - 官方链接：[Paperclip Adapters Overview](https://github.com/paperclipai/paperclip/blob/master/docs/adapters/overview.md)
    - Workspace 与 Runtime Service
      - 含义：项目工作区定义代码位置，执行工作区可以使用隔离目录、Git worktree 或操作分支；Runtime Service 管理开发服务与预览 URL。
      - 示例：两个开发 Agent 分别在独立 worktree 修改不同任务，测试 Agent 访问对应预览 URL 做无头 E2E。
      - 官方链接：[Paperclip Execution Workspaces and Runtime Services](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/execution-workspaces-and-runtime-services.md)
    - Execution Policy 执行策略
      - 含义：运行时在 Issue 上强制评论、Review 和 Approval 阶段，不依赖 Agent 自己记得交接；原执行者不能成为自己的审查者。
      - 示例：开发 Agent 标记完成时，系统自动把任务转为 `in_review` 并分配给 QA；QA 请求修改后又自动退回原执行者。
      - 官方链接：[Paperclip Execution Policy](https://github.com/paperclipai/paperclip/blob/master/docs/guides/execution-policy.md)
    - Approval 审批治理
      - 含义：Board 可以审批策略、招聘和高风险执行，暂停、恢复或终止 Agent，并重新分配任务；每个决定保留操作者、结果、评论和 Run 记录。
      - 示例：发布任务经过 QA Review 后仍需创始人 Approval，拒绝时附原因并返回修改环节。
      - 官方链接：[Paperclip Approvals](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/approvals.md)
    - Budget 与 Cost Control
      - 含义：按公司、Agent、项目、目标、Issue、Provider 和模型记录 Token 与费用，为 Agent 设置月预算、预警阈值和硬停止。
      - 示例：增长 Agent 达到月预算后自动暂停并取消排队工作，创始人根据转化结果决定增加预算或终止活动。
      - 官方链接：[Paperclip Costs and Budgets](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/costs-and-budgets.md)
    - Identity、Access 与 Secrets
      - 含义：区分 Board 用户和 Agent 身份，使用公司成员关系、Agent API Key 和短期 Run JWT；密钥按实例或公司范围保存并只注入需要的运行。
      - 示例：开发 Agent 获得测试环境 Token，但没有生产支付密钥；一次 Run 结束后短期凭据失效。
      - 官方链接：[Paperclip Secrets](https://github.com/paperclipai/paperclip/blob/master/docs/deploy/secrets.md)
    - Activity 与 Audit Trail
      - 含义：任务变化、心跳、费用、审批、评论和工作产物形成持久活动记录，可以回答“谁在什么时候为什么做了什么”。
      - 示例：线上错误可追到具体 Issue、执行 Agent、适配器 Run、审批评论和产生的工作产物。
      - 官方链接：[Paperclip Activity Log](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/activity-log.md)
    - Routines 与 Schedules
      - 含义：用 cron、Webhook 或 API 触发重复工作，并配置并发与补跑策略；每次执行创建可追踪 Issue 并唤醒负责人。
      - 示例：每天 9 点创建“汇总昨日客户反馈”任务，分配给研究 Agent，失败时保留 Issue 和运行日志。
      - 官方链接：[Paperclip Routines API](https://github.com/paperclipai/paperclip/blob/master/docs/api/routines.md)
    - Skills 与 Skills Store
      - 含义：Skill 为 Agent 提供领域流程、脚本和资源；Paperclip 可以管理、分发并在运行时注入 Skill，使组织方法不依赖单个会话记忆。
      - 示例：给客服 Agent 安装“退款政策检查”Skill，给开发 Agent 安装“发布验证”Skill。
      - 官方链接：[Paperclip Skills Store](https://github.com/paperclipai/paperclip/blob/master/docs/guides/agent-developer/skills-store.md)
    - Multi-company 与公司可移植性
      - 含义：一个实例可以运行多个数据隔离的公司，并导出或导入组织、Agent、Skill、项目、Routine 和 Issue；导出时清理密钥并处理标识冲突。
      - 示例：把验证过的 SaaS 公司模板导出，在新公司中导入组织与流程，但重新配置所有密钥和业务目标。
      - 官方链接：[Paperclip Importing and Exporting](https://github.com/paperclipai/paperclip/blob/master/docs/guides/board-operator/importing-and-exporting.md)
    - 部署模式
      - 含义：可在本机以受信任的 loopback 模式运行，也可使用认证模式部署到局域网、Tailnet 或服务器；生产环境可接外部 PostgreSQL 与对象存储。
      - 示例：个人学习先在本机运行，远程访问时使用 Tailscale 私网和认证，不直接把管理端暴露到公网。

    - 本地适配器安全边界

      - 示例：先让 Agent 只访问专用 worktree 和测试密钥，高风险命令走审批，不直接授予整个用户目录和生产凭据。
      - 官方链接：[Paperclip Agent Runtime：Security Notes](https://github.com/paperclipai/paperclip/blob/master/docs/agents-runtime.md#9-security-and-risk-notes)
    - Quickstart
      - 含义：官方推荐使用 Node.js 环境执行 `npx paperclipai onboard --yes` 完成本地初始化；首次进入后创建公司、目标、CEO、组织和预算。
      - 示例：初始化后先创建一个实验公司和两个低权限 Agent，用测试任务验证心跳、日志、费用和审批，再接入真实业务。
      - 官方链接：[Paperclip Quickstart](https://github.com/paperclipai/paperclip/blob/master/docs/start/quickstart.md)
    - 与五类工程的关系
      - Prompt Engineering：每个 Agent 和运行仍需要清楚的指令模板。
      - Context Engineering：目标祖先、Issue、评论、Skill、工作区和会话为每次 Run 提供上下文。
      - Harness Engineering：Paperclip 本身提供组织级 Harness，连接适配器、权限、预算、运行时、审批和审计。
      - Loop Engineering：Heartbeat、任务状态、Review 修改和定时 Routine 构成可恢复循环。
      - Graph Engineering：组织汇报树与 Issue 执行策略形成显式阶段、分支和状态流转，但底层 Agent 内部仍可使用自己的图。
      - 示例：Paperclip 的 QA Review 把 Issue 退回开发 Agent，开发 Agent 内部再运行“修改 -> 测试 -> 评估”循环，最终重新进入 Review。
      - 官方链接：[Paperclip Core Concepts](https://github.com/paperclipai/paperclip/blob/master/docs/start/core-concepts.md)
    - OPC 完整示例
      - 公司目标：三个月验证一款“API 错误日志分析”微型 SaaS，并获得 20 个付费用户。
      - 组织：创始人作为 Board；CEO Agent 管目标；研究 Agent 做需求证据；开发 Agent 实现；QA Agent 审查；增长 Agent 做内容草稿。
      - 任务：CEO 把目标拆成访谈、原型、计费、文档、发布和反馈任务，每项都关联父目标并只有一个负责人。
      - 运行：分配任务或定时器触发 Heartbeat，适配器在隔离工作区启动 Codex 或 Claude Code，Run 记录日志、状态和费用。
      - 治理：代码先由 QA Review；公开发布、客户邮件、预算增加和付款必须由创始人 Approval。
      - 反馈：转化、工单、测试、成本与 Activity Log 回流为新 Issue、Skill 改进和评测案例。
      - 示例：增长 Agent 发现“错误定位耗时”是最高频痛点，CEO 创建 MVP 任务；开发与 QA 完成后，创始人审核数据权限和发布清单再上线。
      - 官方链接：[Paperclip 官方网站](https://paperclip.ing/)
  - OPC 常见失败模式
    - 没有真实需求：Agent 很快产出大量功能，但没有用户证据；示例是连续开发三个月却从未访谈目标客户。
    - 权责不清：多个 Agent 修改同一工作或互相审批；示例是开发 Agent 自己批准自己的发布。
    - 自动化错误规模化：错误 SOP 被定时执行；示例是错误定价内容每天自动发布到所有渠道。
    - 成本失控：高频 Heartbeat 和重复循环持续消耗模型费用；示例是无任务时仍每分钟唤醒全部 Agent。
    - 知识漂移：不同 Agent 使用不同政策版本；示例是客服继续引用已废止的退款规则。
    - 过度授权：Agent 获得生产密钥和不可逆工具；示例是营销 Agent 能直接读取客户数据库并群发邮件。
    - 缺少人工判断：把法律、付款、品牌承诺和伦理决策完全交给模型；示例是 Agent 未经确认自动接受客户合同。
    - 官方链接：[OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)
- 评测、可观察性与团队化
  - 任务评测
    - 是否满足验收条件。
    - 新增和历史测试是否通过。
    - 是否完成真实构建和必要的运行验证。
    - Diff 是否聚焦、可读、可维护并符合架构。
    - 是否引入安全、性能、兼容性或数据风险。
    - 示例：评分同时检查验收、测试、真实构建、Diff 范围和安全风险，而不是只看代码是否生成。

    - 首次正确率、返工次数、人工审查时间和任务周期。
    - Token、模型费用、工具调用次数和总延迟。
    - 自动化节省时间与维护 Agent 基础设施成本的对比。
    - 示例：比较两个工作流的首次正确率、返工次数、人工审查分钟数、Token 和总周期。

    - SWE-bench 等基准用于横向了解能力，不能替代自己的仓库任务集。
    - 建立团队真实任务集：Bug、功能、重构、测试、文档和排障。
    - 固定任务、环境、验收和评分规则，才能比较模型或工作流。
    - 示例：保留十个真实仓库 Bug，固定初始 commit、环境、验收和评分，用于比较模型版本。
    - 官方链接：[LangSmith Manage Datasets](https://docs.langchain.com/langsmith/manage-datasets)
  - 可观察性
    - Trace 记录模型输入摘要、工具序列、错误、重试和完成原因。
    - 记录 Prompt、Skill、模型和仓库版本，支持结果复现。
    - 对失败分类：需求、上下文、模型、工具、环境、验证或权限。
    - 示例：一次失败任务能追到使用的模型、Prompt、工具序列、命令输出、重试与结束原因。
    - 官方链接：[LangSmith Observability Concepts](https://docs.langchain.com/langsmith/observability-concepts)
  - 团队治理
    - 共享项目规则、Skill、Prompt 模板和审查清单。
    - 明确可发送给模型的数据等级和批准的工具范围。
    - 重要任务保留人工 Review、审批和回滚通道。
    - 把高频失败沉淀成规则、测试或工具反馈，而不是反复口头提醒。
    - 示例：团队规定私有数据等级、批准模型、可用 MCP、发布审批和高风险操作审计。
    - 官方链接：[LangSmith Workspace Administration](https://docs.langchain.com/langsmith/administration-overview)

      - 人工审查：关键需求、架构、安全和发布结论必须由负责人确认。

      - 引用来源：外部结论链接到官方文档，代码结论链接到文件、符号、commit 或测试证据。
      - 示例：依赖升级建议同时附官方迁移指南、当前锁文件版本和真实构建结果。
      - 相关官方链接：[SLSA 供应链安全框架](https://slsa.dev/spec/v1.0/)
    - 官方链接：[OpenSpec Documentation Home](https://github.com/Fission-AI/OpenSpec/blob/main/docs/README.md)
  - 开发编码：智能体驱动开发
    - 研发环境标准化
      - 知识点：用脚本、容器和锁文件建立可重复环境，减少“在我机器上能运行”。
      - 示例：Env-Setup Skill 安装指定 Node 版本、依赖和项目规则，再运行健康检查。
      - 可落地产物：Env-Setup Skill。
      - 官方链接：[Docker Build Best Practices](https://docs.docker.com/build/building/best-practices/)
      - 其他官方链接：[nvm 官方仓库](https://github.com/nvm-sh/nvm)
    - 编码与调试
      - IDE Agent：Cursor 或 GitHub Copilot 适合编辑器内补全、问答和局部修改。
      - CLI Agent：Codex 或 Claude Code 适合搜索仓库、跨文件编辑、运行命令和验证。
      - 自动测试闭环：代码修改后触发相关测试；失败时先分析真实输出，再最小修复。
      - 示例：Agent 修改解析函数后运行单测，看到空输入失败，补空值分支并重新运行。
      - 可落地产物：Unit-Test Skill、测试 Hook 和仓库规则。
      - 官方链接：[OpenAI Codex CLI](https://developers.openai.com/codex/cli/)
      - 其他官方链接：[Claude Code 文档](https://code.claude.com/docs/en/overview)
    - 并行研发提效
      - 独立任务并行：只有文件所有权和依赖边界清晰的任务才并行。
      - 隔离环境：每个任务使用独立分支或 worktree，统一由集成者处理冲突和完整验证。
      - 示例：前端页面和后端查询接口并行开发，但共享 Schema 先固定版本。
      - 官方链接：[Git worktree 文档](https://git-scm.com/docs/git-worktree)
    - API 契约同步
      - 知识点：把 OpenAPI 或 Swagger Schema 作为接口结构来源，自动生成类型、客户端和 Mock。

      - 官方链接：[OpenAPI Specification](https://spec.openapis.org/oas/latest.html)

  - 质量保障：自动审计与人工决策
    - 代码评审
      - Agent 审查：检查需求覆盖、Bug、空值、并发、安全、性能、兼容性和测试缺口。
      - 人工决策：对业务取舍、破坏性改动和高风险权限做最终判断。
      - 示例：Review Agent 指出共享组件改动会影响三个页面，并要求补调用方回归验证。
      - 官方链接：[GitHub Pull Request 审查文档](https://docs.github.com/zh/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests)
    - 分层测试门禁
      - 知识点：先运行格式、静态检查和快速单元测试，再并行运行集成、E2E 与真实构建，任何必需门禁失败都不能静默跳过。
      - 示例：Pull Request 先执行 lint、类型和单测，随后运行容器集成测试、无头 E2E 与生产构建。
      - 官方链接：[GitHub Actions Continuous Integration](https://docs.github.com/en/actions/about-github-actions/about-continuous-integration-with-github-actions)
    - 质量失败与基础设施错误
      - 知识点：断言不满足属于质量失败；依赖下载、环境启动、网络超时或执行器异常属于基础设施错误，两者不能混为同一种测试失败。
      - 示例：返回字段错误记为 quality_failed；测试容器没有启动记为 infrastructure_error，修复环境后再判断产品质量。
      - 官方链接：[pytest Exit Codes](https://docs.pytest.org/en/stable/reference/exit-codes.html)
    - 失败诊断产物
      - 知识点：失败任务保存测试报告、日志、截图、视频、Trace 和构建产物，使 Agent 与人工能够基于同一证据复盘。
      - 示例：Playwright 失败后上传 Trace，Midscene 失败后上传可视化报告，后端测试同时保存容器日志。
      - 官方链接：[GitHub Actions Store Workflow Data as Artifacts](https://docs.github.com/en/actions/using-workflows/storing-workflow-data-as-artifacts)
    - AI 生成测试审查门禁
      - 知识点：检查测试是否验证业务行为、是否覆盖根因、是否错误 Mock 被测逻辑，以及是否通过删除断言或跳过用例掩盖失败。
      - 示例：Agent 修复 Bug 后必须展示先失败后通过的回归用例，Review Agent 再核对断言是否能在旧代码上失败。
      - 官方链接：[GitHub Pull Request Reviews](https://docs.github.com/en/pull-requests/reference/pull-request-reviews)
    - 人工决策门禁
      - 知识点：测试通过只证明已覆盖的规则成立，破坏性迁移、权限扩大、生产发布和业务取舍仍需有责任人批准。
      - 示例：数据库迁移和测试全部通过后，发布仍等待负责人审查影响范围、备份和回滚方案。
      - 官方链接：[GitHub Deployment Environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)
    - 官方链接：[GitHub Actions Testing](https://docs.github.com/en/actions/how-tos/use-cases-and-examples/building-and-testing)
  - 构建交付：可重复与精准发布
    - 持续集成
      - 知识点：每次变更自动执行安装、类型检查、lint、测试和真实构建。
      - 示例：Pull Request 只有在单测、E2E 和生产构建全部通过后才允许合并。
      - 官方链接：[GitHub Actions Workflow Syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)
    - 构建工程化

      - 相关官方链接：[npm package.json 文档](https://docs.npmjs.com/cli/v11/configuring-npm/package-json)

    - 流水线状态接入
      - 知识点：通过 MCP 或平台 API 查询 Job、日志、产物和审批状态，让 Agent 基于事实判断。
      - 示例：Agent 查询失败 Job 的日志后定位依赖安装错误，但没有授权就不重新发布。
      - 相关官方链接：[GitHub Actions REST API](https://docs.github.com/zh/rest/actions)

      - 知识点：关联 request_id、trace_id、版本、用户操作和外部调用，重建故障链路。

      - 相关官方链接：[Sentry Alerts](https://docs.sentry.io/product/alerts/)

      - 知识点：只自动执行低风险、可逆、可验证操作；高风险动作必须人工审批。
